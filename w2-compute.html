AWS SAA-C03 / W2 座学

コンピューティング ―― 何で動かし、どう増やすか

SAAでは「この要件をEC2で受けるか、Lambdaで受けるか、コンテナで受けるか」が繰り返し問われます。さらに購入オプションの選択はコスト最適化ドメインの中心でもあります。サービスの機能を覚えるのではなく、要件の言葉から選択肢を絞る回路を作ってください。

01

この講義のゴール

W1のIAMは「誰が触れるか」でした。今週は「何の上で動かすか」です。コンピューティングは3つのドメインにまたがって出題されるうえ、選択肢が多いぶん迷いやすい領域です。今日終わったときに、次の3つができていれば合格です。

  • 01
    購入オプションを、設問の言葉から1つに絞れる。
    オンデマンド、スポット、Reserved Instance、Savings Plans、専有ホスト。「中断できる」「1年使う」「ライセンス持ち込み」という手がかりで即断できる。
  • 02
    ALB / NLB / GWLB を、要件の一語で切り分けられる。
    静的IP、パスベースルーティング、仮想アプライアンス。どの単語が出たらどれか、表を見ずに言える。
  • 03
    EC2・コンテナ・Lambda の三択に順序をつけられる。
    実行時間、状態の持ち方、運用の手離れ。この3軸で、設問ごとに消去法が回せる。
今週の重心

コンピューティングは、ドメイン2（弾力性のあるアーキテクチャ）、ドメイン3（高性能なアーキテクチャ）、ドメイン4（コスト最適化）の三方向から問われます。同じEC2でも、聞かれている角度が違えば正解も変わります。「安いのはどれか」と「落ちないのはどれか」は別の設問です。読むときは、その設問がどのドメインから来ているかを先に判定してください。

02

インスタンスファミリー ―― 型番は覚えない

EC2には数百の型番があります。そのすべてを覚える必要はまったくありません。SAAが問うのは「このワークロードのボトルネックはどこか」という一点で、型番はその答えのラベルにすぎません。

ボトルネックからファミリーを引く

T系のバーストだけは仕組みを知っておく

T系（バースト可能パフォーマンスインスタンス）は、他のファミリーと課金の考え方が違います。ベースラインを下回るCPU使用率のあいだにCPUクレジットを貯め、負荷が跳ねたときにそれを消費してベースラインを超えた性能を出します。クレジットが尽きると、ベースライン性能まで絞られます。

  • スタンダードモードではクレジットが尽きた時点で性能が落ちます。コストは予測可能です。
  • Unlimitedモードではクレジットを超えても性能を維持し、超過分が追加課金されます。既定はインスタンスの世代により異なるため、設問では明示されます。
最頻出の引っかけ

「開発環境でうまく動いていたアプリケーションを本番に移したら、しばらくは速いが数時間後に極端に遅くなる」――T系インスタンスのクレジット枯渇です。断続的な負荷にはT系が最適ですが、定常的に高いCPU使用率が続くワークロードにT系を選ぶ選択肢は不正解になります。この場合はM系かC系に変えるのが正解です。

判断軸

ファミリーの設問で迷ったら、「このワークロードで最初に枯渇するリソースは何か」だけを考えてください。CPUならC、メモリならR、ローカルディスクのIOPSならI。設問文には必ずその手がかりが書かれています。書かれていなければ汎用（M）が答えです。

03

購入オプション ―― コスト設問の中心

ドメイン4の設問の多くは、結局ここに帰着します。6つの選択肢がありますが、選び分けの軸は「どれだけ約束できるか」と「中断を許せるか」の2つだけです。

RI と Savings Plans の違いを一文で

RIは「このインスタンスを使う」という約束、Savings Plansは「毎時これだけ払う」という約束です。この一文がすべてです。RIはインスタンスの属性に紐づくため、構成を変えると割引が当たらなくなります。Savings Plansは金額に紐づくため、その枠内でどう使おうと自由です。SAAでは、この柔軟性の差がそのまま正解の分かれ目になります。

  • Compute Savings Plans は Fargate と Lambda にも効きます。これはRIには絶対にできないことで、設問で「将来コンテナ化を検討している」と書かれていたら、ここが決め手になります。
  • Savings Plans はキャパシティを予約しません。これは重要な非対称です。容量の確保が要件なら、Savings Plansでは答えになりません。
  • RIのうち、AZを指定したゾーンRIはキャパシティ予約を伴います。リージョンを指定したリージョナルRIは割引だけで、容量は保証されません。「割引はいらないが容量だけ確保したい」ならオンデマンドキャパシティ予約です。
  • 支払い方法は3種類――全額前払い、一部前払い、前払いなし。前払いが多いほど割引率は上がります。設問で「初期費用を出せない」と書かれていたら、前払いなしを選びます。割引がゼロになるわけではありません。
Dedicated Host と Dedicated Instance を取り違えない

どちらも「ハードウェアを他の顧客と共有しない」点は同じです。決定的な差は物理サーバーが見えるかどうか。Dedicated Host ではソケット数・物理コア数・ホストIDが見え、同じホストに配置し続けることができます。だから物理コア単位でライセンスされたソフトウェア（Windows Server、SQL Server、Oracle など）の持ち込みが可能になります。Dedicated Instance にはこの可視性がなく、BYOLの要件を満たせません。設問に「ライセンス」「BYOL」「ソケット」「物理コア」が出たら Dedicated Host、単に「専有ハードウェア」としか書かれていなければ Dedicated Instance です。

最頻出の引っかけ

「コストを最小化したい」という一語だけでスポットを選ばせようとする設問が出ます。直前に「24時間365日稼働する本番データベース」と書かれていないか確認してください。常時稼働するステートフルなワークロードにスポットは選べません。逆に「コストを最小化」かつ「中断しても再実行できる」と両方書かれていれば、それはスポットを指す明確な合図です。手がかりは常に2つ以上あります。

04

スポットの中断と、配置グループ

スポットと配置グループは、どちらも「インスタンスが物理的にどこで、いつまで動くか」の話です。この2つは設問の性格が近いので、まとめて押さえます。

中断は予告される

スポットインスタンスは、EC2側が容量を必要としたときに回収されます。このとき中断通知が2分前に発行されます。通知はインスタンスメタデータから読めるほか、EventBridge のイベントとしても受け取れます。アプリケーション側は、この2分でやるべきことを終わらせる設計にします。

  • 処理中のジョブをチェックポイントとして保存する
  • ロードバランサーのターゲットグループから自分を登録解除する
  • キューから取り出したメッセージを、可視性タイムアウトを戻して他のワーカーに渡す

中断動作は終了・停止・休止（ハイバネート）から選べます。ただし休止を選んだ場合は休止処理が即座に始まるため、2分の猶予はありません。また、より早い段階の合図としてEC2インスタンスリバランス推奨があり、中断のリスクが高まった時点で通知されます。2分の通知より前に受け取れるため、余裕をもって退避したい場合はこちらを使います。

実務と試験の接点

本番でスポットを使うときは、Auto Scaling グループの混在インスタンスポリシーで「オンデマンドをベース容量として確保し、それを超える分をスポットで埋める」構成にします。加えて、割り当て戦略を容量最適化（capacity-optimized）にすると、空き容量の多いプールから選ばれるため中断確率が下がります。価格だけを見る戦略より、結果的に安定します。設問で「スポットを使いつつ可用性を確保したい」と来たら、この組み合わせです。

配置グループ ―― 物理的な距離を指定する

配置グループは、インスタンスを物理的に寄せるか、散らすかを指定する仕組みです。追加料金はかかりません。3種類あり、目的が正反対のものが混じっています。

「7」の使い分け

スプレッドとパーティションはどちらも上限が7ですが、数えている対象が違います。スプレッドはインスタンスがAZあたり7台まで。パーティションはパーティションがAZあたり7つまでで、その中に入るインスタンス数に制限はありません。「数百ノードの分散データベースを配置する」という設問でスプレッドを選ぶと不正解です。7台しか置けません。

クラスター配置グループの代償

クラスターは単一AZに閉じるため、AZ障害で全滅します。「レイテンシーを最小化しつつ高可用性も確保したい」という設問は、要件が矛盾しています。この場合、可用性の要件が優先されるなら配置グループを使わずマルチAZに分散させるのが正解です。SAAは可用性を優先する試験だという原則を思い出してください。

ターゲットグループとヘルスチェック

リスナーが受けたリクエストは、ルールに従ってターゲットグループへ送られます。ターゲットグループはロードバランサーとは独立した存在で、ここにヘルスチェックの設定が乗ります。ALBは1つのリスナーから複数のターゲットグループへ、条件に応じて振り分けられます。これがマイクロサービスの入口として使われる理由です。

  • ターゲットの種類は instance / ip / lambda / alb の4つ。ip 型はオンプレミスのサーバーもターゲットにできるため、移行中のハイブリッド構成で使われます。
  • ヘルスチェックは、プロトコル・パス・間隔・タイムアウト・正常しきい値・異常しきい値で構成されます。異常と判定されたターゲットにはトラフィックが送られなくなります。
  • 登録解除の遅延（コネクションドレイニング）は既定300秒。ターゲットを外すとき、処理中のリクエストが終わるのを待ちます。短すぎると処理が途中で切れ、長すぎるとデプロイやスケールインが遅くなります。
ヘルスチェックのパスを甘く見ない

「ヘルスチェックのパスに、データベースへの接続確認を含む重い処理を指定する」設計は、DBが一瞬遅れただけで全台が異常判定され、全滅します。ヘルスチェック用のエンドポイントは軽量に保つ、というのが実務の定石です。試験でも「すべてのインスタンスが同時に異常になった」という設問の原因として登場します。

スティッキーセッションとクロスゾーン負荷分散

スティッキーセッションは、同じクライアントを同じターゲットに送り続ける機能です。ALBには2種類あります。ロードバランサーが発行するCookieを使う期間ベースと、アプリケーションが発行するCookieに従うアプリケーションベース。NLBでは送信元IPに基づくスティッキーネスが使えます。

スティッキーは解ではなく回避策

SAAの設問でスティッキーセッションが選択肢にあるとき、それが正解になるのは「アプリケーションを改修できない」という制約が明記されている場合だけです。スティッキーにすると負荷が偏り、スケールインでセッションが失われます。設計として正しいのは、セッション情報をサーバーの外――ElastiCache や DynamoDB――に出して、サーバーを完全にステートレスにすることです。「水平スケールできるようにしたい」という要件が出たら、この外出しが正解です。

クロスゾーン負荷分散は、あるAZのノードが他のAZのターゲットにもトラフィックを送れるようにする設定です。既定値がタイプによって違います。

  • ALBはロードバランサーのレベルで常に有効です。無効化したい場合はターゲットグループ単位で行います。
  • NLB と GWLBは既定で無効です。有効化するとAZ間のデータ転送料金が発生します。

無効のままだと、AZごとのターゲット台数が揃っていない場合に負荷が偏ります。AZ-aに2台、AZ-cに8台という構成では、トラフィックがAZ間で50:50に分かれるため、AZ-aの2台が4倍の負荷を受けます。「AZごとにターゲット数が違う」と書かれていたら、クロスゾーン負荷分散を疑ってください。

06

Auto Scaling ―― 増やすより、減らすほうが難しい

Auto Scaling グループ（ASG）は、ELBと組んでSAAの中核をなす構成要素です。試験で問われるのは台数の計算ではなく、「なぜ意図どおりに動かないのか」の診断です。

起動テンプレート

ASGが新しいインスタンスを作るときの設計図が起動テンプレートです。旧来の起動設定（Launch Configuration）は非推奨で、新規に選ぶ理由はありません。

  • 起動テンプレートはバージョン管理ができます。設定を変えても過去のバージョンが残り、ロールバックできます。起動設定は一度作ると変更できず、作り直しになります。
  • 混在インスタンスポリシー（複数のインスタンスタイプ、オンデマンドとスポットの組み合わせ）は起動テンプレートでしか使えません。コスト最適化の設問では、ここが決め手になります。
  • T系のUnlimitedモード、Elastic Graphics、専有ホストへの配置なども起動テンプレート側の機能です。

スケーリングポリシーの選び分け

ポリシーやること選ぶ手がかり

予測スケーリングには前提があります。予測を始めるには最低24時間の履歴が必要で、2週間分あると精度が上がります。48時間先までを1時間単位で予測し、6時間ごとに予測を更新します。そして重要な性質として、予測スケーリングはスケールアウトしかしません。負荷が下がる予測でも台数を減らさないため、スケールインは動的ポリシー（ターゲット追跡など）と併用して実現します。「予測スケーリングだけを設定する」選択肢は、コスト最適化の観点で不完全です。

ライフサイクルフックと終了ポリシー

ライフサイクルフックは、インスタンスの起動時（Pending:Wait）と終了時（Terminating:Wait）に処理を割り込ませる仕組みです。EventBridge や SNS で通知を受け、処理が終わったら完了を通知します。タイムアウトまでに完了しなければ、既定の動作に進みます。

  • 終了時のフックが試験では頻出です。「スケールインで終了する前に、ローカルのログをS3へ退避したい」「接続中のユーザーの処理が終わるのを待ちたい」という要件は、すべてここで実現します。
  • 起動時のフックは、設定の投入やウォームアップ用データの読み込みに使います。

終了ポリシーは、スケールインでどのインスタンスを消すかの規則です。既定（Default）の順序はこうです。まずAZ間のバランスが最優先されます。台数が多いAZが選ばれ、その中で古い起動テンプレート／起動設定を使っているものが優先され、次に課金時間の区切りに近いものが選ばれ、それでも並べば無作為です。ほかに OldestInstance、NewestInstance、AllocationStrategy などを指定できます。

判断軸

「インスタンスタイプを新しい世代に入れ替えたい」なら OldestInstance、「新しく試した構成を先に消して元に戻したい」なら NewestInstance。そしてどの終了ポリシーを選んでも、AZ間のバランスが先に評価されます。「最も古いインスタンスを指定したのに、新しいほうが消えた」という設問の答えはこれです。

07

Lambda ―― 制約を先に覚える

Lambdaは「サーバー管理が不要」という長所より、制約のほうが試験に出ます。制約を知っていれば、「この要件はLambdaでは無理だ」と即座に判定でき、選択肢が半分に減ります。

越えられない線

  • 1回の実行は最大15分（900秒）。これがもっとも頻出する数字です。15分で終わらない処理をLambdaに載せる選択肢は不正解になります。
  • メモリは128MBから10,240MBまで。そしてCPU性能はメモリ割り当てに比例します。1,769MBで1vCPU相当です。「Lambdaの処理が遅い、CPUを増やしたい」という設問の答えはメモリ割り当てを増やすで、これは知らないと選べません。
  • /tmp は512MBから10,240MBまで。それ以上の作業領域が要るなら EFS をマウントします。
  • 同期呼び出しのペイロードは6MB。大きなファイルを渡したい場合は、S3に置いてキーだけを渡します。
15分を超えるときの行き先

設問で「処理に30分かかる」「数時間のバッチ」と書かれていたら、Lambdaは消えます。代わりに来るのはAWS Fargate（ECS タスク）、AWS Batch、Step Functions で分割、EC2のいずれかです。どれになるかは残りの要件で決まります。コンテナ化済みなら Fargate、大量のジョブをキューで捌くなら Batch、複数ステップの調整が要るなら Step Functions です。

同時実行数 ―― 2つの「予約」を混同しない

Lambdaのスケーリングは台数ではなく同時実行数で考えます。既定のアカウント上限はリージョンあたり1,000で、引き上げ申請が可能です。この1,000をどう配分するかを制御する仕組みが2つあり、名前が似ているうえに目的が正反対です。

予約済み同時実行
Reserved concurrency		プロビジョニング済み同時実行
Provisioned concurrency
やることアカウントの枠から、その関数専用の取り分を切り出す実行環境を事前に初期化して待機させる
下限としての働き他の関数に奪われない容量を確保する最初のリクエストから温まっている
上限としての働きその数を超えてスケールしない（スロットリング）上限にはならない。超過分は通常どおり起動する
追加料金なしあり
解決する問題下流のRDSやサードパーティAPIが、Lambdaの急増で潰れるのを防ぐコールドスタートによるレイテンシーのばらつきをなくす

予約済み同時実行を設定するときは、アカウントの未予約分から100は残さなければなりません。上限が1,000のアカウントで、1つの関数に1,000を予約することはできません。

RDS を守る設問は定型

「S3への大量アップロードがLambdaをトリガーし、Lambdaが一斉にRDSへ接続して接続数の上限に達した」――この設問の正解は予約済み同時実行で上限を絞る、またはRDS Proxy で接続をプールするです。実務では両方やります。「RDSのインスタンスサイズを上げる」は、症状を先送りしているだけで正解になりません。

コールドスタート

実行環境が存在しないときは、環境の作成とランタイムの初期化、そしてハンドラ外のコードの実行が発生します。これがコールドスタートです。緩和の手段は段階的です。

  1. ハンドラの外で初期化する。データベース接続やSDKクライアントをハンドラ外に置けば、温まった環境では再利用されます。コードの書き方だけで効く、費用ゼロの対策です。
  2. デプロイパッケージを小さくする。不要な依存を削り、共通部分は Lambda Layers に出します。
  3. プロビジョニング済み同時実行を設定する。確実ですが課金されます。予測できる負荷に対しては Application Auto Scaling でスケジュールできます。

Javaランタイムには SnapStart という選択肢もあり、初期化済みの状態をスナップショットとして再利用します。設問に「Java」と「起動が遅い」が同時に出たらこれです。

VPC接続 ―― 最頻出の設計ミス

Lambda関数をVPCに接続すると、VPC内のRDSやElastiCacheにプライベートIPで到達できるようになります。同時に、その関数はVPCのルーティングに完全に従うようになります。ここが引っかけの温床です。

最頻出の引っかけ

「VPCに接続したLambdaから、インターネット上の外部APIを呼べなくなった」――パブリックサブネットに置いても解決しません。VPC内のLambdaにはパブリックIPが割り当てられないためです。正解はプライベートサブネットに配置し、NAT Gateway 経由で出すことです。そしてS3やDynamoDBへのアクセスだけが目的なら、NATを使わずゲートウェイエンドポイントを作るほうが安く、これがコスト設問の正解になります。

イベントソースの3つの型

Lambdaの呼び出され方は3種類あり、失敗したときの挙動が違います。ここは設問の前提条件として効いてきます。

型呼び出し元の例失敗したとき
同期呼び出しAPI Gateway、ALB、Cognito、直接呼び出しエラーが呼び出し元に返る。リトライは呼び出し元の責任
非同期呼び出しS3イベント、SNS、EventBridgeLambdaが自動で2回リトライする。それでも失敗すればデッドレターキューまたは Lambda の送信先へ
イベントソースマッピングSQS、Kinesis Data Streams、DynamoDB Streams、Amazon MSKLambda側がポーリングする。ストリーム系は既定で、成功するかレコードが期限切れになるまでシャードがブロックされる
SQS と組むときの必須設定

SQSをイベントソースにする場合、キューの可視性タイムアウトを、Lambda関数のタイムアウトより長く設定します。これを怠ると、関数がまだ処理している最中にメッセージが再び可視化され、同じメッセージが重複して処理されます。AWSは関数タイムアウトの6倍を推奨しています。「メッセージが重複処理される」という設問の原因は、ほぼこれです。

確認問題

先に自分で答えを決めてから開いてください。当てずっぽうで開くと、この5分が無駄になります。

Q1製造ラインのセンサーデータを夜間にまとめて集計するバッチ処理がある。処理は数時間かかるが、中断されても最初からやり直せる。開始時刻は柔軟で、完了が翌朝までなら問題ない。コストを最小化する購入オプションはどれか。
  • A. 3年 All Upfront の Standard Reserved Instance
  • B. スポットインスタンス
  • C. オンデマンドインスタンス
  • D. Compute Savings Plans

正解: B

「中断されてもやり直せる」「開始時刻が柔軟」という2つの手がかりが、スポットを明確に指しています。最大90%の割引が得られ、この要件ではスポット以外に安い選択肢がありません。

判断軸: AとDは1〜3年の継続利用にコミットするもので、夜間だけ動くワークロードではコミット分を使い切れず割高になります。RIやSavings Plansが有利なのは「常時稼働する定常的な使用量」に対してです。稼働が断続的ならスポットかオンデマンド、常時稼働ならコミット系――この切り分けを先に行ってください。

Q2取引先の企業から、自社が公開するAPIへ接続する。取引先は自社のファイアウォールでアウトバウンドの宛先IPを許可リスト方式で管理しており、IPアドレスが変わらないことを求めている。プロトコルはTCPで、HTTPの内容に基づく振り分けは不要である。適切な構成はどれか。
  • A. Application Load Balancer を作成し、そのDNS名を取引先に伝える
  • B. Network Load Balancer を作成し、各AZに Elastic IP を割り当てる
  • C. Application Load Balancer に Elastic IP を割り当てる
  • D. Gateway Load Balancer を作成し、エンドポイント経由で公開する

正解: B

NLBはAZごとに静的IPを持ち、Elastic IPを割り当てることもできます。「IPアドレスが変わらないこと」という要件を直接満たせるのはNLBだけです。

判断軸: Cは成立しません。ALBにElastic IPは割り当てられず、DNS名の背後でIPが変動します。Aはその制約をそのまま踏んでおり要件を満たしません。DのGWLBは仮想アプライアンスを挟むためのもので、APIの公開には使いません。「静的IP」という語を見た瞬間にNLB、と反射で結び付けてください。

Q3ALBの背後にAuto Scalingグループを配置したWebアプリケーションで、あるインスタンスのアプリケーションプロセスが停止した。ALBはそのインスタンスへのトラフィックを止めたが、数時間経ってもインスタンスは交換されず、グループの実行中台数は変わらないままだった。OS自体は正常に動作している。原因として最も適切なものはどれか。
  • A. Auto Scaling グループのヘルスチェックタイプが EC2 のみに設定されている
  • B. ターゲットグループの登録解除の遅延が長すぎる
  • C. クロスゾーン負荷分散が無効になっている
  • D. スケーリングポリシーがターゲット追跡に設定されている

正解: A

ヘルスチェックタイプがEC2のみの場合、ASGはハイパーバイザーから見たインスタンスの状態しか見ません。OSが動いていればアプリが死んでいても「正常」と判定され、交換されません。ELBヘルスチェックをASGのヘルスチェックタイプに追加して初めて、ALBの判定がインスタンスの入れ替えに反映されます。

判断軸: ELBは「送るのをやめる」だけ、ASGが「入れ替える」――この役割分担が問われています。Bは交換後の切り離しにかかる時間の話で、交換自体が起きないこの状況とは無関係です。Cは負荷の偏りの話、Dは台数の増減の話で、どちらも症状に対応していません。

Q4VPC内のRDSからデータを読み、外部のSaaSのREST APIへ送信するLambda関数を作成した。VPCに接続する設定を加えたところ、RDSへは接続できるようになったが、外部APIの呼び出しがタイムアウトするようになった。関数はパブリックサブネットに配置されている。最小の運用負荷で解決する方法はどれか。
  • A. 関数にパブリックIPアドレスを割り当てる
  • B. 関数をプライベートサブネットに移し、NAT Gateway 経由でインターネットへ出る経路を用意する
  • C. 関数のVPC接続を解除し、RDSをパブリックアクセス可能にする
  • D. 関数のタイムアウトを15分に延長する

正解: B

VPCに接続したLambdaにはパブリックIPが割り当てられません。パブリックサブネットに置いてもインターネットへは出られない、というのがこの設問の核心です。プライベートサブネットに配置し、NAT Gateway をインターネットへの出口にするのが定石です。

判断軸: Aは仕様上できません。CはRDSをインターネットに露出させるもので、セキュリティ上の後退です。Dは疎通できていない問題を待ち時間で解こうとしており、原因に触れていません。なお送信先がS3やDynamoDBだけならNATは不要で、ゲートウェイエンドポイントを使うほうが安価です。宛先がAWSサービスか外部かで答えが変わります。

Q5社内向けの分析アプリケーションをコンテナで運用する。チームにKubernetesの経験者はおらず、運用の手間を最小限にしたい。処理はGPUを必要とせず、タスク数は日中と夜間で大きく変動する。既存のEC2インスタンス群は廃止する方針である。最も適切な構成はどれか。
  • A. EKS クラスターを作成し、マネージドノードグループでEC2インスタンスを運用する
  • B. ECS クラスターを作成し、EC2 起動タイプでAuto Scalingグループを運用する
  • C. ECS クラスターを作成し、Fargate 起動タイプでタスクを実行する
  • D. EC2 インスタンスに Docker をインストールし、systemd でコンテナを管理する

正解: C

Kubernetesの経験がなく、GPUも不要で、タスク数が変動する。この3つがそろえば ECS + Fargate です。オーケストレーターは学習コストの低いECS、実行基盤はサーバー管理の要らないFargate、という2段階の選択がそのまま答えになります。

判断軸: Aは「Kubernetesの経験者がいない」という制約に反し、コントロールプレーン料金も上乗せされます。BとDはEC2の管理が残り、「運用の手間を最小限に」「既存のEC2群は廃止」という要件に逆行します。ECSかEKSかは組織のスキルで、EC2起動タイプかFargateかはワークロードの性質で決まる――2本の軸を別々に判定するのが、この種の設問の解き方です。
