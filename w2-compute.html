01

全体の地図

工場の生産ラインにたとえると、EC2 が機械、ロードバランサーが仕事を配る係、Auto Scaling が「忙しさに合わせて機械を増減する班長」です。まず登場人物を紹介してから、8つの場面がどこの話かを見ます。

この講義の登場人物
EC2Amazon Elastic Compute Cloud
AWS の仮想サーバー。1台1台をインスタンスと呼ぶ（IAM・VPC 講義で既出）
ELBElastic Load Balancing
利用者からの通信を受けて、複数の EC2 に配るサービス（ロードバランサー）。中に ALB・NLB・GWLB の3種類がある → 場面4
Auto ScalingAmazon EC2 Auto Scaling
EC2 の台数を自動で保ったり増減したりするサービス。まとめる単位を Auto Scaling グループ（ASG）と呼ぶ → 場面5・6
CloudWatchAmazon CloudWatch
CPU 使用率などの数字を集めて見張る、AWS の監視サービス → 場面6
LambdaAWS Lambda
サーバーを用意せず、コード（関数）だけを置いておくと、呼ばれたときに AWS が動かしてくれるサービス → 場面7
コンテナ
アプリと動かすのに必要な部品を1つの箱に詰めて、どこでも同じように動かす技術。AWS では ECS・EKS・Fargate を使う → 場面8

そもそも EC2 で動かすのか

同じアプリでも、EC2・Fargate（コンテナを動かす場所を AWS が用意してくれるサービス、場面8）・Lambda のどれで動かすかで、自分が面倒を見る範囲が変わります。図の言語ランタイムは、プログラムを動かすための土台（Python や Java を実行する仕組み）のことです。

この講義の見取り図

場面1〜3は機械そのもの（どの型を、どう払って、どこに置くか）。場面4〜6は機械の群れの扱い（どう配り、どう入れ替え、どう増減するか）。場面7・8は機械を持たない選択肢（Lambda とコンテナ）です。 コンピューティングはドメイン2（弾力性）・3（性能）・4（コスト）の三方向から問われます。「安いのはどれか」と「落ちないのはどれか」は別の設問なので、読むときはどちらを聞かれているかを先に決めてください。

02

場面1 ―― 「開発では速かったのに、本番に移したら数時間後に極端に遅くなった」

この場面で初めて出る言葉
インスタンスタイプ
EC2 の「品番」。CPU の数とメモリの量の組み合わせが決まっている（例：m5.large）
ファミリー
インスタンスタイプの頭の英字。用途の系統を表す（C＝CPU 重視、R＝メモリ重視 など）
vCPU
仮想 CPU の数。EC2 の CPU の量はこれで数える
IOPS
ディスクが1秒間に読み書きできる回数
GPU
もとは画像処理用のチップ。大量の単純な計算を同時にこなせるので、機械学習に使う
T系
普段は控えめに動き、ときどき全力を出せる安いファミリー（バースト可能パフォーマンスインスタンス）
CPU クレジット
T系が全力を出すための「貯金」。ベースライン（普段使ってよい CPU の割合）を下回る間に貯まる

インスタンスタイプは、EC2 を起動するときに一覧から選びます。後から変えるときは、台を止めてタイプを変え、起動し直します。数百の品番がありますが、読み方が決まっているので丸暗記は要りません。

ファミリーは「何が最初に足りなくなるか」で選ぶ

T系だけは仕組みを知っておく

  • この場面の答え：開発環境で使っていた T系の CPU クレジットが、本番のずっと続く負荷で尽きた。M系か C系に替えるのが正解
  • スタンダードモード：クレジットが尽きたら絞られる。費用は読める
  • Unlimited モード：尽きても性能を保ち、超えた分を追加で払う（インスタンスの設定で切り替える）
試験ではこう出る

「1TB のデータをメモリに保持して分析」→ R系。「動画のエンコード」→ C系。「しばらく速いが数時間後に遅くなる」→ T系のクレジット枯渇。ずっと高い CPU 使用率が続く仕事に T系を選ぶ選択肢は不正解。

03

場面2 ―― 「常時動くサーバーと、夜間バッチがある。全体のコストを下げたい」

この場面で初めて出る言葉（購入オプション）
オンデマンド
使った時間だけ払う、定価の買い方。約束なし。基準になる値段
スポットインスタンス
AWS の余っている設備を最大90%引きで借りる。その代わり、AWS が必要になると取り上げられる（中断）
RIReserved Instances（リザーブドインスタンス）
「この型を1年か3年使う」と約束して割引を受ける
Savings Plansセービングプラン
「毎時これだけの金額を1年か3年使う」と約束して割引を受ける
Dedicated Host専有ホスト
物理サーバー1台を丸ごと自分専用にする。中のソケット数・コア数が見える
Dedicated Instance専有インスタンス
他の客とハードウェアを共有しないが、物理サーバーの中身は見えない
BYOLBring Your Own License
手持ちのソフトのライセンスを AWS に持ち込むこと
バッチ
まとめて一気に流す処理。夜間の集計など

ここで大事なのは、RI や Savings Plans は「別の種類の EC2」ではないことです。請求の画面で「割引の約束」を買っておくと、条件に合う普通の EC2 の利用に、後から自動で割引が当たります。一方スポットは、EC2 を起動するときに「購入オプション：スポット」を選んで使います。

選び分けの軸は「どれだけ先まで約束できるか」と「中断を許せるか」の2つだけです。まず、1つのシステムの中に払い方の違う部分が混ざっていることを見ます。

設問を読んだら、上から順に判定する

01物理サーバー単位のライセンスを持ち込むか「BYOL」「ソケット数」「物理コア」「ホストを指定して配置」はい → Dedicated Host
02中断されても、やり直せるか「バッチ」「開始時刻が柔軟」「途中で止まっても困らない」はい → スポット
031〜3年使い続けると言えるか「短期」「初めてで量が読めない」「検証」なら言えないいいえ → オンデマンド
04将来、型・リージョン・コンテナ・Lambda に動くかもしれないか動かないなら EC2 Instance Savings Plans か Standard RI（最大72%）はい → Compute Savings Plans
稼働がときどきならスポットかオンデマンド、ずっと動くなら約束して割引

RI と Savings Plans の違い

  • Savings Plans は2種類：Compute Savings Plans は EC2 のほか Fargate と Lambda にも割引が効く。EC2 Instance Savings Plans はファミリーとリージョンを固定する代わりに割引が大きい
  • Convertible RI：RI のうち、ファミリーや OS を後から交換できる版。割引は Standard RI より小さい
  • 前払い：全額・一部・なしの3種類。前払いが多いほど割引が大きい。「初期費用を出せない」なら前払いなし（割引がゼロになるわけではない）
  • キャパシティ予約：「必要なときに台数を必ず起動できるよう、AWS の設備を取っておく」こと。RI のうち AZ を指定して買ったもの（ゾーン RI）にはこれが付く。割引は要らず台数だけ確保したいならオンデマンドキャパシティ予約。Savings Plans は台数を確保しない
Dedicated Host と Dedicated Instance を取り違えない

違いは物理サーバーの中身が見えるかどうか。Host はソケット数・物理コア数が見えるので、コア単位で数えるライセンス（Windows Server、SQL Server、Oracle など）を持ち込める。「ライセンス」「BYOL」が出たら Host、「他の客と共有しない」としか書かれていなければ Instance。

最頻出の引っかけ

「コストを最小化」の一語だけでスポットに飛びつかない。「24時間365日動く本番データベース」と書かれていないかを確かめる。手がかりは必ず2つ以上ある。「コスト最小」と「中断しても再実行できる」がそろって初めてスポット。

配置グループ ―― 寄せるか、散らすか

配置グループは EC2 の画面で先に作っておき、インスタンスを起動するときに「この配置グループに入れる」と指定します。

「速く」と「落ちない」が両方書かれていたら

クラスターは1つの AZ に閉じるので、AZ 障害で全滅する。「通信の遅れを最小にしつつ高可用性も」という設問で可用性が優先されるなら、配置グループを使わず複数の AZ に分散する。SAA は可用性を優先する試験。数百台の分散データベースにスプレッドを選ぶのも不正解（7台しか置けない）。

場面4 ―― 「取引先に API を公開したい。相手のファイアウォールに IP を登録してもらう」

この場面で初めて出る言葉
ロードバランサー
利用者からの通信を1か所で受けて、後ろの複数の台に配る係
ELBElastic Load Balancing
AWS のロードバランサーのサービス名。作るときに次の3種類から選ぶ
ALBApplication Load Balancer
Web の通信（HTTP）の中身まで読んで配る。Web アプリ向け
NLBNetwork Load Balancer
中身は読まず、ポート番号だけ見て速く配る。固定の IP アドレスを持てる
GWLBGateway Load Balancer
通信を丸ごと、他社製のファイアウォールや侵入検知装置（IDS）などの検査装置に通す
リスナー
ロードバランサーが「何番ポートで受け付けるか」の設定
ターゲットグループ
配り先の台をまとめた名簿。ロードバランサーはここに載っている台に配る
ヘルスチェック
ロードバランサーが各台に定期的にアクセスして、ちゃんと応答するかを確かめること
Elastic IPEIP
AWS で取得できる、変わらないパブリック IP アドレス
WAFAWS WAF（Web Application Firewall）
攻撃らしい Web の通信を見分けて止めるサービス。HTTP の中身を読んで判断する
UDP
動画配信やゲームでよく使う、相手の確認を待たずに送り続ける通信の方式

ロードバランサーは EC2 の画面の「ロードバランサー」から作ります。最初に ALB・NLB・GWLB のどれにするかを選び、リスナーとターゲットグループを決めます。3種類の違いは通信のどこまでを読むかです。

通信は荷物の配送に似ていて、外側から「宛先の住所（IP アドレス）」「部屋番号（ポート番号）」「荷物の中身（HTTP の内容：どのページを見たいか など）」の順に包まれています。この層を L3・L4・L7 と番号で呼びます。

ALBNLBGWLB
扱う通信HTTP / HTTPSTCP / UDPすべて
固定 IP持てない（DNS 名でアクセス）AZ ごとに持てる。EIP も可—
配り先EC2・IP・LambdaEC2・IP・ALB検査装置
AWS WAF付けられる付けられない付けられない

WAF は HTTP の中身を読んで判断するので、HTTP の中身を読める ALB にしか付けられません。

同じ客を同じ台に送る ―― スティッキーセッション

ログイン状態やカートの中身など、客ごとの情報をセッションと呼びます。セッションを各台の中に持っていると、次のアクセスが別の台に配られたとき、ログインが切れてしまいます。そこで「同じ客は同じ台に送り続ける」設定がスティッキーセッションです（ターゲットグループの設定）。

スティッキーセッションは解ではなく回避策

台ごとに負荷が偏り、台が減るとその台にいた客のセッションが消える。正解になるのは「アプリを改修できない」と明記されたときだけ。設計として正しいのは、セッションを台の外の共有の置き場――ElastiCache（Amazon ElastiCache：メモリ上の高速なデータ置き場）や DynamoDB（Amazon DynamoDB：キーで素早く読み書きするデータベース）――に出して、どの台に配られても同じに動くようにすること。

試験ではこう出る

「静的 IP」「相手のファイアウォールに IP を登録」「UDP」→ NLB。「URL のパスごとに別のサービスへ」「WAF を付けたい」→ ALB。「他社製のファイアウォールを通信の途中に挟む」→ GWLB。迷ったら「HTTP の中身を読まないと実現できないか」を自問する。

場面5 ―― 「アプリが落ちたのに、インスタンスが入れ替わらない」「一部の台だけ重い」

この場面で初めて出る言葉
Auto ScalingAmazon EC2 Auto Scaling
EC2 の台数を自動で保ったり増減したりするサービス
ASGAuto Scaling グループ
Auto Scaling が面倒を見る EC2 のまとまり。「最小・希望・最大」の台数を持つ
希望台数Desired capacity
ASG が「今は何台動かすか」の目標。ASG は動いている台をこの数に合わせ続ける
起動テンプレート
ASG が新しい台を作るときの設計図。インスタンスタイプなどを書いておく
AMIAmazon Machine Image
OS とソフトを入れた状態の「台の元型」。ここから同じ台を何台でも作れる
クロスゾーン負荷分散
ロードバランサーが、AZ の境目を越えて全台に均等に配る設定

ASG は EC2 の画面の「Auto Scaling グループ」から作ります。起動テンプレート、どのサブネットに置くか、最小・希望・最大の台数、そして場面4のロードバランサー（のターゲットグループ）につなぐかを決めます。ASG が作った台は、自動でターゲットグループに載ります。

アプリが落ちたのに入れ替わらない

ここで、台の調子を確かめている者が2人いることに注意してください。1人はロードバランサー（場面4のヘルスチェック）、もう1人は ASG です。ASG は既定では「EC2 の OS が動いているか」しか見ていません。

  • どこで設定するか：ASG の設定の「ヘルスチェック」で、確認方法に ELB を加える（既定は EC2 だけ）
  • ヘルスチェックの中身（どの URL に、何秒おきに確かめるか）はターゲットグループの設定
  • 登録解除の遅延（既定300秒）：台を名簿から外すとき、処理中のリクエストが終わるのを待つ時間
ヘルスチェックの確認先を重くしない

ヘルスチェックで、データベースへの接続確認まで行う URL を指定すると、データベースが一瞬遅れただけで全台が同時に異常と判定されて全滅する。「すべての台が同時に異常になった」の原因として出る。

一部の台だけ重い ―― クロスゾーン負荷分散

ロードバランサーは、実は AZ ごとに分身を置いています。クロスゾーン負荷分散が無効だと、各分身は自分の AZ の台にしか配りません。

場面6 ―― 「毎朝9時に重くなる」「起動しては数分で終了するのを繰り返している」

この場面で初めて出る言葉
メトリクス
CloudWatch が集める数字のこと。CPU 使用率、リクエスト数など
CloudWatch アラーム
メトリクスが「80% を超えた」などの条件を満たしたら知らせる仕組み
スケーリングポリシー
ASG に付ける「いつ、何台に変えるか」のルール。CloudWatch の数字を見て希望台数を書き換える
スケールアウト／スケールイン
台数を増やすこと／減らすこと
ライフサイクルフック
台の起動や終了の途中で一時停止させ、その間に作業を差し込む ASG の設定
SNSAmazon Simple Notification Service
メールや他のサービスへ通知を送るサービス

場面5で、ASG は「希望台数に合わせる」だけだと見ました。では、誰が希望台数を変えるのか。それがスケーリングポリシーです。

どこで設定するか：EC2 の画面で ASG を開き、「自動スケーリング」のタブで追加します。たとえばターゲット追跡なら「メトリクス：CPU 使用率の平均」「目標値：40」と入れるだけで、CloudWatch のアラームは AWS が自動で作ります。ポリシーは次の種類があり、同じ1日の負荷に対して動き方が違います。

ポリシーどう動くか選ぶ手がかり
ターゲット追跡指標を目標値に保つよう、増減を自動で計算する「〜を一定に保ちたい」。迷ったらこれ
ステップしきい値の超え方で増やす量を変える「60%超で2台、80%超で4台」
簡易1つのアラームで1回だけ増減する。古い方式正解になることはまずない
スケジュール決めた時刻に希望台数を変える「毎朝9時に」「月末に」
予測過去の周期から先回りして増やす。最低24時間の履歴が要る「周期的」「起動に時間がかかり間に合わない」

3つの待ち時間

どれも ASG の設定項目です。名前が似ていますが、何を待っているかが違います。

設定何を待つか効く場面
ヘルスチェックの猶予期間起動直後の台を、しばらく検査しない上の図。短すぎると起動と終了を繰り返す
インスタンスのウォームアップ起動直後の台の数字を、しばらく平均に入れない起動直後は CPU が 100% になりがち。それにつられてさらに増やす暴走を防ぐ
クールダウン（既定300秒）増減したあと、次の増減を始めるまで待つ簡易スケーリング用

終了の前にやること ―― ライフサイクルフック

台が増減するとき、ASG の中で台の状態は次のように進みます。ライフサイクルフックを付けると、「〜の途中で待つ」状態で止まり、その間に作業を差し込めます。止まったことは EventBridge（場面3）や SNS で知らせが来るので、作業を終えたら「完了」を返します。

どの台から消されるか（終了ポリシー）

スケールインで消す台の選び方も ASG の設定。既定ではまず AZ ごとの台数のバランスが優先され、台数の多い AZ から消す。その中では古い起動テンプレートで作った台が先。「最も古い台を消す設定にしたのに、新しい台が消えた」の答えは、AZ のバランスが先に評価されたから。

スポットを使いつつ落ちないように（場面2・3のつづき）

ASG の混在インスタンスポリシーで「オンデマンドを土台に何台か確保し、上乗せ分をスポットで埋める」ことができる。これは起動テンプレートでしか使えない。スポットの割り当て方を容量最適化にすると、余裕のある設備から選ばれて中断が減る。

一斉に増えて、下流を潰す

S3 に 1,000 ファイルが同時に届けば、Lambda は 1,000 個の実行環境で同時に動きます。それぞれがデータベースに接続しにいけば、データベースの接続数の上限をすぐに超えます。

RDS Proxy は、RDS の手前に置いて接続を束ねる中継役です。Lambda が何百個あっても、データベースへの実際の接続は少数にまとめてくれます。

同時実行には、名前の似た設定が2つあります。どちらも Lambda の関数の設定画面で数字を入れます。

予約済み同時実行プロビジョニング済み同時実行
やること1,000 の枠から、この関数の取り分を切り出す。同時にその数までしか動かない実行環境を前もって作って待たせておく
追加料金なしあり（待たせている間も払う）
解決する問題一斉に増えて下流を潰すコールドスタートの遅さ

Lambda では無理なこと

/tmp は関数が一時的に使える作業用の置き場、同期ペイロードは結果を待つ呼び出しで一度に渡せるデータの量です。

15分を超える処理の行き先は次の3つ。Fargate（コンテナで動かす、場面8）、AWS Batch（大量の計算ジョブを順番に流すサービス）、AWS Step Functions（複数の処理を手順書どおりにつなぐサービス。長い処理を15分以内の小分けにできる）。EFS（Amazon Elastic File System）は、複数の台から同時に使える共有のファイル置き場です。

VPC に入れたら、外へ出られなくなった

Lambda は既定では AWS が管理する場所で動きます。自分の VPC の中にある RDS に接続したいときは、関数の設定で「VPC に接続」を選び、置くサブネットを指定します。すると、VPC 講義で見た道案内（ルートテーブル）に従うようになります。

呼ばれ方は3種類

表に出てくる SQS（Amazon Simple Queue Service）は、処理待ちの仕事（メッセージ）を溜めておく待ち行列です。

型呼び出し元の例失敗したとき

ECS・EKS・Fargate は「3つのコンテナサービス」ではありません。ECS と EKS は指揮役（③）、Fargate は動かす場所（④）です。だから「ECS ＋ Fargate」「EKS ＋ EC2」のように組み合わせて選びます。ECS なら、クラスターを作るときやタスクを起動するときに「起動タイプ：EC2 か Fargate か」を選びます。

  • Fargate で使えないもの：GPU、特権コンテナ（サーバー本体の設定まで触れる特別なコンテナ）。これらが要るなら EC2 起動タイプ
  • EKS の料金：Kubernetes の指揮役そのもの（コントロールプレーン）の料金がクラスターごとにかかる。ECS にはない

ロールは2つある

コンテナも、AWS のサービスを使うには IAM ロールが要ります（IAM 講義）。ECS では、誰が使うかでロールが2つに分かれます。どちらもタスクの設定（タスク定義）で指定します。図の CloudWatch Logs は、CloudWatch のログの置き場です。

Lambda・コンテナ・EC2 の三択

01処理は15分以内に終わり、何かをきっかけに動き、状態を持たないか実行時間が読めない、常に起動しておく必要がある、なら次へはい → Lambda
02OS への依存があるかGPU、特権コンテナ、OS の特別な設定、台に紐づくライセンスはい → EC2（または ECS on EC2）
03アプリはコンテナになっているかなっていない、かつ作り直せない、なら EC2いいえ → EC2
04すでに Kubernetes を使っているか使っていないなら、覚えることの少ない ECSはい → EKS / いいえ → ECS
05サーバーの管理を手放したいかGPU が要る、たくさん詰め込んで安くしたい、なら EC2 起動タイプはい → Fargate
迷ったら、運用の手間が少ないほうが正解

SAA には「運用の手間を最小限に」という言葉が繰り返し出て、そのたびにAWS に任せる部分が多い選択肢が正解になります。EC2 に自分でインストールする案が正解になるのは、他の選択肢が要件を満たせないときだけです。
