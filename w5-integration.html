01

この講義のゴール

サービスの数だけ見ると多く感じますが、問われ方は驚くほど定型です。「どのサービスか」ではなく「どの性質が要るか」で切れば、選択肢は毎回2つに絞れます。今日終わったときに、次の3つができていれば合格です。

  • 01
    SQS・SNS・EventBridge を、設問の一文から選び分けられる。
    「バッファしたい」「同じイベントを複数に配りたい」「AWS の出来事に反応したい」――どれに当たるかを即断できる。
  • 02
    可視性タイムアウトとデッドレターキューが何を防ぐか説明できる。
    「メッセージが二重に処理される」「同じメッセージが延々とリトライされる」の原因と対処を言える。
  • 03
    CloudWatch と CloudTrail の境界線を引ける。
    「誰が消したのか」と「いつ落ちたのか」で、見るべきサービスが違うと即答できる。
この講義の位置づけ

疎結合はドメイン2（回復性の高いアーキテクチャの設計、26%）の中心テーマ、監視と運用はドメイン3とドメイン1にまたがって顔を出します。しかもこの範囲は単独で問われるより、他分野の設問の中に部品として現れるのが特徴です。「S3 にファイルが置かれたら処理する」「RDS の負荷が上がったらスケールする」――こうした設問の接着剤が、今日扱うサービスです。

02

なぜ疎結合にするのか

先にサービスを覚えると失敗します。何が困っていて、キューを挟むと何が解決するのか。そこから入ります。

同期呼び出しの何が問題なのか

注文サービスが在庫サービスを HTTP で直接呼ぶ構成を思い浮かべてください。平常時は問題ありません。問題は平常時以外に出ます。

  1. 送り手が受け手の処理能力に縛られる。セール開始の瞬間に秒間3,000件の注文が来たとします。在庫サービスが秒間500件しか捌けないなら、残りはタイムアウトかエラーです。送り手にできるのは、利用者に失敗を返すことだけ。受け手の限界が、そのままサービス全体の限界になります。
  2. 障害が伝播する。在庫サービスが落ちると注文サービスのスレッドが応答待ちで埋まり、やがて受付そのものが止まります。「在庫更新だけが遅れる」で済んだはずの障害が全体障害に育つ――カスケード障害です。
  3. スケールの単位が揃わない。注文の受付は軽く、在庫の更新は重い。同期だと重い側に合わせて全体を太らせるしかありません。
  4. 相手を知ってしまう。エンドポイントを設定に持つ以上、受け手を1つ増やすたびに送り手のコードと設定が変わります。

間に1本挟むと何が変わるか

あいだにキューを1本入れると、この4つが同時に消えます。送り手は投入した時点で成功を返せ、受け手は自分のペースで取りに行き、受け手が落ちていてもメッセージは残ります。効き方は3つです。

  • バッファリング。流入と処理の速度差を時間で吸収します。ピークの3,000件は消えず、キューに積まれて後から処理されます。
  • 隔離。受け手の障害が送り手に届きません。壊れる範囲を区切るのが回復性設計の基本です。
  • 抽象化。送り手は受け手が誰か、何台いるかを知りません。増やしても送り手は変わりません。
判断軸

設問に「decouple / 疎結合 / コンポーネント間の依存を減らす」「ピーク時にリクエストが失われる」「処理が追いつかない」「下流サービスの障害が上流に影響しないように」という表現が出たら、答えは今日のサービス群です。逆に言えば、この表現がないのに無理にキューを挟む選択肢は、過剰設計として不正解になることがあります。

最頻出の引っかけ

「疎結合にするために ELB を挟む」という選択肢です。ELB はエンドポイントを抽象化しますが、同期のままなのでバッファになりません。受け手が捌けなければ 5xx を返します。ELB は「複数台に分散したい」、キューは「時間で吸収したい」です。

非同期は速くならない

非同期化すると送り手から見た応答時間は短くなりますが、エンドツーエンドの完了時間はむしろ伸びます。設問が「利用者への応答を速くしたい」なら非同期化は有効、「処理そのものを速く終わらせたい」なら並列化やスケールアウトの話です。ここを取り違えると、もっともらしい誤答を掴みます。

03

SQS ―― 詰まりを時間で吸収する

SQS はフルマネージドのメッセージキューです。性質は一言で「プル型で、1つのメッセージは1つのコンシューマが処理する」。この2点がすべての判断の起点です。

標準キューと FIFO キュー

SQS を選んだあと、必ず次に問われる選択です。既定は標準で、FIFO は「業務要件として順序か重複排除が必要なとき」だけ選びます。

標準キューFIFO キュー
順序ベストエフォート。基本は送った順だが保証はないメッセージグループ内で厳密に保証
配信少なくとも1回。重複しうる正確に1回の処理。重複排除ウィンドウは5分
スループットほぼ無制限1つの API アクションあたり毎秒300件、バッチ（10件単位）なら毎秒3,000件。高スループットモードではこれがパーティションごとの値になる
キュー名制約なし.fifo サフィックスが必須
選ぶ場面非同期処理の大半。画像変換、通知、ログ取り込み金融取引、在庫の増減、コマンドの適用順が意味を持つもの

誤解されやすいのが順序の粒度です。FIFO が保証するのはキュー全体の順序ではなく、同じ MessageGroupId を持つメッセージどうしの順序です。顧客IDをグループIDにすれば、顧客単位では順序が守られ、顧客間では並列に処理されます。逆にグループIDを1種類にすると順序は完全に守られますが並列度は1になります。並列度はメッセージグループの数で決まると覚えてください。

重複排除は MessageDeduplicationId を明示するか、ContentBasedDeduplication で本文のハッシュを使います。判定ウィンドウはどちらも5分で、それを過ぎれば同じ内容でも別のメッセージとして通ります。

可視性タイムアウト

メッセージを受信しても、それはキューから消えるのではなく、一定時間だけ他のコンシューマから見えなくなります。これが可視性タイムアウトで、既定は30秒、0秒から最大12時間まで設定できます。処理を終えて DeleteMessage を呼べば、そこで初めて消えます。呼ばないまま可視性タイムアウトが切れると、メッセージは再び現れ、別のコンシューマが受け取ります。

最頻出の引っかけ

「メッセージが二重に処理されてしまう。原因は？」――可視性タイムアウトが処理時間より短いが答えです。処理に90秒かかるのに既定の30秒のままだと、処理中に再びメッセージが見えるようになり、2台目が同じ仕事を始めます。対処は、可視性タイムアウトを処理時間より長くするか、処理中に ChangeMessageVisibility で延長すること。「Lambda の関数タイムアウトを伸ばす」「コンシューマを増やす」は的外れです。

逆に長すぎても困ります。コンシューマが処理中に落ちると、可視性タイムアウトが切れるまでそのメッセージは誰も触れません。処理時間より少し長い、が正解です。Lambda をトリガーにする場合は、関数タイムアウトの6倍程度にするのが AWS の推奨です。

デッドレターキュー

処理に失敗し続ける毒メッセージを隔離する仕組みです。元のキューに maxReceiveCount を設定し、その回数を超えて受信されたメッセージを別のキュー（DLQ）に移します。

  • DLQ がないと、壊れたメッセージが保持期間いっぱいリトライされ続け、正常なメッセージの処理を圧迫します。「1件の不正データでキュー全体が滞留している」と来たら DLQ です。
  • DLQ は元のキューと同じ種類でなければなりません。FIFO キューの DLQ は FIFO キューです。
  • 原因を直したあとは、リドライブ機能で元のキューへ戻せます。DLQ は捨て場ではなく待避所です。経過時間は元のキューに入った時点から数えられるため、DLQ の保持期間は長めに取ります。

ロングポーリングとショートポーリング

コンシューマは ReceiveMessage でキューを見に行きます。待ち時間をゼロにすると、キューが空でも即座に空の応答が返る――これがショートポーリング、既定の挙動です。空振りでも API 呼び出しは課金されるので、メッセージがまばらなキューでは空振りの料金が本体を上回ることすらあります。

待ち時間（ReceiveMessageWaitTimeSeconds）を1秒以上、最大20秒に設定すると、メッセージが到着するまで接続を保持します。これがロングポーリングです。効果は2つ。空振りの API 呼び出しが減ってコストが下がり、メッセージ到着から受信までの遅延も小さくなります。設問で「SQS のコストを下げたい」「空のレスポンスが多い」と来たら、ほぼ確実にロングポーリングです。

遅延キュー、メッセージタイマー、保持期間

可視性タイムアウトと遅延キューも混同されます。遅延キューは「入れてから見えるようになるまで」、可視性タイムアウトは「一度見せてから再び見えるようになるまで」です。配信前か配信後かで取り違えません。保持期間のほうは「メンテナンス中もメッセージを失いたくない」という形で問われ、既定4日では足りなければ最大14日まで延ばします。

大きなメッセージの扱い

メッセージ本文の上限は 1 MiB（1,048,576バイト）で、長く基準だった 256 KB から引き上げられました。問われ方は、上限を超えるペイロードをどう運ぶか、という形です。答えは常に同じです。

  • 実体を S3 に置き、キューには参照（バケット名とキー）だけを流す。SQS Extended Client Library がこの置き換えを自動でやります（最大2 GB）。
  • 「分割して複数に分けて送る」は、順序と再結合の責任がアプリ側に来るのでほぼ不正解です。
  • 「FIFO にすれば大きなメッセージを送れる」は誤りです。サイズ上限はキューの種類と関係ありません。

キューの深さでスケールさせる

SQS で最も出題されるパターンです。キューに溜まった件数をメトリクスにして、コンシューマ側の Auto Scaling グループを伸縮させます。

  • 使うメトリクスは ApproximateNumberOfMessagesVisible（処理待ちの件数）。これが増えている＝処理が追いついていない、というサインです。
  • より精密にやるなら、インスタンス1台あたりのバックログ（件数 ÷ 実行中インスタンス数）をカスタムメトリクスにしてターゲット追跡します。件数そのものは台数に比例しないため、そのまま使うと振動しやすいからです。
  • スパイクが読めないなら、コンシューマを Lambda にするのも手です。SQS をイベントソースにすれば同時実行数が自動で追随します。
この構成が正解になる設問の型

「ピーク時の処理要求が平常時の10倍になる」「処理は多少遅れてもよいが、失われてはいけない」「コストを最小化したい」。この3つが揃っていたら、答えは「SQS + Auto Scaling するコンシューマ」です。さらに「コンシューマはいつ中断されてもよい」と書いてあれば、スポットインスタンスを組み合わせる選択肢が正解になります。

SQS でできないこと

SQS は1つのメッセージを複数のコンシューマに配れません。「同じイベントを在庫と請求と分析の3系統に届けたい」なら、SQS を3本並べるだけでは足りず、前段に SNS か EventBridge が必要です。次の節がその話です。

04

SNS ―― 同じ知らせを複数に配る

SQS がプル型の1対1なら、SNS はプッシュ型の1対多です。トピックに1回発行するだけで、購読者全員にコピーが届きます。

パブリッシュ／サブスクライブという形

登場人物は3つだけです。トピック（宛先の器）、パブリッシャー、サブスクライバー。パブリッシャーはサブスクライバーが誰かを知りません。1つ増やしても発行側のコードは一行も変わらない――これが疎結合の「抽象化」そのものです。

サブスクライバーになれる先は次のとおりです。どれが選べるかは設問でそのまま問われます。

  • SQS キュー――最も重要。ファンアウト構成の中核です。
  • Lambda 関数――イベント駆動でコードを動かす。
  • HTTP / HTTPS エンドポイント――外部のWebhookなど。
  • Eメール、SMS、モバイルプッシュ通知――人への通知。運用アラートの定番。
  • Amazon Data Firehose――S3 や OpenSearch へ流し込んで保管・分析する。

ファンアウト ―― SNS と SQS を組み合わせる

SNS 単体には弱点があります。プッシュ型なので、届けた瞬間に受け手が落ちているとそのメッセージは失われる可能性があります。リトライはしますが永続的なバッファではありません。そこで SNS の下に SQS を並べます。

これが「SNS + SQS ファンアウト」、SAA 最頻出のパターンの一つです。手がかりは「同じデータを複数のシステムが必要としている」「将来、処理を追加する予定がある」「一部のコンシューマが停止してもデータを失いたくない」。どれかが出たら、単体ではなく組み合わせを選びます。

最頻出の引っかけ

「複数のシステムに同じメッセージを届けたい」という設問で、SQS を3本並べて、アプリから3回送るという選択肢が用意されます。動きはしますが、送り手が受け手を知ってしまっているので疎結合になっていません。宛先が増えるたびに送り手を変更することになります。SNS を前段に置くのが正解です。

フィルタポリシー

サブスクリプションごとにフィルタポリシーを設定すると、条件に合うメッセージだけが配信されます。判定対象はメッセージ属性（既定）か本文（JSON）を選べます。

「特定の種類のイベントだけを受け取りたい」「コンシューマ側で不要なメッセージを捨てているのを無くしたい」と書かれていたら、答えはフィルタポリシーです。トピックを種類ごとに分ける選択肢も用意されますが、管理が煩雑になるため1トピック＋フィルタのほうが評価されます。

サブスクリプションのフィルタポリシー（優先度 high の注文だけ受け取る）
{
  "eventType": ["order.created"],
  "priority": ["high"],
  "amount": [{ "numeric": [">=", 10000] }]
}  // 属性がすべて一致したサブスクライバーにだけ配信される

SNS FIFO と、その他の押さえどころ

  • SNS FIFO トピックは順序保証と重複排除を提供しますが、購読できるのは SQS FIFO キューだけです。Lambda やメールを直接購読させることはできません。「順序を保ったままファンアウトしたい」という設問では、SNS FIFO + SQS FIFO の組み合わせになります。
  • サブスクリプション単位で再試行ポリシーとDLQを設定できます。宛先が落ちていた場合の受け皿です。
  • サイズ上限を超えるペイロードは、SQS と同じく S3 に置いて参照を渡します。
  • VPC 内から NAT を通さずに発行したい場合は VPC エンドポイント（PrivateLink）を使います。
05

EventBridge ―― AWS の出来事に反応する

SNS が「自分のアプリが出した知らせを配る」ものなら、EventBridge は「AWS や SaaS で起きたことを受け止めて振り分ける」ものです。出自が違えば得意なことも違います。

イベントバスとルール

構造は3層です。イベントバスに流れ込み、ルールがイベントパターンで判定し、合致したものをターゲットに送ります。バスは3種類です。

  • デフォルトバス――AWS サービスのイベントが自動で流れてきます。EC2 の状態変化、S3 のオブジェクト作成、Health のイベントなど。
  • カスタムバス――自前のアプリが発行するイベント用。
  • パートナーイベントバス――Datadog や Zendesk といった SaaS からのイベントを直接受けます。「SaaS からのイベントを AWS 側で処理したい」ならこれです。

ルールの肝はイベントパターンです。JSON の構造にマッチさせるので本文の中身で細かく絞り込めます。SNS のフィルタポリシーより表現力があると理解してください。

EC2 が停止したときだけ動かすルール（イベントパターン）
{
  "source": ["aws.ec2"],
  "detail-type": ["EC2 Instance State-change Notification"],
  "detail": {
    "state": ["stopped", "terminated"]
  }
}  // ターゲットに Lambda / SNS / SQS / Step Functions などを指定

スケジュール実行

cron 式と rate 式によるスケジュール機能があります。「毎晩2時にバッチを動かしたい」「5分ごとにチェックしたい」の答えは、EC2 上の cron ではなく EventBridge です。サーバーが要らず、単一障害点になりません。専用機能の EventBridge Scheduler は、大量のスケジュールの一元管理、1回限りの実行、タイムゾーン指定に対応します。

判断軸

迷ったときの順番です。①「宛先は1つか、複数か」――1つなら SQS。②「発生源は AWS サービスか、自分のアプリか」――AWS サービスやスケジュールなら EventBridge。③「人に届けるのか、システムにか」――人なら SNS。この3問でほぼ振り分けられます。

06

Step Functions と API Gateway

キューとイベントバスが「流す」仕組みなら、この2つは「束ねる」仕組みです。前者は処理の順番を、後者は入口を束ねます。

Step Functions ―― 手順をコードの外に出す

Lambda を5つ順番に呼ぶ処理を、1つ目が2つ目を呼ぶ形で素直に実装すると、どこまで進んだか分からず、リトライを各関数に書くことになり、手順の変更はコードの変更になります。Step Functions はこの手順をステートマシンとしてコードの外に出します。各ステップの成否、リトライ、分岐、並列実行、待機を定義で表現し、実行の様子はコンソールで可視化されます。手がかりは明確です。「複数ステップの処理をオーケストレーションしたい」「エラー処理とリトライを一元管理したい」「進行状況を可視化したい」「人の承認を挟みたい」。どれかが出たら Step Functions です。

よくある誤解

「Lambda の15分制限を超えたいので Step Functions」――半分だけ正解です。全体は1年走らせられますが、個々の Lambda の15分制限は消えません。15分以内のステップに分割できる場合に有効、という条件付きで、1ステップ自体が長いなら Fargate や Batch が適切です。

  • Cognito オーソライザー――モバイル・Web アプリの一般利用者。ユーザープールが発行したトークンを検証します。「アプリの利用者を認証してAPIを守りたい」の定番解です。

API キーは認証ではない

API キーは使用量プランと結びつけて流量を測るための識別子であって、認証・認可の仕組みではありません。「APIを安全に保護したい」で API キーを選ぶと外します。「顧客ごとに1日あたりのリクエスト数を制限したい」なら正解です。目的が計量か保護かで分けてください。

スロットリング、キャッシュ、ステージ

スロットリングはバックエンドを守る仕組みです。既定ではアカウント単位・リージョン単位で毎秒10,000リクエスト、バースト5,000リクエスト（一部リージョンは低め）で、引き上げ申請ができます。加えてメソッド・ステージ・使用量プラン単位でも上限を設定でき、超過には 429 Too Many Requests が返ります。「特定の利用者が大量に呼んで他に影響が出ている」なら、使用量プランによるスロットリングです。

キャッシュはステージ単位で有効化します。TTL の既定は300秒、最大3600秒、0で無効。「同じ問い合わせが繰り返される読み取り中心のAPIで、バックエンドの負荷を下げたい」ならこれです。時間課金なので、コスト最小化が主眼の設問では選ばれないこともあります。

ステージは dev / prod のようなデプロイ単位で、ステージ変数により同じ定義で接続先を切り替えられます。カナリアリリースを設定すれば、新しいデプロイに一定割合のトラフィックだけを流せます。「新バージョンを段階的に公開したい」の答えです。

07

CloudWatch と CloudTrail

後半の主題はこの2つの違いです。名前が似ていてどちらもログを扱いますが、答える問いが違います。CloudWatch は「どう動いているか」、CloudTrail は「誰が何をしたか」。ここを外さなければ後半の大半は落とせません。

CloudWatch メトリクス

メトリクスは時系列の数値で、名前空間（AWS/EC2 など）とディメンションで識別されます。押さえるべきは標準メトリクスとカスタムメトリクスの境界です。

  • 標準メトリクスは AWS がハイパーバイザー側から取れるもの。EC2 なら CPU使用率、ネットワーク入出力、ディスクの読み書き、ステータスチェックで、設定不要・無料です。
  • エージェントが必要なものは、OS の内側を見ないと分からない値です。代表がメモリ使用率とディスク（ファイルシステム）使用率。スワップ、プロセス数、OS のログファイルも同様です。「メモリ使用率で Auto Scaling したい」「ディスクが埋まる前に気づきたい」なら、答えは必ず CloudWatch エージェントの導入を含みます。
  • EC2 の基本モニタリングは5分間隔（無料）、詳細モニタリングは1分間隔（有料）。「もっと早くスケールアウトを検知したい」なら詳細モニタリングです。高解像度メトリクスなら1秒単位まで記録でき、アラームも10秒・30秒周期にできます。

保持期間は、1分未満のデータが3時間、1分データが15日、5分データが63日、1時間データが455日（約15か月）。短い粒度から順に集約されていきます。「1年以上前と比較したい」なら、S3 への書き出しが必要という話になります。

CloudWatch Logs とアラーム

ログはロググループとログストリームの2階層です。保持期間はロググループ単位で、既定は「失効しない」――放っておくと課金が増え続けます。コスト最適化の設問では、保持期間の設定と、古いログの S3 へのエクスポートが答えです。

  • メトリクスフィルター――ログ中の特定のパターン（ERROR の行数、5xx の数など）を数えてメトリクスに変換します。「ログに特定の文字列が出たら通知したい」の答えは、これとアラームの組み合わせです。ログそのものにアラームは張れず、一度メトリクスにするのがポイントです。
  • サブスクリプションフィルター――ログをほぼリアルタイムで Lambda、Data Firehose、OpenSearch などに流します。別の場所で加工・分析したい場合に使います。
  • Logs Insights――専用のクエリ言語でログを対話的に検索・集計します。事前のインデックス作成は不要で、スキャン量で課金されます。「障害の原因を後から調査したい」「特定のリクエストIDの流れを追いたい」で出てきます。

アラームの状態は OK / ALARM / INSUFFICIENT_DATA の3つ。評価期間と、そのうち何回閾値を超えたらアラームにするか（M out of N）、欠落データをどう扱うかを設定します。アクションは SNS への通知、Auto Scaling ポリシーの実行、EC2 のアクション（停止・終了・再起動・復旧）です。

複合アラームは複数のアラームを AND / OR / NOT で組み合わせます。目的はノイズの削減で、「CPU が高い」だけでなく「CPU が高い AND レスポンスタイムが悪化」なら本当に見るべき事象です。「誤検知が多い」「通知が多すぎる」と書いてあったら複合アラームと覚えてください。

CloudTrail

CloudTrail はAPI 呼び出しの記録です。誰が、いつ、どこから、どのリソースに何をしたか。コンソール操作も CLI も SDK も、内部的にはすべて API 呼び出しなので記録されます。

  • イベント履歴は、追加設定なしで直近90日ぶんの管理イベントを閲覧できる機能です。無料ですが、90日を超えると消え、データイベントは含まれません。長く残したい、複数リージョンをまとめたい、データイベントも取りたいなら、証跡（Trail）を作って S3 に出力します。S3 に置けば保持は無期限です。
  • 管理イベントはコントロールプレーンの操作（インスタンスの起動、バケットの作成、ポリシーの変更など）。既定で記録され、証跡1本目の管理イベントは無料です。
  • データイベントはデータプレーンの操作（S3 のオブジェクトの GET / PUT / DELETE、Lambda の関数実行など）。既定では記録されず、明示的に有効化する必要があり、有料です。量が桁違いに多いためです。
  • 組織証跡を管理アカウントで作ると、全アカウントのイベントを1つのバケットに集約でき、メンバーアカウント側からは削除できません。「全アカウントの操作ログを一元管理したい」の答えです。
  • ログファイル整合性検証を有効にすると、改ざんされていないことを後から検証できます。監査要件のある設問で登場します。
最頻出の引っかけ

「S3 バケットのオブジェクトを誰が削除したかを追跡したい」――CloudTrail を有効にするだけでは足りません。オブジェクトレベルの操作はデータイベントなので、S3 のデータイベントを明示的に有効化する必要があります。「バケットを誰が削除したか」なら管理イベントなので既定で記録されます。バケットへの操作か、オブジェクトへの操作かで答えが変わります。

08

構成管理と運用の道具

残りは記録と自動化を担うサービス群です。機能を網羅する必要はありません。「どれが答えになる要件か」だけを押さえます。

AWS Config ―― 今どうなっているか

Config はリソースの構成を継続的に記録し、あるべき姿から外れていないかを評価します。CloudTrail が「操作の記録」なら Config は「状態の記録」です。

CloudTrailAWS Config
記録するもの誰がどの API を呼んだかリソースの設定内容が時系列でどう変わったか
答える問い「このセキュリティグループを開けたのは誰か」「このセキュリティグループは今どうなっていて、いつからこうなのか」
評価機能なしルールで準拠・非準拠を判定し、自動修復もできる

Config ルールは AWS 管理とカスタムがあり、複数をまとめたコンフォーマンスパックで組織に一括適用できます。非準拠を検知したら Systems Manager Automation で自動修復させるのが定番です。「準拠していない設定を検出したい」「設定変更の履歴を追いたい」なら Config、「操作した人を特定したい」なら CloudTrail です。

Systems Manager

  • Session Manager――踏み台も SSH キーも要らず、インバウンドポートを一切開けずにシェルに入れます。接続は SSM エージェントからのアウトバウンドのみで、操作は CloudTrail に記録され、セッションログを S3 や CloudWatch Logs に残せます。「踏み台をなくしたい」「22番ポートを閉じたい」「誰が入ったか記録したい」の答えです。プライベートサブネットからは VPC エンドポイント経由にします。
  • Patch Manager――パッチ適用を、パッチベースラインとメンテナンスウィンドウに沿って自動化します。「多数のインスタンスに定期的にパッチを当てたい」の答えです。
  • Parameter Store――設定値と機密情報の保管庫。標準パラメータは1件4 KB・10,000件まで無料、アドバンストは8 KB・100,000件で有料、有効期限などのポリシーが使えます。Secrets Manager との違いは自動ローテーションの有無で、「RDS の認証情報を定期的に自動ローテーションしたい」なら Secrets Manager、「単なる設定値をコストをかけずに置きたい」なら Parameter Store です。

CloudFormation

インフラをテンプレートで定義し、スタックとして作成・更新・削除します。問われるのは4つです。

  • 変更セット――適用前に、何が作成・変更・置換・削除されるかを確認します。「本番の更新で意図しない再作成を避けたい」の答えで、置換が起きるリソースをここで見つけます。
  • StackSets――1つのテンプレートを複数アカウント・複数リージョンに一括展開します。「組織のすべてのアカウントに同じ設定を配りたい」の答えです。
  • ドリフト検出――テンプレートの定義と実際のリソースのずれ（手作業の変更など）を検出します。「コンソールで直接変更されていないか確認したい」の答えです。
  • DeletionPolicy――スタックを削除してもデータベースやバケットを残す（Retain）、スナップショットを取る（Snapshot）といった指定ができます。

Trusted Advisor と Health Dashboard

Trusted Advisorはアカウントをベストプラクティスに照らして点検します。カテゴリはコスト最適化、パフォーマンス、セキュリティ、フォールトトレランス、サービスクォータ、運用上の優秀性の6つ。出題の要は、すべてのチェックを使えるのがビジネスサポート以上の契約だという点です。基本・開発者サポートではサービスクォータと一部のチェックに限られます。

AWS Health Dashboardは2面あります。サービス正常性は AWS 全体の障害情報、アカウント固有の正常性は自分のリソースに影響する事象（メンテナンス予定、廃止予定のインスタンスなど）です。後者は EventBridge に流せるので、「AWS 側のメンテナンス予定を自動で受け取って通知したい」の答えは、Health のイベントを EventBridge で捕まえて SNS に送る構成です。Organizations と組み合わせれば全アカウントぶんを集約できます。

確認問題

先に自分で答えを決めてから開いてください。当てずっぽうで開くと、この5分が無駄になります。

Q1注文処理システムで、セール開始時に通常の20倍のリクエストが集中し、在庫更新サービスがタイムアウトして注文の一部が失われている。注文を1件も失わずに処理するために最も適切な構成はどれか。
  • A. 在庫更新サービスの前に ALB を配置し、複数台に分散させる
  • B. 注文サービスと在庫更新サービスの間に SQS キューを挟み、キューの深さに基づいてコンシューマを Auto Scaling させる
  • C. 在庫更新サービスのインスタンスタイプをピークに合わせて常時大きくする
  • D. 注文サービスのリトライ回数を増やし、指数バックオフを実装する

正解: B

キューを挟めば流入と処理の速度差を時間で吸収できます。注文サービスは投入時点で成功を返せ、在庫更新は自分のペースで処理します。キューの深さでコンシューマを伸縮させれば、滞留も短時間で解消します。

判断軸: A は同期のままなのでバッファになりません。C はピークに合わせた常時プロビジョニングでコストが無駄。D は根本解決にならず、リトライ中も送り手のリソースを消費します。「失われてはいけない」と書かれていたら、永続化される置き場、すなわちキューを探します。

Q2SQS キューのメッセージを EC2 上のワーカーが処理している。1件あたりの処理に約3分かかる。運用開始後、同じ注文が2回処理される事象が頻発している。原因として最も可能性が高いのはどれか。
  • A. 標準キューを使っているため、重複配信が避けられない
  • B. 可視性タイムアウトが既定の30秒のままになっている
  • C. ロングポーリングが有効になっていない
  • D. メッセージ保持期間が短すぎる

正解: B

処理に3分かかるのに可視性タイムアウトが30秒だと、1台目の処理中にメッセージが再び見えるようになり、2台目が同じものを取得します。可視性タイムアウトを処理時間より長くするか、ChangeMessageVisibility で延長します。

判断軸: A も標準キューの性質としては正しいのですが、「頻発」と処理時間の情報が揃っているので設計ミスを問う設問だと読みます。処理時間が具体的に書かれていたら、可視性タイムアウトとの比較を疑ってください。C はコストと遅延、D は消失の話で、二重処理とは無関係です。

Q3あるアプリケーションが注文イベントを発行している。現在は在庫システムと請求システムがこれを受け取っているが、来期には分析基盤も追加する予定である。また、いずれかのシステムがメンテナンスで停止していてもイベントを失いたくない。最も適した構成はどれか。
  • A. SNS トピックを作り、各システムを HTTPS エンドポイントとして直接サブスクライブさせる
  • B. SQS キューを2本作り、アプリケーションが両方に送信する
  • C. SNS トピックを作り、システムごとに SQS キューを用意してトピックにサブスクライブさせる
  • D. Kinesis Data Streams にイベントを流し、各システムがコンシューマとして読み取る

正解: C

1回発行すればコピーが各キューに入り、キューがバッファになるので停止中でもイベントは残ります。分析基盤の追加もキューを作ってサブスクライブさせるだけで、発行側は変更不要です。

判断軸: A はキューがないので停止中の配信を失う恐れがあります。B は宛先が増えるたびに送信側を改修することになり疎結合ではありません。D も要件は満たせますが、この規模ではオーバースペックです。「将来コンシューマを追加する」「一部が停止しても失わない」が並んだら SNS + SQS です。

Q4セキュリティ監査で「S3 バケット内のオブジェクトを誰がいつ削除したかを、過去1年分たどれるようにせよ」と指摘された。適切な対応はどれか。
  • A. CloudTrail のイベント履歴をコンソールで確認する
  • B. CloudTrail で証跡を作成し、S3 のデータイベントを有効にして、ログを S3 バケットに保存する
  • C. AWS Config で S3 バケットの構成変更を記録する
  • D. CloudWatch でバケットのオブジェクト数メトリクスにアラームを設定する

正解: B

オブジェクトへの操作はデータイベントで、既定では記録されません。明示的に有効化して S3 に出力すれば、保持期間の制約なく1年分を残せます。

判断軸: A のイベント履歴は90日ぶんかつ管理イベントのみなので、両方の要件を満たしません。C はバケットの設定変更の記録で、オブジェクト単位の操作は追えません。D は増減が分かるだけで、誰がやったかは分かりません。「オブジェクト」か「バケット」かで、必要な設定が変わります。

Q5EC2 上の Java アプリケーションがメモリ不足で不定期に停止する。事前に検知して通知したい。最小の運用負荷で実現する方法はどれか。
  • A. CloudWatch の標準メトリクス MemoryUtilization にアラームを設定する
  • B. EC2 の詳細モニタリングを有効にし、1分間隔でメモリ使用率を取得する
  • C. CloudWatch エージェントを導入してメモリ使用率をカスタムメトリクスとして発行し、アラームから SNS に通知する
  • D. アプリケーションのログを CloudWatch Logs に送り、Logs Insights で定期的に検索する

正解: C

メモリ使用率はハイパーバイザー側から見えないため、標準メトリクスには存在しません。CloudWatch エージェントを入れて OS の内側から取得し、カスタムメトリクスとして発行します。

判断軸: A の MemoryUtilization という標準メトリクスは存在しません。この「あるように見えて存在しないメトリクス」は頻出の誤答です。B の詳細モニタリングは既存メトリクスの粒度を5分から1分に上げるだけで、項目は増えません。D は事後の調査であって事前の検知になっていません。メモリとディスク使用率が出たらエージェント、と即答してください。
