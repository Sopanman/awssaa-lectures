場面1 ―― 「セールが始まった瞬間、注文の一部が消えた。在庫サービスが落ちると受付まで止まる」

この場面で初めて出る言葉
同期／非同期
相手の返事を待ってから次へ進む呼び方が同期。頼むだけ頼んで返事を待たない呼び方が非同期
メッセージ
サービスからサービスへ渡す、仕事1件分のデータ（例：「注文 123 の在庫を引き当てて」）
キュー
メッセージを溜めておく待ち行列。入れる側と取り出す側が、別々の速さで動ける
密結合／疎結合
相手が止まると自分も止まる関係が密結合。間に何かを挟んで、互いの都合に縛られない関係が疎結合（英語の設問では decouple）
バッファ
届く速さと処理する速さの差を吸収する「ため」のこと。キューがこの役をする
カスケード障害
1か所の障害が、それを呼んでいる側へ次々に広がっていくこと
5xx エラー
「サーバー側の都合で処理できなかった」ことを表す HTTP の返事（500 番台）

注文サービスが在庫サービスを HTTP で直接呼んでいる、という構成です。普段は問題ありません。困るのは、普段と違うことが起きたときです。まず、直接呼ぶ形と、間にキューを挟む形を並べます。

直接呼ぶ形には、困りごとが4つあります。

  1. 送り手が、受け手の処理能力に縛られる。セール開始の瞬間に毎秒 3,000 件の注文が来ても、在庫サービスが毎秒 500 件しか捌けないなら、残りはタイムアウトかエラーになります。受け手の限界が、そのまま全体の限界です。
  2. 障害が広がる（カスケード障害）。在庫サービスが落ちると、注文サービスは返事待ちで埋まり、やがて受付そのものが止まります。「在庫の更新が遅れるだけ」で済んだはずの障害が、全体の障害に育ちます。
  3. 増やす単位が揃わない。注文の受付は軽く、在庫の更新は重い。直接つながっていると、重い側に合わせて全体を大きくするしかありません。
  4. 相手を知ってしまう。送り手が受け手の宛先を設定に持つので、受け手を1つ増やすたびに、送り手のコードと設定が変わります。

キューを挟むと、なぜ注文が消えなくなるのか

キューは、届く速さと処理する速さの差を時間で吸収します。下の図で、同じ山（毎秒 3,000 件）に対して何が起きるかを見てください。

キューを1本挟むと、効き方は3つあります。上の4つの困りごとは、この3つで消えます。

  • バッファ：山の分は消えずにキューに積まれ、あとから処理される（困りごと1・3）
  • 隔離：受け手の障害が送り手に届かない。壊れる範囲を区切るのが、回復性の設計の基本（困りごと2）
  • 抽象化：送り手は、受け手が誰で何台いるかを知らない。受け手を増やしても送り手は変わらない（困りごと4）

この場面の答え：注文サービスと在庫サービスの間に SQS のキューを挟みます。キューは SQS の画面で「キューを作成」するだけで用意でき、注文サービスは在庫サービスを呼ぶ代わりに、キューにメッセージを送ります。

ロードバランサーを挟んでも、バッファにはならない

「疎結合にするために ELB（EC2 講義の場面4）を挟む」という選択肢がよく出ます。ELB は宛先を隠してくれますが、返事を待つ呼び方（同期）のままなので、溜めておく場所がありません。受け手が捌けなければ 5xx エラーを返します。ELB は「複数の台に分けたい」とき、キューは「時間で吸収したい」ときです。

非同期にしても、処理は速くならない

キューを挟むと、送り手から見た応答は速くなります（入れたら完了なので）。しかし、注文が入ってから在庫の更新が終わるまでの全体の時間は、むしろ伸びます。設問が「利用者への応答を速くしたい」ならキューは有効、「処理そのものを速く終わらせたい」なら、並列に動かす・台数を増やす話です。

試験ではこう出る

「疎結合にしたい（decouple）」「コンポーネント間の依存を減らす」「ピーク時にリクエストが失われる」「処理が追いつかない」「下流の障害が上流に影響しないように」→ キュー（SQS）を挟む。逆に、こうした言葉がないのにキューを挟む選択肢は、作り込みすぎとして不正解になることがある。

場面2 ―― 「同じ注文が2回処理される」「1件の壊れたデータで、キュー全体が進まない」

プロデューサー／コンシューマー
キューにメッセージを送る側／キューからメッセージを取り出して処理する側（EC2 でも Lambda でもよい）
プル
受け手が自分から取りに行くこと。逆に、送る側が押し込むことをプッシュと呼ぶ（→ 場面4）
ポーリング
コンシューマーがキューに「メッセージはありますか」と聞きに行くこと（API の名前は ReceiveMessage）
可視性タイムアウト
取り出されたメッセージを、他のコンシューマーから見えなくしておく時間（EC2 講義の場面7で既出）
デッドレターキューDLQ：Dead-Letter Queue
何度処理しても失敗するメッセージを移しておく、別のキュー

「この回数だけ受信されても消されなかったら DLQ へ移す」という回数
リドライブ
DLQ に移したメッセージを、元のキューへ戻す機能

2つの依頼はどちらも、SQS のキューの中でメッセージがどう扱われるかを知っていれば解けます。先に、メッセージ1件に何が起きるかを見ます。

大事なのは ③ と ④ です。取り出しても、メッセージはキューから消えません。しばらく他から見えなくなるだけで、処理した側が「消して」と言って（DeleteMessage）初めて消えます。消されないまま時間が過ぎると、メッセージはまた見えるようになり、別のコンシューマーが受け取ります。処理の途中でコンシューマーが落ちても仕事がなくならないのは、この仕組みのおかげです。

同じ注文が2回処理される ―― 可視性タイムアウト

「見えなくしておく時間」が可視性タイムアウトです。既定は 30秒、0秒から最大12時間まで設定できます。これが処理時間より短いと、次のことが起きます。

  • この依頼の答え：可視性タイムアウトを、1件の処理時間より少し長くする
  • どこで設定するか：SQS の画面でキューを開き、「編集」の「可視性タイムアウト」に秒数を入れる（キューごとの設定）。処理が長引きそうなときは、コンシューマーが処理の途中で ChangeMessageVisibility という API を呼んで、そのメッセージだけ延長することもできる
  • 長すぎても困る：コンシューマーが処理中に落ちると、可視性タイムアウトが切れるまで、そのメッセージには誰も触れない。だから「処理時間より少し長く」
  • Lambda がコンシューマーのとき：関数のタイムアウトの6倍程度にするのが AWS の推奨（EC2 講義の場面7）
的外れな選択肢

「メッセージが二重に処理される」に対して、「Lambda の関数のタイムアウトを延ばす」「コンシューマーを増やす」は的外れ。原因は可視性タイムアウトが処理時間より短いことなので、直すのはキューの可視性タイムアウト。

壊れた1件でキュー全体が進まない ―― デッドレターキュー

中身が壊れていて何度処理しても失敗するメッセージ（毒メッセージと呼ばれます）は、取り出されては失敗し、可視性タイムアウトが切れてキューに戻る、を繰り返します。

  • この依頼の答え：キューにデッドレターキュー（DLQ）を付ける。「1件の不正なデータでキュー全体が滞留している」と来たら DLQ
  • どこで設定するか：先に DLQ 用のキューをもう1本作る。次に元のキューの「編集」の「デッドレターキュー」で、移す先のキューと最大受信数を指定する
  • DLQ は元のキューと同じ種類にする：FIFO キュー（→ 場面3）の DLQ は FIFO キュー
  • DLQ の保持期間は長めに：メッセージの経過時間は元のキューに入った時点から数える。DLQ に移ったときにはすでに何日か経っているので、DLQ の保持期間が短いと調べる前に消える

空のキューを見に行くだけでお金がかかる ―― ロングポーリング

コンシューマーは、キューを自分から見に行きます（ポーリング）。キューが空のときに、すぐ帰るか、待つか。これで料金が変わります。

どこで設定するか：キューの「編集」の「メッセージ受信待機時間」（設定名は ReceiveMessageWaitTimeSeconds）に 1〜20秒を入れると、ロングポーリングになります。既定は 0秒（ショートポーリング）です。メッセージがまばらなキューでは、空振りの料金が本体を上回ることすらあります。設問で「SQS のコストを下げたい」「空のレスポンスが多い」と来たら、ほぼロングポーリングです。

似た名前の3つの時間

キューには時間の設定が3つあり、よく取り違えます。1件のメッセージの一生に並べると区別がつきます。

設定効く範囲値使いどころ
配信遅延（遅延キュー）そのキューに入るすべての新しいメッセージ0〜15分（既定 0）下流の準備が整うまで、一律で待たせたい
メッセージタイマーメッセージ1件ごと（送るときに指定）0〜15分特定のメッセージだけ遅らせたい。キューの配信遅延より優先される
可視性タイムアウト受信されたメッセージ0秒〜12時間（既定 30秒）処理中の二重処理を防ぐ
メッセージ保持期間キューの中のメッセージの寿命60秒〜14日（既定 4日）コンシューマーが止まっても失いたくないなら長くする

保持期間は「メンテナンスでコンシューマーを数日止める。その間のメッセージを失いたくない」という形で問われます。既定の4日で足りなければ、最大14日まで延ばします。

試験ではこう出る

「同じメッセージが二重に処理される」＋処理時間が書いてある → 可視性タイムアウトを処理時間より長く。「失敗するメッセージが延々とリトライされる」「キューが滞留」→ デッドレターキュー。「空のレスポンスが多い」「SQS のコストを下げたい」→ ロングポーリング（最大20秒）。「入れてからしばらく処理させたくない」→ 配信遅延。

SQS の既定のキュー。速さ優先で、順番と「1回きり」は保証しない
FIFO キューFirst-In-First-Out（先入れ先出し）
順番を守り、同じメッセージを2回処理させないキュー
メッセージグループ IDMessageGroupId
FIFO キューに送るメッセージに付ける札。同じ札のメッセージどうしの順番が守られる

同じメッセージが2回送られてきても、1回分しか受け付けないこと。メッセージに付ける ID で見分ける

ペイロード
メッセージで運ぶデータの本体

SQS を選んだあとに、必ず次に問われるのがキューの種類です。種類はキューを作るときに選び、あとから変えることはできません。

標準キューFIFO キュー
順序ベストエフォート。基本は送った順だが保証はないメッセージグループの中で厳密に保証
配信少なくとも1回。重複しうる正確に1回の処理。重複を見分ける時間の幅は5分
スループットほぼ無制限1つの API アクションあたり毎秒 300件、バッチ（10件単位）なら毎秒 3,000件。高スループットモードでは、これがパーティションごとの値になる
キュー名制約なし末尾に .fifo が必須
選ぶ場面非同期処理の大半。画像の変換、通知、ログの取り込み金融取引、在庫の増減、適用する順番に意味がある指示
  • この依頼の答え：FIFO キューにして、商品 ID や顧客 ID をメッセージグループ ID にする。既定は標準で、FIFO は業務として順番か重複排除が必要なときだけ選ぶ
  • 並列にできる数は、メッセージグループの数で決まる。グループ ID を1種類にすると、順番は完全に守られるが、同時に処理できるのは1件ずつになる
  • 重複排除のやり方は2つ：送るときに MessageDeduplicationId を自分で付けるか、キューの設定で ContentBasedDeduplication（本文から自動で ID を作る）を有効にする。見分ける時間の幅はどちらも5分で、それを過ぎると同じ内容でも別のメッセージとして通る

大きなデータを流したい

メッセージ1件の本文の上限は 1MiB（1,048,576 バイト）です。長く 256KB が基準でしたが、引き上げられました。設問は「上限を超えるペイロードをどう運ぶか」という形で出て、答えはいつも同じです。

  • 「分割して複数のメッセージに分けて送る」は、順番と組み立て直しの責任がアプリ側に来るので、ほぼ不正解
  • 「FIFO にすれば大きなメッセージを送れる」は誤り。大きさの上限はキューの種類と関係がない

溜まった量に合わせて台数を増やす

SQS でいちばんよく出る構成です。キューに溜まった件数を見て、コンシューマーの Auto Scaling グループ（ASG、EC2 講義の場面5・6）の台数を変えます。

  • どこで設定するか：コンシューマー側の ASG に、スケーリングポリシーを付ける（EC2 の画面で ASG を開き、「自動スケーリング」のタブ）。見る数字に SQS のメトリクスを選ぶ
  • より正確にやるなら：1台あたりのバックログ（処理待ちの件数 ÷ 動いている台数）を自分で計算してカスタムメトリクスにし、ターゲット追跡（EC2 講義の場面6）で一定に保つ。件数そのものは台数に比例しないので、そのまま使うと増やしすぎと減らしすぎを繰り返しやすい
  • 山が読めないなら：コンシューマーを Lambda にする手もある。SQS をきっかけにすれば、同時に動く数が自動でついてくる
この構成が正解になる設問の型

「ピーク時の処理要求が平常時の10倍になる」「処理は多少遅れてもよいが、失われてはいけない」「コストを最小にしたい」。この3つが揃ったら、答えは「SQS ＋ Auto Scaling するコンシューマー」。さらに「コンシューマーはいつ中断されてもよい」と書いてあれば、スポットインスタンス（EC2 講義の場面2・3）を組み合わせる選択肢が正解になる。

SQS でできないこと

SQS は、1つのメッセージを複数のコンシューマーに配れません（取り出した1つが処理して消すので）。「同じ知らせを在庫と請求と分析の3系統に届けたい」なら、キューを3本並べるだけでは足りず、手前に SNS か EventBridge が要ります。次の場面がその話です。

試験ではこう出る

「順序が業務上重要」「重複して処理されてはならない」→ SQS FIFO（並列にしたければメッセージグループ ID を分ける）。「上限を超える大きなメッセージ」→ S3 に置いて参照を送る。「キューに溜まった量で処理能力を増やしたい」→ キューの深さをメトリクスにして Auto Scaling。

場面3の最後で見たとおり、SQS のキューは1件を1つの受け手にしか渡せません。複数に配るには、SNS を使います。まず SNS の形を見ます。

どこで設定するか：SNS の画面でトピックを作り、「サブスクリプションの作成」で、届け先の種類（プロトコル）と宛先を選びます。どれがサブスクライバーになれるかは、設問でそのまま問われます。

SNS だけでは、止まっている相手の分が失われる

SNS は溜めておく場所を持ちません。届けようとした瞬間に受け手が落ちていると、何度かやり直しはしますが、それでも届かなければその知らせは失われます。そこで、SNS の下に SQS のキューを並べます。

  • この場面の答え：SNS トピックを1つ作り、受け手ごとに SQS キューを用意して、トピックを購読させる（SNS ＋ SQS のファンアウト）。SAA で最もよく出る構成の1つ
  • 設定のしかた：キューを作り、SNS の「サブスクリプションの作成」でプロトコルに Amazon SQS、宛先にそのキューを選ぶ。キュー側では、アクセスポリシー（S3 のバケットポリシーと同じく、リソースに付ける許可）で「このトピックからの送信を許可」しておく
  • 手がかりの言葉：「同じデータを複数のシステムが必要としている」「将来、処理を追加する予定がある」「一部の受け手が止まっていてもデータを失いたくない」。どれかが出たら、単体ではなく組み合わせを選ぶ

受け手ごとに、欲しい知らせだけを届ける

どこで設定するか：サブスクリプションを開き、「サブスクリプションフィルターポリシー」に条件を JSON で書きます。判定の対象は、メッセージ属性（既定）か、メッセージの本文（JSON）のどちらかを選べます。

サブスクリプションのフィルタポリシー（優先度 high の注文だけ受け取る）
{
  "eventType": ["order.created"],
  "priority": ["high"],
  "amount": [{ "numeric": [">=", 10000] }]
}  // 属性がすべて一致したサブスクライバーにだけ配信される

「特定の種類の知らせだけを受け取りたい」「受け手の側で不要なメッセージを捨てているのをなくしたい」と書かれていたら、答えはフィルタポリシーです。トピックを種類ごとに分ける選択肢も用意されますが、管理するものが増えるので、1トピック＋フィルタのほうが評価されます。

そのほかの押さえどころ

  • SNS FIFO トピック：順番の保証と重複排除ができるトピック。ただし購読できるのは SQS FIFO キューだけで、Lambda やメールを直接購読させることはできない。「順番を保ったままファンアウトしたい」なら、SNS FIFO ＋ SQS FIFO
  • 届かなかったときの受け皿：サブスクリプションごとに、やり直しの方針（再試行ポリシー）とデッドレターキュー（場面2）を設定できる
  • 大きなデータ：SQS と同じく、S3 に置いて参照を渡す（場面3）
  • VPC の中から NAT を通さずに発行したい：SNS 用の VPC エンドポイント（インターフェース型、PrivateLink。VPC 講義の場面3）を使う
試験ではこう出る

「同じメッセージを複数のシステムに届けたい」「将来、受け手を追加する」「一部が停止しても失わない」→ SNS ＋ SQS のファンアウト。「アプリから複数のキューへ個別に送る」は、送り手が宛先を知ってしまうので不正解。「メール・SMS で人に知らせる」→ SNS。「特定の種類だけ受け取りたい」→ フィルタポリシー。

どこで設定するか：Step Functions の画面で「ステートマシンの作成」を選び、ステップを並べて、各ステップが呼ぶもの（Lambda など）、失敗したときのやり直し、分岐、並列、待機を定義します。実行するたびに、どのステップまで進んだかが画面に図で表示されます。種類（標準か Express か）は作るときに選び、あとから変えられません。

呼んでよい相手かを、どう確かめるか

  • IAM 認可：呼ぶ側が AWS の利用者やロール（IAM 講義）のとき。社内システム、他アカウント、SDK からの呼び出しに使う。リクエストに付けた署名（SigV4：AWS の API で使う署名の方式）を確かめる
  • Cognito オーソライザー：モバイルや Web のアプリの一般利用者。ユーザープールが発行したトークンを確かめる。「アプリの利用者を認証して API を守りたい」の定番
  • Lambda オーソライザー：独自の認証の仕組みや他社の認証基盤など、上の2つに収まらないとき。自分で書いた Lambda 関数が判定する。「既存の認証システムと連携したい」ならこれ。判定の結果はキャッシュできる

どこで設定するか：API Gateway の画面で API を開き、「オーソライザー」を作ってから、守りたいメソッド（API の1つ1つの口）に割り当てます。

API キーは認証ではない

API キーは、使用量プランと結び付けて流量を測るための識別子で、認証・認可の仕組みではありません。「API を安全に保護したい」で API キーを選ぶと外します。「顧客ごとに1日あたりのリクエスト数を制限したい」なら正解です。目的が計量か保護かで分けてください。

スロットリング・キャッシュ・ステージ

  • スロットリング：バックエンドを守る仕組み。既定ではアカウント単位・リージョン単位で毎秒 10,000 リクエスト、瞬間的な山（バースト）は 5,000 リクエストまで（一部のリージョンは低め）で、引き上げを申請できる。加えて、メソッド・ステージ・使用量プランの単位でも上限を決められ、超えた分には 429 Too Many Requests が返る。「特定の利用者が大量に呼んで、他に影響が出ている」なら、使用量プランによるスロットリング
  • キャッシュ：ステージの設定で有効にする。答えを使い回す時間（TTL：Time To Live）は既定 300秒、最大 3600秒、0 で無効。「同じ問い合わせが繰り返される読み取り中心の API で、バックエンドの負荷を下げたい」ならこれ。有効にしている時間に対して料金がかかるので、コスト最小が主題の設問では選ばれないこともある
  • ステージ：dev / prod のような公開の単位。ステージ変数を使うと、同じ定義のまま接続先を切り替えられる。カナリアリリースを設定すれば、新しいデプロイに一定の割合の通信だけを流せる。「新しい版を段階的に公開したい」の答え
試験ではこう出る

「複数ステップの処理をオーケストレーション」「エラー処理とリトライを一元管理」「進行状況を可視化」「人の承認を挟む」→ Step Functions（標準ワークフロー）。「アプリの利用者を認証して API を守る」→ Cognito オーソライザー。「既存の認証システムと連携」→ Lambda オーソライザー。「顧客ごとに流量を制限」→ 使用量プラン＋API キー。「サーバーから push」→ WebSocket API。

メモリ使用率は、最初からは取れていない

最初の依頼です。CloudWatch の画面を見ると、EC2 の CPU 使用率は何も設定しなくても表示されています。しかし、メモリ使用率は探しても見つかりません。理由は、AWS がどこから測っているかにあります。

  • この依頼の答え：CloudWatch エージェントを EC2 に入れて、メモリ使用率をカスタムメトリクスとして送らせる。そのメトリクスにアラームを付けて、SNS で通知する
  • どこで設定するか：エージェントは EC2 の OS にインストールし、何を集めるかを設定ファイルに書く。EC2 に付けるロール（IAM 講義の場面1）に、CloudWatch へ送る許可が要る
  • 「メモリ使用率で Auto Scaling したい」「ディスクが埋まる前に気づきたい」なら、答えは必ず CloudWatch エージェントの導入を含む

数字を集める細かさにも段階があります。

間隔料金手がかり
基本モニタリング5分無料EC2 の既定

詳細モニタリングは、すでにある数字の間隔を5分から1分に縮めるだけで、集める項目は増えません（メモリは取れないまま）。

メトリクスが残る期間は、細かさによって違います。1分未満のデータは3時間、1分のデータは15日、5分のデータは63日、1時間のデータは455日（約15か月）で、細かいものから順に粗くまとめられていきます。「1年以上前と比べたい」なら、S3 への書き出しが必要です。

ログに ERROR が出たら通知する

2つ目の依頼です。ログは文字なので、そのままではアラームを付けられません。一度、数字に変えます。

  • この依頼の答え：メトリクスフィルター ＋ アラーム ＋ SNS。CloudWatch の画面でロググループを開き、「メトリクスフィルターを作成」で数える言葉（ERROR、5xx など）を指定する。できたメトリクスにアラームを付ける
  • サブスクリプションフィルター：ログを、届いたそばから Lambda、Data Firehose（場面4）、OpenSearch などへ流す。別の場所で加工・分析したいとき
  • Logs Insights：専用の問い合わせの書き方で、ログを対話的に検索・集計する。事前の準備（インデックスの作成）は要らず、調べたログの量で課金される。「障害の原因をあとから調査したい」「特定のリクエスト ID の流れを追いたい」で出る
  • 保持期間に注意：ロググループの保持期間の既定は「失効しない」。放っておくと料金が増え続ける。コストの設問では、保持期間の設定と、古いログを S3 へ書き出すことが答え

アラームは、いつ鳴るのか

アラームは CloudWatch の画面の「アラーム」で作り、見るメトリクス、しきい値、判定のしかたを決めます。

  • 状態は3つ：OK / ALARM / INSUFFICIENT_DATA（データ不足）
  • 決めること：何回分を見るか（評価期間）、そのうち何回超えたら ALARM にするか（M out of N）、数字が届かなかった回をどう扱うか
  • アラームが起こせる動作：SNS への通知、Auto Scaling のポリシーの実行、EC2 のアクション（停止・終了・再起動・復旧）
  • 複合アラーム：複数のアラームを AND / OR / NOT で組み合わせる。目的は、うるさい通知を減らすこと。「CPU が高い」だけでなく「CPU が高い AND 応答時間が悪化」なら、本当に見るべき事象になる。「誤検知が多い」「通知が多すぎる」と書いてあったら複合アラーム
試験ではこう出る

「メモリ使用率」「ディスク使用率」→ CloudWatch エージェント（MemoryUtilization という標準メトリクスは EC2 には存在しない）。「ログに特定の文字列が出たら通知」→ メトリクスフィルター ＋ アラーム ＋ SNS。「1分間隔で」→ 詳細モニタリング。「通知が多すぎる」→ 複合アラーム。「ログの料金が増え続ける」→ ロググループの保持期間。

  • どこで設定するか：CloudTrail の画面で「証跡の作成」を選び、保存先の S3 バケットと、記録するイベントの種類（管理イベント・データイベント）を選ぶ。データイベントは、対象のバケットや関数を指定して有効にする

  • ログファイルの整合性検証：有効にすると、記録が書き換えられていないことをあとから確かめられる。監査の要件がある設問で出る

Q1注文処理システムで、セール開始時に通常の20倍のリクエストが集中し、在庫更新サービスがタイムアウトして注文の一部が失われている。注文を1件も失わずに処理するために最も適切な構成はどれか。
  • A. 在庫更新サービスの前に ALB を配置し、複数台に分散させる
  • B. 注文サービスと在庫更新サービスの間に SQS キューを挟み、キューの深さに基づいてコンシューマを Auto Scaling させる
  • C. 在庫更新サービスのインスタンスタイプをピークに合わせて常時大きくする

場面1の2枚目の図（キューあり）と、場面3の「キューの深さでスケール」の図の組み合わせ。キューを挟めば、届く速さと処理する速さの差を時間で吸収できる。注文サービスは入れた時点で成功を返せ、溜まった量に応じてコンシューマーが増えるので、滞留も短時間で解消する。

判断軸: A は同期のままなので溜める場所がない（場面1の注意書き）。C はピークに合わせて常に大きくしておくのでコストが無駄。D は根本の解決にならず、やり直している間も送り手の資源を使う。「失われてはいけない」と書かれていたら、溜めておける置き場、つまりキューを探す。

正解: B

場面2の可視性タイムアウトの図の上段そのもの。処理に3分かかるのに見えない時間が30秒だと、1台目の処理中にメッセージがまた見えるようになり、2台目が同じものを受け取る。可視性タイムアウトを処理時間より長くするか、ChangeMessageVisibility で延長する。

判断軸: A も標準キューの性質としては正しい（場面3の図の左）が、「頻発」と処理時間の情報が揃っているので、設定の誤りを問う設問だと読む。処理時間が具体的に書かれていたら、可視性タイムアウトとの比較を疑う。C はコストと遅れ、D はメッセージが消える話で、二重処理とは関係がない。

Q3あるアプリケーションが注文イベントを発行している。現在は在庫システムと請求システムがこれを受け取っているが、来期には分析基盤も追加する予定である。また、いずれかのシステムがメンテナンスで停止していてもイベントを失いたくない。最も適した構成はどれか。
  • A. SNS トピックを作り、各システムを HTTPS エンドポイントとして直接サブスクライブさせる
  • B. SQS キューを2本作り、アプリケーションが両方に送信する
  • C. SNS トピックを作り、システムごとに SQS キューを用意してトピックにサブスクライブさせる
  • D. Kinesis Data Streams にイベントを流し、各システムがコンシューマとして読み取る

正解: C

場面4のファンアウトの図の下段。1回発行すればコピーが各キューに入り、キューが溜めておくので、停止中でもイベントは残る。分析基盤の追加も、キューを作ってトピックを購読させるだけで、発行する側は変えなくてよい。

判断軸: A はキューがないので、停止中の分を失うおそれがある（SNS は溜めない）。B はファンアウトの図の上段で、宛先が増えるたびに送り手を直すことになる。D（Kinesis Data Streams：大量のデータを流し続けるサービス）でも要件は満たせるが、この規模には大がかりすぎる。「将来コンシューマーを追加する」「一部が停止しても失わない」が並んだら SNS ＋ SQS。

Q4セキュリティ監査で「S3 バケット内のオブジェクトを誰がいつ削除したかを、過去1年分たどれるようにせよ」と指摘された。適切な対応はどれか。
  • A. CloudTrail のイベント履歴をコンソールで確認する
  • B. CloudTrail で証跡を作成し、S3 のデータイベントを有効にして、ログを S3 バケットに保存する
  • C. AWS Config で S3 バケットの構成変更を記録する
  • D. CloudWatch でバケットのオブジェクト数メトリクスにアラームを設定する

正解: B

場面8の「管理イベントとデータイベント」の図の下の行。オブジェクトへの操作はデータイベントで、既定では記録されない。証跡で有効にして S3 に保存すれば、期限なく1年分を残せる。

判断軸: A のイベント履歴は90日分で、しかも管理イベントだけなので、両方の要件を満たさない。C は場面8の2枚目の図のとおり「バケットの設定がどう変わったか」の記録で、オブジェクト単位の操作は追えない。D は増減が分かるだけで、誰がやったかは分からない。「オブジェクト」か「バケット」かで、必要な設定が変わる。

Q5EC2 上の Java アプリケーションがメモリ不足で不定期に停止する。事前に検知して通知したい。最小の運用負荷で実現する方法はどれか。
  • A. CloudWatch の標準メトリクス MemoryUtilization にアラームを設定する
  • B. EC2 の詳細モニタリングを有効にし、1分間隔でメモリ使用率を取得する
  • C. CloudWatch エージェントを導入してメモリ使用率をカスタムメトリクスとして発行し、アラームから SNS に通知する
  • D. アプリケーションのログを CloudWatch Logs に送り、Logs Insights で定期的に検索する

正解: C

場面7の「エージェントが要るもの」の図。メモリ使用率は OS の内側の数字で、AWS が外側から測れないので、標準メトリクスには存在しない。CloudWatch エージェントを入れて内側から送らせ、アラームを付ける。

判断軸: A の MemoryUtilization という EC2 の標準メトリクスは存在しない。この「ありそうで存在しないメトリクス」は頻出の誤答。B の詳細モニタリングは、すでにある数字の間隔を5分から1分に縮めるだけで、項目は増えない。D は起きたあとの調査で、事前の検知になっていない。メモリとディスク使用率が出たらエージェント。
