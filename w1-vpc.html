01

この講義のゴール

VPCの設問は、構成要素の名前を知っているだけでは解けません。問われるのは「このパケットはどこで止まるか」です。今日終わったときに、次の3つができていれば合格です。

  • 01
    サブネットがパブリックかプライベートかを、ルートテーブルだけを見て判定できる。
    名前でも設定項目でもなく、0.0.0.0/0 の向き先で決まることを説明できる。
  • 02
    「つながらない」の原因を、順番に切り分けられる。
    ルートテーブル、セキュリティグループ、ネットワークACL、パブリックIP――どれを先に疑うかの順序が頭に入っている。
  • 03
    接続要件を読んで、使うべきサービスを1つに絞れる。
    エンドポイント / ピアリング / Transit Gateway / Direct Connect / VPN の使い分けを、要件の言葉から逆引きできる。
なぜネットワークが重いのか

SAA-C03の設問は「復元力の高いアーキテクチャ」「高性能なアーキテクチャ」「セキュアなアーキテクチャ」の3方向からネットワークに触れてきます。マルチAZの話をすればサブネットとNATの冗長化が出てきますし、コスト最適化の話をすればデータ転送料とVPCエンドポイントが出てきます。IAMが全分野の土台だったのと同じ意味で、VPCも全分野に顔を出します。ここは投資に見合う領域です。

02

VPC の骨格 ―― 何が経路を決めているか

VPCは箱ではなく、ルーティングの集合だと考えてください。要素はいくつもありますが、通信の可否を最終的に決めているのはルートテーブル1つです。

CIDR の決め方は後から効いてくる

VPCを作るときに指定するCIDRブロックは /16 から /28 の範囲です。この設計を軽く扱うと、後でピアリングやオンプレミス接続をするときに詰みます。CIDRが重複しているVPC同士はピアリングできませんし、オンプレミスのアドレス空間と重なっていればVPNもDirect Connectも素直につながりません。設問で「将来の統合を見据えて」「複数のVPCを接続する予定がある」と書かれていたら、それはCIDR重複の話を振っているサインです。

作成後にプライマリCIDRは変更できませんが、セカンダリCIDRの追加はできます。IPアドレスが枯渇したという設問では、「VPCを作り直す」ではなく「セカンダリCIDRを追加してサブネットを増やす」が正解側です。なお各サブネットで先頭4つと末尾1つ、合計5つのIPアドレスがAWSに予約されるため、/24 で使えるのは251個です。

サブネットは必ず1つのAZに閉じる

サブネットは単一のアベイラビリティゾーンにしか存在できません。制約であると同時に、マルチAZ設計の単位がサブネットであるということでもあります。ALBが最低2つのAZのサブネットを要求するのも、RDSのサブネットグループが同じ要求をするのも理由は同じです。「可用性を高めたい」と来たら、まずサブネットがAZをまたいでいるかを見ます。

パブリックとプライベートは設定項目ではない

ここが最初の関門です。AWSコンソールに「このサブネットをパブリックにする」というチェックボックスはありません。関連付けられたルートテーブルに、Internet Gateway 宛のデフォルトルート（0.0.0.0/0 → igw-xxxx）があるサブネットがパブリックサブネットです。それだけです。

呼び方0.0.0.0/0 の向き先できること
パブリックサブネットInternet Gateway外に出られる。パブリックIPがあれば外から入れる
プライベートサブネットNAT Gateway / NAT インスタンス外に出られる。外から入ることはできない
隔離サブネットルートなし（local のみ）インターネットとは一切通信しない。VPCエンドポイント経由のみ

この3段構えがそのまま「どこに何を置くか」の設計になります。ALBとNAT Gatewayはパブリック、アプリケーションサーバーはプライベート、RDSやElastiCacheのようにインターネットと話す必要のないデータストアは隔離サブネット。「データベースをインターネットから完全に遮断したい」と来たら、セキュリティグループではなく、まずサブネットとルートテーブルの話です。

最頻出の引っかけ

「EC2をパブリックサブネットに置いてInternet Gatewayもアタッチしたのに、インターネットに出られない」。原因はインスタンスにパブリックIPまたはElastic IPが割り当てられていないことです。Internet Gatewayは1対1のNAT（プライベートIPとパブリックIPの変換）を行う装置なので、変換先のパブリックIPがなければ仕事ができません。ルートテーブルとIGWだけでは足りない、という点を必ず押さえてください。

判断軸

Internet Gateway はVPCに1つだけアタッチでき、リージョンサービスなので冗長化も帯域の心配も不要です。AWS側が水平スケールしています。したがって「インターネット接続がボトルネックになっているのでIGWを増やす」という選択肢は常に不正解です。ボトルネックになりうるのはNAT Gatewayの側です。

03

NAT ―― 出るだけの経路をどう作るか

プライベートサブネットのインスタンスがパッチを取りに行く、外部APIを叩く。この「出るだけ」の通信を成立させるのがNATです。SAAでは可用性とコストの2方向から問われます。

NAT Gateway と NAT インスタンス

NATインスタンスはEC2に自分でNATソフトウェアを載せる旧来の方式です。今から新規に選ぶ理由はありませんが、設問では「なぜマネージドが良いのか」を問う形で出ます。

NAT GatewayNAT インスタンス
正体AWSマネージドのNATサービス自分で立てたEC2インスタンス
可用性AZ内で冗長化済み（AZ単位では単一障害点）インスタンス障害でそのまま停止。自前でスクリプト冗長化が必要
帯域自動でスケールするインスタンスタイプに固定される

この表で覚えておくべきは、下から3行です。NAT Gateway にはセキュリティグループをアタッチできません。トラフィックを制御したければ、NAT Gatewayが置かれているサブネットのネットワークACLか、通信元インスタンス側のセキュリティグループで制御します。「NAT Gatewayのセキュリティグループで送信先を制限する」という選択肢が出たら、その時点で不正解です。

また、外から中へのセッションを一切受け付けないのがNATの定義なので、NAT Gatewayは踏み台になりません。「プライベートサブネットのインスタンスに管理者がログインしたい」の答えはNAT Gatewayではなく Systems Manager Session Manager です。踏み台を立てずに済み、SSHポートを開けずに済み、操作がCloudTrailに残ります。

可用性設計 ―― AZごとに置く

NAT GatewayはAZの中に作られます。AZ-aに1つだけ置いて両AZのプライベートサブネットから参照する構成は、動きはしますが2つの問題を抱えます。

  1. AZ-aが落ちるとAZ-bのインスタンスも外に出られなくなる。せっかくマルチAZにしたのに、外向き通信の単一障害点を作ってしまっている状態です。
  2. AZ間データ転送料金が乗る。AZ-bから出る通信が、わざわざAZ-aを経由してから外に出ることになります。

したがって各AZのパブリックサブネットにNAT Gatewayを1つずつ置き、同じAZのプライベートサブネットのルートテーブルを自分のAZのNAT Gatewayに向けるのが定石です。「高可用性」「AZ障害に耐える」という語とともにNAT Gatewayが1つの構成図が示されたら、そこが答えです。

コストの罠

NAT Gatewayは起動している時間と、通したデータ量の両方に課金されます。プライベートサブネットのEC2がS3に大量のデータを書き込む構成では、その全量がNAT Gatewayのデータ処理料金として乗ってきます。「NAT Gatewayの費用が想定より高い」という設問の答えは、ほぼ確実にS3・DynamoDB向けのゲートウェイ型VPCエンドポイントを作ってNATを迂回させるです。次の節で扱います。

もう1点、学習用のハンズオンではNAT Gatewayを消し忘れると課金が続きます。週末のハンズオンの最後に必ず削除してください。

IPv6 の場合は別の装置になる

IPv6はアドレスが枯渇しないのでNATという概念自体がありません。しかし「外には出たいが外からは入られたくない」という要件はIPv4と同じです。これを満たすのが Egress-Only Internet Gateway。IPv6専用でアウトバウンドのみを許可し、ステートフルに戻りを通します。追加料金はかかりません。

設問での見分けは単純です。IPv6 かつ「アウトバウンドのみ」なら Egress-Only Internet Gateway、IPv4 かつ「アウトバウンドのみ」なら NAT Gateway。IPv6でNAT Gatewayを使う選択肢は不正解です。

04

セキュリティグループ と ネットワークACL

この2つの違いはSAAで必ず問われます。しかも「どちらを使うべきか」という形と、「なぜ通らないのか」という形の両方で出ます。丸暗記ではなく、ステートフルかステートレスかという1点から全部を導けるようにしてください。

ステートフルとは何が違うのか

セキュリティグループは通した通信を覚えています。インバウンドで443を許可すれば、応答はアウトバウンドに書かなくても返ります。逆も同じです。セキュリティグループでは「行き」だけを考えればよい、と理解してください。

ネットワークACLは何も覚えません。インバウンドでポート443を許可しただけでは、応答が出ていけません。応答パケットの宛先ポートはクライアントが使ったエフェメラルポート（一時的な高位ポート、一般に1024〜65535）なので、アウトバウンド側でこの範囲を許可しておく必要があります。「NACLでHTTPSを許可したのに通信が成立しない」という設問の答えは、ほぼ常にエフェメラルポートの許可漏れです。これは出題頻度が非常に高い形です。

セキュリティグループを送信元に指定できることの意味

セキュリティグループの送信元には、CIDRだけでなく別のセキュリティグループのIDを書けます。たとえばRDS用のセキュリティグループのインバウンドに「ソース: アプリ層のセキュリティグループ、ポート3306」と書けば、そのセキュリティグループが付いたインスタンスからだけ接続できます。

この書き方の価値は、Auto Scalingでインスタンスが入れ替わってもルールを直さなくてよいことです。「Auto Scaling グループのインスタンスからのみDBへの接続を許可したい。運用負荷を最小に」と来たら答えはこれで、CIDRでサブネット全体を許可する選択肢は動きはしますが最小権限になっていません。ネットワークACLはCIDRしか書けないため、この粒度の制御ができません。

判断軸

「特定のIPアドレスからのアクセスをブロックしたい」という要件だけは、セキュリティグループでは実現できません。セキュリティグループには拒否ルールが書けないからです。DDoSの発信元や、社内のブラックリストIPを遮断する要件が出たら、答えはネットワークACL（またはAWS WAF、AWS Shield、AWS Network Firewall）です。「ブロック」「拒否」「除外」という語が要件に出たら、そこがネットワークACLを選ぶサインです。

よくある誤解

「セキュリティグループとネットワークACLは、どちらか一方を使うもの」――違います。両方が順番に適用されます。インバウンドならサブネットに入るときにNACL、ENIに入るときにSG。アウトバウンドならENIを出るときにSG、サブネットを出るときにNACL。どちらか一方でも拒否されれば通りません。この「二重の関門」の順序が、次の節の切り分けの土台になります。

同じサブネット内の通信

ネットワークACLはサブネットの境界で評価されます。したがって同じサブネット内のインスタンス同士の通信にはNACLは適用されません。この場合に効くのはセキュリティグループだけです。「同一サブネット内の2台が通信できない」という設問でNACLを疑う選択肢は不正解になります。

05

「つながらない」を切り分ける

SAAのネットワーク設問の多くは、この形をしています。構成が説明され、「通信できない。原因として最も可能性が高いものはどれか」と聞かれる。原因の候補は毎回同じ場所にあるので、順番を固定して上から見ていきます。

01送信元サブネットのルートテーブルに、宛先への経路があるかインターネット向けなら 0.0.0.0/0、他VPC向けならピアリングやTGWへのルートない → 届かない
02その経路の出口の種類は要件に合っているかIGW / NAT / エンドポイント / ピアリング接続 / 仮想プライベートゲートウェイ違う → 届かない
03インターネットとの通信なら、パブリックIP または Elastic IP があるかIGWは変換装置。変換先がなければ何もできないない → 届かない
04送信元のセキュリティグループのアウトバウンドが許可しているか既定では全許可なので、絞っている場合だけ疑う不許可 → 拒否
05宛先のセキュリティグループのインバウンドが許可しているかここが最頻出。ポート番号とソース（CIDRかSG ID）の両方を見る不許可 → 拒否
06両サブネットのネットワークACLが行きを許可しているかルール番号の小さい順。上位に広い Deny がないかを見る不許可 → 拒否
07ネットワークACLが戻りのエフェメラルポートを許可しているか1024〜65535。ステートレスなので明示が必要不許可 → 片道で止まる
08インスタンス側でプロセスが待ち受けているかOSのファイアウォール、アプリのバインドアドレスはい → 到達する
すべて通過 → 通信が成立する

この順番が意味を持つ理由

ルートテーブルを先に見るのは、経路がなければパケットはそもそも発射されないからです。セキュリティグループやNACLで落とされた場合は、パケットは飛んでいるが弾かれている状態で、両者は区別できます。

VPC フローログはENIを出入りしたトラフィックを記録し、各レコードに ACCEPT か REJECT を残します。REJECT があればセキュリティグループかネットワークACLで落ちた、何も記録がなければルーティングの問題です。ただしパケットの中身は記録しません。中身が要るなら VPC トラフィックミラーリング です。

VPC Reachability Analyzer は、実際にパケットを流さずに経路上の構成を解析し、到達可能か、不可能ならどのコンポーネントで止まるかを返します。「実際のトラフィックを発生させずに到達性を検証したい」と出たらこれです。フローログは事後の記録、Reachability Analyzer は事前の検証、という役割分担で覚えてください。

判断軸

片方向だけ通っている（リクエストは届くが応答が返らない、あるいはその逆）という記述を見たら、真っ先にネットワークACLを疑います。セキュリティグループはステートフルなので、原理的に片道だけ通るという状態が作れません。この非対称性が、2つを見分ける最短の手がかりです。

06

VPC エンドポイント ―― AWSサービスへ、外に出ずに届く

S3やDynamoDBはVPCの外にあるサービスです。素直に通信するとインターネット経由になり、NAT Gatewayを通り、データ処理料金がかかり、そしてトラフィックが一度パブリックな経路に出ます。これを避けるのがVPCエンドポイントです。コスト最適化とセキュリティの両方の設問に登場します。

使い分けの軸は3つです。S3かDynamoDBで、VPC内からの利用だけなら迷わずゲートウェイ型――無料で、NAT Gatewayのデータ処理料金をまるごと削れます。オンプレミスやピアリング相手からも使いたいなら、S3であってもインターフェース型（S3は両方の型に対応しています）。そしてそれ以外のAWSサービス（SQS、SNS、KMS、Secrets Manager、Systems Manager、CloudWatch Logs など）はインターフェース型しかありません。

ゲートウェイ型を作るとルートテーブルに追加される行と、エンドポイントポリシーの例
# ルートテーブル
pl-xxxxxxxx (com.amazonaws.ap-northeast-1.s3)  →  vpce-0a1b2c3d

// エンドポイントポリシー（このエンドポイント経由で何ができるかの上限）
{
  "Statement": [{
    "Effect": "Allow",
    "Principal": "*",
    "Action": ["s3:GetObject"],
    "Resource": "arn:aws:s3:::quality-reports/*"
  }]
}

ゲートウェイ型はプレフィックスリスト（そのサービスのIPレンジをまとめた識別子）をルートテーブルに追加する形で動きます。宛先がS3のIPレンジに一致するパケットだけがエンドポイントに流れ、それ以外は従来どおりNAT Gatewayへ向かうので、既存構成を壊さずに追加できます。

両方の型にエンドポイントポリシーを付けられます。IAMの講義でやった権限境界と同じく、権限を与えるものではなく上限を絞るものです。「特定のS3バケットにだけアクセスさせたい」と来たときは、エンドポイントポリシーとS3バケットポリシーの aws:SourceVpce 条件が両方とも候補になります。バケット側で締めたいなら aws:SourceVpce、VPC側で締めたいならエンドポイントポリシーという切り分けです。

PrivateLink を自社サービスに使う

この仕組みはAWSサービス専用ではありません。自分のVPCで動かすサービスを Network Load Balancer の背後に置いて「エンドポイントサービス」として公開すると、他のVPCやアカウントからPrivateLink経由で呼び出せます。重要な性質は2点です。

  • CIDRが重複していてもよい。ピアリングと違い、アドレス空間の調整が要りません。消費側のVPCにはENIが生えるだけだからです。
  • 公開されるのは特定のサービスだけ。ピアリングのようにネットワーク同士をつなぐのではなく、1つのエンドポイントを差し出す形なので、露出面が小さく済みます。

「SaaSをインターネット経由せずに利用したい」「自社サービスを取引先のVPCに公開したいが、ネットワーク全体はつなぎたくない」と来たら答えはPrivateLinkです。ピアリングを選ぶと過剰な接続になります。

最頻出の引っかけ

「オンプレミスのサーバーから、Direct Connect経由でS3にプライベートにアクセスしたい」という設問で、ゲートウェイ型エンドポイントを選ぶのは不正解です。ゲートウェイ型はルートテーブルで動くため、VPC内から発したトラフィックにしか効きません。オンプレミスから使うならインターフェース型（またはDirect Connectのパブリック仮想インターフェース）です。同じ理由で、ピアリング相手のVPCからも使えません。

07

VPC 同士と、オンプレミスをつなぐ

つなぎ方は4つ――ピアリング、Transit Gateway、Site-to-Site VPN、Direct Connect。選択の軸は規模と帯域の安定性といつまでに必要かの3つです。

VPC ピアリング と Transit Gateway

VPC ピアリングTransit Gateway

推移的ルーティングできないできる
接続数の増え方VPCがn個なら n(n-1)/2 本VPCごとに1本のアタッチメント

最重要は推移的ルーティングの行です。A-B と B-C がピアリングされていても、A から C には通信できません。ピアリングは接続した2者の間だけの経路であり、中継しないからです。同じ理由でエッジ間ルーティングも禁止されており、相手VPCのInternet Gateway、NAT Gateway、ゲートウェイ型エンドポイント、Direct Connect接続を借りることもできません。「インターネット出口を1つのVPCに集約したい」をピアリングで実現する選択肢は不正解で、正解はTransit Gateway による集約です。

一方でピアリングはリージョンもアカウントもまたげ、追加のデータ処理料金がないので安価です。「2つのVPCをつなぐ最も費用対効果の高い方法は」ならピアリング、「VPCが20個あって今後も増える」「オンプレミス接続も集約したい」ならTransit Gatewayです。

判断軸

設問に出てくる数を数えてください。VPCが3つ以下ならピアリング、それ以上かつ増える見込みがあるならTransit Gateway。そして「オンプレミスもまとめたい」「ルーティングを部門ごとに分離したい」という語が1つでもあれば、数によらずTransit Gatewayです。なお、Transit Gateway同士をリージョン間でピアリングすることもできるので、グローバルなハブ＆スポークも組めます。

Site-to-Site VPN と Direct Connect

オンプレミスとAWSをつなぐ手段は2つです。決定的な違いは、インターネットを通るか、専用線を通るかです。

Site-to-Site VPNDirect Connect
経路インターネット上のIPsecトンネルAWSへの専用線（インターネットを通らない）
帯域の安定性インターネット次第で変動する一貫している
レイテンシー変動する安定して低い
開通までの時間数分〜数時間数週間〜数か月
暗号化IPsecで既定で暗号化既定では暗号化されない

Site-to-Site VPN は1接続につき2本のIPsecトンネルが提供され、それぞれ異なるAWS側エンドポイントに終端するので、AWS側は最初から冗長です。落ちるとすればオンプレミス側のカスタマーゲートウェイなので、そこを2台にするのが次の一手になります。スループットは1トンネルあたり最大約1.25 Gbpsで、超えたい場合はTransit Gatewayと組み合わせて複数トンネルをECMPで束ねます。「VPNの帯域が足りない」なら、この構成かDirect Connectへの移行が答えです。

開通までの時間はそのまま手がかりになります。「今すぐ接続が必要」「一時的な移行期間だけ」ならVPN、「安定した低レイテンシー」「大量データを継続的に転送」「一貫した帯域」ならDirect Connectです。

仮想インターフェースの3種類

物理回線の上には仮想インターフェース（VIF）を作ります。3種類あり、行き先が違います。

  • プライベートVIF ―― VPCのプライベートIP空間へ。仮想プライベートゲートウェイまたはDirect Connect ゲートウェイ経由。
  • パブリックVIF ―― S3やDynamoDBなどAWSのパブリックなエンドポイントへ、インターネットを経由せずに届きます。
  • トランジットVIF ―― Transit Gateway へ。多数のVPCをDX経由でまとめて見せるときに使います。

Direct Connect ゲートウェイを挟むと、1本のDX接続から複数リージョンの複数VPCに届きます。「東京と大阪のVPCに1本のDXで」の答えはこれです。

冗長構成のパターン

DXを1本引いただけでは高可用性になりません。物理回線もDXロケーションも単一障害点だからです。可用性とコストの釣り合いで3段階あります。

  1. Direct Connect ＋ Site-to-Site VPN バックアップ。最も一般的で費用対効果の高い構成です。通常はDXを使い、落ちたらVPNへフェイルオーバーします（BGPのルート優先度でDXを優先させる）。ただしフェイルオーバー後は帯域が落ちるので、「縮退運転で業務が成立するか」が採否の分かれ目です。
  2. Direct Connect 2本（異なるDXロケーション）。回線とロケーションの両方を冗長化します。帯域が落ちないので、フェイルオーバー後も同じ性能が要る要件で選びます。コストは倍以上です。
  3. Direct Connect 2本 × 2ロケーション（計4本）。「最大の回復性」という語が出たときの構成です。

「コストを抑えつつ冗長化」ならDX＋VPNバックアップ、「フェイルオーバー時も同じ帯域が必要」ならDX 2本で切り分けられます。VPNバックアップの選択肢を、安いという理由だけで除外しないでください。

Direct Connect は暗号化されない

専用線なのでインターネットは通りませんが、それ自体は暗号化を意味しません。「転送中の暗号化」が求められる設問ではDX単体は不十分で、答えはパブリックVIF の上に Site-to-Site VPN を張るか、対応する回線なら MACsec です。「DXだからデータは暗号化されている」という選択肢は誤りです。

08

Route 53 ―― どのIPを返すかで経路を決める

DNSは「名前をIPに変える仕組み」ですが、SAAではトラフィックを振り分ける仕組みとして出題されます。ルーティングポリシーの選択は、そのまま可用性設計とレイテンシー設計の選択です。

ルーティングポリシーを要件から逆引きする

ポリシー何を基準に返すか設問に出る言い回し
シンプル常に同じレコードを返す単一のリソース。ヘルスチェックは使えない
加重指定した重みの比率で分配「90:10で新バージョンに流す」「カナリアリリース」「A/Bテスト」
レイテンシーそのユーザーから最も応答が速いリージョン「複数リージョンで最高のパフォーマンスを」
フェイルオーバープライマリが健全ならプライマリ、落ちたらセカンダリ「アクティブ／スタンバイ」「災害対策サイト」「Sorryページ」

地理的近接性ユーザーとリソースの地理的な距離。バイアス値で範囲を伸縮できる「トラフィックの流れ先を地理的に少しずつ移したい」

取り違えが多いのはレイテンシー / 位置情報 / 地理的近接性の3つです。切り分けは単純で、「速さ」が要件ならレイテンシー、「どこの国の人か」なら位置情報、「どのリソースに何割寄せるか」を地理で調整したいなら地理的近接性（トラフィックフローで設定します）。日本のユーザーが東京リージョンに行くとは限らない――経路次第では別リージョンの方が速い――という点で、レイテンシーと位置情報は結果が一致しません。法規制やローカライズが理由なら位置情報です。

もうひとつ、複数値回答は負荷分散装置ではありません。どのIPを使うかはクライアントが決めるので厳密な分散になりません。価値は「ヘルスチェックに応じて不健全なIPを返さなくなる」点にあり、シンプルルーティングとの違いもそこです。

ヘルスチェック

フェイルオーバールーティングはヘルスチェックとセットで初めて機能します。ヘルスチェックには3種類あります。

  • エンドポイントの監視 ―― 指定したIPやドメインに対してHTTP/HTTPS/TCPで疎通を確認します。
  • 他のヘルスチェックの監視（計算型） ―― 複数のヘルスチェックを束ね、「3つのうち2つが健全なら健全」といった判定をします。
  • CloudWatch アラームの監視 ―― アラームの状態を健全性として使います。Route 53のヘルスチェッカーはインターネット側から来るため閉じたリソースには届かないので、プライベートサブネットのリソースを監視したいときはこれです。

エイリアスレコード

エイリアスレコードはRoute 53固有の拡張で、AWSリソース（ALB/NLB、CloudFront、S3の静的ウェブサイト、API Gateway、同一ホストゾーン内の別レコードなど）を指します。CNAMEとの違いを押さえます。

エイリアスCNAME
ゾーン頂点（example.com そのもの）設定できる設定できない
AWSリソースへのクエリ料金無料課金される
指せる先AWSリソースと同一ゾーン内のレコード任意のドメイン名
IPの変化への追従AWS側が自動で追従する名前解決の連鎖で追従

「example.com（wwwなし）をALBに向けたい」という設問の答えは、必ずエイリアスレコードです。CNAMEはゾーン頂点に作れないので、この一点だけで選択肢が絞れます。

ハイブリッドDNS

オンプレミスのDNSとVPC内の名前解決をつなぐのが Route 53 Resolver エンドポイントです。向きを取り違えないでください。「オンプレミスのサーバーがAWS内のRDSのエンドポイント名を解決できない」→ インバウンド、「EC2から社内のホスト名を解決したい」→ アウトバウンドです。

09

CloudFront と Global Accelerator

どちらもAWSのエッジロケーションを使って利用者に近づける仕組みですが、やっていることが根本的に違います。CloudFrontはキャッシュし、Global Acceleratorはキャッシュしません。

CloudFrontGlobal Accelerator
本質コンテンツをエッジにキャッシュするCDNAWSのグローバルネットワークへ最短で乗せるアクセラレーター
対応プロトコルHTTP / HTTPS（とWebSocket）任意のTCP / UDP
キャッシュするしない
クライアントが見るIPエッジごとに変わる2つの固定Anycast IP
フェイルオーバーオリジンフェイルオーバー（オリジングループ）ヘルスチェックに基づき数十秒で切り替え

切り分けは2つのキーワードで決まります。「静的コンテンツ」「キャッシュ」「動画配信」ならCloudFront。「UDP」「非HTTP」「固定IPアドレスが必要」「ファイアウォールでIPを許可リストに登録」ならGlobal Accelerator。とくに「固定IP」は強い手がかりです。企業のファイアウォールが宛先IPで許可を出している環境では、エッジごとにIPが変わるCloudFrontは使えません。

オリジンアクセスコントロール（OAC）

CloudFrontでS3を配信するとき、S3バケットをパブリックにしてはいけません。利用者がCloudFrontを飛ばしてS3のURLを直接叩けてしまい、WAFもキャッシュも署名付きURLも回避されるからです。これを防ぐのが OAC（Origin Access Control）です。

OACを設定するとCloudFrontがS3へのリクエストにSigV4で署名します。バケットポリシーには「このディストリビューションからのみ許可」と書き、パブリックアクセスはブロックしたままにできます。旧来の OAI（Origin Access Identity）も同じ役割でしたが、OACはSSE-KMSで暗号化されたオブジェクトに対応し、GET以外のHTTPメソッドにも対応する点で上位互換です。新規構成の正解は常にOACで、OAIは「レガシー」として選択肢に混ざります。

よく一緒に出る周辺機能

署名付きURL / Cookie ―― 期限付き配信。単一ファイルならURL、複数ファイルをまとめて許すならCookie。地理的制限 ―― 特定の国からのアクセスを遮断。AWS WAF ―― アプリケーション層の攻撃を防ぐ。CloudFront Functions / Lambda@Edge ―― 前者は軽量なヘッダー書き換えやリダイレクト、後者はより複雑な処理に使います。

最頻出の引っかけ

「CloudFrontを導入したのにオリジンの負荷が下がらない」。典型的な原因はキャッシュキーに不要なクエリ文字列・Cookie・ヘッダーを含めてしまっていることです。キャッシュキーが細分化されるとヒット率が落ちます。対策はキャッシュポリシーの見直しで、「TTLを伸ばす」も選択肢に出ますが、キャッシュキーの問題が示唆されていればそちらが正解です。

11

確認問題

先に自分で答えを決めてから開いてください。特にQ2とQ4は、実際の試験と同じ密度で書いています。

Q1プライベートサブネットのEC2インスタンス群が、S3へ毎日大量のログをアップロードしている。NAT Gatewayのデータ処理料金が月額の大半を占めていることが分かった。最もコストを削減できる対応はどれか。
  • A. NAT Gateway を NAT インスタンス（t3.micro）に置き換える
  • B. S3 向けのゲートウェイ型 VPC エンドポイントを作成し、ルートテーブルに関連付ける
  • C. EC2 をパブリックサブネットに移動し、Elastic IP を割り当てる
  • D. S3 向けのインターフェース型 VPC エンドポイントを作成する

正解: B

ゲートウェイ型エンドポイントは追加料金なしで、S3宛のトラフィックをNAT Gatewayを通さずにAWSの内部経路へ流します。データ処理料金がそのまま消えます。

判断軸: Dのインターフェース型でもNATは迂回できますが、時間課金とデータ処理量課金がかかるため「最もコストを削減できる」には劣ります。S3・DynamoDB かつVPC内からの利用だけなら必ずゲートウェイ型が優先。Aは可用性と帯域を犠牲にし、Cはインスタンスをインターネットに露出させます。

Q2パブリックサブネットのWebサーバーに対して、インターネットからのHTTPSアクセスが届かない。セキュリティグループのインバウンドは 443/tcp を 0.0.0.0/0 から許可しており、ネットワークACLのインバウンドにも 443/tcp の許可ルールがある。ルートテーブルには 0.0.0.0/0 → igw-xxxx がある。インスタンスにはパブリックIPが割り当てられている。最も可能性が高い原因はどれか。
  • A. セキュリティグループのアウトバウンドで 443/tcp が許可されていない
  • B. ネットワークACLのアウトバウンドでエフェメラルポート（1024-65535）が許可されていない
  • C. Internet Gateway が VPC にアタッチされていない
  • D. サブネットのルートテーブルに NAT Gateway へのルートがない

正解: B

ネットワークACLはステートレスなので、インバウンドで443を許可しても、応答パケットを外へ出すためのアウトバウンドルールが別途必要です。応答の宛先ポートはクライアント側のエフェメラルポートなので、1024-65535 を許可していないとここで止まります。

判断軸: Aが不正解なのはセキュリティグループがステートフルだからです。Cはルートテーブルに igw-xxxx がある時点で成立せず、Dはパブリックサブネットの話なのでNATは無関係。「行きの許可は確認済みなのに通らない」と念入りに書いてあったら、ステートレスな側＝NACLの戻りを疑ってください。

Q3VPC-A と VPC-B、VPC-B と VPC-C がそれぞれ VPC ピアリングで接続されている。VPC-A のインスタンスから VPC-C のインスタンスへ通信させたい。また今後VPCは20個程度まで増える予定で、オンプレミスとのVPN接続も1か所に集約したい。適切な設計はどれか。
  • A. VPC-A と VPC-C の間にもピアリング接続を追加する
  • B. VPC-B のルートテーブルに VPC-A と VPC-C 向けのルートを追加して中継させる
  • C. Transit Gateway を作成し、各VPCとVPN接続をアタッチする
  • D. 3つのVPCを1つに統合し、サブネットで分離する

正解: C

VPCが20個に増え、VPN接続も集約したいという要件は、ピアリングのフルメッシュでは管理できません（20個なら190本）。Transit Gateway なら各VPCが1本のアタッチメントを持つだけで済み、VPNも同じハブに集約できます。

判断軸: Bはピアリングが推移的ルーティングをしないためルートを書いても通りません。ここが最大の引っかけです。Aは今回の3つは解決しますが、増加と集約の要件を満たしません。設問に将来の数が書かれていたら、それは必ず選択の根拠です。

Q4オンラインゲームのバックエンドを東京と米国の2リージョンで運用している。通信はUDPを使用し、企業ネットワークからも接続されるため、クライアント側のファイアウォールに登録できる固定のIPアドレスが必要である。またリージョン障害時には自動的にもう一方へ切り替わってほしい。適切なサービスはどれか。
  • A. CloudFront ディストリビューションを作成し、2つのオリジンをオリジングループに設定する
  • B. Route 53 のレイテンシールーティングとヘルスチェックを組み合わせる
  • C. AWS Global Accelerator を作成し、両リージョンのNLBをエンドポイントとして登録する
  • D. 各リージョンにElastic IPを割り当てたNLBを置き、クライアント側で切り替える

正解: C

Global Accelerator は2つの固定Anycast IPを提供し、任意のTCP/UDPを扱い、ヘルスチェックに基づいて健全なリージョンへ短時間で切り替えます。3つの要件すべてに一致します。

判断軸: AはCloudFrontがHTTP/HTTPS専用でUDPを扱えません。Bは切り替え自体はできますが、DNSベースなのでクライアント側のTTLに依存して遅く、返すIPも固定になりません。Dは自動切り替えの要件を満たしません。「UDP」「固定IP」のどちらか1語でもあればGlobal Acceleratorと反射で結び付けてください。

Q5S3に置いた静的サイトをCloudFrontで配信している。セキュリティ監査で「利用者がS3のURLを直接指定してオブジェクトを取得できる状態を解消せよ」と指摘された。オブジェクトはSSE-KMSで暗号化されている。適切な対応はどれか。
  • A. S3バケットポリシーで aws:SourceIp に CloudFront のIPレンジを指定する
  • B. オリジンアクセスアイデンティティ（OAI）を作成し、バケットポリシーで OAI からのみ許可する
  • C. オリジンアクセスコントロール（OAC）を設定し、ブロックパブリックアクセスを有効にしたうえでバケットポリシーで当該ディストリビューションからのみ許可する
  • D. バケットを別リージョンに移動し、CloudFront のオリジンを更新する

正解: C

OACはCloudFrontからのリクエストにSigV4署名を付け、バケットポリシー側でそのディストリビューションだけを許可できます。パブリックアクセスをブロックしたままにできるので、直接アクセスは完全に塞がります。

判断軸: Bも同じ目的の旧機能ですが、OAIはSSE-KMSで暗号化されたオブジェクトに対応していません。設問がわざわざ「SSE-KMS」と書いているのは、そこでOAIを落とすためです。Aは管理すべきIPレンジが変動し続け、パブリックアクセス自体も残ります。一見どうでもよい条件（暗号化方式、プロトコル、将来の台数）が選択肢を1つに絞る鍵になっている――SAA全体に通じる読み方です。
