この講義の見取り図

これから出てくる6つの場面のうち、5つは ① ルートテーブルの話です。図の中の「ルートテーブル」の看板に注目して読んでください。残りの1つ（場面4）が、② と ③ の違いの話です。

03

場面1 ―― 「解析用 EC2 を立てたい。外から直接触られたくない」

  • 左の素朴な案が壊れる理由：Unit 42 がハニーポット（おとりのサーバー）を320台クラウドに置いた調査では、80% が24時間以内に侵害され、1週間で全台が侵害された。外とつながったサーバーは、公開した瞬間から世界中のボットにスキャンされる
  • 正解：プライベートサブネットに置く。関所で止める前に、そもそも道を作らないのが一番強い
  • ログインしたいとき：22番ポートを開けずに Session Manager を使う
試験ではこう出る

「パブリックサブネットの条件は?」→ ルートテーブルに IGW へのルートがある。「SSH を開けずに EC2 を管理したい」→ Session Manager。

04

場面2 ―― 「プライベートの EC2 から、パッチとライブラリを取りたい」

場面1で外から届かない場所に置いた結果、EC2 から外へも出られなくなりました。かといってパブリックに移すと場面1の左に逆戻りです。

NAT Gateway の落とし穴：AZ

  • NAT Gateway は止められない。置いているだけで時間料金がかかり、通ったデータ量にも課金される。削除しない限り請求が続く（明日のハンズオンで消し忘れ注意）
  • 古い選択肢として NAT インスタンス（EC2 で自作する NAT）が出ることがある。冗長化もパッチも自前なので、「運用負荷を下げたい」設問では選ばない
試験ではこう出る

「プライベートから外向きだけ通したい」→ NAT Gateway をパブリックサブネットに。「NAT の可用性を高めたい」→ AZ ごとに配置。

05

場面3 ―― 「S3 から毎晩大量に読むようにしたら、請求が跳ねた」

ゲートウェイ型インターフェース型（PrivateLink）
対象S3 と DynamoDB だけそれ以外の多くの AWS サービス
仕組みルートテーブルに道を足すサブネットに専用の窓口（プライベート IP）を置く
料金無料時間料金＋データ量
  • ルートテーブルは宛先がより具体的な行が優先される。だから「S3 の範囲」の行が 0.0.0.0/0 より先に効く
  • IAM とのつながり：バケットポリシーに aws:SourceVpce を付けると「このエンドポイント経由でしか読めないバケット」にできる。鍵が漏れても VPC の外からは読めない
試験ではこう出る

「NAT のコストを下げたい」「S3・DynamoDB へインターネットを経由させたくない」→ ゲートウェイ型エンドポイント。インターフェース型と並んでいたら、S3・DynamoDB なら無料のゲートウェイ型。

06

場面4 ―― 「つながらない。どこが悪い?」

SAA のネットワーク設問の多くはこの形です。原因の候補は毎回同じ場所にあるので、上から順に見ます。

01ルートテーブルに宛先への道があるかない → 届かない
02外とやり取りするならパブリック IP があるかない → 届かない
03ネットワークACLが行きと帰りの両方を許可しているか下の図の話。ここが最頻出片方なし → 片道で止まる
04宛先のセキュリティグループが許可しているかなし → 拒否
05OS とアプリが待ち受けているかはい → 到達
全部通過 → 通信が成立する
セキュリティグループネットワークACL
付く場所インスタンスサブネット
帰りの通信自動で通す（ステートフル）別途許可が必要（ステートレス）
書けるルール許可のみ許可と拒否
評価全ルールを見て、どれかが許可すれば通す番号の小さい順に見て、最初に一致したもので決まる
試験ではこう出る

「特定 IP を拒否したい」→ ネットワークACL（SG は拒否を書けない）。「行きは届くのに応答が返らない」→ ACL のエフェメラルポート。

07

場面5 ―― 「工場の検査装置のデータを、VPC に直接送りたい」

インターネット越しに HTTPS で送ると、帯域が日によって変わり、夜間バッチが朝までに終わらない日が出ます。生産系データをインターネットに出すこと自体が社内規定で通らないことも多い。工場と VPC の間に専用の道を引きます。

Site-to-Site VPNDirect Connect
開通までその日のうちに数週間〜数か月（回線工事）
性能インターネットの状況に左右される一貫している
暗号化標準で暗号化標準では暗号化されない
コスト安い高い
試験ではこう出る

「すぐに」「低コストで」→ VPN。「一貫したネットワーク性能」→ Direct Connect。「DX の冗長化を低コストで」→ VPN を予備に。「DX で暗号化も必要」→ DX の上に VPN を張る。

08

場面6 ―― 「別部署の VPC ともつなぎたい。部署は今後も増える」

2つの VPC を1対1でつなぐのが VPC ピアリングです。設定は簡単ですが、増えていくと破綻します。

  • もう一つの落とし穴：アドレス範囲（CIDR）が重なっている VPC 同士はピアリングできない。各部署が勝手に 10.0.0.0/16 で作っていると、後からつなげない
試験ではこう出る

「2つの VPC を低コストで」→ ピアリング。「多数の VPC」「推移的」「ハブ＆スポーク」→ Transit Gateway。

場面 → 答えの早見表

設問文にこの手がかりが出たら、この答えに寄せる。下の3行（Route 53・CloudFront・Global Accelerator）は、EC2 と S3 の講義で場面として扱います。

パブリックサブネットの条件→ルートテーブルに IGW へのルート
SSH を開けずに EC2 を管理したい→Session Manager
プライベートから外向きだけ通したい→NAT Gateway（パブリックサブネットに）
NAT の可用性を高めたい→AZ ごとに NAT Gateway
NAT のコストを下げたい（S3・DynamoDB）→ゲートウェイ型エンドポイント
他の AWS サービスへ閉域で→インターフェース型エンドポイント
特定 IP を拒否したい→ネットワークACL
行きは届くのに応答が返らない→ACL のエフェメラルポート
オンプレと、すぐに・安く→Site-to-Site VPN
オンプレと、一貫した性能で→Direct Connect
Direct Connect の冗長を低コストで→VPN をバックアップに
多数の VPC をつなぐ／推移させたい→Transit Gateway
DNS で障害時に切り替えたい→Route 53 フェイルオーバールーティング
静的コンテンツを世界に速く配信→CloudFront
固定 IP で、TCP/UDP を世界から速く→Global Accelerator
10

確認問題

先に自分の答えを決めてから開いてください。

Q1あるサブネットを「パブリックサブネット」にしているものは何か。
  • A. サブネット作成時に「パブリック」を選んだこと
  • B. サブネットのルートテーブルに、インターネットゲートウェイへのルートがあること
  • C. サブネットの CIDR にグローバル IP アドレスを使っていること
  • D. サブネット内のセキュリティグループが 0.0.0.0/0 を許可していること

正解: B

サブネットに「パブリック／プライベート」というスイッチはありません。ルートテーブルに IGW への道があるかどうかだけで決まります。

判断軸: D はもっともらしい誤答です。セキュリティグループは「入ってよいか」の関所で、道そのものを作るわけではありません。道がなければ、関所を開けても届かない。

Q23つの AZ にプライベートサブネットがあり、どれも AZ-a の NAT Gateway を経由して外へ出ている。可用性を高めるための最も適切な変更はどれか。
  • A. AZ-a の NAT Gateway のサイズを大きくする
  • B. 各 AZ に NAT Gateway を置き、各 AZ のルートテーブルを同じ AZ の NAT Gateway に向ける
  • C. NAT Gateway を NAT インスタンスに置き換える
  • D. プライベートサブネットを1つの AZ にまとめる

正解: B

NAT Gateway は AZ の中に作られます。1か所に集約すると、その AZ の障害で全 AZ の外向き通信が止まります。

判断軸: C は可用性を自分で作り込む必要があり、運用負荷が上がります。D は可用性を下げる方向です。「AZ をまたいで冗長化」の設問では、部品を AZ ごとに置くのが基本形です。

Q3プライベートサブネットの EC2 が S3 から大量のデータを読み、NAT Gateway のデータ処理料金が高額になっている。最もコスト効率の良い対策はどれか。
  • A. NAT Gateway を NAT インスタンスに置き換える
  • B. S3 用のゲートウェイ型 VPC エンドポイントを作成する
  • C. S3 用のインターフェース型 VPC エンドポイントを作成する
  • D. EC2 をパブリックサブネットに移す

正解: B

ゲートウェイ型は S3 と DynamoDB 専用で無料です。S3 宛ての通信が NAT を通らなくなり、処理料金が消えます。

判断軸: C でも NAT は回避できますが、時間料金とデータ量の料金がかかります。「最もコスト効率が良い」なら B。D はコストは下がってもセキュリティを犠牲にしているので、SAA では選びません。

Q4Web サーバーのサブネットのネットワークACLで、インバウンドとアウトバウンドの両方に TCP 443 の許可を入れた。セキュリティグループも 443 を許可している。しかしブラウザから接続すると応答が返らない。最も可能性が高い原因はどれか。
  • A. セキュリティグループのアウトバウンドに 443 の許可がない
  • B. ネットワークACLのアウトバウンドで、エフェメラルポート（1024〜65535）を許可していない
  • C. ネットワークACLはステートフルなので、原因は別にある
  • D. ルートテーブルに IGW へのルートがない

正解: B

サーバーの応答は、ブラウザ側が一時的に開いたポート宛てに送られます。ACL はステートレスなので、帰り道を明示的に許可しない限り通りません。

判断軸: A は誤り。セキュリティグループはステートフルで、帰りは自動で通ります。C は性質が逆です。「行きは届く、帰りが来ない」はステートレスな ACL を疑うのが定石です。

Q5VPC-A と VPC-B、VPC-B と VPC-C をそれぞれピアリングした。VPC-A から VPC-C のサーバーに接続できない。今後も VPC が増える前提で、最も適切な対策はどれか。
  • A. VPC-A のルートテーブルに、VPC-C 宛てで VPC-B 向けピアリングを指すルートを追加する
  • B. Transit Gateway を作成し、すべての VPC をそこに接続する
  • C. VPC-C のセキュリティグループで VPC-A の CIDR を許可する
  • D. VPC-A と VPC-C の CIDR を同じにする

正解: B

ピアリングは推移しないため、B を経由して A から C へは通れません。A-C 間を直接ピアリングする方法もありますが、「今後も増える」なら Transit Gateway に集約するのが適切です。

判断軸: A はルートを書いても B が中継しないので通りません。D は逆で、CIDR が重なるとピアリング自体ができなくなります。「多数」「今後増える」「推移的」は Transit Gateway の合図です。

今日の宿題

20分で、ここまでやってください。

6つの場面を、資料を閉じて書き出す「どんな依頼で、答えは何だったか」を6行。書けたら、チャットに貼ってもらえれば私が notes/ に清書します
書けなかった場面だけ、その節に戻る全部は読み返さない
「つながらない」の切り分け順を、何も見ずに言うルートテーブル → パブリックIP → ACL（行きと帰り）→ セキュリティグループ → OS
セキュリティグループとネットワークACLの違いを3つ言う帰りの扱い、拒否が書けるか、付く場所
終わったことを伝えるIssue のチェックと plan/log.md は私が更新します
明日のハンズオン（VPC をゼロから作る）

今日の場面1〜3を、手で組み立てます。VPC を作る → パブリックとプライベートのサブネットを作る → IGW を付けてパブリック側のルートテーブルに道を書く → NAT Gateway をパブリック側に置いてプライベート側のルートテーブルに道を書く → プライベートの EC2 から curl で外に出られることを確かめる。

最後に NAT Gateway を必ず削除してください。場面2で書いたとおり、止める機能はなく、削除しない限り時間料金がかかり続けます。Elastic IP も一緒に解放します。
