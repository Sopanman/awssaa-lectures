コスト最適化 ―― 課金はどこで発生しているか

出題比率20%のドメイン4は、実は独立した知識が少なく、これまでの各サービスの「安い側の選択肢」を集めたものです。ただしデータ転送料金だけは別で、ここを知らないと解けない設問が確実に出ます。課金がどこで発生するかを地図として持っておくのが今日の目的です。

01

この講義のゴール

ドメイン4は新しいサービスをほとんど覚えません。これまで学んだサービスそれぞれに「安い側の選択肢」があり、それをどういう条件で選ぶかを問われます。唯一の例外がデータ転送料金です。次の3つができていれば合格です。

  • 01
    データが動いたときに課金されるかどうかを即答できる。
    同一AZ内、AZ間、リージョン間、インターネット向き、NAT Gateway 経由――それぞれで誰が払うかを地図として持っている。
  • 02
    ワークロードの説明文から購入オプションを選べる。
    「常時稼働」「中断に耐えられる」「1年以上使う」「将来インスタンスを変えるかもしれない」という言葉と、オンデマンド／スポット／RI／Savings Plans が結びついている。
  • 03
    「コストを下げる」設問で、要件を壊す選択肢を弾ける。
    安いだけの答えと、要件を満たしたうえで安い答えを区別できる。
なぜ今この順番か

コスト最適化を最初に学ぶと、何を削っているのか分からないまま数字だけ覚えることになります。EC2、S3、VPC、RDS を一通り見た今だからこそ、「この構成のどこに課金メーターが回っているか」という見方ができます。逆に、この講義で分からない箇所はコストの理解不足ではなく、そのサービス自体の理解不足です。W1〜W5 に戻ってください。

02

コスト設問の2つの型

ドメイン4の設問は、ほぼ2つの言い回しに集約されます。どちらの型かを見分けることが、選択肢を絞る最初の一手です。

型1「最もコスト効率が高いのはどれか」

この型で最初にやることは設問文から要件を抜き出すことです。可用性、耐久性、レイテンシ、保持期間、復旧時間は必ず書いてあります。選択肢には、その要件を静かに落とすことで安くしているものが混ざっています。

たとえば「本番データベースの可用性を維持しながらコストを下げたい」という設問で「マルチAZ配置をシングルAZに変更する」という選択肢は、安いけれども要件を満たしていません。コスト最適化とは「安くすること」ではなく「要件を満たす構成のうち最も安いものを選ぶこと」です。

型2「運用負荷を上げずにコストを下げる」

こちらは運用負荷という第二の軸が加わった型です。「運用オーバーヘッドを最小限に」「管理を追加せずに」「最小の労力で」という表現が出てきたら、この型です。

この型では、自前でスクリプトを書く、cron で定期実行する、担当者が毎月レビューする――といった選択肢が並びます。コスト削減としては正しくても、運用負荷が増えるため不正解です。正解は AWS 側が自動でやってくれるマネージドな機能で、S3 のアクセスパターンが不明なときに「Intelligent-Tiering を有効にする」が選ばれるのはこの軸のためです。

罠になる選択肢の5パターン

誤答の作られ方には型があります。模試で間違えたときは、自分がどのパターンに引っかかったかを分類しておくと再発が減ります。

パターン選択肢の見え方見分け方
要件破りマルチAZをやめる、バックアップ保持期間を短くする、重要データを One Zone-IA に置く設問文の可用性・耐久性の要件と突き合わせる。設問に書いてある制約は絶対
運用負荷の付け替えLambda とスクリプトで自前の自動化を作る、定期的に手動でレビューする「運用負荷を上げずに」とあれば不正解。マネージド機能があるならそちらが優先
期間のミスマッチ3か月のプロジェクトに3年の RI、検証環境に長期コミットメント設問に書かれた利用期間とコミットメント期間を比べる
特性のミスマッチステートフルな本番DBをスポットインスタンスで動かす、即時取り出しが必要なデータを Glacier Deep Archive へそのサービスが前提とする使い方から外れていないか
隠れコストS3 へのアクセスを NAT Gateway 経由のままにする、少量の通信に Interface エンドポイントを大量に立てる時間料金とデータ処理料金が別に乗るものを知っているか。ここが今日の中心
最頻出の引っかけ

「コストを削減したい」とだけ見て最も安い選択肢を選ぶと外れます。設問文の前半には必ず「99.99%の可用性を維持しながら」「監査のため7年間保持する」といった条件が埋まっています。後半の「最もコスト効率が高いのは」だけを読んで選ぶのが、この分野の最大の失点源です。

03

購入オプションを選ぶ

EC2 の料金は、突き詰めれば「インスタンス時間 × 単価」です。購入オプションは、このうち単価を下げる手段です。使わない時間を減らすのは後の節で扱います。

4つの選択肢を1枚に並べる

設問はこの4つのどれを選ぶかを聞いてきます。割引率の大小ではなく何を差し出して割引を得ているかで覚えてください。

オプション差し出すもの割引の大きさ中断キャパシティ確保設問に出る言葉
オンデマンド何も差し出さない基準（割引なし）されない保証なし「予測できない」「短期」
スポット中断されない保証最大（オンデマンドの数分の一）される（通知あり）保証なし「中断に耐えられる」「ステートレス」「バッチ」
Reserved Instance1年または3年の利用コミット、および構成の固定大されないゾーン指定なら確保できる「常時稼働」「安定した使用量」
Savings Plans1年または3年の金額コミット大されない保証しない「柔軟性を保ちながら」「Fargate や Lambda も使う」

この表で大事なのは「差し出すもの」の列です。スポットは可用性を、RI と Savings Plans は期間の自由を差し出している。差し出せないものが設問に書いてあれば、その選択肢は消えます。

Reserved Instance の中身

RI は「このインスタンスを1年（または3年）使い続けます」と宣言して割引を得る仕組みです。物理的な予約ではなく、請求上の割引が稼働インスタンスに自動適用されます。軸は2つあります。

Standard RIConvertible RI
割引率大きいStandard より小さい
インスタンスファミリーの変更できないできる（同等以上の価値への交換）
OS・テナンシーの変更できないできる
途中での売却RI マーケットプレイスで売れる売れない
向く状況構成が固まっていて3年変えない世代交代やリファクタリングの可能性がある

支払い方法は3つあり、全額前払い → 一部前払い → 前払いなしの順に割引が大きくなります。「初期費用を抑えたい」なら前払いなし、「割引を最大化したい」なら全額前払いです。

もうひとつ、リージョン指定 RI とゾーン指定 RIの違いがあります。リージョン指定は AZ を固定せず、同一ファミリー内でサイズをまたいで割引が適用されます（Linux かつ共有テナンシーの場合）。ゾーン指定は AZ を固定する代わりにキャパシティの予約が付きます。「特定の AZ でキャパシティを確保したい」ならゾーン指定 RI か、独立した機能であるオンデマンドキャパシティ予約です。

よく混同されるところ

「Reserved」という語感から RI は常にキャパシティを予約すると思われがちですが、リージョン指定 RI は予約しません。純粋に請求上の割引です。Savings Plans もどちらの形でも予約しません。「キャパシティを保証したい」という要件は割引の話と切り離し、オンデマンドキャパシティ予約かゾーン指定 RI を選んでください。

Savings Plans の2種類

Savings Plans は「1時間あたりいくら使い続けます」という金額のコミットです。タイプではなく金額を約束するので RI より柔軟で、種類は2つあります。

Compute Savings PlansEC2 Instance Savings Plans
割引率Compute のほうが小さいこちらが大きい
インスタンスファミリー自由に変えられる指定したファミリーに固定
リージョンまたげる指定したリージョンに固定
インスタンスサイズ・OS・テナンシー自由自由
対象サービスEC2 に加えて Fargate と Lambda もカバーEC2 のみ
向く状況構成が変わる、サーバーレスへの移行を進めている使うファミリーとリージョンが決まっている

Compute は広く浅く、EC2 Instance は狭く深く。設問に「Fargate」「Lambda」が出てきたら Compute Savings Plans しか選べません。逆に「今後もこのファミリーを使い続ける」「リージョンは固定」なら、割引の大きい EC2 Instance Savings Plans が正解です。

判断軸

RI と Savings Plans のどちらかを選ばせる設問では、柔軟性を求める言葉が出ていれば Savings Plansです。Savings Plans は個々のインスタンスに紐づかず、最も割引額の大きいリソースへ自動で適用されるため、管理の手間も少なくて済みます。

ワークロードの言葉から逆引きする

  • 「24時間365日稼働、今後3年間は構成を変えない」 → Standard RI（3年・全額前払い）または EC2 Instance Savings Plans。
  • 「常時稼働だが、来年タイプを見直すかもしれない」 → Convertible RI または Compute Savings Plans。
  • 「夜間に走るバッチ、失敗しても翌朝やり直せる」 → スポット。
  • 「ベースラインは一定で、日中だけ増える」 → ベースライン分を RI か Savings Plans、増分をオンデマンドまたはスポットで賄う組み合わせ。この型はよく正解になります。
04

スポットに向くもの、向かないもの

スポットインスタンスは、AWS の余剰キャパシティを大幅な割引で使う仕組みです。余剰がなくなれば取り上げられる――この一点で向き不向きは判断できます。

中断はどう起きるか

キャパシティが必要になると AWS はインスタンスを回収します。このとき2分前に中断通知がインスタンスメタデータと EventBridge 経由で届き、アプリケーションはその間に状態を保存し、ロードバランサーから外れ、ジョブをキューへ戻します。さらに早い段階で中断の可能性を知らせるキャパシティ再調整の推奨もあり、Auto Scaling グループと組み合わせれば先回りして代替を立ち上げられます。

向く向かない
ステートレスな Web/API のスケールアウト分ステートフルなデータベース、プライマリノード
バッチ処理、ETL、データ変換中断すると最初からやり直しになる長時間処理
CI/CD のビルドエージェントライセンスがホストに固定された商用ソフトウェア
EMR のタスクノード、コンテナのワーカーEMR のマスターノード、コアノード
動画エンコード、シミュレーション、レンダリング締め切りが厳格でやり直す時間がない処理

中断への備え

  1. チェックポイント。途中経過を定期的に S3 や EFS に書き出し、再開できるようにします。「長時間のバッチをスポットで動かしたい」の正解はたいていこれです。
  2. キューで作業単位を管理する。SQS に作業を入れ、可視性タイムアウトで、完了しなかった作業が自動的に別のインスタンスへ渡るようにします。中断を検知しなくても処理が失われません。
  3. 容量プールを分散する。スポットの空きはインスタンスタイプと AZ の組み合わせ（容量プール）ごとに独立しています。複数のタイプと複数の AZ を指定するほど同時に枯れる確率が下がる――これが Spot Fleet や EC2 Fleet、混在インスタンスポリシーの核心です。
  4. 割り当て戦略をキャパシティ最適化にする。最安値優先（lowest-price）は単価の安いプールを選びますが、そこは枯渇しやすい。キャパシティ最適化（capacity-optimized）は空きの多いプールを選ぶため中断されにくく、「中断を最小化したい」という設問ではこちらです。
  5. オンデマンドと混ぜる。Auto Scaling グループでは「ベース台数はオンデマンド、超過分の何%をスポット」と指定できます。最低限の可用性を確保しつつスケールアウト分だけ安くする定番です。
最頻出の引っかけ

「コストを最小化したい」とだけ見るとスポットが正解に見えます。しかし「ミッションクリティカル」「中断できない」「常に稼働している必要がある」があれば即座に消えます。逆に「フォールトトレラント」「中断に耐えられる」「時間に余裕がある」は、出題者がスポットを選ばせるために置いたサインです。

コンテナの場合

ECS と EKS では Fargate Spot が使えます。サーバーを管理せずスポットの割引を得る選択肢で、「運用負荷を上げずにコンテナのコストを下げたい」の正解です。中断される性質は同じです。

05

データ転送料金の地図

この節が今日の中心です。データ転送料金は他のサービスの知識からは導けない独立した知識で、「なぜこの構成のほうが安いのか」という形で必ず問われます。一度地図にしてしまえば、あとは当てはめるだけです。

まず4つの境界を覚える

データがどこを越えたかで課金が決まります。境界は内側から「同一 AZ」「AZ 間」「リージョン間」「インターネット」の4つです。

原則を言葉で確認する

データの動き課金設問での意味
インターネットから AWS へ（インバウンド）原則無料取り込みは安く、出すのが高い。移行時の転送コストを心配する選択肢は的外れ
AWS からインターネットへ（アウトバウンド）課金コスト削減設問の主戦場。CloudFront やキャッシュで削る
同一 AZ 内、プライベート IP での通信無料同じ AZ に寄せると安い。ただし可用性とのトレードオフになる
同一 AZ 内でも、パブリック IP や Elastic IP 経由課金同じ VPC にいるのに公開エンドポイント名で呼ぶ構成ミスが設問になる
AZ をまたぐ通信（同一リージョン）課金。しかも送信側・受信側の双方向マルチ AZ 構成のコストはここに出る。可用性のために払う費用
リージョンをまたぐ通信課金（送信元リージョン側）クロスリージョンレプリケーション、DR 構成のコスト
同一リージョンの AWS サービス間（S3 から EC2 など）同一 AZ なら無料同じリージョンに置くのはレイテンシだけでなくコストの理由もある
AWS のオリジンから CloudFront へ無料オリジン側の転送料金がなくなり、配信は CloudFront の料金体系になる

「インバウンド無料、アウトバウンド課金」――この非対称性がすべての出発点です。だから「オンプレミスから数十テラバイトを移行する」設問で転送コストを心配する選択肢は的外れになり、「解析結果を社外に大量配信する」設問ではコストが論点になります。

CloudFront を挟むと何が安くなるか

CloudFront を前に置くと、コストの構造が2か所で変わります。第一に、オリジン（S3 や EC2、ALB）から CloudFront への転送は無料です。第二に、エンドユーザーへの配信は CloudFront の料金体系になり、直接インターネットに出す場合より単価が低く設定されています。キャッシュが効けばオリジンへのリクエスト自体も減ります。「静的コンテンツを世界中に配信していて転送コストが高い」という設問の答えは、ほぼ確実に CloudFront です。

NAT Gateway ―― この講義でいちばん出るところ

NAT Gateway には起動時間に対する料金と通過データ量に対する処理料金の2つがかかります。重要なのは、処理料金がアウトバウンド転送料金とは別に上乗せでかかることです。外に出るデータは二重取りになります。

また、AZ ごとに NAT Gateway を置くのが可用性の定石ですが、時間料金は AZ の数だけ増えます。1つにまとめれば他の AZ からの通信が AZ 間転送料金を生みます。冗長性を取るか、時間料金を取るかのトレードオフです。

最頻出の引っかけ

「プライベートサブネットの EC2 が S3 に大量のデータを書き込んでいる。NAT Gateway のコストが想定以上に高い。運用負荷を増やさずにコストを下げる方法は？」――答えは S3 用の Gateway エンドポイントを作成し、ルートテーブルを向けることです。追加料金がなく、S3 への通信が NAT Gateway を通らなくなるため処理料金も転送料金も消えます。形を変えて何度も出ます。

誤答としてよく並ぶのは「NAT インスタンスに置き換える」（運用負荷が増え可用性も落ちる）、「VPC ピアリングを設定する」（S3 は対象外）、「Interface エンドポイントを作る」（S3 でも使えるが時間料金と処理料金がかかる）です。

VPC エンドポイントの2種類

Gateway エンドポイントInterface エンドポイント（PrivateLink）
対象サービスS3 と DynamoDB のみ多数の AWS サービス、および他社・自社の公開サービス
実体ルートテーブルのエントリサブネット内の ENI（プライベート IP を持つ）
料金追加料金なしAZ ごとの時間料金 ＋ 処理データ量あたりの料金
オンプレミスから利用できないできる（Direct Connect / VPN 経由）
コスト設問での位置S3・DynamoDB の NAT 迂回はこれ一択他サービスで NAT を避けたいとき。通信量が少ないと割高になる
判断軸

S3 か DynamoDB が相手なら Gateway エンドポイント、それ以外なら Interface エンドポイント。ただしオンプレミスから VPC 経由で S3 に届かせたい場合は Gateway エンドポイントが使えず、Interface エンドポイントが正解です。「オンプレミス」の一語で答えが変わります。

その他、転送料金が論点になる構成

  • VPC ピアリング。接続そのものに時間料金はなく、通過データに通常の AZ 間・リージョン間の転送料金が適用されます（同一 AZ 内なら無料）。
  • Direct Connect。ポートの時間料金がかかる一方、アウトバウンドの転送単価はインターネット経由より低く設定されています。「オンプレミスとの継続的な大量転送」ではコストの理由でも正解になります。
06

ストレージのコストを削る

ストレージのコスト削減は「置き場所を変える」「使っていないものを消す」の2つです。設問では前者が圧倒的に多く、S3 のストレージクラス選択が本丸です。

S3 のストレージクラスをどう選ぶか

ストレージクラスは保管料金と取り出しコスト（料金と時間）のトレードオフです。保管が安いほど取り出しに料金と時間がかかります。設問が与えてくるのは「アクセス頻度」「取り出しにどれだけ待てるか」「その AZ が落ちたら困るか」の3点です。

クラス選ぶ条件注意点
S3 Standard頻繁にアクセスする。パターンが分かっていて高頻度取り出し料金なし。保管が最も高い
Intelligent-Tieringアクセスパターンが分からない、あるいは変わるオブジェクトごとのモニタリング料金がかかる。取り出し料金はかからない
Standard-IAアクセスは少ないが、必要なときは即座に取り出す最低保管期間 30 日、取り出し料金あり、最小課金オブジェクトサイズあり
One Zone-IAアクセスは少なく、失われても再生成できるデータ単一 AZ。AZ 障害でデータが失われる。本番の唯一のコピーには使わない
Glacier Instant Retrievalたまにしかアクセスしないが、必要なときはミリ秒で取り出す最低保管期間 90 日
Glacier Flexible Retrieval年に数回、数分から数時間待てる最低保管期間 90 日。取り出しには時間がかかる
Glacier Deep Archive法令対応のアーカイブ。年に一度あるかどうか、取り出しに半日待てる最低保管期間 180 日。最安だが最も待つ
Intelligent-Tiering が正解になる条件

Intelligent-Tiering はアクセスパターンが不明または変動するときに選びます。設問に「30日後にアクセスされなくなる」と書いてあれば、ライフサイクルで Standard-IA に移すほうが安く、Intelligent-Tiering は不正解です。判断の言葉は「予測できない」「変化する」。明確な日数が書いてあればライフサイクルです。

ライフサイクルルールと、消し忘れの回収

ライフサイクルには移行（transition）と失効（expiration）の2つのアクションがあります。「保持期間を過ぎたら削除」なら失効、「古くなったら安いクラスへ」なら移行です。

もうひとつ設問に出るのが不完全なマルチパートアップロードの削除です。分割アップロードの途中で失敗すると断片が残って課金され続け、しかもオブジェクト一覧には現れません。ライフサイクルルールで一定日数後に中止・削除するのが定石です。

コストの穴を塞ぐライフサイクル設定の骨格
{
  "Rules": [
    {
      "ID": "archive-then-expire",
      "Status": "Enabled",
      "Filter": { "Prefix": "logs/" },
      "Transitions": [
        { "Days": 30,  "StorageClass": "STANDARD_IA" },
        { "Days": 180, "StorageClass": "DEEP_ARCHIVE" }
      ],
      "Expiration": { "Days": 2555 }        // 7年で削除
    },
    {
      "ID": "abort-incomplete-uploads",   // これを入れていない環境が多い
      "Status": "Enabled",
      "Filter": {},
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
    }
  ]
}

バージョニングを有効にしたバケットでは古いバージョンも課金対象です。削除したつもりのオブジェクトが非現行バージョンとして残るため、非現行バージョンの移行と失効もルールに入れます。「オブジェクト数は増えていないのに S3 のコストが増え続ける」という設問の答えは、バージョニングか不完全なマルチパートアップロードです。

どこに何があるか分からないとき

「まずコストの内訳を可視化したい」段階では、S3 Storage Lens（バケット横断の利用状況と推奨）や S3 Storage Class Analysis（アクセスパターンから移行日数を提案）が答えです。

EBS ―― ボリュームとスナップショット

  • gp2 から gp3 へ。gp3 は同容量で gp2 より安く、IOPS とスループットを容量と切り離して設定できます。「性能を維持したままコストを下げる」という EBS の設問では、まずこれを疑ってください。
  • ボリュームタイプの選択。高い IOPS が要る場合のみ io1/io2、大容量のシーケンシャルアクセスなら st1、めったに読まないなら sc1。過剰な io2 は削減余地の典型です。
  • スナップショットは増分。2回目以降は変更ブロックのみ課金されますが、世代が溜まれば増えます。Data Lifecycle Manager で作成と世代削除を自動化するのが、運用負荷を上げずに削る答えです。長期保管分はアーカイブ階層へ移せます（最低保管期間あり）。
  • プロビジョニングしたぶんだけ課金される。EBS は使用量ではなく確保した容量に課金されます。100 GiB のボリュームに 10 GiB しか入っていなくても 100 GiB 分です。

使っていないのに課金されているもの

コスト設問の地味な定番です。Trusted Advisor で洗い出される代表格を挙げます。

  • どこにも関連付けられていない Elastic IP。実行中のインスタンスに紐づかない Elastic IP は課金されます。加えて現在はパブリック IPv4 アドレス自体に時間料金がかかります。
  • アタッチされていない EBS ボリューム。インスタンスを終了しても、終了時削除の設定によってはボリュームが残ります。残れば課金され続けます。
  • 停止したままのインスタンスのボリューム。停止すればコンピューティング料金は止まりますが、EBS の料金は止まりません。「停止しているのに課金される」の答えはこれです。
  • 使われていないロードバランサー、古いスナップショット、放置されたテスト用 RDS。いずれも時間課金です。
07

コンピューティングのコストを削る

単価を下げるのが購入オプションでした。この節は使う量そのものを減らす話です。設問が「購入オプション」と「サイジング・スケジューリング」のどちらを問うているかを見分けてください。

適切なサイジング

過剰なインスタンスサイズは、最も見つけやすく最も大きい削減余地です。根拠は実測値で、CPU 使用率が数%のまま推移しているインスタンスは1〜2段階小さくできます。ここで出てくるのが AWS Compute Optimizer です。CloudWatch のメトリクスを分析し、EC2・Auto Scaling グループ・EBS・Lambda・Fargate 上の ECS について最適なサイズを推奨します。Trusted Advisor も低使用率のインスタンスを指摘しますが、具体的な推奨サイズまで出すのは Compute Optimizer という切り分けです。

メモリ使用率は既定では見えない

EC2 の CloudWatch 標準メトリクスにメモリ使用率は含まれません。メモリを根拠にサイジングするには CloudWatch エージェントが必要です。設問にエージェントの選択肢があれば、それが正解の一部です。

Graviton への移行

AWS 自社設計の Arm ベースプロセッサである Graviton は、同等の x86 インスタンスより価格性能比が高いという位置づけで、EC2 のほか RDS、ElastiCache、OpenSearch、Lambda、Fargate でも選べます。

判断軸はアーキテクチャを変えられるかどうかです。Java、Python、Node.js、Go やコンテナ化されたアプリなら移行は容易で、コスト削減の正解になります。逆に x86 バイナリに依存する商用ソフトでは選べません。設問に「再コンパイルできる」「コンテナ化されている」とあれば、Graviton が狙われているサインです。

Auto Scaling と停止スケジュール

そもそも動いていなければ課金されません。これが最も確実な削減です。

  1. 需要に追随させる。ターゲット追跡ポリシーで必要な台数だけ動かします。ピークに合わせて台数を固定した構成は、削減余地そのものです。
  2. スケジュールで増減させる。負荷の波が時間帯で決まっているならスケジュールされたアクションで台数を変えます。予測が可能なら予測スケーリングも選択肢です。
  3. 開発・検証環境を夜間と週末に止める。平日の日中しか使わない環境を24時間動かす理由はありません。Auto Scaling グループなら希望容量をゼロにするスケジュール、単体なら EventBridge Scheduler から停止・起動を呼ぶのが定石です。設問では「開発環境のコストが本番と同程度」という形で出ます。
  4. スケールインを恐れない。スケールアウトだけ設定した構成は、事実上ピーク固定です。
停止と終了の違いを踏まえる

停止（stop）でコンピューティング料金は止まりますが、EBS とアタッチされた Elastic IP の料金は続きます。ゼロにするには終了（terminate）が必要で、その場合は再構築が要ります。「夜間停止」の削減効果は EBS の分だけ目減りする――ここまで読めていると選択肢を比較できます。

Lambda のメモリ設定とコストの関係

Lambda の料金はリクエスト数と実行時間 × 割り当てメモリ量（GB 秒）で決まります。ここで直感に反するのは、メモリ割り当てを増やすと比例して CPU 性能も上がる点です。CPU を使う処理ではメモリを増やすと実行時間が縮み、単価は上がっても総コストが下がる場合があります。メモリを最小にするのが常に最安、という思い込みは誤りです。

設問で「Lambda の実行時間が長くコストが高い」と来たら、メモリ設定の見直しが候補です。最適点は関数ごとに違うため実測して決めます。加えて Arm（Graviton）を選べば同じ処理をより安く実行できます。

引っかけ

プロビジョニングされた同時実行はコールドスタート対策であって、コスト削減策ではありません。待機分にも課金されるためむしろコストは上がります。「コストを下げたい」で選ぶと誤答、「コールドスタートのレイテンシを解消したい」なら正解――目的によって正解にも誤答にもなる典型です。

そもそも EC2 でなくてよいか

断続的にしか動かないバッチを常時起動の EC2 で回しているなら、Lambda や Fargate、AWS Batch に移せばアイドル時間の課金が消えます。目安は稼働率――ほぼ常時なら EC2 とコミットメント、たまにしか使わないならサーバーレスです。

08

コスト管理ツールの役割分担

名前が似ていて混同しやすい領域です。過去を見るのか、未来を止めるのか、詳細を掘るのか、異常を検知するのか、改善案を出すのか――この5つの動詞で切り分ければ、設問はほぼ一発で解けます。

ツール何をするか設問に出る言葉選ばない場面
Cost Explorer過去の利用実績を可視化・分析し、将来を予測する。RI / Savings Plans の購入推奨も出す「傾向を分析したい」「どのサービスにいくらかかっているか見たい」「購入すべき量を知りたい」リソース単位の明細が必要なとき
AWS Budgets予算のしきい値を決め、超過や超過予測を通知する。アクションで自動制御もできる「上限を決めて通知したい」「予算超過を防ぎたい」分析そのものが目的のとき
Cost and Usage Report最も詳細な明細を S3 に出力する。Athena や QuickSight で自由に分析「時間単位」「リソース単位」「独自の集計」「社内の請求システムに取り込む」「手早く見たい」だけのとき（負荷が高い）
Cost Anomaly Detection機械学習で通常と異なる支出パターンを検知して通知する「想定外の請求に気づきたい」「異常な増加を検知」「しきい値を決めずに」決まった上限を守らせたいとき（それは Budgets）
Compute Optimizerメトリクスを分析し、EC2・ASG・EBS・Lambda の適切なサイズを推奨する「オーバープロビジョニングを見つけたい」「推奨サイズが欲しい」コストの内訳を見たいとき
Trusted Advisorコスト・セキュリティ・信頼性など複数の観点でベストプラクティス違反をチェックする「使われていないリソースを洗い出す」「幅広く点検したい」詳細な推奨サイズが必要なとき

いちばん迷う組み合わせ

  • Budgets と Cost Anomaly Detection。Budgets は自分で決めたしきい値の超過を通知し、Anomaly Detection はしきい値なしで普段と違う動きを検知します。金額が書いてあれば Budgets、「想定外の」「異常な」とあれば Anomaly Detection です。
  • Cost Explorer と Cost and Usage Report。前者はコンソールでグラフを見る道具、後者は生データを吐き出す道具です。「リソース単位」「Athena で分析」とあれば CUR です。
設計前に見積もる

まだ何も動かしていない段階――「移行前に費用を試算したい」――では AWS Pricing Calculator が答えです。Cost Explorer は実績がないと使えません。

タグによるコスト配分

「どの部署が、どのプロジェクトがいくら使っているか」を知りたいという要件は頻出です。答えはコスト配分タグです。

タグには AWS が自動で付ける生成タグ（aws: で始まる）と、利用者が付けるユーザー定義タグがあります。どちらも請求コンソールでコスト配分タグとして有効化しないと、Cost Explorer や請求レポートで内訳に使えません。ここが設問になります。

タグは遡及しない

コスト配分タグを有効化しても、有効化より前の期間には適用されません。「先月分の部署別内訳を今すぐ出したい」という設問で、今からタグを有効化する選択肢は解決になりません。タグ付けは事前に、組織的に強制する――そのために Organizations のタグポリシーや、必須タグがなければ作成させない SCP を併用します。

Organizations の一括請求

Organizations で複数アカウントをまとめると、請求は管理アカウントに集約されます。支払いの手間の話にとどまらず、コスト上の実利が2つあります。

  1. ボリューム割引の合算。使用量に応じて単価が下がる従量段階（S3 のストレージやデータ転送など）は、組織全体の使用量を合算して判定されます。アカウントを分けていても、割引の観点では1つの利用者として扱われます。
  2. Reserved Instance と Savings Plans の共有。あるアカウントで購入した RI / Savings Plans の未使用分が、組織内の他のアカウントに自動で適用されます。環境別・チーム別に分割していてもコミットメントを使い切れます。共有はアカウント単位でオフにもできます。

設問での見分け方は「複数アカウント」＋「コスト」の組み合わせです。この2語が並んだら、一括請求によるボリューム割引と RI/SP 共有を思い出してください。「部門ごとに請求を切りたい」なら、アカウントを分割したうえで一括請求とコスト配分タグで内訳を出すのが標準的な答えです。

09

Well-Architected Framework の6つの柱

最後に、SAA 全体を貫く観点を置いておきます。Well-Architected Framework は、AWS が「良い設計とは何か」を6つの視点に分解したものです。試験は、この6つのうちどれを優先するかを選ばせる形で作られています。コスト最適化は、そのひとつにすぎません。

柱問うていること
運用上の優秀性
Operational Excellence		手作業を自動化し、小さく変更し、監視して改善できるか。「運用負荷を上げずに」という設問文は、この柱の言い換えです。
セキュリティ
Security		データと資産を守れているか。最小権限、多層防御、保管時と転送時の暗号化、追跡可能性。W1 の IAM がここに入ります。
信頼性
Reliability		障害から回復し、需要の変化に応えられるか。単一障害点の排除、マルチ AZ、自動復旧、RTO / RPO。
パフォーマンス効率
Performance Efficiency		要求される性能を無駄のない資源で満たせているか。適切なサービスの選択、キャッシュ、需要に合わせた調整。
コスト最適化
Cost Optimization		不要な支出をなくし、支出の所在を把握できているか。今日の講義がまるごとこの柱です。
持続可能性
Sustainability		環境負荷を減らせているか。使用リソースの最小化、効率の高いハードウェア（Graviton など）の活用、不要データの削除。後から追加された6番目の柱です。

重要なのはこれらがしばしば互いに衝突することです。マルチ AZ は信頼性を上げますが AZ 間転送料金でコストは上がり、スポットはコストを下げますが信頼性を落とします。Well-Architected Framework は「全部を最大化せよ」ではなく、要件に応じてどれを優先するかを意識的に選べと言っています。

試験での使い方

SAA の設問は、設問文が優先する柱を必ず名指ししています。「可用性を維持しながら」なら信頼性、「レイテンシを最小化」ならパフォーマンス効率、「運用負荷を最小限に」なら運用上の優秀性、「最もコスト効率が高い」ならコスト最適化。複数並ぶ場合は制約として書かれているほうが上位です。「可用性を維持しながらコストを削減する」なら、可用性は満たすべき制約、コストは最小化すべき目的。この読み分けが全分野で効きます。

設問文にこの手がかりが出たら、この答えに寄せる――という対応表です。コスト分野は選択肢の言い換えが多く、この対応が入っているかどうかで解答速度が変わります。

この表は暗記するものではなく、模試で間違えたときに戻ってくる場所です。誤答の原因が「対応を知らなかった」なら覚え直す、「知っていたが設問文の制約を読み落とした」なら読み方の問題――と切り分けてください。コスト分野は後者が多いはずです。

11

確認問題

先に自分で答えを決めてから開いてください。この分野は「なんとなく安そう」で選ぶ癖がつきやすいので、選んだ理由を一文で言えるか確かめてから開くこと。

Q1プライベートサブネットの複数の EC2 が、同一リージョンの S3 バケットへ日次で数テラバイトのログを書き込んでいる。請求を見ると NAT Gateway の費用が大半を占めていた。運用負荷を増やさずにコストを削減する方法はどれか。
  • A. NAT Gateway を NAT インスタンスに置き換える
  • B. S3 用の Gateway エンドポイントを作成し、ルートテーブルに追加する
  • C. EC2 インスタンスをパブリックサブネットに移動し、パブリック IP を割り当てる
  • D. VPC ピアリング接続を S3 との間に設定する

正解: B

Gateway エンドポイントには追加料金がありません。S3 宛ての通信が NAT Gateway を通らなくなるため、処理データ量料金が消えます。設定はルートテーブルの変更だけです。

判断軸: A は自前で管理するインスタンスが増えて運用負荷が上がり、可用性も落ちます。C はセキュリティ要件を壊します。D は S3 がピアリングの対象ではありません。相手が S3 か DynamoDB なら Gateway エンドポイント――反射で出るようにしてください。

Q2ある企業は、今後3年間サイズを変えずに稼働させる基幹システムを EC2 で運用している。同時にコンテナ化を進めており、一部を Fargate へ移す計画がある。移行後もコミットメントの割引を無駄にしたくない。最も適した購入オプションはどれか。
  • A. 3年の Standard Reserved Instance を購入する
  • B. 3年の EC2 Instance Savings Plans を購入する
  • C. 3年の Compute Savings Plans を購入する
  • D. スポットインスタンスに移行する

正解: C

Compute Savings Plans は EC2 に加えて Fargate と Lambda もカバーします。EC2 から Fargate へワークロードが移っても、コミットした金額分の割引が自動的に適用先を移します。

判断軸: A と B は割引率では有利ですが EC2 のみが対象です。Fargate や Lambda という単語が出た時点で、選べるのは Compute Savings Plans だけ。D は基幹システムに中断のリスクを持ち込みます。「割引率が最大のもの」ではなく「要件を満たすもののうち割引が大きいもの」という順序を守ってください。

Q3データ分析チームが新しい S3 バケットにデータを蓄積し始めた。当初は頻繁に参照されるが、その後どの程度参照されるかは読めず、データセットごとにも差がある。取り出し料金は避けたい。運用負荷を最小限にストレージコストを最適化する方法はどれか。
  • A. すべてのオブジェクトを S3 Standard-IA に保存する
  • B. S3 Intelligent-Tiering を使用する
  • C. 30日後に S3 One Zone-IA へ移行するライフサイクルルールを設定する
  • D. アクセスログを Athena で毎月分析し、結果に基づいて手動でストレージクラスを変更する

正解: B

アクセスパターンが予測できず、データセットごとにも異なるという条件は Intelligent-Tiering のためにある設問文です。自動で階層が切り替わり、取り出し料金がかからない点も要件に合致します。

判断軸: A は当初の頻繁なアクセスで取り出し料金が膨らみます。C は日数が根拠のない決め打ちで、One Zone-IA は単一 AZ のため元データには適しません。D は毎月の手作業が発生し「運用負荷を最小限に」に反します。「予測できない」は Intelligent-Tiering、「◯日後と分かっている」はライフサイクルです。

Q4ある部門から「先月の請求が突然増えたが原因が分からない。今後は想定外の増加にすぐ気づきたい。ただし、どの金額を超えたら異常なのかは自分たちでも決められない」と相談を受けた。最も適した方法はどれか。
  • A. AWS Budgets で月次のコスト予算を作成し、80%超過時に通知する
  • B. AWS Cost Anomaly Detection でモニターを作成し、検知時に通知する
  • C. Cost and Usage Report を S3 に出力し、Athena で毎日集計するクエリを実行する
  • D. Cost Explorer を毎朝開いて前日との差分を確認する運用を定める

正解: B

Cost Anomaly Detection は過去の支出パターンを学習し、通常と異なる支出を検知して通知します。しきい値を人が決めなくてよい点が設問の条件に対応しています。

判断軸: A はしきい値を決められるという前提が要件と合いません。C は自前の集計を作る必要があり運用負荷が高い。D は自動化されておらず検知が遅れます。「しきい値を自分で決める → Budgets」「決められない → Cost Anomaly Detection」で覚えてください。

Q5Auto Scaling グループで動く EC2 の Web 層が AZ-a と AZ-c に分散しており、同一 VPC 内の別 AZ にある内部 API を、パブリック DNS 名で直接呼び出している。可用性要件を維持したままデータ転送コストを下げたい。最も効果があるのはどれか。
  • A. すべてのインスタンスを単一の AZ に集約する
  • B. 内部 API の呼び出しをプライベート IP（または内部 DNS 名）に変更する
  • C. 内部 API の前に CloudFront ディストリビューションを配置する
  • D. VPC ピアリング接続を追加する

正解: B

同一 VPC 内でもパブリック DNS 名を使うとトラフィックがパブリック IP 経由で扱われ、転送料金が発生します。プライベート IP（内部 DNS 名）に切り替えれば同一 AZ 内の通信は無料になり、可用性構成には一切手を触れません。

判断軸: A は AZ 間転送料金をなくせますが可用性要件を壊すため不正解――最初に疑うべき「要件破り」です。C は外部配信向けで内部通信には効きません。D は同一 VPC 内なのでピアリングの出番がありません。同一 VPC 内でパブリック名、という記述はコスト設問の仕込みです。
