場面1 ―― 「コストを下げてと言われた。いちばん安い選択肢を選べばいいのでは？」

この場面で初めて出る言葉
要件

制約と目的
制約は「〜を維持しながら」のように必ず守る条件。目的は「最も〜なのは」のように、その中で良くしたいもの
可用性
止まらずに使い続けられること（VPC 講義・EC2 講義で既出）。「マルチ AZ」は複数の AZ（アベイラビリティーゾーン：データセンターのまとまり）に分けて置き、1つが落ちても動き続ける構成
耐久性

AWS 側が面倒を見てくれること。自前でスクリプトを書く代わりに、設定を1つ有効にするだけで済む機能を指す

ドメイン4の設問は、ほぼ2つの言い回しに集約されます。どちらも「安いものを選ぶ」問題ではなく、「条件を満たすものの中から安いものを選ぶ」問題です。

型1「最もコスト効率が高いのはどれか」

最初にやることは、設問文から制約を抜き出すことです。可用性、耐久性、応答の速さ、保持期間、復旧までの時間は必ず書いてあります。選択肢には、その制約を静かに落とすことで安くしているものが混ざっています。図の上2つがそれです。

型2「運用負荷を上げずにコストを下げる」

こちらは運用負荷という2つ目の制約が加わった型です。「運用オーバーヘッドを最小限に」「管理を追加せずに」「最小の労力で」と書かれていたらこの型です。

この型では、自前でスクリプトを書く、cron（決まった時刻にプログラムを動かす仕組み）で定期実行する、担当者が毎月レビューする、といった選択肢が並びます。コスト削減としては正しくても、運用負荷が増えるので不正解です。正解は AWS 側が自動でやってくれるマネージドな機能です（例：S3 の Intelligent-Tiering → 場面6）。

誤答の作られ方は5通り

模試で間違えたときは、どのパターンに引っかかったかを分類しておくと再発が減ります。行き先の場面も書いておきます。

パターン選択肢の見え方見分け方
要件破りマルチ AZ をやめる、バックアップの保持期間を短くする、重要データを One Zone-IA（単一 AZ の S3 クラス、場面6）に置く設問文の可用性・耐久性の制約と突き合わせる。設問に書いてある制約は絶対
運用負荷の付け替えLambda とスクリプトで自前の自動化を作る、定期的に手動でレビューする「運用負荷を上げずに」とあれば不正解。マネージドな機能があるならそちらが優先
期間のミスマッチ3か月のプロジェクトに3年の予約、検証環境に長期の約束（場面2）設問に書かれた利用期間と、約束の期間を比べる
特性のミスマッチ本番データベースをスポットで動かす（場面3）、すぐ取り出すデータを Glacier Deep Archive へ（場面6）そのサービスが前提とする使い方から外れていないか
隠れコストS3 へのアクセスを NAT Gateway 経由のままにする、少量の通信にインターフェース型エンドポイントを大量に立てる（場面5）時間料金と処理料金が別に乗るものを知っているか。今日の中心
最頻出の引っかけ

「コストを削減したい」とだけ見て、最も安い選択肢を選ぶと外れます。設問文の前半には必ず「99.99% の可用性を維持しながら」「監査のため7年間保持する」といった制約が埋まっています。後半の「最もコスト効率が高いのは」だけを読んで選ぶのが、この分野の最大の失点源です。

試験ではこう出る

「本番データベースの可用性を維持しながらコストを下げたい」で「マルチ AZ 配置をシングル AZ に変更する」→ 要件破りで不正解。「運用負荷を増やさずに」で「Lambda で毎晩チェックするスクリプトを作る」→ 運用負荷の付け替えで不正解。選択肢を安い順に並べる前に、制約を破っているものを消す。

EC2 の料金は、突き詰めれば「動かした時間 × 単価」です。購入オプションは、このうち単価を下げる手段です。時間のほうを減らす話は場面7で扱います。購入オプションは EC2 講義の場面2・3で図にしたので、ここでは1枚で思い出します。

オプション差し出すもの割引の大きさ中断キャパシティの確保設問に出る言葉
オンデマンド何も差し出さない基準（割引なし）されない保証なし「予測できない」「短期」

大事なのは「差し出すもの」の列です。差し出せないものが設問に書いてあれば、その選択肢は消えます。「ステートレス」は、処理の途中経過を台の中に持たない（どの台で処理しても同じ結果になる）作りのことです。

RI の中身 ―― 3つの軸

RI は EC2 のコンソールの「リザーブドインスタンス」から購入します。買うときに決めることが3つあります。

① 種類Standard RIConvertible RI
割引率大きいStandard より小さい
インスタンスファミリーの変更できないできる（同等以上の価値のものへ交換）
OS・テナンシーの変更できないできる
途中での売却RI マーケットプレイスで売れる売れない
向く状況構成が固まっていて3年変えない世代交代や作り直しの可能性がある
  • ② 支払い方法：全額前払い・一部前払い・前払いなしの3つ。先に多く払うほど割引が大きい。「初期費用を抑えたい」なら前払いなし、「割引を最大にしたい」なら全額前払い（All Upfront）
  • ③ 範囲：リージョン指定 RI は AZ を固定せず、同じファミリーの中でサイズをまたいで割引が当たる（Linux かつ共有テナンシーの場合）。ゾーン指定 RI は AZ を固定する代わりに、キャパシティ予約が付く
「Reserved」でも台数は押さえていない

名前の印象から、RI は常に台数の枠を確保すると思われがちですが、リージョン指定 RI は確保しません。純粋に請求上の割引です。Savings Plans もキャパシティは確保しません。「特定の AZ で必ず起動できるようにしたい」という要件は割引と切り離して考え、オンデマンドキャパシティ予約（EC2 の「キャパシティーの予約」から作る、割引なしで枠だけ確保する機能）か、ゾーン指定 RI を選びます。

Savings Plans の2種類

Savings Plans は Billing and Cost Management の「Savings Plans」から購入します。型ではなく金額を約束するので、個々のインスタンスには紐づかず、割引額が最も大きくなる利用へ自動で当たります。管理の手間も RI より少なくて済みます。

サイズ・OS・テナンシー自由自由

Compute は広く浅く、EC2 Instance は狭く深く。設問に「Fargate」「Lambda」が出てきたら、選べるのは Compute Savings Plans だけです。

データベースは、データベースの予約で下げる

ここからが EC2 講義になかった話です。Savings Plans の名前に「Compute」「EC2 Instance」と付いているとおり、これらはコンピュートの割引です。常時動く RDS や ElastiCache には効きません。データベース系のサービスは、それぞれ自分の予約の仕組みを持っています。

買う場所は各サービスのコンソールです（RDS なら RDS のコンソールの「リザーブドインスタンス」）。考え方は EC2 の RI と同じで、「常時稼働」「1年以上使う」データベースが対象です。開発用にときどき起動するだけのデータベースを予約すると、場面1の「期間のミスマッチ」になります。DynamoDB のリザーブドキャパシティは、読み書きの量をあらかじめ決めておく方式（プロビジョンドモード、DB 講義）で使うときの予約です。

この場面の答え ―― 言葉から逆引きする

  • 「24時間365日稼働、今後3年間は構成を変えない」 → Standard RI（3年・全額前払い）または EC2 Instance Savings Plans
  • 「常時稼働だが、来年タイプを見直すかもしれない」 → Convertible RI または Compute Savings Plans。この場面の EC2 の答えはこれ
  • 「常時動く RDS の料金を下げたい」 → リザーブド DB インスタンス。この場面の DB の答えはこれ
  • 「夜間に走るバッチ、失敗しても翌朝やり直せる」 → スポット（場面3）
  • 「土台は一定で、日中だけ増える」 → 土台の分を RI か Savings Plans、増える分をオンデマンドかスポットで賄う組み合わせ。この型はよく正解になる（EC2 講義 場面2の図）
試験ではこう出る

RI と Savings Plans のどちらかを選ばせる設問では、柔軟性を求める言葉が出ていれば Savings Plans。「Fargate や Lambda に移る予定」→ Compute Savings Plans。「キャパシティを保証したい」→ オンデマンドキャパシティ予約かゾーン指定 RI（割引の話ではない）。「3か月だけ使う」→ 1年・3年の約束はすべて不正解。

スポットは「AWS の余りを安く借りる。余りがなくなれば取り上げられる」という仕組みでした（EC2 講義 場面3の時間軸の図）。向き不向きは、この一点で判断できます。取り上げられたときに、失われるものがあるかどうかです。

ステートレスな Web / API の、増やした分の台ステートフルなデータベース、プライマリノード

EMR のタスクノード、コンテナのワーカーEMR のマスターノード、コアノード

備え1・2 ―― 途中経過と仕事を、台の外に出す

右の列の「向かない」仕事も、失われるものを台の外に出せば左の列に移せます。

備え3・4 ―― 同時に枯れないように散らす

スポットを起動するときは、ASG の起動設定（混在インスタンスポリシー）や Spot Fleet・EC2 Fleet で、使ってよいタイプと AZ を複数指定し、割り当て戦略を選びます。

備え5 ―― オンデマンドと混ぜる

  • この場面の答え：夜間バッチは途中経過を S3 に書き出す（チェックポイント）か、仕事を SQS に入れる。タイプと AZ を複数指定し、割り当て戦略をキャパシティ最適化にする
  • 中断通知の2分でやること：途中結果を保存する、ロードバランサーから外れる、やりかけの仕事をキューへ戻す。リバランス推奨を ASG と組み合わせると、回収される前に代わりの台を立ち上げられる
  • コンテナの場合：ECS と EKS（コンテナを指揮するサービス、EC2 講義 場面8）では Fargate Spot が使える。サーバーを管理せずにスポットの割引を得る選択肢で、「運用負荷を上げずにコンテナのコストを下げたい」の正解。中断される性質は同じ
最頻出の引っかけ

「コストを最小化したい」とだけ見るとスポットが正解に見えます。しかし「ミッションクリティカル」「中断できない」「常に稼働している必要がある」があれば即座に消えます。逆に「フォールトトレラント（一部が壊れても全体は動き続ける）」「中断に耐えられる」「時間に余裕がある」は、出題者がスポットを選ばせるために置いた手がかりです。

試験ではこう出る

「長時間のバッチをスポットで動かしたい」→ チェックポイント。「スポットの中断を最小化したい」→ キャパシティ最適化（capacity-optimized）と、複数のタイプ・AZ。「最低限の台数は確保しつつ安く」→ ベースをオンデマンド、超過分をスポット。「EMR をスポットで」→ タスクノードだけ。

NAT Gateway は、VPC のコンソールで作ってパブリックサブネットに置き、プライベートサブネットのルートテーブルに「それ以外の宛先（0.0.0.0/0）→ NAT Gateway」と書いて使います。便利ですが、通ったデータの量にも料金がかかることが見落とされます。

S3 は VPC の外にあるサービスです。プライベートサブネットの EC2 から S3 に書き込むと、何も設定していなければ通信は NAT Gateway を通ります。日次で数テラバイトを書けば、②の処理料金がそのまま数テラバイト分かかります。

ゲートウェイ型エンドポイントは、VPC のコンソールの「エンドポイント」から作り、対象のルートテーブルを選ぶだけです。アプリ側の変更は要りません。

最頻出の引っかけ

「プライベートサブネットの EC2 が S3 に大量のデータを書き込んでいる。NAT Gateway のコストが想定以上に高い。運用負荷を増やさずにコストを下げる方法は？」――答えは S3 用のゲートウェイ型エンドポイントを作り、ルートテーブルに関連付けることです。形を変えて何度も出ます。

誤答としてよく並ぶのは、「NAT インスタンスに置き換える」（運用負荷が増え、可用性も落ちる）、「VPC ピアリングを設定する」（S3 はピアリングの相手にならない）、「インターフェース型エンドポイントを作る」（S3 でも使えるが、時間料金と処理料金がかかる）です。

エンドポイントの2種類を、コストで比べる

ゲートウェイ型インターフェース型（PrivateLink）
対象サービスS3 と DynamoDB のみ多数の AWS サービスと、他社・自社が公開するサービス
実体ルートテーブルの1行サブネットの中の ENI（プライベート IP を持つ）
料金追加料金なしAZ ごとの時間料金 ＋ 処理したデータ量の料金

仕組みの違い（道を1本足すのか、窓口を置くのか）は VPC 講義 場面3 を見てください。ここで覚えるのは料金の違いです。

NAT Gateway を何個置くか

NAT Gateway は1つの AZ の中に置かれます。AZ ごとに1つずつ置くのが可用性の定石ですが、①の時間料金は AZ の数だけ増えます。1つにまとめれば、他の AZ の台からの通信が AZ をまたぐので、場面4の②（AZ 間の転送料金）がかかり、その AZ が落ちると全体が外へ出られなくなります。冗長性を取るか、時間料金を取るかの引き換えです。設問に可用性の制約があれば、AZ ごとに置くほうが正解です。

ほかに転送料金が論点になる構成

  • VPC ピアリング：接続そのものに時間料金はない。通ったデータに、ふつうの AZ 間・リージョン間の転送料金がかかる（同じ AZ 内なら無料）
  • Direct Connect：ポート（接続口）の時間料金がかかる一方、アウトバウンドの転送単価はインターネット経由より低い。「オンプレミスとの継続的な大量転送」では、コストの理由でも正解になる
試験ではこう出る

「NAT Gateway のコストが高い」＋「相手は S3 か DynamoDB」→ ゲートウェイ型エンドポイント。相手がそれ以外（SQS・ECR・Systems Manager など）→ インターフェース型エンドポイント。「オンプレミスから VPC 経由で S3 に届かせたい」→ ゲートウェイ型は使えないのでインターフェース型。「オンプレミス」の一語で答えが変わる。

「オブジェクトは増えていないのに料金が増える」の答えは、一覧に見えないところにあります。

どちらも、S3 バケットの「管理」タブにあるライフサイクルルールで片付けます。ルールに書けることは、現行バージョンの移行と失効、非現行バージョンの移行と失効、不完全なマルチパートアップロードの中止です。JSON で書くと次の形になります。

コストの穴を塞ぐライフサイクル設定の骨格
{
  "Rules": [
    {
      "ID": "archive-then-expire",
      "Status": "Enabled",
      "Filter": { "Prefix": "logs/" },
      "Transitions": [
        { "Days": 30,  "StorageClass": "STANDARD_IA" },
        { "Days": 180, "StorageClass": "DEEP_ARCHIVE" }
      ],
      "Expiration": { "Days": 2555 }        // 7年で削除
    },
    {
      "ID": "abort-incomplete-uploads",   // これを入れていない環境が多い
      "Status": "Enabled",
      "Filter": {},
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
    }
  ]
}

「保持期間を過ぎたら削除」なら失効（Expiration）、「古くなったら安いクラスへ」なら移行（Transitions）です。

どこに何があるか分からないとき

「まずコストの内訳を見えるようにしたい」段階では、S3 のコンソールにある S3 Storage Lens（バケットをまたいで使用状況と改善の提案を見せる機能）や S3 Storage Class Analysis（アクセスの実績から「何日で移すとよいか」を提案する機能）が答えです。

EBS ―― 確保した分に払っている

  • ボリュームタイプの選び方：高い IOPS が要るときだけ io1 / io2、大容量を順番に読み書きするなら st1、めったに読まないなら sc1。必要以上の io2 は、削れる余地の典型
  • スナップショットは増分：2回目以降は変わったブロックだけが課金されるが、世代がたまれば増える。Data Lifecycle Manager で作成と古い世代の削除を自動にするのが、運用負荷を上げずに削る答え。長く置く分はアーカイブ階層（スナップショット用の安い保管先。最低保管期間あり）へ移せる

止めたのに課金されている

Trusted Advisor（AWS の使い方を点検して指摘するサービス → 場面8）が洗い出す「使っていないのに課金されているもの」の代表を挙げます。

  • どこにも関連付けられていない Elastic IP：課金される。現在はパブリック IPv4 アドレスそのものに時間料金がかかる
  • EC2 に付いていない EBS ボリューム：インスタンスを終了しても、「終了時に削除」の設定によってはボリュームが残る。残れば課金され続ける
  • 停止したままのインスタンスのボリューム：停止で稼働料金は止まるが、EBS の料金は止まらない
  • 使われていないロードバランサー、古いスナップショット、放置されたテスト用の RDS：どれも置いてあるだけで時間や量に課金される
試験ではこう出る

「オブジェクト数は増えていないのに S3 のコストが増え続ける」→ 非現行バージョンか不完全なマルチパートアップロード。ライフサイクルルールで消す。「7年保持、取り出しに半日待てる」→ Glacier Deep Archive。「性能を維持したまま EBS のコストを下げる」→ gp2 から gp3。「停止しているのに課金される」→ EBS と Elastic IP。

大きすぎる型を小さくする

Compute Optimizer は、コンソールで有効にする（オプトインする）だけで使えます。推奨を出す対象は EC2・Auto Scaling グループ・EBS・Lambda・Fargate 上の ECS です。Trusted Advisor も使用率の低いインスタンスを指摘しますが、具体的な推奨サイズまで出すのは Compute Optimizer です。

Graviton に替える

Graviton は EC2 のほか、RDS、ElastiCache、OpenSearch Service、Lambda、Fargate でも選べます。EC2 ならインスタンスタイプの名前に g が付くもの（m7g、c6g など）を選びます。判断の軸はCPU の方式を変えられるかどうかです。Java、Python、Node.js、Go で書いたアプリや、コンテナにしたアプリなら移行は容易で、コスト削減の正解になります。x86 用に作られた商用ソフトに依存しているなら選べません。設問に「再コンパイルできる」「コンテナ化されている」とあれば、Graviton を選ばせる手がかりです。

使わない時間は止める

  1. 需要に合わせて増減する：ASG のターゲット追跡ポリシー（EC2 講義 場面6）で、必要な台数だけ動かす。ピークに合わせて台数を固定した構成は、削れる余地そのもの
  2. 時刻で増減する：負荷の波が時間帯で決まっているなら、ASG のスケジュールされたアクションで台数を変える。予測できるなら予測スケーリングも選べる
  3. 開発・検証環境を夜間と週末に止める：ASG なら希望台数をゼロにするスケジュール、単体の EC2 なら EventBridge Scheduler から停止・起動を呼ぶ。この場面の答えはこれ
  4. スケールインを設定する：増やす設定だけで減らす設定がない構成は、事実上ピークに固定されている
停止と終了の違いを踏まえる

場面6の図のとおり、停止で稼働料金は止まりますが、EBS と Elastic IP の料金は続きます。ゼロにするには終了が必要で、その場合は作り直しが要ります。「夜間停止」の削減効果は、EBS の分だけ目減りする。ここまで読めていると選択肢を比べられます。

Lambda は、メモリを増やすと安くなることがある

メモリの割り当ては、Lambda のコンソールで関数ごとに「設定」→「一般設定」から変えます。「Lambda の実行時間が長く、コストが高い」と来たら、メモリ設定の見直しが候補です。加えて、関数のアーキテクチャに Arm（Graviton）を選べば、同じ処理をより安く実行できます。

引っかけ

プロビジョニング済み同時実行はコールドスタート対策であって、コスト削減策ではありません。待機している分にも課金されるので、むしろコストは上がります。「コストを下げたい」で選ぶと誤答、「最初の1件の遅さを解消したい」なら正解。目的によって正解にも誤答にもなる典型です。

そもそも EC2 でなくてよいか

ときどきしか動かないバッチを、常時起動の EC2 で回しているなら、Lambda や Fargate、AWS Batch に移せば、待っている時間の課金が消えます。目安は稼働率です。ほぼ常時動くなら EC2 とコミットメント（場面2）、たまにしか使わないならサーバーレス（サーバーを自分で持たない方式）です。

「オーバープロビジョニングを見つけて、推奨サイズが欲しい」→ Compute Optimizer。「メモリ使用率を根拠にしたい」→ CloudWatch エージェント。「開発環境のコストが本番と同程度」→ 夜間・週末に止めるスケジュール。「コンテナ化されている、コストを下げたい」→ Graviton。

Q1プライベートサブネットの複数の EC2 が、同一リージョンの S3 バケットへ日次で数テラバイトのログを書き込んでいる。請求を見ると NAT Gateway の費用が大半を占めていた。運用負荷を増やさずにコストを削減する方法はどれか。
  • A. NAT Gateway を NAT インスタンスに置き換える
  • B. S3 用の Gateway エンドポイントを作成し、ルートテーブルに追加する
  • C. EC2 インスタンスをパブリックサブネットに移動し、パブリック IP を割り当てる
  • D. VPC ピアリング接続を S3 との間に設定する

正解: B

場面5の2枚の図そのもの。NAT Gateway には通したデータ量にかかる処理料金があり、S3 宛ての数テラバイトがそこを通っていた。ゲートウェイ型（Gateway）エンドポイントを作るとルートテーブルに1行増え、S3 宛ての通信は NAT Gateway を通らなくなる。エンドポイントに追加料金はない。

判断軸: A は自分で面倒を見る EC2 が増えて運用負荷が上がり、可用性も落ちる（場面1の「運用負荷の付け替え」）。C はプライベートに置くというセキュリティの要件を壊す。D は S3 がピアリングの相手にならない。相手が S3 か DynamoDB なら、ゲートウェイ型エンドポイント。

Q2ある企業は、今後3年間サイズを変えずに稼働させる基幹システムを EC2 で運用している。同時にコンテナ化を進めており、一部を Fargate へ移す計画がある。移行後もコミットメントの割引を無駄にしたくない。最も適した購入オプションはどれか。
  • A. 3年の Standard Reserved Instance を購入する
  • B. 3年の EC2 Instance Savings Plans を購入する
  • C. 3年の Compute Savings Plans を購入する
  • D. スポットインスタンスに移行する

正解: C

場面2の Savings Plans の表。Compute Savings Plans は EC2 に加えて Fargate と Lambda にも効く。約束するのは金額なので、EC2 から Fargate へ仕事が移っても、割引は自動で移った先に当たる。

判断軸: A と B は割引率では有利だが、対象が EC2 だけ。Fargate や Lambda という単語が出た時点で、選べるのは Compute Savings Plans だけ。D は基幹システムに中断のリスクを持ち込む（場面3）。「割引率が最大のもの」ではなく「要件を満たすもののうち割引が大きいもの」という順序（場面1の図）を守る。

Q3データ分析チームが新しい S3 バケットにデータを蓄積し始めた。当初は頻繁に参照されるが、その後どの程度参照されるかは読めず、データセットごとにも差がある。取り出し料金は避けたい。運用負荷を最小限にストレージコストを最適化する方法はどれか。
  • A. すべてのオブジェクトを S3 Standard-IA に保存する
  • B. S3 Intelligent-Tiering を使用する
  • C. 30日後に S3 One Zone-IA へ移行するライフサイクルルールを設定する

正解: B

場面6のストレージクラスの図の、黄色い帯。「読めない」「データセットごとに差がある」は Intelligent-Tiering を選ばせるための言葉。自動で階層が切り替わり、取り出し料金がかからない点も要件に合う。

  • B. 内部 API の呼び出しをプライベート IP（または内部 DNS 名）に変更する
  • C. 内部 API の前に CloudFront ディストリビューションを配置する
