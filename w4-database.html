データベース ―― 可用性のためか、性能のためか

この分野で最も多い失点は、Multi-AZ とリードレプリカの混同です。前者は可用性のため、後者は読み取り性能のため。目的が違うものを同じ「複製」として覚えていると、設問文の要件を読み違えます。今日はその区別を軸に、RDS・Aurora・DynamoDB・ElastiCache を整理します。

01

この講義のゴール

データベースの設問は、サービス名を知っているかを問うものではありません。要件の一文を読んで、どの軸で切るかを問われます。今日終わったときに、次の3つができていれば合格です。

  • 01
    Multi-AZ とリードレプリカを、目的から即座に切り分けられる。
    設問に「可用性」と書いてあるか「読み取り負荷」と書いてあるかで、迷わず一方を選べる。
  • 02
    リレーショナルか DynamoDB かを、設問の言葉から判断できる。
    「複雑な結合」「ミリ秒未満」「スキーマが頻繁に変わる」といった語を手がかりにできる。
  • 03
    GSI と LSI、Redis と Memcached の使い分けを説明できる。
    どちらでも動く場面ではなく、片方しか成立しない条件を言える。
この分野の位置づけ

データベースはドメイン2（回復力のあるアーキテクチャ）とドメイン3（高性能なアーキテクチャ）の両方にまたがります。同じ RDS の設問でも、ドメイン2では「AZ障害で落ちないか」を、ドメイン3では「読み取りが詰まらないか」を聞いてきます。同じサービスが、問われる観点によって別の答えを要求する――これがデータベース分野の難しさであり、逆に言えば、観点さえ読み取れれば選択肢は一気に2つに絞れます。

02

選択はワークロードの言葉から始まる

AWSのデータベースは十数種類あります。しかしSAAで問われる選択は、ほとんどの場合「リレーショナルか、キーバリューか、それ以外か」の三択に還元できます。設問文に現れる言葉から逆引きしてください。

「速い」には二種類ある

設問で最も紛らわしいのが速度の表現です。ここを取り違えると、DynamoDB と ElastiCache のどちらを選ぶかで間違えます。

  • 一桁ミリ秒（single-digit millisecond）――DynamoDB の標準的な応答です。この語が出たら DynamoDB を疑ってください。
  • マイクロ秒（microsecond）――キャッシュ層の世界です。DynamoDB の前段なら DAX、リレーショナルの前段なら ElastiCache。「マイクロ秒」と書いてあるのに DynamoDB 単体を選ぶのは不正解です。
  • クエリが数秒〜数分かかってよい代わりに巨大――分析系です。Redshift か Athena の領域で、RDS に押し込む選択肢は不正解になります。
判断軸

「アクセスパターンが決まっているか」が、リレーショナルと DynamoDB を分ける本質です。リレーショナルは「どう問い合わせるかを後で決められる」代わりに、スケールに上限があります。DynamoDB は「どう問い合わせるかを先に決める」代わりに、規模に事実上の上限がありません。設問に「新しい分析要件が次々に出てくる」とあればリレーショナル、「決まった画面から決まったキーで引くだけ」とあれば DynamoDB です。

よくある誤解

「DynamoDB は NoSQL だからスキーマを考えなくてよい」――逆です。DynamoDB こそ設計を先にしなければならないデータベースです。テーブルを作ったあとにパーティションキーを変更することはできません。リレーショナルなら後から索引を足せますが、DynamoDB では前提が崩れるとテーブルを作り直すことになります。この非対称性が、後の GSI／LSI の設問に直結します。

03

RDS ―― 複製が二種類ある理由

RDS の設問は、ほぼ Multi-AZ とリードレプリカの区別に集約されます。どちらも「データベースが増える」ように見えますが、作られる理由がまったく違います。ここを一度で固めます。

目的から入る

Multi-AZ は壊れたときのための仕組みです。別のアベイラビリティゾーンに待機系を置き、プライマリが死んだら自動的に切り替えます。待機系は普段なにもしません。読み取りにも使えません。「無駄では」と思うかもしれませんが、待機系に仕事をさせないから、切り替えたときに遅れがゼロで済むのです。

リードレプリカは混んできたときのための仕組みです。読み取り専用の複製を増やし、参照系のクエリを逃がします。こちらは非同期複製なので、わずかに古いデータが返ることがあります。その代わり、同じリージョンにも別リージョンにも置けますし、数も増やせます。

最頻出の引っかけ

「読み取りが重いのでレポート用のクエリを逃がしたい。Multi-AZ を有効にする」――不正解です。スタンバイには接続できないので、読み取り負荷は1ミリも減りません。逆に「AZ障害時にダウンタイムを最小化したい。リードレプリカを作る」も不正解です。レプリカは自動では昇格しません。この2つを入れ替えた選択肢は、ほぼ毎回どこかの設問に紛れています。

Multi-AZ DB クラスター

近年は Multi-AZ の派生形として「Multi-AZ DB クラスター」があります。こちらはライター1台と読み取り可能なスタンバイ2台の計3台を3つのAZに置く構成で、従来の Multi-AZ より速いフェイルオーバーと、スタンバイの読み取り活用を両立します。設問で「Multi-AZ なのに読める」と読めるときは、この構成を指しています。ただし従来型の「スタンバイは読めない」が原則であることは変わりません。

バックアップとスナップショットは別物

ここも混同されます。呼び名が似ているだけで、管理の主体も寿命も違います。

復元の挙動にも注意が必要です。バックアップからの復元は、常に新しいDBインスタンスの作成になります。既存のインスタンスに上書きすることはできません。復元後にエンドポイントが変わるため、アプリの向き先を切り替える作業が発生します。設問で「復元にかかる時間を最小化したい」と問われたとき、この作り直しが必要な点が答えの分かれ目になることがあります。

暗号化は最初に決める

RDS の保管時暗号化は KMS で行いますが、後から有効化することができません。これが設問の題材になります。既存の暗号化されていないDBを暗号化するには、次の手順を踏みます。

  1. 暗号化されていないDBのスナップショットを取得する。
  2. そのスナップショットをコピーする。コピーの操作の中で暗号化を指定する。
  3. 暗号化されたコピーから新しいDBインスタンスを復元する。
  4. アプリの接続先を新しいエンドポイントに切り替える。

要点は2番です。スナップショット自体に後から暗号化をかけることはできず、コピーという操作が暗号化の入口になっている――ここを知っているかどうかだけで一問取れます。なお、暗号化されたDBのリードレプリカやスナップショットは自動的に暗号化され、暗号化を外すことはできません。

停止しても課金は続く

RDS インスタンスは停止できますが、停止していてもプロビジョニング済みストレージとバックアップストレージの課金は続きます。止まるのはインスタンス時間（コンピュート）の課金だけです。さらに、停止状態は最大7日間で、それを過ぎるとAWSが自動的に起動します。「週末は止めておけば無料」ではありません。学習用に作ったものは、止めるのではなく削除してください。

RDS Proxy ―― コネクションが枯れるとき

RDS Proxy は、アプリとDBの間に入るフルマネージドのコネクションプールです。SAAで問われる使いどころは、ほぼ次の2つです。

  • Lambda など、同時実行数が急増する構成。Lambda は呼び出しごとに実行環境が増えるため、それぞれがDB接続を張ると容易に上限に達します。Proxy が接続を束ねて再利用することで、DB側の接続数を抑えます。設問に「Lambda」「コネクション枯渇」「too many connections」が出たら Proxy です。
  • フェイルオーバー時のダウンタイムを短くしたい。Proxy はアプリからの接続を維持したまま、裏側で新しいプライマリへ張り替えます。アプリから見た切り替え時間が短くなります。

あわせて、DBの資格情報を Secrets Manager で管理し、アプリからは IAM 認証で Proxy に接続する構成が取れます。「認証情報をアプリに持たせたくない」という要件と組み合わせて出題されます――W1でやったIAMの原則がそのまま効いてくる場面です。

04

Aurora ―― ストレージが分離されている意味

Aurora を「速いRDS」と覚えていると、設問の半分を落とします。Aurora の特徴はほぼすべて、コンピュートとストレージが分離されているという一点から導かれます。そこを押さえれば、個別の機能は暗記せずに説明できます。

構成を先に理解する

Aurora のクラスターは、1つの共有ストレージ層と、そこにぶら下がる複数のDBインスタンスでできています。ストレージ層は3つのAZにまたがってデータを6重に保持し、10GB単位で自動的に拡張します。上限は Aurora のバージョンによって 128 TiB または 256 TiB です。

この構造から、次のことが自動的に導かれます。

  • レプリカを追加してもデータのコピーは発生しない。同じストレージを見るだけなので、追加が速く、レプリケーションラグも小さくなります。RDS のリードレプリカが「別のDBにデータを流し込む」のとは仕組みが違います。
  • ストレージの容量設計が不要。事前に何GBと決める必要がなく、使った分だけ増えます。RDS では割り当てた容量に対して課金されるのとは対照的です。
  • ライターが死んでもデータは無事。インスタンスとストレージが別なので、リーダーの1台を昇格させれば復旧します。

エンドポイントを使い分ける

Auto Scaling とサーバーレス

Aurora のレプリカには Auto Scaling を設定できます。CPU使用率や接続数をトリガーに、リーダーを自動で増減させる仕組みです。読み取り負荷が日中だけ跳ねるような設問では、「リードレプリカを固定台数用意する」よりこちらが正解になります。

もう一段進んだのが Aurora Serverless v2 です。インスタンスクラスを選ぶ代わりに、ACU（Aurora Capacity Unit）の下限と上限を指定し、負荷に応じて0.5 ACU刻みで自動的に容量が変わります。上限は最大256 ACU、対応バージョンでは下限を0にして未使用時に一時停止させることもできます。

  • 使いどころ――開発環境、負荷が予測できないアプリ、断続的にしか使われないワークロード。「ピークが読めない」「使わない時間が長い」と書いてあれば候補です。
  • 使わないところ――負荷が安定しているシステム。常時動いているなら、プロビジョンドのほうが費用対効果は高くなります。

Global Database

Aurora Global Database は、プライマリリージョンのクラスターから最大10のセカンダリリージョンへ、専用の基盤で複製する仕組みです。複製の遅延は通常1秒未満で、セカンダリ側は読み取りに使えます。

設問での使われ方は2つです。ひとつは災害対策――リージョン丸ごとの障害に備え、別リージョンへ昇格させる。もうひとつはグローバルな読み取り――世界各地の利用者に、近いリージョンから低遅延で読ませる。「リージョン障害からの復旧を分単位で」「複数大陸にまたがる読み取り」といった語が手がかりです。クロスリージョンのリードレプリカでも似たことはできますが、遅延と昇格の速さで Global Database が選ばれます。

Backtrack

Backtrack は、クラスターを過去の時点まで巻き戻す機能です。スナップショットからの復元と違い、新しいクラスターを作らずに、その場で時間を戻します。復元より格段に速く、誤って DELETE を流してしまったといった事故から短時間で回復できます。

ただし制約が多く、そこが出題されます。

  • Aurora MySQL 互換でのみ利用可能。PostgreSQL 互換では使えません。
  • 巻き戻せる幅は最大72時間です。
  • クラスターの作成時に有効化しておく必要があります。後から既存のクラスターに追加することはできません。
  • 巻き戻しの間、データベースは短時間停止します。無停止ではありません。
判断軸

「誤操作からの高速な復旧」が要件で、エンジンが Aurora MySQL なら Backtrack。PostgreSQL だったり、72時間より前に戻したければポイントインタイムリカバリ。両方とも成立しない書き方（たとえば「別リージョンに退避したい」）ならスナップショットのコピーです。要件の時間軸と、エンジンの2つを見てください。

05

DynamoDB ―― キーで設計がほぼ決まる

DynamoDB の設問は、性能でもコストでも、最後はキー設計に帰着します。パーティションキーが何かを決めた時点で、そのテーブルにできることの大半が決まってしまうからです。

2種類の主キー

DynamoDB の主キーには2つの形があります。

  • パーティションキーのみ――値が一意に1アイテムを指します。ユーザーIDで引くだけのテーブルなど。
  • パーティションキー + ソートキー（複合キー）――同じパーティションキーの中に複数のアイテムが並び、ソートキーで順序が決まります。「ユーザーIDごとの注文履歴を日時順に」といった構造がこれです。

パーティションキーはデータの物理的な置き場所を決めるハッシュの元になります。だから値が広く散らばっていることが重要です。「国名」のように偏りのある属性をパーティションキーにすると、特定のパーティションにアクセスが集中します。これがホットパーティションで、設問では「一部のキーだけスロットリングされる」という形で現れます。対処は、キーに接尾辞を付けて分散させるか、より散らばる属性を選び直すことです。

ソートキーが効くのは範囲の問い合わせです。「この日付以降」「この接頭辞で始まるもの」をQueryで一発で取れます。逆に、ソートキーにない条件で絞りたい場合は、全件を舐めるScanになってしまいます。設問に「Scanを使う」選択肢があれば、まず疑ってください。効率が悪く、たいてい不正解側に置かれます。

GSI と LSI

主キー以外の属性で引きたくなったときに使うのがセカンダリインデックスです。2種類あり、違いがそのまま出題されます。

実務でも試験でも、迷ったら GSI です。LSI は強い整合性が必要な場合に限って選ぶもので、後から追加できず10GB制約も抱えるため、使いどころが狭い。設問で LSI が正解になるのは、ほぼ「強い整合性で、別のソート順が欲しい」という書き方をされたときだけです。逆に「運用中のテーブルに新しい検索条件を足したい」と来たら、LSI は後から作れないので自動的に GSI になります。

最頻出の引っかけ

「本番稼働中のテーブルに、新しい属性での検索を追加したい。LSI を作成する」――不正解です。LSI はテーブル作成時にしか作れません。この選択肢は、LSI という語を知っているだけの受験者を落とすために置かれています。「後から」「既存のテーブルに」という語を見たら、その時点で LSI は消えます。

キャパシティモード

DynamoDB の課金と性能を決めるのがキャパシティモードです。

  • プロビジョンドモード――読み書きのキャパシティユニットを事前に指定します。1 WCU は1KBまでのアイテムを毎秒1回書き込む能力、1 RCU は4KBまでのアイテムを毎秒1回強く整合性のある読み取り、または毎秒2回の結果整合性のある読み取りをする能力です。トランザクションを使う場合はこの2倍を消費します。負荷が予測できるなら最も安くなります。Auto Scaling を併用すれば、指定した範囲内で自動的に増減します。
  • オンデマンドモード――事前の指定が不要で、来たリクエストの分だけ課金されます。単価はプロビジョンドより高いものの、容量の見積もりが要りません。負荷が予測できない、急峻なスパイクがある、新規サービスで実績がない――このいずれかが設問に書かれていればオンデマンドです。

切り分けは単純です。「予測できるか」だけを見てください。予測できるならプロビジョンド + Auto Scaling、予測できないならオンデマンド。「コストを最適化したい」という語だけでは決まらず、その前に負荷の性質が書かれているはずです。

整合性

DynamoDB の読み取りは既定で結果整合性です。書き込み直後に読むと、まだ反映前の値が返ることがあります。パラメータで強い整合性の読み取りを要求でき、その場合は必ず最新の値が返りますが、消費するキャパシティが2倍になり、レイテンシもやや増えます。

設問では「書き込んだ直後に必ず最新を読む必要がある」と明記されているかどうかで判断します。GSI からの読み取りは常に結果整合性であることも忘れないでください――「強い整合性が必要」かつ「主キー以外で引く」という要件が並んだら、GSI では成立せず LSI が答えになります。

セッションストアとしてのキャッシュ

これはキャッシュとは別の用途ですが、SAAでは頻出です。EC2を複数台に増やしてロードバランサーの後ろに置くと、ユーザーが毎回同じサーバーに当たるとは限りません。セッション情報をサーバーのメモリに持っていると、リクエストのたびにログイン状態が失われます。

解決は2つあります。

  • スティッキーセッション――ロードバランサーが同じ利用者を同じサーバーに送り続ける。手軽ですが、そのサーバーが落ちるとセッションが消え、負荷も偏ります。
  • 外部のセッションストア――ElastiCache for Redis か DynamoDB にセッションを置き、アプリケーションサーバーをステートレスにする。これがSAAの推す答えです。

「Auto Scaling でインスタンスが入れ替わるとログアウトしてしまう」という設問を見たら、外部セッションストアを選んでください。「ステートレスにする」はSAA全体を貫く設計思想で、この分野でも同じ原則が効きます。

07

分析系・専用DB・移行

ここからは、深く覚える必要はないものの、選択肢に並んだときに「これではない」と切れるだけの知識が要る領域です。一行ずつの対応で押さえます。

Redshift ―― 分析はRDSでやらない

Redshift は列指向のデータウェアハウスです。行単位で読み書きするOLTPではなく、多数の行にまたがる集計（OLAP）に最適化されています。RDS が「注文を1件登録する」ためのものなら、Redshift は「過去3年の売上を製品カテゴリ別に集計する」ためのものです。

設問で Redshift が答えになるのは、次の語が出たときです。データウェアハウス、BI、ダッシュボード、ペタバイト規模、複雑な集計クエリ、複数のデータソースを統合した分析。逆に、「ミリ秒で応答」「1件ずつ大量に更新」と書かれていたら Redshift は不正解側です。

Redshift Spectrum は、S3 に置いたままのデータに対して、Redshift から直接クエリを投げる機能です。ロードの手間と保管コストを避けたいときに使います。「S3のデータをRedshiftにロードせずに分析したい」と来たら Spectrum。なお、Redshift クラスターを持たずにS3を直接クエリしたいだけなら Athena が選択肢に入ります。クラスターの有無が両者の分かれ目です。

専用データベースの一行対応

  • DocumentDB――MongoDB互換が要件に書いてあるとき。JSON文書をそのまま格納し、既存のMongoDBアプリを載せ替える移行先です。
  • Neptune――「関係性」「つながり」を辿るクエリが主題のとき。ソーシャルグラフ、レコメンデーション、不正検知、ナレッジグラフ。
  • Timestream――時系列が主題のとき。IoTセンサー、メトリクス、時間軸での集計。時系列を無理にRDSに入れる選択肢は不正解です。
  • Keyspaces――Apache Cassandra 互換が要件に書いてあるとき。CQLをそのまま使いたい場合の移行先です。

これらは設問に固有名詞（MongoDB、Cassandra）か、固有の構造（グラフ、時系列）が明記されているときだけ正解になります。書かれていないのに選ぶと外れます。

移行 ―― DMS と SCT の分担

データベース移行の設問では、2つのサービスの役割分担を問われます。

  • DMS（Database Migration Service）――データを運ぶ役です。移行元と移行先をつなぎ、データを転送します。移行中も移行元を稼働させたまま継続的に変更を反映（CDC）できるため、ダウンタイムを最小化できます。
  • SCT（Schema Conversion Tool）――形を変える役です。テーブル定義、ストアドプロシージャ、関数などを移行先のエンジンの文法に書き換えます。

判断は単純です。エンジンが変わるなら SCT が要る。変わらないなら DMS だけでよい。Oracle から Aurora PostgreSQL への移行なら異種間なので SCT + DMS、オンプレミスのMySQLから RDS for MySQL への移行なら同種間なので DMS のみ。設問はこの区別をそのまま聞いてきます。

ダウンタイムの扱い

移行の設問では、ほぼ必ず「ダウンタイムを最小化したい」という条件が付きます。そのとき答えになるのは DMS の継続的レプリケーション（CDC）です。「一度エクスポートして、深夜にインポートする」という選択肢はもっともらしく見えますが、停止時間が長くなるため要件を満たしません。

確認問題

先に自分で答えを決めてから開いてください。当てずっぽうで開くと、この5分が無駄になります。

Q1RDS for PostgreSQL で稼働する業務システムがある。日中、経理部門が実行するレポートクエリによってアプリケーションの応答が悪化する。加えて、AZ障害時のダウンタイムも最小化したい。適切な構成はどれか。
  • A. Multi-AZ 配置を有効にし、レポートクエリはスタンバイに向ける
  • B. リードレプリカを2台作成し、障害時はそのうち1台を手動で昇格させる
  • C. Multi-AZ 配置を有効にしたうえで、リードレプリカを作成してレポートクエリを向ける
  • D. インスタンスクラスを2段階大きいものに変更する

正解: C

要件が2つあります。「レポートで応答が悪化する」は読み取り性能の問題、「AZ障害時のダウンタイム」は可用性の問題です。前者にはリードレプリカ、後者には Multi-AZ。両方が書かれているなら両方を使います。この2つは排他ではなく、併用できます。

判断軸: A はスタンバイに接続できないので成立しません。B は自動フェイルオーバーがなく可用性の要件を満たしません。D はスケールアップで一時的に楽にはなりますが、可用性の要件に何も答えていません。要件が2つ書かれている設問では、片方しか解いていない選択肢を落とすのが定石です。

Q2DynamoDB のテーブルが本番稼働中である。新しい画面の要件として、これまで主キーに使っていなかった「ステータス」属性で絞り込む検索を追加する必要が出た。結果整合性の読み取りで問題ない。最も適切な対応はどれか。
  • A. LSI を作成し、ステータスをソートキーにする
  • B. GSI を作成し、ステータスをパーティションキーにする
  • C. Scan に FilterExpression を付けてステータスで絞り込む
  • D. テーブルを作り直し、パーティションキーをステータスに変更する

正解: B

GSI はテーブル作成後でも追加でき、パーティションキーを自由に選べます。結果整合性で問題ないという条件も GSI の制約と合致しています。

判断軸: A は LSI がテーブル作成時にしか作れないため不可能です。C は動作しますが、Scan は全アイテムを読んでから絞り込むためキャパシティを浪費し、テーブルが育つほど悪化します。D は既存データの移行が必要で、既存の検索も壊れます。「稼働中」「後から」という語を見た瞬間に LSI と作り直しが消える――これがこの型の設問の解き方です。

Q3暗号化されていない RDS for MySQL のインスタンスが本番で稼働している。監査要件により、保管時の暗号化が必須になった。実施すべき手順はどれか。
  • A. インスタンスを変更し、暗号化オプションを有効にする
  • B. スナップショットを取得し、そのスナップショットを暗号化を指定してコピーし、コピーから新しいインスタンスを復元する
  • C. 暗号化されたリードレプリカを作成し、それを昇格させる
  • D. EBS ボリュームを直接暗号化する

正解: B

RDS の暗号化は作成時にしか設定できません。既存インスタンスを暗号化する唯一の経路が、スナップショットのコピー操作で暗号化を指定するこの手順です。復元後にエンドポイントが変わるため、アプリの切り替えが伴います。

判断軸: A は「後から有効化できない」という制約に反します。C は、暗号化されていないインスタンスから暗号化されたリードレプリカを作ることはできません（逆に、暗号化されたDBのレプリカは必ず暗号化されます）。D は RDS がマネージドサービスであり、基盤のボリュームに直接触れないため不可能です。「後から変えられない設定」はSAAの頻出テーマで、暗号化はその代表です。

Q4EC2 の Auto Scaling グループで動く Web アプリケーションがある。スケールインでインスタンスが終了すると、そのインスタンスに接続していた利用者がログアウトしてしまう。今後はリージョン障害にも備えたい。最も適切な対応はどれか。
  • A. ロードバランサーでスティッキーセッションを有効にする
  • B. セッション情報を各インスタンスのローカルディスクに書き出す
  • C. セッション情報を ElastiCache for Redis または DynamoDB に外部化する
  • D. スケールインを無効にし、インスタンス数を固定する

正解: C

アプリケーションサーバーをステートレスにし、セッションを外部のストアに持たせるのが正攻法です。インスタンスが入れ替わっても、どのインスタンスに当たってもセッションが維持されます。リージョン障害への備えという点でも、Redis のレプリケーションや DynamoDB Global Tables で複製先を持てます。

判断軸: A はインスタンスが終了すれば結局セッションが失われ、根本解決になりません。B はローカルディスクがインスタンスと運命をともにするため意味がありません。D は Auto Scaling の利点を捨てており、そもそも要件（スケールさせたい）に反します。「状態をどこに置くか」を問う設問では、インスタンスの外に出す選択肢が正解です。

Q5オンプレミスの Oracle データベースを AWS へ移行する。移行先は Aurora PostgreSQL とし、移行中も業務は止められない。必要な作業の組み合わせはどれか。
  • A. DMS のみを使い、継続的レプリケーションで移行する
  • B. SCT でスキーマを変換し、DMS の継続的レプリケーションでデータを移行する
  • C. Oracle の物理バックアップを S3 に置き、Aurora に復元する
  • D. 深夜にデータをエクスポートし、翌朝までにインポートを完了させる

正解: B

Oracle から PostgreSQL は異種エンジン間の移行です。テーブル定義やストアドプロシージャの文法が違うため、SCT による変換が必要になります。そのうえで、業務を止められないという条件があるので DMS の継続的レプリケーション（CDC）を使い、切り替え直前まで差分を反映し続けます。

判断軸: A は同種エンジン間なら成立しますが、今回はスキーマ変換が抜けています。C は Oracle の物理バックアップを異なるエンジンに復元することはできません。D は停止時間が発生し、「止められない」という条件に反します。移行の設問は「エンジンが変わるか」と「止められるか」の2軸で切ると、ほぼ一意に決まります。

課金の注意

ハンズオンの前に一度だけ念を押します。RDS は「停止」しても課金が止まりません。止まるのはインスタンス時間だけで、ストレージとバックアップの課金は続きます。しかも停止できるのは最大7日間で、それを過ぎるとAWSが勝手に起動します。Multi-AZ にすると台数分のストレージ課金がかかる点も併せて頭に入れてください。学習用に作ったものは、停止ではなく削除で終わらせる。削除時に「最終スナップショットを作成」を選ぶとそのスナップショットの保管料が残るので、不要なら作らない設定にしてください。
