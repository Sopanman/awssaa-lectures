01

全体の地図

データベースは、アプリが扱うデータをしまっておき、必要なときに取り出す場所です。AWS には十数種類ありますが、SAA で問われる選択は、ほとんどが「表を組み合わせて聞くのか、キーで1件を引くのか、それ以外か」の三択に戻せます。まず登場人物を紹介してから、9つの場面がどこの話かを見ます。

この講義の登場人物
データベース
データを決まった形でしまい、条件を指定して取り出せるようにしたソフト。AWS ではサービスとして借りる
RDSAmazon Relational Database Service
表の形でデータを持つデータベース（リレーショナルデータベース → 場面1）を、AWS が用意して面倒を見てくれるサービス → 場面2〜4
AuroraAmazon Aurora
AWS が作り直したリレーショナルデータベース。RDS の画面から作るが、中の造りが違う → 場面5
DynamoDBAmazon DynamoDB
キーを渡して1件を素早く受け取る型のデータベース。サーバーを意識せずに使える（EC2 講義の場面4で名前だけ既出）→ 場面6・7
ElastiCacheAmazon ElastiCache
よく使うデータをメモリの上に置いておき、データベースより速く返す置き場（キャッシュ）のサービス（EC2 講義の場面4で名前だけ既出）→ 場面8
RedshiftAmazon Redshift

この講義の見取り図

場面1はどれを選ぶか。場面2〜5はリレーショナル（RDS の複製、バックアップと暗号化、接続の束ね方、Aurora）。場面6・7は DynamoDB（キーの決め方と、量・新しさの決め方）。場面8はキャッシュ、場面9は分析・専用データベース・移行です。 データベースはドメイン2（回復力）とドメイン3（性能）の両方から問われます。同じ RDS の設問でも、ドメイン2は「AZ が落ちても止まらないか」を、ドメイン3は「読み取りが詰まらないか」を聞いてきます。同じサービスが、聞かれる観点によって別の答えを要求するので、読むときはどちらを聞かれているかを先に決めてください。

02

場面1 ―― 「新しいシステムのデータを、どのデータベースに置くか決めたい」

この場面で初めて出る言葉
リレーショナルデータベース
データを行と列の表（テーブル）で持ち、複数の表を組み合わせて問い合わせられるデータベース
SQL
リレーショナルデータベースに問い合わせるための言語。「この条件の行を、この列で集計して」と書く
結合JOIN
2つの表を、共通の列（顧客ID など）でつないで1つの結果にすること
スキーマ
表にどんな列があり、どんな型の値が入るかの決まり。リレーショナルでは先に決める
トランザクション
「在庫を1減らす」と「注文を1件足す」のような複数の更新を、全部成功か全部取り消しかのどちらかにまとめる仕組み
ACID
トランザクションが守るべき4つの性質の頭文字。設問では「一貫性を厳密に保ちたい」の合図として出る
キーバリュー
キー（探すための値）と値（中身）を対にして置くだけの型。NoSQL（SQL のデータベースではないもの）の代表
ミリ秒・マイクロ秒
1ミリ秒は 1/1,000 秒、1マイクロ秒はその 1/1,000。応答の速さを表す単位
ワークロード
そのシステムにかかる仕事の中身と量（読み取りが多い、急に増える、など）

データベースを作る前に決めるのは、型です。型が違うと、聞き方も、速さも、大きくできる限界も違います。

設問の言葉から、3つの家族に振り分ける

家族設問に現れる言葉第一候補
リレーショナル
RDS / Aurora		トランザクション、ACID、複雑な結合、集計クエリ、既存のスキーマ、レポート、既存の Oracle／SQL Server からの移行、正規化Aurora（MySQL／PostgreSQL 互換で済むなら）。それ以外は RDS
キーバリュー／ドキュメント
DynamoDB		ミリ秒未満、一桁ミリ秒、サーバーレス、スキーマレス、キーで一意に引く、予測不能なトラフィック、無制限にスケール、運用管理をなくしたいDynamoDB
専用型
Redshift ほか		分析、BI、データウェアハウス、ペタバイト、列指向、時系列、グラフ、関係性の探索用途ごとの専用サービス（場面9）

表の中の言葉のうち、クエリは問い合わせのこと、正規化は同じ情報を重複して持たないよう表を分けること、サーバーレスは自分でサーバーを用意・管理しないこと（EC2 講義の Lambda と同じ意味）、スキーマレスは列を先に決めなくてよいこと、トラフィックは届くリクエストの量、スケールは規模を大きくすることです。専用型の行の言葉（BI、データウェアハウス、列指向など）は場面9で説明します。

「速い」には段階がある

設問で最も紛らわしいのが速さの表現です。ここを取り違えると、DynamoDB とキャッシュのどちらを選ぶかで間違えます。

  • 一桁ミリ秒（single-digit millisecond）：DynamoDB の標準的な応答。この語が出たら DynamoDB を疑う
  • マイクロ秒：キャッシュの世界。DynamoDB の手前なら DAX（場面7）、リレーショナルの手前なら ElastiCache（場面8）
  • 数秒〜数分かかってよい代わりに巨大：分析。Redshift か Athena（場面9）の領域
リレーショナルと DynamoDB を分ける本質

「どう問い合わせるか（アクセスパターン）が決まっているか」です。リレーショナルは、どう聞くかを後で決められる代わりに、大きくできる限界があります。DynamoDB は、どう聞くかを先に決める代わりに、規模に事実上の上限がありません。設問に「新しい分析要件が次々に出てくる」とあればリレーショナル、「決まった画面から決まったキーで引くだけ」とあれば DynamoDB です。

よくある誤解

「DynamoDB は NoSQL だから、設計を考えなくてよい」――逆です。DynamoDB こそ、設計を先にしなければならないデータベースです。テーブルを作ったあとに、探すためのキーを変えることはできません（場面6）。リレーショナルなら後から索引（探しやすくするための目次）を足せますが、DynamoDB で前提が崩れると、テーブルを作り直すことになります。

試験ではこう出る

「複雑な結合」「トランザクション」「既存の Oracle から」→ RDS / Aurora。「一桁ミリ秒」「サーバーレス」「無制限にスケール」→ DynamoDB。「マイクロ秒」→ DAX / ElastiCache。「ペタバイトの集計」「BI」→ Redshift。「マイクロ秒」と書いてあるのに DynamoDB 単体を選ぶ選択肢は不正解。

場面2 ―― 「経理がレポートを流すとアプリが遅くなる」「AZ が落ちても止めたくない」

この場面で初めて出る言葉
DB インスタンス
RDS で動かすデータベース1台のこと。EC2 のインスタンス（EC2 講義で既出）と同じく、CPU とメモリの大きさ（インスタンスクラス）を選ぶ
エンジン
データベースのソフトの種類。RDS では MySQL・PostgreSQL・MariaDB・Oracle・SQL Server などから選ぶ
AZアベイラビリティゾーン
リージョンの中の、離れた場所にあるデータセンターのまとまり（VPC 講義で既出）
複製レプリケーション
あるデータベースへの書き込みを、別のデータベースにも同じように反映すること
同期／非同期
複製先にも書けたことを確かめてから完了を返すのが同期、確かめずに先に完了を返すのが非同期
プライマリ
アプリからの読み書きを受ける、主役の DB インスタンス
スタンバイ
プライマリが使えなくなったときに交代するため、待機しているだけの DB インスタンス
Multi-AZマルチ AZ 配置
別の AZ にスタンバイを置き、同期で複製しておく RDS の設定
リードレプリカ
読み取り専用の複製。非同期で複製し、読み取りの問い合わせを引き受ける
レプリケーションラグ
非同期の複製で、複製先への反映が遅れている時間
フェイルオーバー
主役の台が使えなくなったとき、待機していた台に自動で交代すること
エンドポイント
アプリが接続先として指定する名前（DNS 名）。IP アドレスではなく、この名前でつなぐ
昇格
リードレプリカを、読み書きできる独立したデータベースに切り替えること

RDS は、RDS の画面の「データベースの作成」から作ります。エンジン、インスタンスクラス、ストレージの量を選ぶと、OS やデータベースソフトの導入・更新は AWS がやってくれます。その画面に、データベースを「増やす」設定が2種類あります。どちらも複製ですが、複製のやり方が違うので、できることが違います。

この2つのやり方を、それぞれ別の目的に使ったのが、Multi-AZ とリードレプリカです。

Multi-AZ のスタンバイは、普段なにもしません。「無駄では」と思うかもしれませんが、仕事をさせずに同期で複製だけを受けているから、交代したときにデータの抜けがありません。リードレプリカは逆に、読み取りという仕事をさせるための台です。

交代するとき、何が起きるか

比較表で固める

Multi-AZ 配置リードレプリカ
目的可用性・耐障害性（壊れたときのため）読み取り性能のスケールアウト（混んできたときのため）
複製方式同期非同期
複製先同一リージョンの別 AZ同一 AZ・別 AZ・別リージョンのいずれも可
普段の読み取りできない（スタンバイには接続不可）できる（これが存在理由）
自動フェイルオーバーありなし（手動で昇格させる）
エンドポイント1つ。指す先が切り替わるのでアプリの変更は不要レプリカごとに別。アプリ側で読み書きを振り分ける
データの新しさプライマリと完全に一致レプリケーションラグの分だけ遅れる
バックアップ時の影響スタンバイから取得するので、プライマリの読み書きが止まらない―
どこで設定するか作成時の「可用性と耐久性」。後からは DB インスタンスの「変更」DB インスタンスを選び、「アクション」→「リードレプリカの作成」
  • この場面の答え：レポートの重さはリードレプリカで逃がし、AZ 障害には Multi-AZ で備える。2つは排他ではなく、併用できる
  • スケールアウトは台を横に増やして処理能力を上げること（EC2 講義で既出）。インスタンスクラスを大きくするのはスケールアップ
  • リードレプリカは、RDS for MySQL／MariaDB／PostgreSQL では1つのプライマリあたり最大15個作れる。ただし設問で個数が焦点になることは稀で、問われるのはほぼ上の表の行
最頻出の引っかけ

「読み取りが重いのでレポート用のクエリを逃がしたい。Multi-AZ を有効にする」――不正解です。スタンバイには接続できないので、読み取りの負荷は少しも減りません。逆に「AZ 障害時のダウンタイムを最小化したい。リードレプリカを作る」も不正解です。レプリカは自動では昇格しません。この2つを入れ替えた選択肢は、ほぼ毎回どこかの設問に紛れています。

Multi-AZ DB クラスター ―― 「Multi-AZ なのに読める」形

Multi-AZ には派生形の「Multi-AZ DB クラスター」があります。書き込みを受ける1台（ライター）と、読み取りできるスタンバイ2台の計3台を、3つの AZ に置く構成です。従来の Multi-AZ より速いフェイルオーバーと、スタンバイの読み取り活用を両立します。設問で「Multi-AZ なのに読める」と読めるときは、この構成を指しています。ただし、従来型の「スタンバイは読めない」が原則であることは変わりません。

試験ではこう出る

設問はしばしば「データベースを複製する」とだけ書き、目的を別の文に隠します。複製という語を見たら、その前後で「可用性」と「性能」のどちらが語られているかを探す。「AZ 障害」「ダウンタイム」「可用性」→ Multi-AZ。「読み取りが重い」「レポート」「分析クエリを逃がす」「別リージョンにも」→ リードレプリカ。両方書いてあれば両方。

場面3 ―― 「誤って消したデータを戻したい」「暗号化していない DB を暗号化するよう監査で言われた」

この場面で初めて出る言葉
スナップショット
ある時点のデータを丸ごと写し取ったもの（S3 講義の EBS で既出）。RDS では DB インスタンス全体を写し取る
自動バックアップ
AWS が毎日自動でとるバックアップ。RDS の機能で、DB インスタンスごとに保持期間を決める
トランザクションログ
データベースに加えられた変更を、順番に書き留めた記録
PITRPoint-in-Time Recovery（ポイントインタイムリカバリ）
保持期間の中の、好きな時点の状態に戻すこと
保管時の暗号化
ディスクに置いてあるデータを暗号化しておくこと（S3 講義で既出）
KMSAWS Key Management Service
暗号化に使う鍵を管理するサービス（S3 講義で既出）。RDS の暗号化もこの鍵を使う

「バックアップ」と「スナップショット」は呼び名が似ていますが、誰がとるか、いつまで残るか、どこへ戻せるかが違います。

自動バックアップ手動スナップショット
取得AWS が日次で自動取得。加えてトランザクションログを継続的に保存人またはスクリプトが任意のタイミングで取得
保持期間0〜35日。0 は自動バックアップの無効化を意味する明示的に削除するまで無期限
できる復元ポイントインタイムリカバリ（任意の時点へ）そのスナップショットの時点へ
DB 削除時原則として一緒に削除される残る
別リージョンへクロスリージョン自動バックアップの設定が必要コピーするだけ
どこで設定・操作するかDB インスタンスの設定「バックアップ保持期間」DB インスタンスの「アクション」→「スナップショットの取得」

バックアップからの復元は、常に新しい DB インスタンスの作成になります。既存のインスタンスに上書きすることはできません。復元後はエンドポイントが変わるので、アプリの接続先を切り替える作業が発生します。「復元にかかる時間を最小化したい」と問われたとき、この作り直しが答えの分かれ目になることがあります。

暗号化は最初に決める

RDS の保管時の暗号化は、DB インスタンスを作るときの「暗号化」の欄で有効にし、KMS の鍵を選びます。この設定は後から有効にできません。では、すでに動いている暗号化なしの DB はどうするか。それがそのまま設問になります。

  1. 暗号化されていない DB のスナップショットを取得する
  2. そのスナップショットをコピーする。コピーの操作の中で暗号化を指定する
  3. 暗号化されたコピーから、新しい DB インスタンスを復元する
  4. アプリの接続先を新しいエンドポイントに切り替える

暗号化された DB のリードレプリカやスナップショットは、自動的に暗号化されます。暗号化を外すことはできません。逆に、暗号化されていない DB から、暗号化されたリードレプリカを作ることもできません。

止めても、料金は止まらない

RDS の DB インスタンスは「アクション」→「一時的に停止」で止められますが、止まるのはインスタンスの料金だけです。あらかじめ確保したストレージ（プロビジョニング済みストレージ）とバックアップの料金は続きます。Multi-AZ にしていれば、台数ぶんのストレージ料金がかかります。

試験ではこう出る

「特定の時刻の状態に戻したい」→ 自動バックアップの PITR。「DB を削除した後も残したい」「別リージョンに退避」→ 手動スナップショット（のコピー）。「既存の DB を暗号化したい」→ スナップショットをコピーするときに暗号化を指定し、復元する。「インスタンスの変更で暗号化を有効にする」「EBS ボリュームを直接暗号化する」は不正解。「週末は停止して費用をゼロに」も不正解。

場面4 ―― 「Lambda から RDS につないだら、アクセスが増えたときに接続エラーで落ちる」

この場面で初めて出る言葉
接続コネクション
アプリとデータベースの間に張る通信の道。問い合わせの前に張っておく必要があり、データベースが同時に持てる数には上限がある
コネクションプール
張った接続を使い捨てにせず、ためておいて使い回す仕組み
RDS ProxyAmazon RDS Proxy
アプリと RDS／Aurora の間に置く、AWS が管理するコネクションプール
実行環境
Lambda が関数を動かす小さな箱。同時に届いた数だけ作られる（EC2 講義の場面7で既出）
Secrets ManagerAWS Secrets Manager
データベースのパスワードなどの秘密の値を預けておくサービス
IAM 認証
パスワードの代わりに、IAM のロール（IAM 講義で既出）で「誰か」を確かめてデータベースに接続する方法

EC2 講義の場面7で、Lambda は同時に届いた数だけ実行環境が増え、下流を潰すことを見ました。その「下流」の代表が RDS です。あのときは Lambda の側を絞りました（予約済み同時実行）。ここでは、RDS の手前に置く道具を見ます。

どこで設定するか：RDS の画面の「プロキシ」から作り、対象の DB と、認証情報を預けた Secrets Manager のシークレットを選びます。アプリ（Lambda）の接続先を、DB のエンドポイントからプロキシのエンドポイントに替えます。

SAA で問われる使いどころは、ほぼ次の2つです。

  • 同時実行数が急に増える構成：Lambda のように、呼び出しごとに接続を張る相手が大量に増える場合。設問に「Lambda」「コネクション枯渇」「too many connections」が出たら RDS Proxy
  • フェイルオーバー時のダウンタイムを短くしたい：Proxy はアプリからの接続を保ったまま、裏側で新しいプライマリへ張り替える。アプリから見た切り替え時間が短くなる

あわせて、DB の認証情報を Secrets Manager で管理し、アプリからは IAM 認証で Proxy に接続する構成が取れます。「認証情報をアプリに持たせたくない」という要件と組み合わせて出題されます。IAM 講義の「鍵を配らず、ロールで許す」という原則が、そのまま効く場面です。

試験ではこう出る

「Lambda が多重に起動して DB の接続が枯渇する」→ RDS Proxy。「フェイルオーバー時にアプリの接続が切れる時間を短くしたい」→ RDS Proxy。「DB のパスワードをコードに書きたくない」→ Secrets Manager ＋ IAM 認証。インスタンスクラスを大きくする選択肢は、接続数の根本的な解決にならないので不正解側。

Aurora は RDS の画面の「データベースの作成」で、エンジンに Aurora（MySQL 互換／PostgreSQL 互換）を選んで作ります。Aurora を「速い RDS」と覚えていると、設問の半分を落とします。特徴はほぼすべて、計算する台とデータの置き場が分かれているという一点から出てきます。

  • レプリカを追加してもデータのコピーが起きない：同じストレージを見るだけなので、追加が速く、レプリケーションラグも小さい
  • ストレージの容量設計が要らない：10GB 単位で自動的に拡張する。上限は Aurora のバージョンによって 128 TiB または 256 TiB。RDS が割り当てた容量に課金されるのに対し、使った分だけ増える

負荷に合わせて伸び縮みさせる

読み取りが日中だけ跳ねるなら、リーダーを固定の台数で持つより、クラスターの「アクション」→「レプリカの Auto Scaling の追加」で Aurora Auto Scaling を付けます。CPU 使用率や接続数を目安に、リーダーが自動で増減します（EC2 講義のターゲット追跡と同じ考え方です）。

もう一段進んだのが Aurora Serverless v2 です。インスタンスクラスを選ぶ代わりに、ACU の下限と上限を指定し、負荷に応じて 0.5 ACU 刻みで自動的に能力が変わります。上限は最大 256 ACU。対応バージョンでは下限を 0 にして、使っていない間は一時停止させることもできます。

  • 使いどころ：開発環境、負荷が予測できないアプリ、断続的にしか使われないワークロード。「ピークが読めない」「使わない時間が長い」と書いてあれば候補
  • 使わないところ：負荷が安定しているシステム。常時動いているなら、プロビジョンドのほうが費用対効果は高い

リージョンをまたぐ ―― Aurora Global Database

プライマリリージョンのクラスターから最大10のセカンダリリージョンへ、専用の基盤で複製します。「リージョン障害からの復旧を分単位で」「複数大陸にまたがる読み取り」といった語が手がかりです。別リージョンに置いたリードレプリカ（クロスリージョンのリードレプリカ）でも似たことはできますが、遅れの小ささと昇格の速さで Global Database が選ばれます。

誤操作を巻き戻す ―― Backtrack

  • Aurora MySQL 互換でのみ使える。PostgreSQL 互換では使えない
  • 巻き戻せる幅は最大72時間
  • クラスターの作成時に有効にしておく必要がある。後から既存のクラスターに追加することはできない
  • 巻き戻しの間、データベースは短時間停止する。無停止ではない
試験ではこう出る

「レプリカを追加してもアプリケーションを変更したくない」→ Aurora のリーダーエンドポイント。「ピークが読めない」「使わない時間が長い」→ Aurora Serverless v2。「リージョン障害から分単位で復旧」「世界各地で低遅延の読み取り」→ Aurora Global Database。「誤操作からの高速な復旧」でエンジンが Aurora MySQL なら Backtrack。PostgreSQL だったり、72時間より前に戻したければポイントインタイムリカバリ。「別リージョンに退避したい」ならスナップショットのコピー。要件の時間軸と、エンジンの2つを見る。

DynamoDB のテーブルは、DynamoDB の画面の「テーブルの作成」で、テーブル名とパーティションキー（必要ならソートキー）を入れるだけで作れます。サーバーの大きさも台数も選びません。その代わり、ここで決めるキーが、そのテーブルにできることの大半を決めます。

  • パーティションキーのみ：値が1アイテムを指す。ユーザーID で引くだけのテーブルなど
  • パーティションキー ＋ ソートキー（複合キー）：同じパーティションキーの中に複数のアイテムが並び、ソートキーで順序が決まる。「顧客ごとの注文履歴を日時順に」といった形

パーティションキーは、置き場を決める

だから、パーティションキーは値が広く散らばっていることが重要です。設問では「一部のキーだけスロットリングされる」という形で現れます。対処は、キーに接尾辞（末尾に付ける番号など）を付けて分散させるか、より散らばる属性を選び直すことです。

読み方は Query と Scan

ソートキーが効くのは範囲の問い合わせです。「この日付以降」「この接頭辞（先頭の文字列）で始まるもの」を Query 一発で取れます。逆に、キーにない条件で絞りたい場合は、Scan で全件を読んでから絞ること（FilterExpression）になります。

キャパシティモードは、テーブルを作るときの設定で選びます（後からテーブルの「追加の設定」で切り替えられます）。

  • プロビジョンドモード：1 WCU は、1KB までのアイテムを毎秒1回書き込む能力。1 RCU は、4KB までのアイテムを毎秒1回強い整合性で読む、または毎秒2回結果整合性で読む能力。トランザクション（複数アイテムの読み書きをまとめる機能）を使う場合は、この2倍を消費する。負荷が予測できるなら最も安い。Auto Scaling を併用すれば、指定した範囲内で自動的に増減する
  • オンデマンドモード：事前の指定が不要。単価はプロビジョンドより高いが、量の見積もりが要らない。負荷が予測できない、急な山（スパイク）がある、新規サービスで実績がない――このいずれかが設問に書かれていればオンデマンド

書いた直後に読むと古い ―― 整合性

どこで設定するか：テーブルの設定ではなく、読み取りのたびにアプリが指定します（読み取りの API に ConsistentRead というパラメータがあり、これを有効にすると強い整合性になります）。強い整合性は、キャパシティを2倍使い、応答もやや遅くなります。

場面6の表にあったとおり、GSI からの読み取りは常に結果整合性です。「強い整合性が必要」かつ「主キー以外で引く」という要件が並んだら、GSI では成立せず、LSI が答えになります。

永続化・バックアップあり（スナップショットから復元できる）なし（ノードが落ちればデータは消える）
Pub/Subありなし
マルチスレッドなしあり（CPU のコアを使い切れる）
水平分割クラスターモード有効時にシャーディング可能ノード間でデータを分散できる

表の言葉のうち、永続化はメモリの中身をディスクにも残すこと、Pub/Sub は「発信する側」と「受け取る側」をつないでメッセージを配る仕組み、ソート済みセットは得点順に並んだ一覧（ランキング＝リーダーボードに使う）、シャーディングはデータを複数のノードに分けて持つことです。

  • 消えたら困る／高可用性が要る／複雑なデータ構造が要る → Redis。設問に「フェイルオーバー」「永続化」「リーダーボード」「Pub/Sub」「セッション」のいずれかが出たら Redis
  • 消えても作り直せる単純なキャッシュで、とにかく安く速く、横に足していきたい → Memcached。「シンプルなキャッシュ」「スケールアウトしたいだけ」という書き方をされる

迷ったときは Redis が無難です。Memcached が正解になるのは、設問が明示的に「機能は不要」「シンプルで十分」と言っているときに限られます。

もう1つの使い道 ―― セッションの置き場

EC2 講義の場面4で、スティッキーセッションは「解ではなく回避策」で、正しいのはセッションを台の外に出すことだと見ました。その「外の置き場」が、ElastiCache（Redis）か DynamoDB です。

  • スティッキーセッション：手軽だが、その台が落ちるとセッションが消え、負荷も偏る
  • 外部のセッションストア：ElastiCache for Redis か DynamoDB にセッションを置き、アプリの台をステートレスにする。これが SAA の推す答え
試験ではこう出る

「同じ問い合わせが繰り返され DB の読み取りが重い」→ ElastiCache。「フェイルオーバー」「永続化」「リーダーボード」「Pub/Sub」→ Redis。「シンプルなキャッシュで十分」→ Memcached。「Auto Scaling で台が入れ替わるとログアウトする」→ セッションを ElastiCache for Redis か DynamoDB へ。「ステートレスにする」は SAA 全体を貫く設計の考え方で、「状態をどこに置くか」を問う設問では、台の外に出す選択肢が正解。

移行 ―― DMS と SCT の分担

判断は単純です。エンジンが変わるなら SCT が要る。変わらないなら DMS だけでよい。Oracle から Aurora PostgreSQL への移行なら別のエンジン（異種間）なので SCT ＋ DMS、オンプレミスの MySQL から RDS for MySQL への移行なら同じエンジン（同種間）なので DMS のみです。

どこで設定するか：DMS の画面で、作業用の台（レプリケーションインスタンス）、移行元と移行先の接続情報（エンドポイント）、何をどう運ぶか（タスク）を作ります。タスクの種類で「既存データの移行と、継続的な変更のレプリケーション」を選ぶと、図の①②を続けて行います。

ダウンタイムの扱い

移行の設問では、ほぼ必ず「ダウンタイムを最小化したい」という条件が付きます。答えになるのは DMS の継続的レプリケーション（CDC）です。「一度エクスポートして、深夜にインポートする」という選択肢はもっともらしく見えますが、停止時間が長くなるため要件を満たしません。

試験ではこう出る

「ペタバイト規模の集計」「BI」「データウェアハウス」→ Redshift。「S3 に置いたまま Redshift から」→ Spectrum。「クラスターなしで S3 に SQL」→ Athena。「MongoDB 互換」→ DocumentDB。「グラフ・関係性」→ Neptune。「時系列・IoT」→ Timestream。「Cassandra 互換」→ Keyspaces。移行は「エンジンが変わるか」と「止められるか」の2軸で切る。

確認問題

先に自分で答えを決めてから開いてください。当てずっぽうで開くと、この5分が無駄になります。

Q1RDS for PostgreSQL で稼働する業務システムがある。日中、経理部門が実行するレポートクエリによってアプリケーションの応答が悪化する。加えて、AZ障害時のダウンタイムも最小化したい。適切な構成はどれか。
  • A. Multi-AZ 配置を有効にし、レポートクエリはスタンバイに向ける
  • B. リードレプリカを2台作成し、障害時はそのうち1台を手動で昇格させる
  • C. Multi-AZ 配置を有効にしたうえで、リードレプリカを作成してレポートクエリを向ける
  • D. インスタンスクラスを2段階大きいものに変更する

正解: C

場面2の左右の図を、両方使う問題。「レポートで応答が悪化する」は読み取り性能の話（右：リードレプリカ）、「AZ障害時のダウンタイム」は可用性の話（左：Multi-AZ）。両方が書かれているなら両方を使う。この2つは排他ではなく、併用できる。

判断軸: A はスタンバイに接続できないので成立しない。B は自動フェイルオーバーがなく、可用性の要件を満たさない。D はスケールアップで一時的に楽にはなるが、可用性の要件に何も答えていない。要件が2つ書かれている設問では、片方しか解いていない選択肢を落とす。

Q2DynamoDB のテーブルが本番稼働中である。新しい画面の要件として、これまで主キーに使っていなかった「ステータス」属性で絞り込む検索を追加する必要が出た。結果整合性の読み取りで問題ない。最も適切な対応はどれか。
  • A. LSI を作成し、ステータスをソートキーにする
  • B. GSI を作成し、ステータスをパーティションキーにする
  • C. Scan に FilterExpression を付けてステータスで絞り込む
  • D. テーブルを作り直し、パーティションキーをステータスに変更する

正解: B

場面6の GSI と LSI の図の右側。GSI はテーブル作成後でも追加でき、パーティションキーを自由に選べる。「結果整合性で問題ない」という条件も、GSI の制約と合っている。

判断軸: A は、LSI がテーブル作成時にしか作れないので不可能。C は動くが、場面6の Query と Scan の図のとおり全アイテムを読んでから絞るので、キャパシティを浪費し、テーブルが育つほど悪化する。D は既存データの移行が必要で、既存の検索も壊れる。「稼働中」「後から」という語を見た瞬間に、LSI と作り直しが消える。

Q3暗号化されていない RDS for MySQL のインスタンスが本番で稼働している。監査要件により、保管時の暗号化が必須になった。実施すべき手順はどれか。
  • A. インスタンスを変更し、暗号化オプションを有効にする
  • B. スナップショットを取得し、そのスナップショットを暗号化を指定してコピーし、コピーから新しいインスタンスを復元する
  • C. 暗号化されたリードレプリカを作成し、それを昇格させる
  • D. EBS ボリュームを直接暗号化する

正解: B

場面3の「後から暗号化する手順」の図そのもの。RDS の暗号化は作成時にしか設定できない。既存の DB を暗号化する唯一の経路が、スナップショットのコピー操作で暗号化を指定するこの手順。復元後にエンドポイントが変わるため、アプリの切り替えが伴う。

判断軸: A は「後から有効にできない」という制約に反する。C は、暗号化されていない DB から暗号化されたリードレプリカを作ることができない（逆に、暗号化された DB のレプリカは必ず暗号化される）。D は、RDS では AWS がディスクを管理しており、利用者が基盤のボリュームに直接触れないので不可能。「後から変えられない設定」は SAA の頻出テーマで、暗号化はその代表。

Q4EC2 の Auto Scaling グループで動く Web アプリケーションがある。スケールインでインスタンスが終了すると、そのインスタンスに接続していた利用者がログアウトしてしまう。今後はリージョン障害にも備えたい。最も適切な対応はどれか。
  • A. ロードバランサーでスティッキーセッションを有効にする
  • B. セッション情報を各インスタンスのローカルディスクに書き出す
  • C. セッション情報を ElastiCache for Redis または DynamoDB に外部化する
  • D. スケールインを無効にし、インスタンス数を固定する

正解: C

場面8の「セッションの置き場」の図の右側。アプリの台をステートレスにし、セッションを外の置き場に持たせる。台が入れ替わっても、どの台に当たってもセッションが続く。リージョン障害への備えという点でも、Redis のレプリケーションや DynamoDB Global Tables（場面7）で複製先を持てる。

判断軸: A は、台が終了すれば結局セッションが失われ、根本解決にならない。B は、ローカルディスクが台と運命をともにするので意味がない。D は Auto Scaling の利点を捨てており、そもそも要件（スケールさせたい）に反する。「状態をどこに置くか」を問う設問では、台の外に出す選択肢が正解。

Q5オンプレミスの Oracle データベースを AWS へ移行する。移行先は Aurora PostgreSQL とし、移行中も業務は止められない。必要な作業の組み合わせはどれか。
  • A. DMS のみを使い、継続的レプリケーションで移行する
  • B. SCT でスキーマを変換し、DMS の継続的レプリケーションでデータを移行する
  • C. Oracle の物理バックアップを S3 に置き、Aurora に復元する
  • D. 深夜にデータをエクスポートし、翌朝までにインポートを完了させる

正解: B

場面9の移行の図の、中段と下段。Oracle から PostgreSQL は別のエンジンへの移行（異種間）なので、表の定義やストアドプロシージャを SCT で書き換える。そのうえで「止められない」という条件があるので、DMS の継続的レプリケーション（CDC）で、切り替えの直前まで差分を反映し続ける。

判断軸: A は同じエンジンどうしなら成立するが、今回はスキーマの変換が抜けている。C は、Oracle の物理バックアップを別のエンジンに復元することはできない。D は停止時間が発生し、「止められない」という条件に反する。移行の設問は「エンジンが変わるか」と「止められるか」の2軸で切ると、ほぼ一意に決まる。
