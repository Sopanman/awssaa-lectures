01

全体の地図

セキュリティサービスは、守るものと見張るものに分かれます。守る側は「置いてあるデータを暗号化する」「通り道を暗号化する」「入口で攻撃を止める」の3つ。見張る側は何も止めませんが、起きたことや弱点を教えます。まず登場人物を紹介してから、9つの場面がどこの話かを見ます。

この講義の登場人物
KMSAWS Key Management Service
暗号化に使う鍵を作り、保管し、使わせるサービス。S3・EBS・RDS などの暗号化は、裏でこれを呼んでいる → 場面2〜4
Secrets ManagerAWS Secrets Manager
データベースのパスワードなどを預かり、定期的に取り替えるサービス → 場面5

CloudFront・ALB
利用者からの通信を最初に受ける入口。CloudFront は世界中の拠点から配信するサービス（VPC 講義で既出）、ALB は HTTP の中身を見て配るロードバランサー（EC2 講義で既出）
WAFAWS WAF（Web Application Firewall）
HTTP リクエストの中身を読んで、攻撃を止めるサービス → 場面7
ShieldAWS Shield
大量の通信を送りつける攻撃（DDoS）を和らげるサービス → 場面7

GuardDuty・Inspector・Macie・Config・Security Hub・Detective。どれも「見張る」サービスで、止めはしない → 場面8

この講義の見取り図

場面1〜4は置いてあるデータの暗号化（何を暗号化と呼ぶか、鍵の種類、仕組み、鍵の運用）。場面5・6は秘密の置き場と通り道（パスワードと証明書）。場面7は止める、場面8は見張る、場面9は利用者を確かめるです。

IAM はアクセスの可否を決める仕組みでした。この講義が扱うのは、IAM では守れない領域――ディスクの盗難、通信の盗聴、アプリへの攻撃、設定ミスの放置――への備えです。IAM の代わりではなく、上に積み重ねます。設問に「多層防御（defense in depth）」とあれば、「対策を1つだけ選ぶ選択肢は不正解」という合図です。

02

場面1 ―― 「データを暗号化しろと言われた。RDS を使っているから、AWS がやってくれるのでは？」

この場面で初めて出る言葉
暗号化
鍵を使って、データを読めない形に変えること。元に戻すことを復号と呼ぶ
平文／暗号文
暗号化する前の読めるデータが平文、暗号化した後の読めないデータが暗号文
保管時の暗号化encryption at rest
ディスクやバケットに置いてあるデータを暗号化すること
転送時の暗号化encryption in transit
ネットワークを流れている途中のデータを暗号化すること
TLSTransport Layer Security
通信を暗号化する決まりごと。これを使った Web の通信が HTTPS → 場面6
責任共有モデル
セキュリティの作業のうち、どこまでが AWS の担当で、どこからが利用者（顧客）の担当かを決めた取り決め
マネージド
運用（故障対応やパッチ当て）を AWS が代わりにやってくれること。その度合いはサービスごとに違う
パッチ
ソフトウェアの弱点を直す更新プログラム
ハイパーバイザー
1台の物理サーバーの上で、複数の仮想サーバー（EC2）を動かす土台のソフトウェア

種類の話に入る前に、暗号化が何を守っているのかを1枚で確かめます。

保管時か、転送時か

暗号化の設問は、ほぼすべてが2つのどちらかです。設問は「暗号化したい」とだけ書くことは少なく、状況の描写にヒントを埋めてきます。

軸守る対象中心になるサービス設問に出る語
保管時ディスク、オブジェクト、バックアップ、ログKMS（と各サービスの暗号化の設定）、CloudHSM（場面4）スナップショット、バケット、アーカイブ、媒体の廃棄、鍵の管理
転送時利用者とサービスの間、サービス同士の間ACM（証明書）、TLS の終端（場面6）、VPN、PrivateLinkHTTPS、TLS、盗聴、傍受、公衆インターネットを経由させたくない

「AWS がやってくれる」のはどこまでか

CLF では「AWS はクラウドのセキュリティ、顧客はクラウド内のセキュリティ」という標語で覚えたはずです。SAA では標語ではなく、具体的な作業がどちらの担当かを問われます。

  • この場面の答え：RDS でも、暗号化を有効にするかどうかを決めて設定するのは自分。AWS が肩代わりするのは、設備とソフトウェアの保守まで
  • 設定する場所：保管時の暗号化は、各サービスでリソースを作るときの設定項目にある（RDS ならデータベースの作成画面、EBS ならボリュームの作成画面、S3 ならバケットの「デフォルトの暗号化」）。そこでどの KMS キーを使うかを選ぶ
  • ディスク媒体の廃棄・消去は、どのサービスでも AWS の担当
最頻出の引っかけ

「RDS を使っているので、認証情報の管理も AWS の責任である」――誤りです。マネージドサービスでも、アクセス制御と設定は常に顧客側。責任共有モデルの設問で、アクセス制御・暗号化の有効化・データの分類のどれかが AWS 側に振られている選択肢は、読んだ時点で消せます。

試験ではこう出る

「スナップショット」「バケット」「媒体の廃棄」→ 保管時（KMS）。「HTTPS」「盗聴」「中間者」→ 転送時（ACM と TLS）。両方を求められたら二段構えの選択肢。「インターネットを経由させたくない」は暗号化ではなく経路の話なので、VPC エンドポイント / PrivateLink（VPC 講義で既出）。「EC2 の OS のパッチは誰の担当か」→ 顧客。「RDS の OS のパッチは」→ AWS。

場面2 ―― 「鍵がいつ誰に使われたかを記録したい。特定のロールにだけ復号を許したい」

この場面で初めて出る言葉

KMS の中に作る鍵。暗号化と復号の「元締め」になる。リージョンごとに作る
AWS 所有キーAWS owned key
AWS がサービスの裏側で使っている鍵。利用者のアカウントからは見えない
AWS マネージドキーAWS managed key
S3 や EBS を使うと自動で作られる鍵。aws/s3 のような名前で一覧に出るが、設定は変えられない
カスタマー管理キーCustomer managed key。問題集では CMK と略すことがある
自分で作る鍵。使える人・周期・共有・削除を自分で決められる
キーポリシー

kms:Decrypt
KMS キーで復号する、という操作の名前。IAM ポリシーやキーポリシーの Action に書く
プリンシパル
操作をする主体。ユーザーやロールのこと（IAM 講義で既出）
ローテーション

KMS キーは、KMS のコンソールの「カスタマー管理型のキー」で作ります。S3・EBS・RDS・DynamoDB・Secrets Manager・SNS・SQS など、ほぼすべてのサービスの暗号化が KMS を呼んでいます。最初に押さえるのは、キーに3種類あることです。この分け方が、料金・ローテーション・共有の設問すべてに効きます。

AWS 所有キーAWS マネージドキーカスタマー管理キー
誰が作るかAWS がサービス横断で用意サービスを使うと自動で作られる自分で作る
ローテーションAWS が管理（設定不可）年1回で固定（止められない）任意。既定 365日、90〜2560日で指定可
削除不可不可待機期間つきで可能（場面4）
料金無料キー自体は無料、API 呼び出しは課金1キーあたり月額 1 USD ＋ API 呼び出し
  • この場面の答え：カスタマー管理キーを作り、キーポリシーで復号できるロールを絞る。鍵が使われた記録は CloudTrail（API 呼び出しを記録するサービス、IAM 講義で既出）に残る
  • 逆の場面：「特別な要件はなく、暗号化されていればよい」「運用の手間を最小に」なら AWS マネージドキーで足りる

関所は2つある ―― キーポリシーと IAM ポリシー

KMS で最も間違えやすい部分です。KMS キーには必ずキーポリシーが付きます。S3 バケットのように「リソース側のポリシーを付けない」という選択はできず、空にもできません。そして、IAM ポリシーで許可するだけでは足りません。

キーポリシーは、KMS のコンソールでキーを開いた「キーポリシー」タブで編集します。既定のキーポリシーには、次の一文が入っています。

既定のキーポリシーに入っている「委ねる」一文
{
  "Sid": "Enable IAM User Permissions",
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::111122223333:root" },
  // ↑ root ユーザーに許すという意味ではなく、
  //   「このアカウントの IAM ポリシーに判断を委ねる」という定型句
  "Action": "kms:*",
  "Resource": "*"
}

この一文を外したり、狭い条件に書き換えたりすると、管理者権限を持っていてもキーを使えなくなります。

最頻出の引っかけ

「IAM ポリシーで kms:Decrypt を許可したのに、暗号化された S3 オブジェクトが読めない。原因は？」――キーポリシーでそのプリンシパルが許可されていない、が答えです。バケットポリシーや IAM ポリシーの書き間違いを疑う選択肢が並びますが、KMS が絡む「読めない」は、まずキーポリシーを見ます。暗号化されたオブジェクトを読むには、S3 側の権限と KMS 側の権限の両方が要ります。

別アカウントから使うときは3か所

試験ではこう出る

「鍵の使用を監査したい」「特定のロールだけに復号を許したい」「別アカウントと共有したい」「独自のローテーション周期にしたい」「鍵を無効化して即座にアクセスを遮断したい」――どれか1つでも出たらカスタマー管理キー。AWS マネージドキーはキーポリシーを触れないので、どれも満たせない。

場面3 ―― 「数 GB のログを KMS で暗号化している。中で何が起きているのか説明してほしい」

この場面で初めて出る言葉
鍵素材key material
鍵の実体であるビット列。KMS キーの鍵素材は KMS の外に出ない
データキー
データ本体を暗号化するために、その場で作る使い捨ての鍵
エンベロープ暗号化envelope encryption
データをデータキーで暗号化し、そのデータキーを KMS キーで暗号化する二階建ての方式。エンベロープは「封筒」
GenerateDataKey
KMS にデータキーを作らせる API（KMS に頼む操作）の名前
SSE-KMSServer-Side Encryption with AWS KMS keys
S3 が KMS キーを使ってオブジェクトを暗号化する方式（S3 講義で既出）。KMS を使わず S3 自身の鍵で暗号化するのが SSE-S3
S3 バケットキー
SSE-KMS で KMS を呼ぶ回数を減らすための、バケット単位の短期の鍵

S3 の暗号化も EBS の暗号化も、同じ1つの仕組みの応用です。まず、なぜ鍵が二階建てになるのかを見ます。

この二階建てを、暗号化するときと復号するときの手順に並べたのが次の図です。S3 や EBS を使っているときは、この手順を各サービスが代わりにやっています。

  • この場面の答え：ファイル全体が KMS に送られるのではない。KMS が作ったデータキーでファイルを暗号化し、そのデータキーを KMS キーで暗号化して、暗号文と一緒に保存している
  • なぜ数 GB でも成り立つか：KMS を往復するのは小さなデータキーだけだから
  • 復号には毎回 KMS が要る：だから「キーを無効化する」「キーポリシーから外す」だけで、暗号文を持っている相手からもアクセスを断てる

KMS を呼ぶ回数が料金になる ―― S3 バケットキー

S3 バケットキーは、バケットの「プロパティ」→「デフォルトの暗号化」で有効にします。

試験ではこう出る

「KMS での暗号化の動作として正しいものは」→ データキーで暗号化し、データキーを KMS キーで暗号化して一緒に保存。「ファイル全体を KMS に送る」「鍵素材が S3 にコピーされる」「復号に KMS は不要」はすべて誤り。「SSE-KMS を使いたいが、KMS のリクエスト料金を抑えたい」→ S3 バケットキー（暗号化をやめる、SSE-S3 に切り替える、は要件を満たさない）。

場面4 ―― 「鍵を定期的に替えたい」「別リージョンでも復号したい」「要らない鍵を消したい」「専用の装置を求められた」

KMS が決まった周期で、キーの鍵素材を新しく作り直す機能

鍵を替える ―― 自動ローテーション

自動ローテーションは、KMS のコンソールでカスタマー管理キーを開いた「キーローテーション」タブで有効にします。

  • カスタマー管理キー：有効にすると既定で 365日ごと。周期は 90〜2560日で指定できる
  • AWS マネージドキー：年1回のローテーションが強制で、設定は変えられない
  • 「ローテーションすると過去のデータが読めなくなる」と心配させる選択肢は不正解
自動ローテーションできないキー

自動ローテーションが使えるのは、KMS が鍵素材を作った対称暗号化キーだけです。インポートした鍵素材のキー、非対称キー、HMAC キー、カスタムキーストア上のキーは対象外。これらを替えたいときは、新しいキーを作ってエイリアスを付け替える手動ローテーションになります。設問に「オンプレミスで生成した鍵素材を使う」とあれば、自動ローテーションを答えにする選択肢は消えます。

別リージョンでも復号する ―― マルチリージョンキー

使いどころは、暗号化されたデータを別リージョンへ運ぶ設計です。S3 のクロスリージョンレプリケーション（S3 講義で既出）、DynamoDB グローバルテーブル（DB 講義で既出）、ディザスタリカバリ（災害時に別リージョンで復旧する備え）で出てきます。マルチリージョンにするかどうかは、キーを作る画面で選びます。

鍵を消す ―― まず無効化

無効化も削除のスケジュールも、KMS のコンソールでキーを選んだ「キーのアクション」から行います。マルチリージョンのプライマリキーは、すべてのレプリカを削除し終えてからでないと待機期間が始まりません。

専用の装置を求められた ―― CloudHSM

AWS KMSAWS CloudHSM
鍵の管理主体AWS が運用。AWS は鍵素材を取り出せない設計だが、サービス自体は AWS が管理顧客が完全に管理。AWS は HSM 内の鍵にアクセスできない
AWS サービスとの統合S3・EBS・RDS など広く統合済み直接の統合は限定的（カスタムキーストア経由で橋渡し）
特殊な用途対称・非対称の一般的な用途SQL Server / Oracle の TDE、独自の認証局（→ 場面6）、コード署名、SSL オフロード（暗号化通信の処理を HSM に肩代わりさせること）
試験ではこう出る

「暗号化データを別リージョンでも復号したい」→ マルチリージョンキー（「既存のキーをマルチリージョン化する」は不可能なので不正解）。「鍵を消したいが、まだ使われているかもしれない」→ まず無効化、確認してから削除をスケジュール。「専用のハードウェアセキュリティモジュール」「FIPS 140-3 レベル3」「鍵素材に AWS が一切アクセスできない」「規制当局から鍵の単独管理を求められた」→ CloudHSM。書いていなければ KMS。「AWS サービスとの統合は保ちつつ、鍵は専用 HSM に」→ KMS カスタムキーストア。

パスワードをコードや環境変数に直接書くと、取り替えるたびにアプリを直して配り直すことになります。そこで、パスワードを外の置き場に預け、アプリには「使うときに聞きに行く」だけをさせます。

  • もっと手間を減らす：RDS・Aurora のデータベースを作る画面で「マスター認証情報を Secrets Manager で管理する」を選ぶと、パスワードの作成からローテーションまで任せられる（マネージドマスターユーザーパスワード）

よくある誤解

「Parameter Store は暗号化できない」――できます（SecureString 型）。両者の差はローテーション・コスト・共有であって、暗号化できるかどうかではありません。なお Parameter Store からは /aws/reference/secretsmanager/ というパスで Secrets Manager のシークレットを参照できます。アプリのコードは Parameter Store を読む形に揃えたまま、秘密だけ Secrets Manager に置けます。

試験ではこう出る

転送時の暗号化の主役は TLS で、TLS の主役は証明書です。まず、証明書がどこで何をしているかを見ます。

ACM は、パブリック証明書を無料で発行し、自動で更新するサービスです。ACM のコンソールで「証明書をリクエスト」し、できた証明書を CloudFront のディストリビューションや ALB のリスナー（EC2 講義で既出）の設定で選びます。設問で問われるのは、機能そのものより置ける場所の制約です。

  • この場面の答え：証明書を us-east-1 以外（たとえば東京）で発行していた。ACM で us-east-1 に同じドメインの証明書を発行し、それを CloudFront に指定する。CloudFront を作り直す必要はない
  • 1つのドメインについて、複数のリージョンで証明書を持っても問題ない
EC2 に TLS が必要なとき

「EC2 上のアプリで HTTPS を終端したい」と来たら、SAA の答えは基本的に「ALB や CloudFront で TLS を終端し、EC2 は背後に置く」です。それでも EC2 自身に証明書が要るなら、AWS Private CA のプライベート証明書か、自分で用意した証明書になります。Private CA は内部の通信用で、一般のブラウザには信頼されません。「社内システム間の相互 TLS（お互いに証明書を見せ合う通信）」とあれば Private CA です。

自動更新が働く条件

試験ではこう出る

「CloudFront の設定画面に証明書が出てこない」→ us-east-1 で発行し直す（「証明書をエクスポートして持っていく」は、秘密鍵を取り出せないので不可能）。「証明書の更新を完全に自動化したい」→ ACM 発行 ＋ DNS 検証。「証明書が期限切れになった。なぜか」→ インポートした証明書だった／どこにも付けていなかった／E メール検証の承認をしなかった。「インポートした証明書の期限切れを防ぎたい」→ EventBridge で通知、または AWS Config のルールで検出（EventBridge と Config は場面8）。手動でカレンダーに入れる選択肢は常に不正解。

場面7 ―― 「Web サイトへの SQL インジェクションを止めたい。攻撃してくる IP アドレスも遮断したい」

この場面で初めて出る言葉

通信のどこを見るかの呼び名。L3 は IP アドレス、L4 はポート番号、L7 は HTTP の中身（EC2 講義の場面4で既出）

通信を止めるサービスは、全部が同じに見えるので混乱します。止める場所とどこまで読むかで並べると、設問の手がかりと一対一で対応します。セキュリティグループ（SG）とネットワーク ACL は VPC 講義で扱いました。

  • この場面の答え：SQL インジェクションは HTTP の中身の話なので WAF。特定の IP の遮断は、WAF の IP セットかネットワーク ACL の拒否ルール
  • セキュリティグループでは遮断できない：許可しか書けないので、「この IP だけ拒否」が書けない
  • ネットワーク ACL：番号の小さいルールから順に評価する。ステートレスなので、戻りの通信も明示的に許可が要る
  • 外向きの通信を宛先のドメイン名で絞る：Network Firewall（または Route 53 Resolver DNS Firewall。VPC の中からの名前の問い合わせを、ドメイン名で許可・拒否する機能）

WAF のルール

WAF は、WAF のコンソールで Web ACL を作り、守りたい CloudFront・ALB・API Gateway（API の入口を作るサービス、場面6で既出）・AppSync（GraphQL という形式の API を作るサービス）などに関連付けて使います。

  • マネージドルールグループ：OWASP Top 10 相当の防御を、自分でルールを書かずに有効にできる。AWS のものと、マーケットプレイスのベンダーのものがある
  • レートベースルール：5分間の枠で送信元 IP ごとのリクエスト数を数え、しきい値を超えた IP をブロックする
  • 地理的一致ルール：CloudFront の地理的制限でも似たことができるが、WAF のほうがほかの条件と細かく組み合わせられる

DDoS ―― Shield Standard と Advanced

試験ではこう出る

「SQL インジェクション」「XSS」「既知の悪性ボット」→ WAF。「迅速に、運用負荷を抑えて一般的な攻撃を防ぐ」→ マネージドルールグループ。「単一の IP から大量のリクエスト」「ログイン画面への総当たり」→ レートベースルール。「サービス提供国以外を遮断」→ 地理的一致ルール。「特定の IP だけをブロック」→ ネットワーク ACL の拒否ルールか WAF の IP セット（SG を選ぶ選択肢は必ず不正解）。「最低限の DDoS 対策」→ Shield Standard（すでに有効）。「攻撃による予期しない課金を避けたい」「SRT の支援」→ Shield Advanced。

最頻出の引っかけ

「S3 バケットに個人情報が保存されていないか確認したい」で GuardDuty を選ぶ――不正解です。GuardDuty の S3 保護は「S3 へのアクセスが不審かどうか」を見るもので、オブジェクトの中身は分類しません。GuardDuty は中身を見ず、Inspector は振る舞いを見ず、Macie は S3 の外を見ない。この3つを言えれば、この系統の設問は落としません。

試験ではこう出る

「アプリの利用者が直接 S3 にアップロード」「モバイルアプリから DynamoDB を読む」→ ID プール。「ログイン機能を実装したい」「Google アカウントでサインインさせたい」「API Gateway で認証を強制したい」→ ユーザープール。「未ログインの利用者にも限定的にアクセスさせたい」→ ID プールのゲストロール。「従業員のシングルサインオン」→ IAM Identity Center。

確認問題

先に自分で答えを決めてから開いてください。特に3問目と4問目は、紛らわしい選択肢をわざと残してあります。

Q1ある企業が、S3に保存する大容量のログファイルをKMSで暗号化している。ソリューションアーキテクトが、暗号化の仕組みについて経営層に説明することになった。KMSを使った暗号化の動作として正しいものはどれか。
  • A. ファイル全体がKMSに送信され、KMS内で暗号化されてからS3に保存される
  • B. KMSが生成したデータキーでファイルを暗号化し、そのデータキーをKMSキーで暗号化して暗号文と一緒に保存する
  • C. KMSキーの鍵素材がS3にコピーされ、S3側で暗号化処理が行われる
  • D. ファイルはKMSキーのハッシュ値で暗号化され、復号にはKMSへのアクセスは不要である

正解: B

場面3の手順の図（①〜④）そのもの。KMS を往復するのはデータキーだけで、データ本体は送られない。

判断軸: A は「KMS が直接暗号化できるのは 4 KB まで」に反する（場面3の最初の図の赤い点線）。C は「鍵素材は KMS の外に出ない」に反する。D は復号に KMS が不要としている点が誤りで、手順の⑥のとおり復号のたびに KMS へのアクセス権が要る。だから「鍵を無効化してアクセスを断つ」が成り立つ。

Q2Webアプリケーションが Aurora に接続している。セキュリティ監査により、データベースの認証情報を90日ごとにローテーションすることが義務付けられた。運用負荷を最小限に抑える方法はどれか。
  • A. 認証情報を Systems Manager Parameter Store の SecureString に保存し、90日ごとに手動で更新する
  • B. 認証情報を Secrets Manager に保存し、Aurora 向けのマネージドローテーションを有効にする
  • C. 認証情報をKMSで暗号化してS3に置き、EventBridge で90日ごとにLambdaを起動して更新する
  • D. 認証情報をEC2のインスタンスメタデータに保存し、起動テンプレートで更新する

正解: B

場面5の図。Secrets Manager は Aurora・RDS・Redshift・DocumentDB について、Lambda 関数を自分で書かなくて済むマネージドローテーションを持っている。

判断軸: A は手動なので「運用負荷を最小限」を満たさない（Parameter Store にはローテーションの機能がない）。C は動くが、Lambda の実装と保守を自分で抱えるので、標準機能で済む選択肢に負ける。D はそもそも認証情報の置き場所として不適切。「ローテーション」を見たら Secrets Manager。

Q3企業が、複数のS3バケットに顧客の個人情報が意図せず保存されていないかを継続的に確認したいと考えている。さらに、EC2インスタンスに未適用の既知の脆弱性がないかも把握したい。この2つの要件を満たす組み合わせはどれか。
  • A. 個人情報の検出に GuardDuty、脆弱性の把握に AWS Config
  • B. 個人情報の検出に Macie、脆弱性の把握に Inspector
  • C. 個人情報の検出に Security Hub、脆弱性の把握に Detective
  • D. 個人情報の検出に Inspector、脆弱性の把握に Macie

正解: B

場面8の「材料と出力」の図の2行目と3行目。S3 のオブジェクトの中身を読んで機密データを見つけるのは Macie だけ。EC2・ECR のイメージ・Lambda の既知の CVE を調べるのが Inspector。

判断軸: A は両方外している。GuardDuty は S3 へのアクセスの不審さを見るだけで中身を分類せず、Config は設定が規則どおりかを見るので CVE は扱わない。C の Security Hub は結果を集めるだけで自分では検出せず、Detective は既にある検出結果を掘る道具。D は役割が入れ替わっている。「中身を分類するのは Macie」「弱点を探すのは Inspector」。

Q4東京リージョンで稼働するWebアプリケーションの前段にCloudFrontを導入し、カスタムドメインでHTTPSを提供しようとしている。ACMで ap-northeast-1 に証明書を発行したが、CloudFrontの設定画面で証明書を選択できない。とるべき対応はどれか。
  • A. CloudFrontディストリビューションを us-east-1 に作り直す
  • B. ACM で us-east-1 に同じドメインの証明書を発行し、それをCloudFrontに指定する
  • C. ap-northeast-1 の証明書をエクスポートし、CloudFrontにインポートする
  • D. 証明書の検証方法をEメール検証からDNS検証に変更する

正解: B

場面6の「置ける場所」の図の左。CloudFront に付ける証明書は、us-east-1（バージニア北部）の ACM にあるものしか参照できない。CloudFront 自体は世界共通のサービスなので作り直す必要はなく、証明書だけを us-east-1 で発行する。

判断軸: A は、CloudFront にリージョンという考え方がないので意味を成さない。C は、ACM のパブリック証明書は秘密鍵を取り出せないので不可能（同じ図の右）。D は検証方法の話で、リージョンの制約とは無関係。「CloudFront に関わる証明書は常に us-east-1」は、そのまま覚えてよい数少ない固定の知識。

Q5あるアカウントで、EC2インスタンスが既知のマルウェア指令サーバーと通信していることが検出された。セキュリティ担当者は、この通信がいつ始まり、どのIAMプリンシパルの操作が起点になったのかを時系列でたどりたい。最も適したサービスはどれか。
  • A. AWS Config で構成変更の履歴を確認する
  • B. Security Hub でセキュリティスコアを確認する
  • C. Amazon Detective でGuardDutyの検出結果を起点に調査する
  • D. Amazon Inspector で該当インスタンスの脆弱性をスキャンする

正解: C

場面8の「材料と出力」の図の下段右。Detective は、GuardDuty の検出結果・CloudTrail・VPC フローログをつなぎ合わせ、「いつ始まったか」「どのプリンシパルが関わったか」「何が連鎖したか」を時系列でたどれるようにする。

判断軸: A は設定の変更履歴は分かるが、通信の振る舞いと結び付けられない。B は全体の準拠状況を見る画面で、1件の深掘りには向かない。D は脆弱性の有無は分かるが、すでに起きた通信の経緯は分からない。「調査」「根本原因」「時系列」は Detective。「全社の状況を1画面で」なら Security Hub、と対で覚える。
