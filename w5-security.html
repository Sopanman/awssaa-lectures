セキュリティサービス ―― 守るのか、見張るのか

ドメイン1の残り半分です。IAMが「誰が何をできるか」なら、こちらは「データをどう守り、異常をどう見つけるか」。AWSのセキュリティサービスは名前が似ていて役割が重なって見えますが、実際には守る層がそれぞれ違います。どの層を担当するサービスなのかで整理すれば、設問で迷わなくなります。

01

この講義のゴール

セキュリティサービスは数が多く、暗記しようとすると必ず崩れます。狙うのは名前の暗記ではなく、設問の一文から「これは守る側の話か、見張る側の話か」を切り分けられる状態です。今日終わったときに、次の3つができていれば合格です。

  • 01
    設問が保管時の暗号化を問うているのか、転送時の暗号化を問うているのかを即座に判別できる。
    そのうえで、KMS・ACM・CloudHSM のどれが答えの中心になるかを言える。
  • 02
    エンベロープ暗号化を、図を見ずに順を追って説明できる。
    なぜ2段階にするのか、KMSが何を持っていて何を持っていないのかを、自分の言葉で言える。
  • 03
    WAF・GuardDuty・Inspector・Macie・Config を、担当する層で並べられる。
    「攻撃を止める」「侵害の兆候を見つける」「弱点を洗い出す」「置いてはいけないデータを探す」「設定が規則どおりか確かめる」の対応を間違えない。
IAM 講義との関係

IAMはアクセスの可否を決める仕組みでした。今日扱うのは、そのアクセス制御をすり抜けられた場合や、そもそもアクセス制御では守れない領域――物理的な媒体の盗難、通信経路の盗聴、アプリケーション層への攻撃、設定ミスの放置――に対する備えです。この2つは代替関係ではなく、積み重ねる関係にあります。設問で「多層防御（defense in depth）」という語が出たら、それは「一つの対策だけを選ぶ選択肢は不正解」という合図です。

02

暗号化の2つの軸と、責任の境目

暗号化の設問は、ほぼすべてが2つの軸のどちらかに属します。保管時（at rest）か、転送時（in transit）か。この判別を最初にやると、選択肢が半分に落ちます。

設問文のどこを見るか

設問は「データを暗号化したい」とだけ書いてくれることは少なく、状況の描写のなかに軸のヒントを埋め込んできます。ディスク・バケット・スナップショット・バックアップ・アーカイブといった置き場所を指す語が出てきたら保管時。ネットワーク・通信・クライアントとサーバーの間・盗聴・中間者といった経路を指す語が出てきたら転送時です。両方を要求する設問もあり、その場合は「KMSで保管時を、ACMとHTTPSで転送時を」という二段構えの選択肢が正解になります。

「インターネットを経由させたくない」は、厳密には暗号化ではなく経路の話です。ここで正解になるのは VPC エンドポイントや PrivateLink であって、暗号化サービスではありません。「暗号化したい」のか「経路を閉じたい」のかを読み分けてください。

責任共有モデルの読み方

責任共有モデルは、CLFでは「AWSはクラウドのセキュリティ、顧客はクラウド内のセキュリティ」という標語で覚えたはずです。SAAでは標語そのものは問われず、具体的な作業がどちら側に落ちるかという形で問われます。判定のコツは一つで、そのサービスがマネージドである度合いが上がるほど、AWS側の責任範囲が広がるという一本の軸で考えることです。

03

KMS ―― キーの種類とポリシーの二重構造

KMSは保管時暗号化の中心にあり、S3・EBS・RDS・DynamoDB・Secrets Manager・SNS・SQS など、ほぼすべてのサービスがKMSを呼んでいます。まずキーの種類を3つに分けることから始めます。この分け方が、料金・ローテーション・クロスアカウントの設問すべてに効きます。

設問に「鍵の使用を監査したい」「特定のロールだけに復号を許したい」「別アカウントと共有したい」「独自のローテーション周期にしたい」「鍵を無効化して即座にアクセスを遮断したい」のどれか一つでも出てきたら、答えはカスタマー管理キーです。AWSマネージドキーはキーポリシーを触れないので、これらの要件を一つも満たせません。逆に「特別な要件はなく、とにかく暗号化されていればよい」「運用負荷を最小にしたい」ならAWSマネージドキーで十分、という書き分けになります。

キーポリシーとIAMポリシーの関係

ここがKMSで最も間違えやすい部分です。KMSキーは、必ずリソースベースポリシー（キーポリシー）を持ちます。しかも、S3バケットのように「リソースポリシーを付けない」という選択肢がありません。キーを作った時点で既定のキーポリシーが付き、これを空にすることはできません。

そして評価の仕方が独特です。IAMポリシーで kms:Decrypt を許可しても、キーポリシー側がそのプリンシパルに権限を委ねていなければアクセスできません。既定のキーポリシーには「このアカウントのIAMポリシーによる権限委任を有効にする」という一文が入っていて、これがあるおかげで普段はIAMポリシーだけで話が済んでいます。この一文を外したり、狭い条件に書き換えたりすると、管理者権限を持っていてもキーを使えなくなります。

既定のキーポリシーに入っている「委任を有効にする」ステートメント
{
  "Sid": "Enable IAM User Permissions",
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::111122223333:root" },
  // ↑ rootユーザーに許すという意味ではなく、
  //   「このアカウントのIAMポリシーに判断を委ねる」という定型句
  "Action": "kms:*",
  "Resource": "*"
}
最頻出の引っかけ

「IAMポリシーで kms:Decrypt を許可したのに、暗号化されたS3オブジェクトが読めない。原因は？」――答えはキーポリシーでそのプリンシパルが許可されていないです。S3のバケットポリシーを疑う選択肢、IAMポリシーの記述ミスを疑う選択肢が並びますが、KMSが絡む「読めない」系の設問では、まずキーポリシーを見ます。暗号化されたオブジェクトを読むには、S3側の権限とKMS側の権限の両方が要るという構造を押さえてください。

クロスアカウントでは3か所

別アカウントから暗号化されたリソースを使う場合、必要なのは3か所です。①キーポリシーに相手アカウントを書く、②相手アカウント側のIAMポリシーで kms:Decrypt 等を許可する、③リソース側のアクセスも許可する。キーポリシーだけでは相手アカウントのプリンシパルに権限が届きません。IAM講義でやった「クロスアカウントは両側の合意」が、KMSでも同じ形で出てきます。

04

エンベロープ暗号化と、鍵の運用

KMSが実際に何をしているかを理解すると、S3の暗号化オプションもEBSの暗号化も、同じ一つの仕組みの応用だと分かります。その仕組みがエンベロープ暗号化です。

なぜ2段階にするのか

KMSのキー素材は、KMSの外に出ません。強い性質ですが不便でもあり、暗号化するにはデータをKMSに送る必要があります。実際、KMSのAPIで直接暗号化できるのは4KBまでです。数GBのEBSボリュームやS3の動画ファイルをKMSに送ることは、性能面でもコスト面でも成立しません。

そこで、鍵を二階建てにします。データを暗号化するのは、その場で生成した使い捨ての「データキー」。そして、そのデータキー自体をKMSのキー（CMK）で暗号化して、暗号文と一緒に保存します。手紙を封筒に入れて、封筒に鍵をかけるイメージから「エンベロープ（封筒）暗号化」と呼ばれます。

S3 バケットキー

S3でSSE-KMSを使うと、既定ではオブジェクトごとにKMSへのリクエストが発生し、オブジェクト数が多いと呼び出し料金が無視できなくなります。S3バケットキーはバケット単位の短期キーを再利用してこのリクエスト数を大幅に削減します。「SSE-KMSを使いたいが、KMSのリクエスト料金を抑えたい」の答えはこれです。暗号化をやめる選択肢やSSE-S3への切り替えは、要件を満たしていません。

自動ローテーション

カスタマー管理キーの自動ローテーションは、有効にすると既定で365日ごとに新しい鍵素材が生成されます。周期は90日から2560日の範囲で指定できます。AWSマネージドキーは年1回のローテーションが強制で、こちらは設定を変えられません。

押さえるべきは、ローテーションしてもキーIDもARNもエイリアスも変わらない点です。古い鍵素材はKMSに保持され続けるため、ローテーション前に暗号化したデータもそのまま復号でき、アプリ側の書き換えも不要です。「過去のデータが読めなくなるのでは」と心配させる選択肢は不正解です。

自動ローテーションできないキー

自動ローテーションが使えるのは、KMSが鍵素材を生成した対称暗号化キーだけです。自分で鍵素材をインポートしたキー（オリジンがEXTERNAL）、非対称キー、HMACキー、カスタムキーストア上のキーは対象外です。これらを回したい場合は、新しいキーを作ってエイリアスを付け替える手動ローテーションになります。設問に「オンプレミスで生成した鍵素材を使う」と書いてあれば、自動ローテーションを答えにする選択肢は消えます。

マルチリージョンキー

KMSキーは通常リージョンに閉じていて、東京で暗号化したデータを大阪で復号することはできません。これを越えるのがマルチリージョンキーです。プライマリキーを作り、それを別リージョンにレプリカとして複製すると、同じ鍵素材とキーIDを持つキーが両方のリージョンに存在します。片方で暗号化した暗号文を、もう片方でKMSを跨がずに復号できます。

  • 典型的な用途は、S3のクロスリージョンレプリケーション、DynamoDBグローバルテーブル、そしてディザスタリカバリです。暗号化されたデータを別リージョンに運ぶ設計で出てきます。
  • キーポリシーはリージョンごとに独立です。複製したからといって権限まで同じになるわけではありません。
  • 作成時に決める必要があります。すでにある単一リージョンキーを、後からマルチリージョンキーに変換することはできません。設問で「既存のキーをマルチリージョン化する」という選択肢が出たら不正解です。
  • レプリカもそれぞれ1キーとして課金されます。無条件にマルチリージョンにするのはコスト面で不利です。

キーの削除

KMSキーは即座に削除できません。削除をスケジュールすると、7日から30日の待機期間が始まり、既定は30日です。この間キーは「削除保留中」になり暗号化にも復号にも使えませんが、待機期間中ならキャンセルできます。鍵を消すことはその鍵で暗号化された全データを永久に読めなくすることなので、猶予が設けられています。

設問では「不要になったキーを削除したいが、まだどこかで使われているかもしれない」という文脈で出ます。正解は多くの場合「まずキーを無効化（disable）して、影響が出ないことを確認してから削除をスケジュールする」です。無効化は即時に効き、即時に戻せます。なお、マルチリージョンのプライマリキーは、すべてのレプリカを削除し終えてからでないと待機期間が始まりません。

CloudHSM との使い分け

CloudHSMは、KMSと同じ「鍵を守るサービス」ですが、位置づけが違います。KMSがマネージドな共有基盤なのに対し、CloudHSMは自分専用のハードウェアセキュリティモジュールをVPC内に立てるサービスです。

設問での切り分け

  • 「認証情報を定期的に自動でローテーションしたい」「RDSのマスターパスワードを90日ごとに変更」――Secrets Manager。ここは迷う余地がありません。Parameter Store にはローテーション機能そのものがないので、「Parameter Store＋Lambdaで実装する」という選択肢があっても、標準機能で満たせるSecrets Managerが正解になります。
  • 「コストを最小限に抑えたい」「追加費用なしで」「大量の設定値を管理したい」――Parameter Store。ローテーションの要件が書かれていないのに Secrets Manager を選ぶと、コスト面で減点される作りの設問が多いです。
  • 「環境ごと・アプリごとに設定を整理してまとめて取得したい」――Parameter Store の階層パス。GetParametersByPath で /myapp/prod/ 配下を一括取得できます。
  • 「AMIのIDやエンドポイントURLのような、秘密ではない設定値」――Parameter Store。
RDS のマネージドマスターパスワード

RDSとAuroraには、マスターユーザーのパスワードをSecrets Managerに自動で作らせ、ローテーションまで任せる設定があります。設問で「データベースの認証情報を人手を介さずに管理し、定期的にローテーションしたい。運用負荷は最小に」と来たら、Secrets Managerと統合したRDSのマネージドパスワードが正解です。Lambdaローテーション関数を自分で書く選択肢は、要件は満たしますが運用負荷の面で劣ります。SAAは「要件を満たす最も運用負荷の低い方法」を問うので、この差がそのまま正誤になります。

よくある誤解

「Parameter Store は暗号化できない」――できます。SecureString 型を選べばKMSで暗号化されます。両者の差はローテーションとコストと共有機能であって、暗号化の可否ではありません。逆に、Parameter Store で String 型を選ぶと平文で保存される点は押さえてください。「Parameter Store にパスワードを保存したが平文だった」という設問は、型の選び間違いが原因です。なお Parameter Store からは /aws/reference/secretsmanager/ というパスでSecrets Managerのシークレットを参照でき、アプリ側のコードをParameter Store一本に寄せたまま、秘密だけSecrets Managerに置くこともできます。

06

ACM ―― 証明書はどこに置けるか

転送時の暗号化の主役はTLSで、TLSの主役は証明書です。ACMはパブリック証明書を無料で発行し、自動で更新するサービスですが、設問で問われるのは機能そのものより置ける場所の制約です。

置ける場所と、置けない場所

ACMの証明書は、AWSのマネージドな終端点に紐づけて使うのが基本形です。ALB、NLB、CloudFront、API Gateway あたりが代表です。ここで重要なのは、ACMが発行したパブリック証明書は秘密鍵をエクスポートできないという点です。EC2インスタンス上のNginxやApacheに証明書ファイルを置く、という使い方は成立しません。

置き先ACMのパブリック証明書証明書を用意するリージョン
CloudFront使えるus-east-1（バージニア北部）固定
ALB / NLB使えるロードバランサーと同じリージョン

最頻出の引っかけ

「CloudFrontディストリビューションにカスタムドメインのHTTPSを設定しようとしたが、コンソールの証明書の一覧に目的の証明書が出てこない。」――原因は証明書を us-east-1 以外のリージョンで発行したことです。CloudFrontはグローバルサービスですが、証明書だけは us-east-1 のACMを参照します。東京リージョンで作った証明書は、どれだけ正しく発行されていても選べません。この設問は表現を変えて繰り返し出ます。

EC2にTLSが必要なとき

「EC2上のアプリでHTTPSを終端したい」という要件が出たら、SAAの答えは基本的に「ALBやCloudFrontでTLSを終端し、EC2は背後に置く」です。それでもEC2自身に証明書が要る場合は、AWS Private CA のプライベート証明書か、持ち込みの証明書になります。Private CA は内部通信用で、ブラウザには信頼されません。「社内システム間の相互TLS」と書いてあれば Private CA です。

自動更新が働く条件

ACMの「自動更新」は無条件ではありません。条件を外すと更新されず、期限切れで障害になります。設問でも「証明書が期限切れになった。なぜか」という形で問われます。

  • ACMが発行した証明書であること。持ち込んだ（インポートした）証明書は自動更新の対象外です。期限が来る前に自分で入れ替える必要があります。
  • 使われていること。ACMに置いてあるだけで、どのAWSサービスにも紐づいていない証明書は、更新の対象になりません。
  • DNS検証であること。DNS検証（Route 53などにCNAMEレコードを置く方式）なら、レコードが残っている限り人手を介さずに更新されます。Eメール検証の場合は、更新のたびに承認メールへの対応が必要です。「証明書の更新を完全に自動化したい」と書いてあればDNS検証が答えです。
インポート証明書の見張り方

インポートした証明書は自動更新されませんが、ACMは有効期限が近づくとイベントを発行します。EventBridge でこれを受けて通知する、あるいは AWS Config のマネージドルールで期限切れ間近の証明書を非準拠として検出する、という構成が「期限切れを防ぎたい」型の設問の正解になります。手動でカレンダーに入れる、という選択肢は常に不正解です。

07

守る層で並べる ―― SG・NACL・WAF・Network Firewall

防御サービスが混乱するのは、全部が「通信を止めるもの」に見えるからです。止める場所と、見ている情報の深さで並べると、設問の手がかりと一対一で対応します。

どこに効くか見ている情報拒否ルール状態管理

WAFCloudFront、ALB、API Gateway、AppSync などHTTPリクエストの中身（L7）。URL、ヘッダー、ボディ、クエリ文字列許可も拒否も書ける―
Network FirewallVPC（専用サブネットに置いたエンドポイント）パケットとセッション。ドメイン名でのフィルタリングも可能許可も拒否も書けるステートフル／ステートレス両方のルールグループ

WAF が担当するもの

WAFはHTTPリクエストの中身を読むので、IPとポートしか見ないSGやNACLでは絶対に止められない攻撃を扱えます。SQLインジェクション、クロスサイトスクリプティング（XSS）、既知の悪性ボット――これらが設問に出たらWAFです。

  • マネージドルールグループ――AWSやマーケットプレイスのベンダーが用意した既製のルール集。OWASP Top 10 相当の防御を、自分でルールを書かずに有効化できます。「迅速に、運用負荷を抑えて一般的な攻撃を防ぎたい」ならこれです。
  • レートベースルール――5分間のウィンドウで、送信元IPごとのリクエスト数を数え、閾値を超えたIPをブロックします。「単一のIPから大量のリクエストが来ている」「ログインエンドポイントへの総当たり攻撃」と書いてあればこれです。
  • 地理的一致ルール――国単位で許可／拒否。「サービス提供国以外からのアクセスを遮断したい」に対応します。CloudFrontの地理的制限機能でも似たことができますが、WAFのほうが細かい条件と組み合わせられます。
  • IPセット――特定のIPレンジの許可リスト・拒否リスト。
判断軸

「止めたい対象がHTTPリクエストの中身で決まるならWAF、IPとポートで決まるならSGかNACL、宛先ドメインで決まるなら Network Firewall（またはRoute 53 Resolver DNS Firewall）」。この3分岐で大半が片付きます。加えて、SGは拒否を書けないという一点だけは確実に。「特定のIPアドレスからのアクセスだけをブロックしたい」という設問でSGを選ぶ選択肢は、必ず不正解です。答えはネットワークACLの拒否ルール、あるいはWAFのIPセットです。

Shield Standard と Advanced

Shield Standard はすべてのAWS利用者に自動で適用され、追加料金はかかりません。SYNフラッドのようなL3/L4の一般的なDDoSを自動で緩和します。「最低限のDDoS対策は何か」の答えは「もう有効になっている」です。

Shield Advanced は月額3,000USD・1年契約の有償サービスで、差分は次の点です。

  • DDoSレスポンスチーム（SRT）への連絡と、攻撃中の支援。
  • コスト保護――DDoSによってスケールアウトやデータ転送が急増した分の請求が還付されます。設問で「攻撃による予期しない課金を避けたい」と書いてあればこれです。
  • WAFのルール料金が含まれ、SRTによるWAFルールの代理作成が受けられる。
  • L7も含めた高度な検出と、攻撃の可視化。
よくある誤解

「DDoS対策と書いてあれば Shield Advanced」――これは半分だけ正しいです。設問にコストの制約が書かれている場合、月額3,000USDのサービスは選べません。その場合は「CloudFront と Route 53 の前段に置く」「WAFのレートベースルール」「Auto Scaling で吸収する」といった、Shield Standard を前提にした設計が正解になります。Advanced が正解になるのは、SRTの支援・コスト保護・専用のSLAといった Advanced 固有の機能が要件に書かれているときです。

この表を上から2行と、それ以降で切ると性格が変わります。WAFとShieldは予防的統制――起きる前に止めます。GuardDuty以降は発見的統制――起きたことや今ある弱点を教えますが、それ自体は何も止めません。

設問が「防ぎたい」「ブロックしたい」と言っているのに検知系を選ぶ、「検出したい」「可視化したい」と言っているのに遮断系を選ぶ、というのが典型的な失点です。要件の動詞を読む――セキュリティ設問全体に効く技術です。

GuardDuty をもう少し詳しく

GuardDutyの設問での強みは、準備が要らないことです。エージェントもログの有効化も保存先の設計も不要で、有効にすれば数分で分析が始まります。VPCフローログを自分で有効化していなくても、独立したストリームとして読み取ります。「最小の運用負荷で、すぐに脅威検知を始めたい」はほぼGuardDutyです。

検出結果（Findings）には重要度が付き、EventBridge に流せます。「脅威を検出したら自動で対応したい」という設問の正解は、GuardDuty → EventBridge → Lambda（またはSNS通知、Systems Manager Automation）という連鎖です。GuardDutyが単独で何かを遮断するわけではない、という点を押さえてください。

Config と GuardDuty の分かれ目

両者は「見張る」という点では同じに見えますが、見ているものが違います。Configはリソースの構成――「このEBSボリュームは暗号化されているか」「このセキュリティグループは0.0.0.0/0で22番を開けていないか」。GuardDutyは振る舞い――「このインスタンスが既知のマルウェアのC2サーバーと通信している」「普段使わないリージョンでIAMユーザーが作られた」。

設問の言葉で言えば、「設定が基準を満たしているか確認したい」ならConfig、「攻撃されていないか知りたい」ならGuardDutyです。Config は非準拠を見つけたときに Systems Manager Automation で自動修復までできるので、「非準拠のリソースを自動的に是正したい」という設問もConfigです。

最頻出の引っかけ

「S3バケットに個人情報が保存されていないか確認したい」でGuardDutyを選ぶ――不正解です。中身を見て機密データを探すのはMacieだけです。GuardDutyのS3保護は「S3へのアクセスが不審かどうか」を見るもので、オブジェクトの中身は分類しません。同様に「EC2に未適用のパッチがないか」はInspectorで、GuardDutyではありません。GuardDutyは中身を見ず、Inspectorは振る舞いを見ず、Macieは S3 の外を見ない。この3行を覚えておけば、この系統の設問はまず落としません。

Security Hub と Detective の違い

どちらも「複数のサービスの情報をまとめる」サービスに見えますが、目的が逆方向です。Security Hubは広く浅く――組織全体・複数アカウントの検出結果を一画面に集め、CISベンチマークやAWS基礎セキュリティベストプラクティスへの準拠状況をスコアで示します。日常的に見るダッシュボードです。Detectiveは狭く深く――一件のインシデントについて、関係するリソースとイベントをグラフでたどり、いつ始まったのか、何が連鎖したのかを突き止めます。インシデント発生後に開くツールです。設問に「調査」「根本原因」「時系列で追う」とあればDetective、「一元的に把握」「複数アカウント」「準拠状況」とあればSecurity Hubです。

確認問題

先に自分で答えを決めてから開いてください。特に3問目と4問目は、紛らわしい選択肢をわざと残してあります。

Q1ある企業が、S3に保存する大容量のログファイルをKMSで暗号化している。ソリューションアーキテクトが、暗号化の仕組みについて経営層に説明することになった。KMSを使った暗号化の動作として正しいものはどれか。
  • A. ファイル全体がKMSに送信され、KMS内で暗号化されてからS3に保存される
  • B. KMSが生成したデータキーでファイルを暗号化し、そのデータキーをKMSキーで暗号化して暗号文と一緒に保存する
  • C. KMSキーの鍵素材がS3にコピーされ、S3側で暗号化処理が行われる
  • D. ファイルはKMSキーのハッシュ値で暗号化され、復号にはKMSへのアクセスは不要である

正解: B

エンベロープ暗号化の説明そのものです。KMSが直接暗号化できるのは4KBまでで、それを超えるデータはこの2段階で扱います。KMSを往復するのはデータキーだけで、データ本体は送られません。

判断軸: Aは4KBの制限に反し、性能面でも成立しません。Cは「鍵素材はKMSの外に出ない」というKMSの根本原則に反します。Dは復号にKMSが不要としている点が誤りで、復号のたびにKMSへのアクセス権が必要だからこそ「鍵を無効化してアクセスを断つ」という運用が成立します。

Q2Webアプリケーションが Aurora に接続している。セキュリティ監査により、データベースの認証情報を90日ごとにローテーションすることが義務付けられた。運用負荷を最小限に抑える方法はどれか。
  • A. 認証情報を Systems Manager Parameter Store の SecureString に保存し、90日ごとに手動で更新する
  • B. 認証情報を Secrets Manager に保存し、Aurora 向けのマネージドローテーションを有効にする
  • C. 認証情報をKMSで暗号化してS3に置き、EventBridge で90日ごとにLambdaを起動して更新する
  • D. 認証情報をEC2のインスタンスメタデータに保存し、起動テンプレートで更新する

正解: B

Secrets Manager は Aurora・RDS・Redshift・DocumentDB について、ローテーション用のLambdaを自分で書かなくても済むマネージドローテーションを提供します。ローテーション要件があり、かつ運用負荷の最小化が条件なら、ここは一択です。

判断軸: Aは手動なので「運用負荷を最小限」を満たしません。Cは動きますが、Lambdaの実装と保守を自分で抱えることになり、標準機能で済む選択肢に劣ります。Dはそもそも認証情報の置き場所として不適切です。「ローテーション」という語が出たらSecrets Manager、というのが第一反応です。

Q3企業が、複数のS3バケットに顧客の個人情報が意図せず保存されていないかを継続的に確認したいと考えている。さらに、EC2インスタンスに未適用の既知の脆弱性がないかも把握したい。この2つの要件を満たす組み合わせはどれか。
  • A. 個人情報の検出に GuardDuty、脆弱性の把握に AWS Config
  • B. 個人情報の検出に Macie、脆弱性の把握に Inspector
  • C. 個人情報の検出に Security Hub、脆弱性の把握に Detective
  • D. 個人情報の検出に Inspector、脆弱性の把握に Macie

正解: B

S3オブジェクトの中身を読んで機密データを分類できるのはMacieだけです。EC2・ECRイメージ・Lambdaの既知のCVEをスキャンするのがInspectorです。この2つは担当が重なりません。

判断軸: Aは両方外しています。GuardDutyはS3へのアクセスの不審さを見るだけでオブジェクトの中身を分類せず、Configは構成が規則どおりかを見るのでCVEは扱いません。Cは、Security Hubが他サービスの結果を集約するだけで自分では検出せず、Detectiveは既存の検出結果を掘り下げる調査ツールです。Dは役割が完全に入れ替わっています。「中身を分類するのはMacie」「弱点を探すのはInspector」の2行で判定できます。

Q4東京リージョンで稼働するWebアプリケーションの前段にCloudFrontを導入し、カスタムドメインでHTTPSを提供しようとしている。ACMで ap-northeast-1 に証明書を発行したが、CloudFrontの設定画面で証明書を選択できない。とるべき対応はどれか。
  • A. CloudFrontディストリビューションを us-east-1 に作り直す
  • B. ACM で us-east-1 に同じドメインの証明書を発行し、それをCloudFrontに指定する
  • C. ap-northeast-1 の証明書をエクスポートし、CloudFrontにインポートする
  • D. 証明書の検証方法をEメール検証からDNS検証に変更する

正解: B

CloudFrontに紐づける証明書は、us-east-1（バージニア北部）のACMにあるものしか参照できません。CloudFront自体はグローバルサービスなので作り直す必要はなく、証明書だけを us-east-1 で発行し直します。1つのドメインに対して複数リージョンで証明書を持つことは問題ありません。

判断軸: Aは、CloudFrontにリージョンという概念がないので意味を成しません。Cは、ACMのパブリック証明書は秘密鍵をエクスポートできないため不可能です。Dは検証方法の話であって、リージョンの制約とは無関係です。「CloudFront に関わる証明書は常に us-east-1」は、そのまま覚えてよい数少ない固定知識です。

Q5あるアカウントで、EC2インスタンスが既知のマルウェア指令サーバーと通信していることが検出された。セキュリティ担当者は、この通信がいつ始まり、どのIAMプリンシパルの操作が起点になったのかを時系列でたどりたい。最も適したサービスはどれか。
  • A. AWS Config で構成変更の履歴を確認する
  • B. Security Hub でセキュリティスコアを確認する
  • C. Amazon Detective でGuardDutyの検出結果を起点に調査する
  • D. Amazon Inspector で該当インスタンスの脆弱性をスキャンする

正解: C

Detective は、GuardDutyの検出結果・CloudTrail・VPCフローログを取り込んでグラフモデルを作り、「いつ始まったか」「どのプリンシパルが関与したか」「何が連鎖したか」を時系列でたどれるようにするサービスです。まさに根本原因分析のためのツールです。

判断軸: Aは構成の変更履歴は分かりますが、ネットワークの振る舞いと結び付けられません。Bは全体の準拠状況を見るダッシュボードで、一件の深掘りには向きません。Dは脆弱性の有無を教えてくれますが、すでに起きた通信の経緯は分かりません。「調査」「根本原因」「時系列」の3語はDetectiveの指定席です。逆に「全社の状況を一画面で」ならSecurity Hub、と対で覚えてください。
