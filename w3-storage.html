AWS SAA-C03 / W3 座学

ストレージ ―― どこに置き、いつ移すか

ストレージはSAAで最も選択肢の数が多い領域です。S3のストレージクラスだけで6種類以上あり、さらにEBS・EFS・FSxが並びます。設問は必ず「アクセス頻度」「共有の要否」「プロトコル」「取り出しまでの許容時間」のどれかを手がかりとして与えてきます。その手がかりと答えの対応を作るのが今日の目的です。

01

この講義のゴール

ストレージの設問は、サービス名を知っているかではなく、要件の一文からどの軸で切るかを判断できるかを問います。今日終わったときに、次の3つができていれば合格です。

  • 01
    アクセス頻度と取り出し時間から、S3のストレージクラスを1つに絞れる。
    最小保存期間という落とし穴も含めて、なぜそれを選ぶか言える。
  • 02
    ブロック・ファイル・オブジェクトの3分類を反射的に切り分けられる。
    「複数EC2から共有」「Windowsから」「1台に速いディスク」が、それぞれどこに着地するか即答できる。
  • 03
    暗号化とアクセス制御を、要件の言葉から逆引きできる。
    「監査したい」「鍵を預けられない」「期限付きで外部に渡す」が、それぞれ何を指すか分かる。
今日の全体像

ストレージは3つの型しかありません。オブジェクト（S3。HTTPで出し入れする、部分更新しない）、ブロック（EBS・インスタンスストア。OSがファイルシステムを載せる生ディスク）、ファイル（EFS・FSx。NFSやSMBでマウントして複数台から共有する）。設問を読んだらまずこの3つのどれかを決める。それだけで選択肢の半分は消えます。

02

S3 のストレージクラス

6つ以上あって覚えにくく見えますが、実際に効いている軸は3つだけです。どれくらいの頻度で読むか、読むときに何秒待てるか、AZが1つ落ちたときに失われてよいか。この3つを設問から拾えば、クラスは自動的に決まります。

比較表

クラス想定アクセス頻度取り出しにかかる時間最小保存期間AZ
S3 Standard頻繁（日常的に読む）ミリ秒なし3以上
S3 Intelligent-Tiering予測できない／変動する階層による（既定の階層はミリ秒）なし3以上
S3 Standard-IA月1回程度ミリ秒30日3以上
S3 One Zone-IA月1回程度かつ失っても再作成できるミリ秒30日1
S3 Glacier Instant Retrieval四半期に1回程度ミリ秒90日3以上
S3 Glacier Flexible Retrieval年に1〜2回Expedited 1〜5分 / Standard 3〜5時間 / Bulk 5〜12時間90日3以上
S3 Glacier Deep Archive年1回未満（ほぼ読まない）Standard 12時間以内 / Bulk 48時間以内180日3以上

この表で最も設問に直結するのは「取り出しにかかる時間」の列です。設問は必ず、要件のどこかに待てる時間を書いてきます。「監査時には即座に参照できる必要がある」と書いてあれば Glacier Flexible Retrieval は消えます。「取り出しに数時間かかっても問題ない」と書いてあれば、Glacier Instant Retrieval を選ぶ理由はなくなります（より高いので）。

Intelligent-Tiering が正解になる条件

Intelligent-Tiering は、オブジェクトごとのアクセス状況を監視して自動で階層を移します。既定では次のように進みます。

  • Frequent Access（最初はここ）→ 30日連続で未アクセス → Infrequent Access → さらに90日連続で未アクセス → Archive Instant Access。ここまではすべてミリ秒で読めます。
  • 任意で Archive Access（90日以上）と Deep Archive Access（180日以上）を有効化できます。こちらに落ちると取り出しに分〜時間かかるので、業務要件を確認してから有効にします。
  • 取り出し料金がかかりません。代わりにオブジェクト単位の監視・自動化料金がかかります。
  • 128KB未満のオブジェクトは監視対象外で、Frequent Access に留まります。小さいファイルが大量にある場合、思ったほどコストが下がりません。
判断軸

設問に「アクセスパターンが予測できない」「時間とともに変化する」「運用の手間をかけずに」という語が出たら Intelligent-Tiering です。逆に「30日後にはほとんど読まれないことが分かっている」と明言されていたら、それはライフサイクルルールで Standard-IA に落とす設問であって、Intelligent-Tiering ではありません。パターンが既知かどうかが分かれ目です。

One Zone-IA を選んでよい場面は限られる

One Zone-IA は単一AZにしかデータを置きません。安いのは事実ですが、そのAZが失われればオブジェクトも失われます。設問で正解になるのは、元データが別の場所にあり、再作成できるものに限られます。具体的には、S3にある原本から生成したサムネイル、別リージョンにレプリカがあるコピー、オンプレにマスターがあるバックアップの二次コピーなどです。監査ログ、法定保存文書、唯一の原本を One Zone-IA に置く選択肢は、コストが安くても不正解です。

最頻出の引っかけ

「最小保存期間」を無視した選択肢です。たとえば7日間だけ保持する一時ファイルを Standard-IA に置くと、30日分の保存料金を請求されます。Standard に置いたほうが安い。短命なデータに IA 系・Glacier 系を選ばせる選択肢は、コスト最適化に見えて逆です。加えて IA 系と Glacier Instant Retrieval には128KBの課金下限があり、10KBのファイルも128KB分として課金されます。小さいファイルを大量に IA へ落とす選択肢も同じ罠です。

03

ライフサイクルと遷移の制約

クラスを選べたら、次は「いつ移すか」です。ライフサイクルルールは、日数を条件にして自動で遷移・削除を行います。ここには方向と日数の制約があり、設問はその制約を突いてきます。

ルールに書ける5つのアクション

  1. Transition ―― 現行バージョンを別クラスへ移す。
  2. Expiration ―― 現行バージョンを削除する。バージョニング有効なら削除マーカーが付くだけです。
  3. NoncurrentVersionTransition / NoncurrentVersionExpiration ―― 非現行（古い）バージョンを移す・消す。バージョニングを有効にしたまま容量を抑える定番です。
  4. AbortIncompleteMultipartUpload ―― 途中で失敗したマルチパートアップロードの断片を消す。これを設定していないと、見えないパートに課金され続けます。「請求額に説明のつかないS3の容量がある」型の設問の答えです。
  5. ExpiredObjectDeleteMarker ―― 中身のない削除マーカーだけが残った状態を掃除します。
ライフサイクルルールの例（現行版を段階的に落とし、古い版は短く切る）
{
  "ID": "logs-tiering",
  "Filter": { "Prefix": "logs/" },
  "Status": "Enabled",
  "Transitions": [
    { "Days": 30,  "StorageClass": "STANDARD_IA" },   // 30日未満は指定できない
    { "Days": 120, "StorageClass": "DEEP_ARCHIVE" }
  ],
  "NoncurrentVersionExpiration": { "NoncurrentDays": 30 },
  "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
}

覚えておく制約

  • Standard から Standard-IA / One Zone-IA へは、最低30日経ってから。29日で移すルールは作れません。
  • 128KB未満のオブジェクトは、既定ではどのクラスにも遷移しません。移したい場合は ObjectSizeGreaterThan などのサイズフィルタを明示します。ただし遷移のリクエスト料金のほうが節約額を上回ることが多く、AWS自身が推奨していません。
  • Glacier 系に置いたオブジェクトには、1件あたり約40KBのメタデータ課金が付きます。内訳は S3 Standard 料金で8KB、Glacier 料金で32KBです。小さいファイルを何億件も Deep Archive に送ると、本体より管理データのほうが高くなります。この場合は先にまとめて（アーカイブファイル化して）から送るのが正解です。
  • 最小保存期間より前に削除・遷移すると、残りの期間分が課金されます。Deep Archive に入れた翌日に消しても180日分払います。
04

バージョニング・保持・レプリケーション

「消えては困る」という要件には段階があります。うっかり消したものを戻したいのか、規制で誰にも消させたくないのか、リージョンごと失われても残したいのか。設問はこの3段階のどれかを書いてきます。

バージョニング ―― すべての前提

バージョニングを有効にすると、上書きも削除も既存データを壊しません。削除は削除マーカーという新しいバージョンを積むだけで、マーカーを消せば元に戻ります。

  • 一度有効にしたバージョニングは無効化できません。できるのは「停止（Suspended）」までで、それまでに作られたバージョンは残り続けます。
  • 古いバージョンも課金対象です。ライフサイクルの NoncurrentVersionExpiration とセットで設計するのが実務の定石です。
  • この後に出てくる Object Lock もレプリケーションも、バージョニングが有効であることが前提です。ここが試験で最も繰り返し問われます。

MFA Delete

バージョンの完全削除と、バージョニング状態の変更に、MFAのコードを要求する設定です。特徴が2つあります。バージョニングが有効でなければ設定できないこと、そしてバケット所有者のルートユーザーが CLI / API から設定する必要があること（マネジメントコンソールからは設定できません）。「IAM管理者が有効化する」という選択肢は不正解です。

Object Lock ―― WORM

Object Lock は書き込み後に変更できない状態（Write Once Read Many）を作ります。モードが2つあり、誰が解除できるかだけが違います。

ガバナンスモードコンプライアンスモード
解除できる人s3:BypassGovernanceRetention を持つプリンシパル誰も解除できない（ルートユーザーを含む）
保持期間の短縮権限があれば可能不可
典型的な目的誤操作の防止。設定のテスト金融・医療などの法規制対応

これとは別にリーガルホールドがあります。期限がなく、s3:PutObjectLegalHold の権限があればいつでも着脱できます。訴訟対応や監査中など、いつまで保持すべきか分からないときに使います。保持期間とリーガルホールドは独立していて、同時にかけられます。

最頻出の引っかけ

「管理者を含め誰も削除できないようにしたい」という要件に、バケットポリシーで s3:DeleteObject を Deny するという選択肢が並びます。これは不正解です。バケットポリシー自体を管理者が書き換えられるからです。同じ理由でガバナンスモードも不正解。「誰も」「ルートユーザーでも」と書いてあったらコンプライアンスモード、と直結させてください。

レプリケーション ―― CRR と SRR

CRR（クロスリージョン）SRR（同一リージョン）
目的DR、地理的に離れた利用者へのレイテンシ短縮、法規制による地理分散ログの集約、本番から検証環境へのデータ複製、アカウント分離による保護
設問の手がかり「別リージョンに」「災害復旧」「海外拠点からの読み取りが遅い」「同じリージョンの別バケット／別アカウントに」「監査用に隔離」

どちらにも共通する前提と挙動があります。

  • 送信元・送信先の両方でバージョニングが有効であること。片方だけでは設定できません。
  • S3がレプリケートするためのIAMロールが必要です。
  • 非同期です。書き込んだ瞬間に相手側にあるとは限りません。所要時間に保証が欲しい場合は S3 Replication Time Control（RTC） を使うと、99.99%のオブジェクトを15分以内に複製するSLAが付きます。
  • ルール作成時点で既に存在しているオブジェクトは複製されません。既存分は S3 Batch Replication で別途流します。「設定したのに古いデータが複製されない」型の設問の答えです。
  • 削除マーカーの複製は任意設定です。バージョンIDを指定した削除は複製されません（複製先に削除が伝播して両方消える、という事故を防ぐ設計です）。
05

S3 のアクセス制御

S3には権限の書ける場所が複数あります。並べて覚えるのではなく、「誰に」「何を」「どの粒度で」渡したいかから逆引きします。

仕組み主語これが正解になる要件
IAMポリシー自アカウントのユーザー／ロール「この人（このEC2）は何にアクセスできるか」を管理したい。対象バケットが多数あり、人の側でまとめたい
バケットポリシーバケットクロスアカウントで許可したい。VPCエンドポイント経由のみ（aws:SourceVpce）、HTTPSのみ（aws:SecureTransport）といった条件をバケット全体に強制したい
ACLバケット／オブジェクト個別原則として使わない。新規バケットでは既定で無効（Object Ownership が Bucket owner enforced）。AWSも無効化を推奨
署名付きURLURLを渡された誰か期限付きで特定のオブジェクトだけを、AWSアカウントを持たない相手に渡したい。アップロード用にも発行できる
Block Public Accessアカウント／バケットポリシーやACLが何と書かれていても公開を上書きで禁じたい。既定で有効。ガードレール
Access Pointsアプリケーション／チーム1つの大きなバケットを多数のチームが共有していて、バケットポリシーが肥大化して管理できなくなった

署名付きURLの性質

署名付きURLは発行した主体の権限の範囲でしか動きません。読み取り権限しかないロールが発行したURLで書き込むことはできません。有効期限は発行時に指定します。「社外のパートナーに、このレポートだけ、48時間だけ渡したい」という設問は常にこれです。逆に「動画を世界中の視聴者に配信」なら CloudFront であり、その場合はバケットを公開せず OAC（Origin Access Control） で CloudFront 経由だけに絞るのが正解の形です。

Access Points の役割

Access Points は、1つのバケットに対して名前付きのエンドポイントを複数作り、それぞれに個別のポリシーを付ける仕組みです。分析チームは analytics/ 配下だけ読める、取り込みジョブは raw/ 配下にだけ書ける、といった分割を、巨大な1枚のバケットポリシーを書かずに実現できます。VPCからのみアクセスできるアクセスポイントも作れます。さらに Multi-Region Access Points は、複数リージョンのバケット群に対して単一のグローバルなエンドポイントを提供し、最も近いバケットへルーティングします。

Block Public Access の位置づけ

これは権限を与える仕組みではなく、与えられた公開権限を無効化する上書きスイッチです。バケットポリシーに "Principal": "*" と書いてあっても、Block Public Access が有効なら公開されません。設問で「バケットが意図せず公開されていた。再発を防ぐには」と来たら、アカウントレベルでの Block Public Access 有効化と、IAM Access Analyzer for S3 による検知が答えになります。

06

暗号化 ―― 鍵を誰が持つか

暗号化の選択肢は、機能の差ではなく鍵を誰が持ち、誰が管理し、使用履歴を追えるかの差です。設問は必ずそのどれかを要件として書いてきます。

方式鍵を管理するのは鍵の使用を監査できるかこれが正解になる要件
SSE-S3
AES-256		AWS（完全におまかせ）キー単位の使用記録は追えない要件が「保存時に暗号化されていること」だけ。追加費用なし。2023年1月以降、新規オブジェクトは既定でこれが適用されます
SSE-KMS顧客（KMSキー）CloudTrail に Decrypt / GenerateDataKey が残る「誰がいつ復号したか監査したい」「鍵のローテーションを自分で制御したい」「鍵ポリシーで、S3の権限とは別に復号を止められるようにしたい」
DSSE-KMS顧客（KMSキー）同上二重に暗号化する必要がある、極めて厳格な規制要件
SSE-C顧客（毎リクエストで鍵を送る）AWS側に鍵は残らない「鍵をAWSに預けられない」が暗号化処理はS3に任せたい。HTTPS必須で、鍵を失えば復号不能
クライアントサイド暗号化顧客（アプリ側で完結）AWSは平文を一切見ない「AWSに平文を渡さない」ことそのものが要件。鍵管理の責任はすべて自分

実務でも試験でも、判断の中心は SSE-S3 と SSE-KMS のどちらかです。切り分けの言葉はひとつ、監査とアクセス制御の粒度です。「暗号化してあればよい」なら SSE-S3、「鍵の使用者を特定・制限したい」なら SSE-KMS。

最頻出の引っかけ

SSE-KMS でオブジェクトを読み書きすると、リクエストごとに KMS の API が呼ばれます。毎秒数万件を処理するデータパイプラインでは KMS 側のリクエストクォータに当たり、ThrottlingException や 503 が出ます。ここで「SSE-S3 に切り替える」を選ぶと監査要件を落とすので不正解。正解は S3 Bucket Keys の有効化です。バケット単位のキーを使って KMS の呼び出し回数を大幅に削減し、暗号化方式も監査も維持したまま解決します。

転送中の暗号化

保存時の暗号化とは別の話です。HTTPS を強制したい場合は、バケットポリシーで aws:SecureTransport が false のリクエストを Deny します。「保存時の暗号化は有効なのに、監査で転送経路を指摘された」型の設問はこの形を問うています。

07

S3 の性能と大きなファイルの扱い

性能の設問は「遅い」「失敗する」「高い」のどれかで来ます。原因の切り分けが、そのまま答えになります。

マルチパートアップロード

  • 単一の PUT で送れる上限は 5GB。それを超えるオブジェクトはマルチパートが必須です。オブジェクト自体の上限は 5TB。
  • AWSは100MBを超えたらマルチパートを使うことを推奨しています。パートを並列に送れるので速く、失敗したパートだけ再送できるので不安定な回線に強い。
  • パートは最大10,000個です。
  • 中断したアップロードのパートは課金され続けます。ライフサイクルの AbortIncompleteMultipartUpload で必ず掃除します。

Transfer Acceleration

CloudFront のエッジロケーションを入口にして、そこから AWS のバックボーン経由でバケットまで運びます。効くのはクライアントとバケットが地理的に遠いときです。同一リージョン内のEC2からのアップロードには効果がありません。「海外の拠点から東京のバケットへの大容量アップロードが遅い」という設問の答えがこれです。なお、有効化前に効果を測定できる比較ツールがAWSから提供されています。

プレフィックス設計

S3のリクエストレートはプレフィックス単位で決まります。1プレフィックスあたり、書き込み系（PUT / COPY / POST / DELETE）が毎秒3,500、読み取り系（GET / HEAD）が毎秒5,500です。プレフィックスの数に上限はありません。したがって、プレフィックスを分けて並列化すればリニアにスケールします。10個に分ければ読み取りは毎秒55,000まで伸びます。

設問で 503 Slow Down が出てくる場合、原因は「バケットの上限」ではなく「1つのプレフィックスに集中している」ことです。日付をパスの先頭に置く設計（2026/09/20/...）は、その日のデータが1プレフィックスに集中するので不利になりがちです。スケーリングは即座ではなく段階的に行われる点も押さえてください。急激なスパイクでは一時的に503が出て、しばらくすると収まります。

S3 Select とバイト範囲フェッチ

大きな CSV / JSON / Parquet から必要な行と列だけを SQL のサブセットで抜き出し、転送量とアプリ側の処理を減らす機能です。効くのは「1つのオブジェクトの一部だけが欲しい」ケースです。複数オブジェクトをまたいだ集計や JOIN は Athena の仕事で、ここが切り分けの線になります。オブジェクトの特定バイト範囲だけを並列に取得するバイト範囲フェッチも、大きなファイルの先頭メタデータだけ読みたいときに使えます。

08

EBS とインスタンスストア

ブロックストレージの設問は、SSD か HDD かとデータが消えてよいかの2択に還元できます。

ボリュームタイプの選択軸

タイプ種別選ぶ決め手ブートボリューム
gp3汎用SSD既定の選択肢。3,000 IOPS と 125 MiB/s が容量に関係なく含まれ、IOPSとスループットを容量と独立に追加できる。gp2 より安い可
gp2汎用SSD旧世代。性能が容量に比例（1GiBあたり3 IOPS）し、小さいボリュームはバーストに依存する。新規に選ぶ理由はほぼない可
io2 / io2 Block ExpressプロビジョンドIOPS SSD耐久性 99.999%。Block Express は最大 256,000 IOPS / 4,000 MiB/s。単一ボリュームに極端なIOPSと低レイテンシが要る本番データベース可
st1スループット最適化HDD最小125GiB、最大500 MiB/s。大容量のシーケンシャル読み書き（ログ処理、ビッグデータ、データウェアハウス）を安く不可
sc1コールドHDD最小125GiB、最大250 MiB/s。EBSの中で最安。めったにアクセスしない大容量データ不可
判断軸

設問に IOPS という語が出たら SSD 系（gp3 / io2）、スループット（MiB/s）やシーケンシャルという語が出たら HDD 系（st1 / sc1）です。「gp2 を使っているが性能が足りない。コストは増やしたくない」と来たら、ほぼ確実に gp3 への変更が正解です。io2 は高価なので、「データベース」と書いてあるだけでは飛びつかず、サブミリ秒や数万IOPSといった数字の裏付けがあるかを確認してください。

スナップショットと暗号化

  • スナップショットは内部的に S3 に保存される増分バックアップです。2回目以降は差分だけを取ります。
  • EBSボリュームは単一AZのリソースです。別AZにコピーしたければスナップショットを経由します。別リージョン・別アカウントへのコピーもでき、これがDRの基本形になります。
  • 自動化は Data Lifecycle Manager（DLM）、または複数サービスをまとめるなら AWS Backup。
  • スナップショットから作ったボリュームは、初回アクセス時にレイテンシが出ます。これを避けるのが Fast Snapshot Restore（追加料金あり）です。
  • 暗号化は KMS を使います。有効にすると、保存データ・インスタンスとボリューム間の転送・スナップショット・そのスナップショットから作るボリュームまで、すべて暗号化されます。
  • 既存の暗号化されていないボリュームを、その場で暗号化することはできません。スナップショットを取り、暗号化を指定してそのスナップショットをコピーし、コピーからボリュームを作ります。この3手順が設問の正解になります。アカウント単位で「既定で暗号化」を有効化しておけば、以後の新規ボリュームは自動的に暗号化されます。

マルチアタッチ

1つのボリュームを複数のEC2に同時にアタッチする機能です。条件が厳しく、io1 / io2 のみ、同一AZ、Nitro世代のインスタンス、最大16台です。さらに重要なのは、XFS や ext4 のような通常のファイルシステムでは壊れることです。クラスタ対応のファイルシステムが前提になります。したがって「複数のEC2からファイルを共有したい」という一般的な設問の答えはマルチアタッチではなく EFS です。マルチアタッチが正解になるのは、クラスタソフトウェアを前提とした高可用性構成が明示されている場合に限られます。

インスタンスストアとの違い

EBSインスタンスストア
実体ネットワーク越しのブロックストレージホストに物理的に直結したディスク
性能プロビジョニングした分最高のIOPSと最低のレイテンシ
インスタンス停止・終了時残る消える（再起動では残る）
スナップショット取れる取れない
サイズ変更後から変更可能インスタンスタイプで固定

インスタンスストアが正解になるのは、失われても構わないデータのときだけです。キャッシュ、一時的なスクラッチ領域、シャッフル処理の中間ファイル、レプリカを他ノードに持つ分散データベース。設問に「一時的な」「バッファ」「最高のI/O性能」が揃っていればこれです。逆に「永続化が必要」と一言でも書いてあれば消えます。

09

共有ファイルストレージ ―― EFS と FSx

「複数のサーバーから同じファイルを見たい」と書いてあったら、この節の話です。あとはプロトコルとOSで一意に決まります。

EFS

EFS は NFS v4.1 のマネージドファイルシステムです。複数のAZにある複数のEC2から同時にマウントできます。容量は自動で伸縮し、事前のサイズ指定は不要です。Auto Scaling グループのインスタンスが増減しても、同じディレクトリを共有し続けられる――これが EFS の存在理由であり、そのまま設問の手がかりになります。

  • Linux 専用です。Windows からの SMB は FSx の領域です。
  • ストレージクラスは Standard / Infrequent Access（IA）/ Archive の3つ。加えて、単一AZに置く One Zone のバリアントがあり、開発環境や再作成可能なデータのコストを下げられます。
  • ライフサイクル管理の既定は、30日アクセスがなければ IA、90日で Archive へ移動します。アクセスされても自動では戻りませんが、「初回アクセスで Standard に戻す」設定を有効にできます。
  • スループットモードは Elastic（既定。使った分だけ）、Provisioned、Bursting から選べます。「容量は小さいがスループットが要る」場合に Provisioned を選びます。
  • アクセスにはAZごとのマウントターゲットと、NFS のポート 2049 を許可するセキュリティグループが必要です。「マウントできない」型の設問はたいていここです。

FSx の4種類

FSx は「既にあるファイルシステムの世界を、そのままAWSに持ってくる」サービス群です。設問には必ず固有名詞のヒントが埋まっています。

種類プロトコル設問に出る手がかり
FSx for Windows File ServerSMB「Windows」「SMB」「Active Directory との統合」「既存の共有ドライブを移行」。Windows と書いてあればこれ
FSx for LustreLustre（POSIX）「HPC」「機械学習の学習データ」「ゲノム解析」「金融シミュレーション」「数百GB/秒」。S3バケットとリンクして、S3のオブジェクトをファイルとして高速に処理できるのが決め手
FSx for NetApp ONTAPNFS / SMB / iSCSI を同時「NetApp」「オンプレの ONTAP をそのまま」「複数プロトコルを同時に使いたい」「スナップショットや重複排除を維持」
FSx for OpenZFSNFS「ZFS」「オンプレのLinuxファイルサーバーを移行」「NFSだけでよい」「低レイテンシ」

Lustre にはデプロイタイプが2つあります。Scratch は一時的な処理用でレプリケートされず、サーバー障害でデータを失いますが最も速い。Persistent は長期利用向けで、同一AZ内で自動的に復旧します。「一時的な処理」「長期保存は不要」と書いてあれば Scratch です。

3秒で切る順番

① Windows / SMB → FSx for Windows File Server。② HPC・機械学習・S3と連携した超高速処理 → FSx for Lustre。③ NetApp / ZFS という固有名詞 → 対応する FSx。④ それ以外で Linux から NFS 共有 → EFS。⑤ そもそも共有が要らない1台だけの話 → EBS。この順で潰せば迷いません。

10

ハイブリッド構成とデータ移行

オンプレミスが絡む設問は、移行して終わりなのか、使い続けるのかをまず読み分けます。使い続けるなら Storage Gateway、移すだけなら DataSync か Snow です。

Storage Gateway の4形態

形態オンプレ側から見た姿クラウド側の保存先設問の手がかり
S3 File GatewayNFS / SMB の共有S3 のオブジェクト「ファイルをそのままS3に置きたい」「オンプレにキャッシュを残しつつ容量を無限に」
FSx File GatewaySMB の共有FSx for Windows File Server「オンプレの拠点から FSx への低レイテンシアクセスとキャッシュ」
Volume GatewayiSCSI のブロックデバイスS3 / EBSスナップショット「ブロックストレージ」「既存アプリがiSCSIを使う」。Cached は主データがクラウドで手元はキャッシュ、Stored は主データが手元でクラウドはバックアップ
Tape Gateway仮想テープライブラリ（VTL）S3 / Glacier「テープ」「既存のバックアップソフトを変えずに物理テープを廃止したい」

Volume Gateway の2モードは頻出です。切り分けの言葉は「主データがどちらにあるか」。低レイテンシで全データにアクセスし続ける必要があるなら Stored、手元のディスク容量を減らしたいなら Cached です。

AWS Backup

EBS、EFS、FSx、RDS、DynamoDB、S3、Storage Gateway など複数サービスのバックアップを1か所で定義・実行・監査するサービスです。バックアップ計画に頻度と保持期間とライフサイクル（一定期間後にコールドストレージへ）を書き、タグで対象を選びます。クロスリージョン・クロスアカウントのコピーにも対応します。Backup Vault Lock を使えば、バックアップ自体を WORM 化でき、ガバナンスモードとコンプライアンスモードという Object Lock と同じ構図の選択肢を持ちます。

設問での切り分けはこうです。「複数サービスにまたがるバックアップを中央で管理し、コンプライアンス報告を出したい」→ AWS Backup。「EBSスナップショットのスケジュール取得と世代管理だけ」→ Data Lifecycle Manager でも足ります。

大容量移行は計算で決める

ここは暗記ではなく計算の問題です。所要日数 = データ量 ÷ 実効回線速度。この一本で判断できます。例えば 100 TB を 1 Gbps の回線で送ると、100 TB = 800,000 Gbit、1 Gbps で 800,000 秒、およそ 9.3 日。回線を100%占有した理想値なので、実際はこの数倍を見ます。同じ 100 TB を 100 Mbps で送れば約93日で、たいていの期限に間に合いません。

状況選ぶもの
回線で期限内に終わる。かつ継続的に同期したいAWS DataSync（NFS / SMB / HDFS / オブジェクトストレージ ↔ S3・EFS・FSx。増分転送、検証、スケジュール実行）
回線が細い、または一度きりの大量移行に期限があるAWS Snowball Edge（物理デバイスを郵送。現行世代は Storage Optimized 210TB）
移行ではなくハイブリッドで使い続けるStorage Gateway
恒常的に太い専用線が欲しいDirect Connect（ただし開通に数週間〜数か月。「今月中に移行」には間に合わない）
Snow ファミリーの現状

試験の選択肢には Snowcone や旧世代の Snowball Edge が今も登場しますが、実機としては2024年11月に Snowcone と旧世代 Snowball Edge モデルの提供が終了しており、現行は Snowball Edge Storage Optimized 210TB などに絞られています。AWS は新規の大容量移行に DataSync や AWS Data Transfer Terminal を案内する方向です。試験では「回線では間に合わない量のオフライン移行 = Snow」という対応で答えつつ、実務ではまず DataSync を検討する、と二段構えで持っておいてください。

12

確認問題

先に自分で答えを決めてから開いてください。特にQ3は、計算してから開くこと。

Q1新しいデータレイクを構築する。取り込まれるデータがどの程度読まれるかは事前に予測できず、データセットによって大きく異なる見込みである。運用の手間を増やさずにストレージコストを最適化したい。最も適切なのはどれか。
  • A. すべて S3 Standard に保存する
  • B. S3 Intelligent-Tiering に保存する
  • C. 30日後に S3 Standard-IA へ遷移するライフサイクルルールを設定する
  • D. すべて S3 One Zone-IA に保存し、コストを最小化する

正解: B

「アクセスパターンが予測できない」かつ「運用の手間をかけたくない」は Intelligent-Tiering の定義そのものです。オブジェクトごとに監視して自動で階層を移し、取り出し料金もかかりません。

判断軸: C は読まれ方が分かっているときの手段です。この設問では30日後も頻繁に読まれるデータが混在する可能性があり、IA の取り出し料金でかえって高くつきます。D は単一AZで、データレイクの原本を置く先としては耐久性の要件を満たしません。A は間違いではありませんが最適化になっていません。「予測できない」という語を見た瞬間に B に寄せてください。

Q2金融規制により、取引記録を5年間、社内の管理者やルートユーザーを含む誰も削除・改変できない状態で S3 に保存する必要がある。適切な構成はどれか。
  • A. バケットポリシーで s3:DeleteObject と s3:PutObject を Deny する
  • B. バージョニングを有効にし、Object Lock をガバナンスモードで保持期間5年に設定する
  • C. バージョニングを有効にし、Object Lock をコンプライアンスモードで保持期間5年に設定する
  • D. バージョニングと MFA Delete を有効にする

正解: C

コンプライアンスモードは、保持期間中はルートユーザーを含め誰もオブジェクトを削除できず、保持期間の短縮もモードの変更もできません。前提としてバージョニングが有効である必要があり、選択肢もそれを含んでいます。

判断軸: A はバケットポリシー自体を管理者が書き換えられるので、要件の「管理者を含む」を満たしません。B は s3:BypassGovernanceRetention 権限を持つ者が解除できます。D は MFA を持つルートユーザーが削除できます。「誰も」「ルートユーザーでも」という語は、コンプライアンスモード以外を全部落とすための合図です。

Q3オンプレミスのデータセンターにある 300 TB のアーカイブを S3 に移行する。専用線はなく、インターネット回線の実効速度は 500 Mbps。移行の期限は3週間で、移行完了後に継続的な同期は不要である。最も適切な方法はどれか。
  • A. AWS DataSync でインターネット経由の転送を行う
  • B. AWS Snowball Edge を注文し、デバイスに書き込んで返送する
  • C. S3 Transfer Acceleration を有効にして aws s3 sync で転送する
  • D. AWS Direct Connect を新規に契約し、専用線経由で転送する

正解: B

計算します。300 TB は 2,400,000 Gbit。500 Mbps（0.5 Gbps）で割ると 4,800,000 秒、およそ56日です。これは回線を100%占有した理想値なので、実際はさらに長くかかります。3週間には到底収まらないため、オフライン移送を選びます。

判断軸: A と C は同じ物理回線を使う以上、上限は変わりません。Transfer Acceleration は経路を最適化するもので、回線帯域そのものを増やすわけではありません。D は Direct Connect の開通に数週間から数か月かかるため、期限に間に合いません。移行の設問を見たら、まずデータ量を bit に直して回線速度で割る。それが3桁の日数になれば Snow、数日で済むなら DataSync です。

Q43つのアベイラビリティゾーンにまたがる Auto Scaling グループの Linux EC2 インスタンス群が、同じディレクトリに対して POSIX 準拠で同時に読み書きする必要がある。インスタンス数は負荷に応じて増減する。適切なストレージはどれか。
  • A. io2 ボリュームをマルチアタッチで全インスタンスにアタッチする
  • B. Amazon EFS をすべてのインスタンスにマウントする
  • C. FSx for Windows File Server を共有ドライブとしてマウントする
  • D. 各インスタンスに gp3 ボリュームを付け、cron で相互に rsync する

正解: B

EFS は複数AZの複数インスタンスから同時にマウントでき、容量も自動で伸縮します。Auto Scaling でインスタンスが増減する構成と相性が良い、というより、そのために存在するサービスです。

判断軸: A はマルチアタッチが同一AZ内の最大16台に限られ、さらに通常のファイルシステムでは同時書き込みでデータが壊れます。この設問は3AZなので成立しません。C は SMB / Windows 向けで、Linux の POSIX 要件に合いません。D は各インスタンスのデータがずれるため、同時読み書きの整合性を満たせません。「複数AZ」「Linux」「同時に読み書き」の3語が揃ったら EFS です。

Q5データ取り込みパイプラインが毎秒数万件のオブジェクトを S3 に書き込んでいる。すべてのオブジェクトは SSE-KMS で暗号化しており、鍵の使用履歴を CloudTrail で監査する要件がある。運用開始後、ThrottlingException と 503 エラーが頻発するようになった。要件を維持したまま解決する方法はどれか。
  • A. 暗号化方式を SSE-S3 に変更する
  • B. S3 Bucket Keys を有効にする
  • C. 書き込み先のプレフィックスを10個に分割する
  • D. 暗号化方式を SSE-C に変更し、鍵をアプリケーション側で管理する

正解: B

SSE-KMS はオブジェクトごとに KMS の API を呼ぶため、高スループットのパイプラインでは KMS 側のリクエストクォータに当たります。S3 Bucket Keys を有効にすると、バケット単位で生成したキーを再利用して KMS の呼び出し回数を大幅に削減できます。暗号化方式も CloudTrail での監査も維持されたままです。

判断軸: A と D は要件（鍵の使用履歴を CloudTrail で監査）を落としています。「エラーは消えるが要件を満たさない」選択肢は、SAAでは常に不正解です。C はプレフィックス分割で S3 側のリクエストレート上限には効きますが、KMS のクォータには一切効きません。エラーがどの層で出ているかを特定してから対策を選ぶ、という読み方が問われています。
