場面1 ―― 「監査用のログを7年残す。読むのは年に数回。どこに置けば安いか」

この場面で初めて出る言葉

ストレージクラスは、オブジェクトをアップロードするときに指定します。何も指定しなければ Standard です。後から変えるときは、次の場面のライフサイクルルールで自動的に移すのが普通です。クラスは6つ以上ありますが、並べると1本の線になります。

クラス読む頻度の目安読むときに待つ時間最小保存期間AZ
S3 Standard頻繁（日常的に読む）ミリ秒なし3以上
S3 Intelligent-Tiering予測できない／変動する階層による（既定の階層はミリ秒）なし3以上
S3 Standard-IA月1回程度ミリ秒30日3以上
S3 One Zone-IA月1回程度かつ失っても作り直せるミリ秒30日1
S3 Glacier Instant Retrieval四半期に1回程度ミリ秒90日3以上
S3 Glacier Flexible Retrieval年に1〜2回Expedited 1〜5分 / Standard 3〜5時間 / Bulk 5〜12時間90日3以上
S3 Glacier Deep Archive年1回未満（ほぼ読まない）Standard 12時間以内 / Bulk 48時間以内180日3以上

Expedited・Standard・Bulk は、取り出し（復元）を頼むときに選ぶ速さの種類です。速いほど高くなります。

設問にいちばん効くのは「読むときに待つ時間」です。設問は必ず、待てる時間をどこかに書いてきます。「監査時には即座に参照できる必要がある」とあれば Glacier Flexible Retrieval は消えます。「取り出しに数時間かかっても問題ない」とあれば、Glacier Instant Retrieval を選ぶ理由はなくなります（より高いので）。

  • この場面の答え：7年残して、読むのは年に数回。読むときに半日待てるなら Glacier Deep Archive、数時間なら Glacier Flexible Retrieval、すぐ読めないと困るなら Glacier Instant Retrieval

「安いクラス」が高くつくとき

右のクラスほど安く見えますが、最小保存期間と課金の下限があるので、短命なデータや小さなファイルではかえって高くなります。

いちばん多い引っかけ

7日間だけ保持する一時ファイルを Standard-IA に置く選択肢は、コスト最適化に見えて逆です。30日分の保存料金を請求されるので、Standard に置いたほうが安い。短命なデータに IA 系・Glacier 系を選ばせる選択肢は不正解です。10KB のファイルを大量に IA へ落とす選択肢も、128KB の下限があるので同じ罠です。

読まれ方が分からないとき ―― Intelligent-Tiering

ここまでのクラスは「どれくらい読むか」が分かっている前提でした。分からないときは、S3 に見張らせます。

  • 取り出し料金がかかりません。代わりに、オブジェクト1個ごとに見張りと自動化の料金がかかります
  • 128KB 未満のオブジェクトは見張りの対象外で、Frequent Access に留まります。小さいファイルが大量にあると、思ったほど安くなりません
  • 任意の階層（Archive Access・Deep Archive Access）は、バケットの「プロパティ」タブにある Intelligent-Tiering のアーカイブ設定で有効にします

One Zone-IA を選んでよい場面は限られる

One Zone-IA は1つの AZ にしかデータを置きません。安いのは事実ですが、その AZ が失われればオブジェクトも失われます。正解になるのは、元のデータが別の場所にあり、作り直せるものに限られます。S3 にある原本から作ったサムネイル、別のリージョンに複製があるコピー、オンプレミスに原本があるバックアップの二次コピーなどです。監査ログ、法定保存の文書、唯一の原本を One Zone-IA に置く選択肢は、安くても不正解です。

試験ではこう出る

「アクセスパターンが予測できない」「時間とともに変化する」「運用の手間をかけずに」→ Intelligent-Tiering。「30日後にはほとんど読まれないと分かっている」→ ライフサイクルルールで Standard-IA へ（場面2）。読まれ方が分かっているかどうかが分かれ目。「アーカイブだが即座に」→ Glacier Instant Retrieval。「取り出しは12時間でよい」→ Glacier Deep Archive。

場面2 ―― 「30日たったら安いクラスへ、7年たったら消したい」「請求書に、説明のつかない S3 の容量がある」

ライフサイクルルールは、バケットの「管理」タブで作ります。まず知っておくのは、移せる方向が決まっていることです。

1つのルールには、いくつかの動きをまとめて書けます。場面の依頼をそのまま図にすると、こうなります。

上の図と同じ内容のライフサイクルルール
{
  "ID": "logs-tiering",
  "Filter": { "Prefix": "logs/" },
  "Status": "Enabled",
  "Transitions": [
    { "Days": 30,  "StorageClass": "STANDARD_IA" },   // 30日未満は指定できない
    { "Days": 120, "StorageClass": "DEEP_ARCHIVE" }
  ],
  "Expiration": { "Days": 2555 },
  "NoncurrentVersionExpiration": { "NoncurrentDays": 30 },
  "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
}

ルールに書ける5つの動き

  1. Transition ―― 現行バージョンを別のクラスへ移す
  2. Expiration ―― 現行バージョンを削除する。バージョニングが有効なら、実際には削除マーカー（場面3）が付くだけ
  3. NoncurrentVersionTransition / NoncurrentVersionExpiration ―― 古いバージョンを移す・消す。バージョニングを有効にしたまま容量を抑える定番
  4. AbortIncompleteMultipartUpload ―― 途中で失敗したマルチパートアップロードの断片を消す。設定していないと、一覧に見えない断片に課金され続ける。「請求額に説明のつかない S3 の容量がある」の答え
  5. ExpiredObjectDeleteMarker ―― 中身がなくなり、削除マーカーだけが残った状態を掃除する

覚えておく制約

  • Standard から Standard-IA / One Zone-IA へは、最低30日たってから。29日で移すルールは作れません
  • 128KB 未満のオブジェクトは、既定ではどのクラスにも遷移しません。移したいときは ObjectSizeGreaterThan などのサイズの条件を明示します。ただし遷移のリクエスト料金が節約額を上回ることが多く、AWS も勧めていません
  • Glacier Flexible Retrieval と Deep Archive に置いたオブジェクトには、1件あたり約40KB のメタデータの課金が付きます。内訳は S3 Standard の料金で 8KB、Glacier の料金で 32KB。小さいファイルを何億件も Deep Archive に送ると、本体より管理用のデータのほうが高くなります。先に1つのファイルにまとめてから送るのが正解です
  • 最小保存期間より前に削除・遷移すると、残りの期間分が課金されます。Deep Archive に入れた翌日に消しても、180日分を払います（場面1の図）
試験ではこう出る

「30日後にはほとんど読まれない」→ ライフサイクルルールで Standard-IA へ。「説明のつかない容量に課金されている」→ AbortIncompleteMultipartUpload。「アーカイブしたデータを通常のクラスに戻す」→ ルールでは戻せない。復元（restore）してからコピーし直す。「バージョニングで容量が増え続ける」→ NoncurrentVersionExpiration。

「消えては困る」には3つの段階があります。うっかり消したものを戻したい、誰にも消させたくない、リージョンごと失っても残したい。順に見ます。どれも土台はバージョニングです。

うっかり消したものを戻す ―― バージョニング

バージョニングは、バケットの「プロパティ」タブで有効にします。

  • 一度有効にしたバージョニングは無効には戻せません。できるのは「停止（Suspended）」までで、それまでに作られた版は残り続けます
  • 古い版も課金の対象です。場面2の NoncurrentVersionExpiration と組み合わせて設計するのが定石です
  • この後の Object Lock もレプリケーションも、バージョニングが有効であることが前提です。ここが試験でいちばん繰り返し問われます

MFA Delete は、版の完全な削除と、バージョニングの状態の変更に、MFA のコードを求める設定です。特徴は2つ。バージョニングが有効でなければ設定できないこと、そしてバケットの所有者のルートユーザーが CLI か API から設定する必要があること（マネジメントコンソールからは設定できません）。「IAM の管理者が有効にする」という選択肢は不正解です。

誰にも消させない ―― Object Lock

Object Lock は WORM の状態を作ります。バケットのプロパティで有効にし、保持期間はオブジェクトごと、またはバケットの既定値として決めます。モードが2つあります。

ガバナンスモードコンプライアンスモード
解除できる人s3:BypassGovernanceRetention を持つプリンシパル誰も解除できない（ルートユーザーを含む）
保持期間の短縮権限があれば可能不可
典型的な目的誤操作の防止。設定のテスト金融・医療などの法規制への対応
いちばん多い引っかけ

「管理者を含め誰も削除できないようにしたい」という要件に、バケットポリシーで s3:DeleteObject を Deny する選択肢が並びます。不正解です。バケットポリシーそのものを管理者が書き換えられるからです。同じ理由でガバナンスモードも不正解。「誰も」「ルートユーザーでも」とあったらコンプライアンスモード、と直結させてください。

リージョンごと失っても残す ―― レプリケーション

レプリケーションは、バケットの「管理」タブでレプリケーションルールとして作ります。

CRR（別のリージョンへ）SRR（同じリージョンへ）
目的DR、地理的に離れた利用者の遅延を縮める、法規制による地理的な分散ログの集約、本番から検証環境へのデータの複製、アカウントを分けて保護する
設問の手がかり「別リージョンに」「災害復旧」「海外拠点からの読み取りが遅い」「同じリージョンの別バケット／別アカウントに」「監査用に隔離」
  • コピー元・コピー先の両方でバージョニングが有効であること。片方だけでは設定できません
  • S3 が複製するための IAM ロールが必要です（S3 がそのロールを引き受けて、コピー元を読み、コピー先へ書く）
  • 非同期です。書き込んだ瞬間に相手側にあるとは限りません。時間の保証が欲しいときは S3 Replication Time Control（RTC）を使うと、99.99% のオブジェクトを15分以内に複製するという SLA（サービスの品質の約束）が付きます
  • ルールを作った時点ですでにあるオブジェクトは複製されません。前からある分は S3 Batch Replication で別に流します
  • 削除マーカーを複製するかどうかは任意の設定です。版を指定した削除は複製されません（コピー先まで削除が伝わって両方消える、という事故を防ぐ設計です）
試験ではこう出る

「誤って上書き・削除したものを戻したい」→ バージョニング。「ルートユーザーでも削除できない」→ Object Lock のコンプライアンスモード。「期限は未定だが、訴訟の間は消させない」→ リーガルホールド。「設定したのに古いデータが複製されない」→ S3 Batch Replication。「15分以内に複製される保証」→ RTC。

性能の設問は「遅い」「失敗する」「エラーが返る」のどれかで来ます。原因を切り分けると、そのまま答えになります。

  • 1回の PUT で送れる上限は 5GB。それを超えるオブジェクトはマルチパートが必須です。オブジェクト自体の上限は 5TB
  • AWS は 100MB を超えたらマルチパートを使うことを勧めています
  • パートは最大 10,000 個です
  • マルチパートにするかどうかはバケットの設定ではなく、送る側（CLI や SDK）が決めます。aws s3 cp などの CLI は、大きなファイルを自動でマルチパートにします

有効にする前に、効果を測れる比較ツールが AWS から提供されています。

  • 1つのプレフィックスあたり、書き込み系（PUT / COPY / POST / DELETE）が毎秒 3,500、読み取り系（GET / HEAD）が毎秒 5,500。10個に分ければ、読み取りは毎秒 55,000 まで伸びます
  • 日付をキーの先頭に置く設計（2026/09/20/...）は、その日のデータが1つのプレフィックスに集中するので不利になりがちです
  • 受けられる回数は、すぐにではなく段階的に増えます。急に増えたときは一時的に 503 が出て、しばらくすると収まります

S3 Select は、大きな CSV / JSON / Parquet（どれも表形式のデータを入れるファイルの形式）から必要な行と列だけを SQL の一部の文法で抜き出し、転送する量とアプリ側の処理を減らします。効くのは「1つのオブジェクトの一部だけが欲しい」ときです。複数のオブジェクトにまたがる集計や結合（JOIN）は Athena の仕事で、ここが切り分けの線になります。オブジェクトの決まった範囲のバイトだけを取り出すバイト範囲フェッチも、大きなファイルの先頭だけ読みたいときや、範囲を分けて並列に取り出したいときに使えます。

バックアップをまとめて管理する ―― AWS Backup

AWS Backup は、EBS、EFS、FSx、RDS、DynamoDB、S3、Storage Gateway など複数のサービスのバックアップを1か所で決めて、実行し、監査するサービスです。AWS Backup の画面でバックアップ計画を作り、そこに頻度と保持期間とライフサイクル（一定の期間が過ぎたら安い保管先へ移す）を書き、タグで対象を選びます。別のリージョン・別のアカウントへのコピーにも対応します。Backup Vault Lock（バックアップの保管庫に鍵をかける機能）を使えば、バックアップそのものを WORM にでき、場面3の Object Lock と同じく、ガバナンスモードとコンプライアンスモードを選べます。

切り分けはこうです。「複数のサービスにまたがるバックアップを中央で管理し、コンプライアンスの報告を出したい」→ AWS Backup。「EBS スナップショットを決まった間隔で取って、世代を管理するだけ」→ DLM（場面7）でも足ります。

Q1新しいデータレイクを構築する。取り込まれるデータがどの程度読まれるかは事前に予測できず、データセットによって大きく異なる見込みである。運用の手間を増やさずにストレージコストを最適化したい。最も適切なのはどれか。
  • A. すべて S3 Standard に保存する
  • B. S3 Intelligent-Tiering に保存する
  • C. 30日後に S3 Standard-IA へ遷移するライフサイクルルールを設定する
  • D. すべて S3 One Zone-IA に保存し、コストを最小化する

正解: B

「予測できない」「運用の手間をかけたくない」の2つが Intelligent-Tiering を指している。場面1の3枚目の図のとおり、S3 がオブジェクトごとに読まれ方を見張って自動で階層を移し、取り出し料金もかからない。

判断軸: C は読まれ方が分かっているときの手段（場面2）。この設問では30日後も頻繁に読まれるデータが混ざる可能性があり、IA の取り出し料金でかえって高くつく。D は AZ が1つで、データレイクの原本を置く先としては失ってよい条件を満たさない。A は間違いではないが最適化になっていない。「予測できない」を見たら B に寄せる。

Q2金融規制により、取引記録を5年間、社内の管理者やルートユーザーを含む誰も削除・改変できない状態で S3 に保存する必要がある。適切な構成はどれか。
  • A. バケットポリシーで s3:DeleteObject と s3:PutObject を Deny する
  • B. バージョニングを有効にし、Object Lock をガバナンスモードで保持期間5年に設定する
  • C. バージョニングを有効にし、Object Lock をコンプライアンスモードで保持期間5年に設定する
  • D. バージョニングと MFA Delete を有効にする

正解: C

場面3の Object Lock の図の右側。コンプライアンスモードは、保持期間中はルートユーザーを含め誰もオブジェクトを削除できず、保持期間の短縮もモードの変更もできない。前提のバージョニングも選択肢に含まれている。

判断軸: A はバケットポリシーそのものを管理者が書き換えられるので、「管理者を含む」を満たさない。B は s3:BypassGovernanceRetention の権限を持つ人が解除できる（図の左側）。D は MFA を持つルートユーザーが削除できる。「誰も」「ルートユーザーでも」は、コンプライアンスモード以外を全部落とすための合図。

Q3オンプレミスのデータセンターにある 300 TB のアーカイブを S3 に移行する。専用線はなく、インターネット回線の実効速度は 500 Mbps。移行の期限は3週間で、移行完了後に継続的な同期は不要である。最も適切な方法はどれか。
  • A. AWS DataSync でインターネット経由の転送を行う
  • B. AWS Snowball Edge を注文し、デバイスに書き込んで返送する
  • C. S3 Transfer Acceleration を有効にして aws s3 sync で転送する
  • D. AWS Direct Connect を新規に契約し、専用線経由で転送する

正解: B

場面9の割り算をする。300 TB は 2,400,000 ギガビット。500 Mbps（0.5 Gbps）で割ると 4,800,000 秒、およそ56日。回線を 100% 使えた場合の理想の値なので、実際はさらに長い。3週間には収まらないので、機器に書き込んで運ぶ。

判断軸: A と C は同じ回線を使う以上、上限は変わらない。Transfer Acceleration（場面6）は経路を良くするもので、回線の太さを増やすわけではない。D は Direct Connect の開通に数週間から数か月かかり、期限に間に合わない。移行の設問を見たら、まずデータ量をビットに直して回線速度で割る。期限を超えるなら Snow、数日で済むなら DataSync。

Q43つのアベイラビリティゾーンにまたがる Auto Scaling グループの Linux EC2 インスタンス群が、同じディレクトリに対して POSIX 準拠で同時に読み書きする必要がある。インスタンス数は負荷に応じて増減する。適切なストレージはどれか。
  • A. io2 ボリュームをマルチアタッチで全インスタンスにアタッチする
  • B. Amazon EFS をすべてのインスタンスにマウントする
  • C. FSx for Windows File Server を共有ドライブとしてマウントする
  • D. 各インスタンスに gp3 ボリュームを付け、cron で相互に rsync する

正解: B

場面8の EFS の図そのもの。EFS は複数の AZ の複数のインスタンスから同時にマウントでき、容量も自動で伸び縮みする。Auto Scaling で台が増減しても、全員が同じフォルダを見続けられる。

判断軸: A のマルチアタッチ（場面7）は同じ AZ の中の最大16台に限られ、普通のファイルシステムでは同時に書き込むとデータが壊れる。この設問は 3AZ なので成り立たない。C は SMB / Windows 向けで、Linux の POSIX の要件に合わない。D は各インスタンスのデータがずれるので、同時の読み書きの整合性を満たせない。「複数 AZ」「Linux」「同時に読み書き」が揃ったら EFS。

Q5データ取り込みパイプラインが毎秒数万件のオブジェクトを S3 に書き込んでいる。すべてのオブジェクトは SSE-KMS で暗号化しており、鍵の使用履歴を CloudTrail で監査する要件がある。運用開始後、ThrottlingException と 503 エラーが頻発するようになった。要件を維持したまま解決する方法はどれか。

  • B. S3 Bucket Keys を有効にする
  • C. 書き込み先のプレフィックスを10個に分割する
  • D. 暗号化方式を SSE-C に変更し、鍵をアプリケーション側で管理する

正解: B

場面5の2枚目の図。SSE-KMS は読み書きのたびに KMS を呼ぶので、大量の書き込みでは KMS 側の回数の上限に当たる。S3 Bucket Keys を有効にすると、バケットごとの鍵を使い回して KMS を呼ぶ回数を大きく減らせる。暗号化の方式も CloudTrail での監査も保たれる。

判断軸: A と D は要件（鍵の使用履歴を CloudTrail で監査）を落としている。「エラーは消えるが要件を満たさない」選択肢は、SAA では常に不正解。C のプレフィックスの分割（場面6）は S3 側のリクエストレートの上限には効くが、KMS の上限には効かない。エラーがどの層で出ているかを見分けてから対策を選ぶ。
