01

この講義のゴール

暗記ではなく、設問を読んだときに手が動く状態を目指します。今日終わったときに、次の3つができていれば合格です。

  • 01
    ポリシーのJSONを読んで、何が許可されるか言える。
    Effect / Action / Resource / Condition の4つが何を意味するか、実物を見て説明できる。
  • 02
    「ロールを使う」が正解になる理由を説明できる。
    アクセスキーとの違いを、一時認証情報という言葉を使って言える。
  • 03
    Allow と Deny がぶつかったときの勝敗を即答できる。
    権限境界とSCPが絡んでも、順を追って結論を出せる。
なぜIAMから始めるか

IAMはドメイン1の中心ですが、そこに閉じません。「EC2からS3を読む」「Lambdaがデータベースに書く」「別アカウントのバケットを参照する」――ドメイン2〜4の設問にも、権限の話は必ず顔を出します。IAMを固めることは、実質的に全分野への投資です。

道筋は、登場人物 → ポリシーの文法 → ロールと一時認証情報 → フェデレーション → 評価ロジックと上限の順です。機能名を覚えるのではなく「この要件が来たらこの箱」という対応を作りながら読んでください。

02

登場人物を整理する

IAMには似た名前の要素が並びます。まず役割で切り分けます。

要素正体試験での扱われ方
ルートユーザーアカウント作成時のメールアドレス。全権限を持ち、剥奪できない。「日常業務でrootを使う」選択肢は常に不正解。MFAを有効化して封印するのが正解。
IAMユーザー長期の認証情報（パスワード、アクセスキー）を持つ主体。人間の管理者には可。アプリケーションやEC2に使うのは不正解。
IAMグループユーザーをまとめてポリシーを適用する入れ物。グループはプリンシパルになれない。ロールを引き受けることも、リソースポリシーの Principal に書くこともできない。
IAMロール一時的に被る「帽子」。認証情報を持たず、引き受けた時点で発行される。EC2・Lambda・クロスアカウント・フェデレーション、すべての正解ルート。
インスタンスプロファイルロールをEC2に渡すための容れ物。「EC2にロールを付ける」の実体。
サービスリンクロールAWSサービス自身が使う専用のロール。サービスが自動で作る。SCPやRCPの対象外という例外が問われる。
ポリシー何を許可／拒否するかを書いたJSON文書。AWS管理・カスタマー管理・インラインの3種。再利用性ではカスタマー管理が基本。

ポリシーの3つの持ち方

種類共有設問での位置づけ
AWS管理ポリシーできるすぐ使えるが粒度が粗い。AdministratorAccess は「最小権限に反する」誤答として置かれる
カスタマー管理ポリシーできる再利用とバージョン管理ができる。基本はこれ
インラインポリシーできない1つのIDに埋め込む。IDを消せば消える
よくある誤解

「ロールは人が使うもの、ユーザーは機械が使うもの」――逆です。ロールこそ機械（EC2、Lambda、他サービス）に使わせるもので、人間もフェデレーション経由でロールを引き受けるのが現代的な形です。IAMユーザーは、どうしても長期の認証情報が必要な例外的ケースのために残っている、と理解してください。

03

ポリシーの読み方

ポリシーは「誰が / 何を / どれに対して / どんな条件で」の4点セットです。実物を見ます。

アイデンティティベースポリシーの例
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadReportsOnly",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::quality-reports",
        "arn:aws:s3:::quality-reports/*"
      ],
      "Condition": {
        "Bool": { "aws:MultiFactorAuthPresent": "true" }
      }
    }
  ]
}

読み下すとこうです。MFAで認証しているときに限り、quality-reportsバケットの中身を読むことだけできる。書き込みも削除も許可していません。

ここで押さえる4点

  • Version は日付ではない。"2012-10-17"はポリシー言語のバージョン番号で、固定値です。作成日ではありません。
  • バケット本体とオブジェクトは別のARN。ListBucketはバケット(:::name)に対する操作、GetObjectはオブジェクト(:::name/*)に対する操作。片方だけ書くと動きません。設問でも狙われます。
  • Condition が効く場面を意識する。MFA必須、送信元IP制限(aws:SourceIp)、特定VPCエンドポイント経由のみ(aws:SourceVpce)、タグ一致(aws:ResourceTag)あたりが頻出です。
  • 書かれていないものは許可されない。暗黙の拒否が既定です。

要素は6つしかない

必ず書くのが Effect / Action / Resource、リソースベースでだけ書くのが Principal、任意が Sid / Condition。Principal があればリソース側、無ければID側――設問のJSONはこれで即座に分類できます。

  • 否定形は Effect とセットで読む。NotAction と NotResource は「それ以外すべて」です。Allow と組めば範囲が一気に広がって危険、Deny と組めば「これだけ残して全部禁止」という便利な書き方になります。
  • ARN は6部構成。arn:パーティション:サービス:リージョン:アカウントID:リソース。S3のようにリージョンとアカウントIDが空になるサービスがあり、コロンの連続（arn:aws:s3:::bucket）はそのためです。
  • Statement に順序はない。集めてから Deny 優先で判定されるだけで、「上に書いた Allow が下の Deny に勝つ」ことは起きません。
NotAction / NotResource の罠

"NotAction": ["s3:*"] は「S3以外のすべて」を指します。Allow と組み合わせると意図せず広大な権限になりがちで、設問では「最小権限の原則に反する選択肢」として登場します。見かけたら疑ってください。

04

Condition と ポリシー変数

Allow と Deny だけでは実務の要件は表現できません。「社内ネットワークからだけ」「HTTPSのときだけ」「自分のフォルダだけ」を書き切る道具が Condition とポリシー変数です。正解の選択肢がこの2つを使った一文で書かれていることがよくあります。

演算子は条件キーの「型」で選ぶ

演算子型使いどころ
StringEquals / StringNotEquals文字列（完全一致）タグ値、リージョン、組織IDの照合
StringLike / StringNotLike文字列（* 可）プレフィックス一致。s3:prefix でのフォルダ制限
ArnEquals / ArnLikeARNaws:SourceArn で呼び出し元リソースを限定
Bool真偽値aws:MultiFactorAuthPresent、aws:SecureTransport
IpAddress / NotIpAddressCIDRaws:SourceIp での送信元制限
...IfExistsサフィックスキーがあるときだけ評価。無ければ条件は通る
ForAllValues: / ForAnyValue:セット演算子aws:TagKeys のような複数値キーに前置する
Deny を書くときは「キーが無い場合」を考える

aws:MultiFactorAuthPresent: "false" を Deny 条件に書いても、MFAを使っていないリクエストではキー自体が存在しないことがあり、条件が一致せず Deny が発動しません。「MFAを強制したつもりが効いていない」型の設問では、BoolIfExists を使うか、Allow 側で "true" を要求するのが正解です。

頻出の条件キー

キー何を見るか設問での典型
aws:SourceIp送信元のパブリックIP「社内のIPレンジからのみ許可」
aws:SourceVpce経由したVPCエンドポイントのID「このエンドポイント経由以外は拒否」
aws:SecureTransportHTTPS（TLS）かどうか「暗号化されていない通信を拒否」
aws:PrincipalOrgID呼び出し元が属する組織のID「組織内の全アカウントに共有。アカウントIDを列挙したくない」
aws:PrincipalTag/キー呼び出した人・ロールのタグABACの主役
aws:RequestTag/キーこれから付けるタグ「タグを付けずにリソースを作らせない」
aws:ResourceTag/キーすでに付いているタグ「自分の部門のリソースだけ操作可」
aws:TagKeysリクエスト中のタグキー一覧「決められたタグキー以外を使わせない」
aws:RequestedRegion呼び出し先のリージョン「指定リージョン以外を全面禁止」
最頻出の引っかけ

aws:RequestTag と aws:ResourceTag の取り違えです。これから付けるのが Request、すでに付いているのが Resource。設問の動詞が作る・付けるなら Request、読む・変える・消すなら Resource です。

SourceIp は VPCエンドポイント経由では効かない

エンドポイント経由のリクエストはパブリックIPを通らないため、aws:SourceIp の制限は意図どおりに働きません。「IP制限を入れたのに想定と違う挙動になる」設問では、aws:SourceVpce や aws:SourceVpc への置き換えが正解です。

ポリシー変数で「一人ひとり用」を1枚に畳む

自分の名前のフォルダだけ読み書きできるポリシー
{
  "Effect": "Allow",
  "Action": ["s3:GetObject", "s3:PutObject"],
  "Resource": "arn:aws:s3:::team-share/${aws:username}/*"
}

${...} は評価時にリクエストの値で置き換わり、ユーザーごとにポリシーを作らずに済みます。使えるのは ${aws:username}、${aws:userid}、${aws:PrincipalTag/キー} など。${aws:username} はIAMユーザーにしか値が入りません。ロールセッションやフェデレーションユーザーでは空なので、Identity Center 環境でこれを使う選択肢は疑い、プリンシパルタグに読み替えてください。

Deny と NotAction と Condition の合わせ技

東京リージョン以外を禁止する（グローバルサービスは例外）
{
  "Effect": "Deny",
  "NotAction": ["iam:*", "organizations:*", "route53:*", "support:*"],
  "Resource": "*",
  "Condition": {
    "StringNotEquals": { "aws:RequestedRegion": "ap-northeast-1" }
  }
}

「グローバルサービス以外のすべてを、宛先が東京でないときに拒否する」。NotAction で例外を作り、Condition で発動条件を絞る2段構えです。例外が要るのは、IAMやRoute 53が内部的に us-east-1 として扱われ、素直に縛ると自分たちのIAM操作まで止まるからです。「リージョン制限のSCPでログインできなくなった」型の設問は、この抜けが原因です。

05

2種類のポリシー

ポリシーには、人・機械の側に貼るものと、リソースの側に貼るものがあります。この区別が評価ロジックの理解に直結します。

アイデンティティベースリソースベース
貼る先IAMユーザー / グループ / ロールS3バケット、SQSキュー、KMSキー、Lambda関数など
Principal 要素書かない（貼った相手が主語）必須（誰に許すかを明記）
答える問い「この人は何ができるか」「このリソースには誰が触れるか」
クロスアカウント単独では不可可能（相手アカウントを Principal に書ける）

リソースベースポリシーはすべてのサービスにあるわけではありません。S3バケット、SQSキュー、SNSトピック、KMSキー、Lambda、Secrets Manager、そしてIAMロールの信頼ポリシーが代表です。EC2インスタンスにはありません。「EC2にポリシーを貼って別アカウントから触らせる」という選択肢は成立しないので、見たら落とせます。

判断軸

「別アカウントからアクセスさせたい」という設問が出たら、リソースベースポリシー（またはクロスアカウントロール）が絡みます。アイデンティティベースだけでは、自分のアカウントの外には届きません。逆に「ロールを引き受けさせず、相手のIDのまま直接触らせたい」ならリソースベースポリシー一択です。

06

ABAC ―― タグで権限を決める

ここまでの書き方は、突き詰めると「このロールにはこのリソース」と列挙する RBAC（ロールベース）です。プロジェクトが増えるたびにポリシーが増えるのが弱点で、そこを解くのが ABAC（属性ベース、タグベース）。「組織が拡大してもポリシーを増やしたくない」という言い回しで出ます。

RBACABAC
許可の決め方ポリシーにリソースのARNを列挙するプリンシパルのタグとリソースのタグが一致するかで決める
プロジェクトが増えたらポリシーとロールを追加タグを付けるだけ。ポリシーは変えない
リソースが増えたらARN一覧を更新タグが付いていれば自動で対象になる
人の異動別のロールを割り当て直すプリンシパルのタグを書き換えるだけ
ポリシーの本数職務の数だけ増える原理的には1本で足りる
弱点管理対象が線形に増えるタグ付けの規律が崩れると権限も崩れる
ABAC の定型 ―― 自分と同じ project タグのインスタンスだけ起動・停止できる
{
  "Effect": "Allow",
  "Action": ["ec2:StartInstances", "ec2:StopInstances"],
  "Resource": "arn:aws:ec2:*:*:instance/*",
  "Condition": {
    "StringEquals": {
      "aws:ResourceTag/project": "${aws:PrincipalTag/project}"
    }
  }
}

Resource が全インスタンスで、絞り込みをARNではなく条件式が担当しているのがポイントです。プロジェクトが100個に増えても、このポリシーは変わりません。

ABACを成立させる3点セット

  1. プリンシパルにタグが付いている。IAMユーザーやロールに直接付けるか、フェデレーション時にセッションタグとして渡します。SAMLやOIDCのIdPから属性を持ち込めるので、社内ディレクトリの情報をそのまま権限に使えます。
  2. リソースにタグが付いている。ここが崩れると全部崩れるので、aws:RequestTag と aws:TagKeys でタグ無しではリソースを作れないようにする制御がセットで出てきます。
  3. タグを勝手に書き換えられない。自分のタグを変えられるなら他人のリソースにも手が届きます。ec2:CreateTags や iam:TagRole を絞るのが必須で、「ABACの弱点は何か」の答えはここです。
どんな設問でABACが答えになるか

手がかりは3つ。「チームやプロジェクトが継続的に増える」「ポリシーの数を増やさずに」「新しく作られたリソースにも自動で適用したい」。どれかがあれば、タグと条件キーを使っている選択肢を選びます。逆に職務も対象リソースも固定なら、ABACにする選択肢はオーバーエンジニアリングとして落とされます。

07

ロールと AssumeRole

ロールは、SAAで最も繰り返し問われる概念です。ロールは認証情報を持ちません。引き受けた瞬間に、期限付きの認証情報が発行されます。

ロールには2つのポリシーがある

ポリシー答える問い書く内容
信頼ポリシー
Trust policy		誰がこの帽子を被れるかPrincipal（EC2サービス、別アカウント、IdPなど）
許可ポリシー
Permissions policy		被ると何ができるかAction と Resource

この2つは役割がまったく違います。「アクセスできない」というトラブルの設問では、どちらが欠けているかを問われます。信頼ポリシーはロールに貼られたリソースベースポリシーそのもので、Principal は用途で決まります。EC2なら ec2.amazonaws.com、Lambdaなら lambda.amazonaws.com、別アカウントならそのARN、オンプレからなら rolesanywhere.amazonaws.com です。

クロスアカウントで両側に設定が要る理由

一時認証情報の性質

  • 返ってくるのは3点セット――アクセスキーID、シークレットアクセスキー、セッショントークン。3つ目があるのが一時認証情報の目印です。
  • 既定の有効期間は1時間、ロールの設定で最大12時間まで延長可能。ロールから別のロールへ連鎖（ロールチェーン）する場合は最大1時間に制限されます。
  • EC2ではインスタンスプロファイル経由で自動的に取得・更新されます。アプリ側でキーを書く必要はありません。
  • Lambdaでは実行ロールが同じ役割を果たします。
  • 引き受け時のロールセッション名はCloudTrailに記録されます。共有ロールでも誰が使ったか追えるのはこのおかげで、sts:SourceIdentity を要求すれば以降のセッションでも消せない識別子が残ります。
ExternalId

サードパーティのSaaSに自社アカウントへのアクセスを許すとき、信頼ポリシーに sts:ExternalId の条件を付けます。これは「混乱した代理人問題」――そのSaaSが他の顧客のIDを使って、意図しないアカウントに侵入されるのを防ぐ仕組みです。設問に「サードパーティ」「外部ベンダー」が出たらExternalId、と覚えてください。同じ問題をAWSサービス相手に防ぐキーは aws:SourceArn と aws:SourceAccount です。外部の会社ならExternalId、AWSサービスならSourceArnと対応させておくと迷いません。

iam:PassRole を忘れない

「EC2を起動してロールを付ける」「Lambda関数に実行ロールを指定する」には、ec2:RunInstances などのほかに iam:PassRole が要ります。ロールをサービスに渡す権限です。「EC2は起動できるのに、ロールを付けようとすると失敗する」型の設問はこれが答え。逆に iam:PassRole を Resource: "*" で与えると、開発者は管理者権限のロールをEC2に付けて権限昇格できます。渡せるロールをARNで限定するのが正しい書き方です。

08

STS の主要なAPI

一時認証情報を出す窓口が STS です。5つあり、ロールを引き受けるのかと呼ぶときにAWSの認証情報が要るかで使い分けが決まります。設問はAPI名そのものより「この状況ならどれか」の形で出ます。

API何のためAWS認証情報有効期間設問の手がかり
AssumeRole同一／別アカウントのIAMロールを引き受ける必要15分〜12時間、既定1時間。ロールチェーンは1時間クロスアカウント、EC2・Lambda、ExternalId
AssumeRoleWithWebIdentityOIDC・ソーシャルログインで認証済みの利用者にロールを渡す不要15分〜12時間、既定1時間モバイル／Webアプリ、Google・Facebook、Podに権限を渡す
AssumeRoleWithSAMLSAML 2.0 のIdPで認証した従業員にロールを渡す不要15分〜12時間。アサーションの SessionNotOnOrAfter が早ければそちらActive Directory、ADFS、既存の社内IdP
GetSessionTokenIAMユーザーの権限のまま、MFA付きの一時認証情報を得る必要15分〜36時間、既定12時間。ルートは最大1時間「MFAを条件にしたAPI操作」
GetFederationToken自前のIDブローカーがフェデレーションユーザー用の認証情報を発行必要15分〜36時間、既定12時間。ルートは最大1時間「独自の認証プロキシ」「コンソールのサインインURLを発行」

3つの見分け方

  • ロールになるか、ユーザーのままか。AssumeRole 系はロールの権限に切り替わり、GetSessionToken は呼び出したIAMユーザーの権限をそのまま引き継いでMFAの事実だけを足します。
  • 長期キーが要るか。AWS認証情報なしで呼べるのは AssumeRoleWithWebIdentity と AssumeRoleWithSAML だけ。「アプリにAWSの認証情報を埋め込まずに」ならこの2つかCognitoです。
  • 最長は12時間か36時間か。ロールを引き受ける系は12時間が上限です。「長時間バッチのために延ばしたい」ならロールの最大セッション時間を延ばすのが正解で、それ以上を求める選択肢は成立しません。
GetSessionToken の制限

得られた認証情報はMFAの情報を含めない限りIAMのAPIを呼べず、STSも AssumeRole と GetCallerIdentity 以外は呼べません。欠陥ではなく、MFAを強制するための設計です。

09

フェデレーションと IAM Identity Center

「IAMユーザーを作らずにAWSを使わせる」のがフェデレーションです。選択肢は多く見えますが、相手が社内の従業員か、アプリの一般利用者か、AWS外のワークロードかでほぼ決まります。

方式相手仕組み設問の手がかり
IAM Identity Center社内の従業員許可セットが各アカウントにIAMロールとして展開される「複数アカウント」「従業員」「一元管理」
SAML 2.0 フェデレーション社内の従業員IAMにSAMLプロバイダを登録し AssumeRoleWithSAML「既存のSAML IdPをそのまま」「単一アカウント」
OIDC / Web IDアプリ利用者、AWS外のワークロードIAMにOIDCプロバイダを登録し AssumeRoleWithWebIdentity「Googleでログイン」「CI/CDから鍵なしでデプロイ」
Cognito ユーザープールアプリの一般利用者サインアップ／サインインを提供する認証基盤「アプリ独自のユーザー登録」
Cognito IDプールアプリの一般利用者認証済み利用者にAWSの一時認証情報を配る「利用者が直接S3にアップロード」
IAM Roles AnywhereオンプレミスのサーバーX.509証明書で認証して一時認証情報を得る「データセンターのサーバーからAWS API」

IAM Identity Center ―― 従業員アクセスの本命

旧称 AWS SSO。実態は複数アカウントの権限を一箇所で配るサービスです。Organizations の管理アカウントで有効化する組織インスタンスが本来の使い方で、試験で問われるのもこちらです。

  • アイデンティティソースは3択。Identity Center 自身のディレクトリ、Active Directory、外部IdP（SAML 2.0 でのサインインとSCIMでのユーザー同期）。「既存の社内IDでAWSにログインさせたい」はこのどれかで、IAMユーザーを人数分作る選択肢は常に不正解です。
  • 許可セットが中核。ポリシーの束に名前を付けたもので、「ユーザーまたはグループ × アカウント × 許可セット」で割り当てます。割り当てると対象アカウントにIAMロールが自動でプロビジョニングされます。実体はロールなので、ログ上もそう見えます。
  • アクセスポータルから入る。利用者は専用URLでサインインし、使えるアカウントと許可セットを選びます。CLIは aws configure sso で一時認証情報が自動更新され、アクセスキーをローカルに置かない運用が完成します。
Identity Center と Organizations の関係

組織インスタンスは AWS Organizations が前提です。また配られるのはロールへの割り当てなので、SCPの上限はそのまま効きます。「Identity Center で管理者権限を割り当てたのに操作できない」ならSCPを疑います。

IAM Roles Anywhere ―― オンプレミスから鍵なしで

アクセスキーを配るしかなかった場面を、社内に既にある証明書の仕組みで置き換えます。構成要素は3つです。

  • トラストアンカー。信頼するCAの登録。AWS Private CA でも、自社の既存CAの証明書を持ち込む形でも構いません。
  • プロファイル。引き受けられるロールの集合と、任意のセッションポリシー。ここでさらに権限を絞れます。
  • ロールの信頼ポリシー。rolesanywhere.amazonaws.com を信頼し、aws:SourceArn でトラストアンカーを限定します。この条件が無いと、同じアカウントのどのトラストアンカーの証明書でもロールを引き受けられてしまいます。
「どこから呼ぶか」の対応表

EC2ならインスタンスプロファイル、Lambdaなら実行ロール、ECSならタスクロール、EKSのPodならOIDC経由のサービスアカウント連携、オンプレならIAM Roles Anywhere。この5つを言えれば「認証情報を安全に渡す方法はどれか」型は考えずに解けます。どの場合も、アクセスキーを配る選択肢が正解になることはありません。

10

評価ロジック ―― Allow と Deny の勝敗

ここが本日の山場です。AWSはリクエストごとに、関係するすべてのポリシーを集めて次の順で判定します。

01どこかに明示的な Deny があるかアイデンティティ、リソース、SCP、権限境界、セッション――どれか一つでもあり → 拒否
02SCP で許可されているか組織のメンバーアカウントの場合のみ。管理アカウントには適用されないいいえ → 拒否
03リソースベースポリシーで許可されているか同一アカウント内なら、これだけで許可が成立する（多くのサービスで）はい → 許可
04権限境界の範囲内か設定されている場合のみいいえ → 拒否
05アイデンティティベースポリシーで許可されているかセッションポリシーがあればその範囲内でもあることいいえ → 拒否（暗黙の拒否）
すべて通過 → 許可

3つの原則に圧縮する

  1. 明示的な Deny は絶対。他に何個 Allow があっても覆りません。AdministratorAccess を持っていても、SCPで Deny されていれば実行できません。
  2. 何も書かれていなければ拒否。暗黙の拒否が既定値です。「許可されていないから拒否」と「Denyされたから拒否」は、結果は同じでも設問での意味が違います。
  3. Allow は足し算、制約は掛け算。同一アカウント内のアイデンティティとリソースは和集合（どちらかが許せば通る）。権限境界・SCP・セッションポリシーは積集合（すべてが許してはじめて通る）。
組み合わせ論理意味
アイデンティティ + リソース（同一アカウント）和集合 ORどちらか一方が許可すれば通る
アイデンティティ + リソース（別アカウント）積集合 AND両方が許可して初めて通る
アイデンティティ + 権限境界積集合 AND境界は権限を与えない。上限を決めるだけ
アイデンティティ + SCP積集合 ANDSCPも権限を与えない。組織の天井
ロールの許可ポリシー + セッションポリシー積集合 ANDセッションポリシーは権限を増やせない

クロスアカウントは「2回」評価される

アカウント境界をまたぐとき、AWSは評価を2回行います。呼び出し元で「このIDは外に出てよいか」、リソース側で「この相手を入れてよいか」。両方が Allow のときだけ通り、どちらかに明示的な Deny があれば拒否です。

これが「同一アカウントなら和集合、別アカウントなら積集合」の正体です。境界をまたぐと呼び出し元のアイデンティティベースポリシーが必ず要ります。相手のバケットポリシーに自分のロールARNが書いてあっても、自分の側で s3:GetObject が許可されていなければ通りません。「バケットポリシーは正しいのにアクセスできない」なら、疑うのは呼び出し元です。ロールを引き受けたあとはそのロールが属するアカウントの中の話に変わるので、「いま自分はどちらのアカウントのプリンシパルか」を常に確認してください。

セッションポリシーの位置づけ

AssumeRole や GetFederationToken を呼ぶときに渡す、その場限りのポリシーです。ロールの許可ポリシーとの積集合になり、書いても権限は増えません。役割は「広めのロールを共通で用意し、呼び出し側が用途ごとに狭める」ことで、1つのロールを複数のテナントで使い分ける構成の答えになります。Roles Anywhere のプロファイルも効き方は同じ「上から被せる上限」です。GetFederationToken だけは特殊で、セッションポリシーを渡さなければ、そのフェデレーションユーザーにはほぼ何の権限も残りません。

「暗黙の拒否」と「明示的な拒否」の書き分け

結果はどちらも「アクセス拒否」ですが、設問での意味と正解の対処法が違います。

暗黙の拒否明示的な拒否
原因どこにも Allow が書かれていないどこかに "Effect": "Deny" がある
設問での書かれ方「権限が付与されていない」「アタッチし忘れた」「新しく作ったロールで」「管理者権限があるのに」「ポリシーを追加しても解決しない」「組織のポリシーで」
正解の方向必要な Allow を足すAllow を足しても無駄。Deny か上限を直す
出どころポリシーの書き漏れ、ARNの指定ミスSCP、RCP、バケットポリシーの Deny、条件付き Deny

もうひとつ、どちらでもない第3のパターンが権限境界やSCPの範囲外です。Deny が1行も書かれていないのに、上限の外という理由で拒否されます。設問では「上限を超えている」「境界の外」という言い方になります。「Allow を足して解決するか」で3種類を切り分けると選択肢が一気に絞れます。

最頻出の引っかけ

「ユーザーに AdministratorAccess が付いているのに操作できない。原因は？」――答えはSCPか権限境界です。権限を与えるポリシーをいくら足しても、上限を超えることはできません。この形の設問は必ず出ます。「より強いポリシーをアタッチする」「インラインで上書きする」という選択肢は全部不正解で、ポリシーに優先度や上書きという概念はありません。

権限境界 と SCP の違い

どちらも「上限を決める」仕組みで、混同されがちです。適用先が決定的に違います。

権限境界
Permissions boundary		SCP
Service Control Policy
適用先個々のIAMユーザー／ロールAWSアカウント（OU単位・組織単位）
設定場所IAMAWS Organizations
典型的な目的開発者にIAM操作を任せつつ、自分より強い権限を作らせない組織全体のガードレール（例：特定リージョン以外を全面禁止）
管理アカウント概念として無関係適用されない
権限を付与するかしない（上限のみ）しない（上限のみ）

SCP で押さえる3点

  • 継承は積み重なる。ルート・OU・アカウントの各階層のSCPをすべて満たす必要があり、上位で許可されていないものを下位で許可し直すことはできません。「子OUで例外を作る」選択肢はここで落ちます。
  • 既定で FullAWSAccess が付く。主流は拒否リスト戦略――これを残したまま禁止したいものを Deny で足す形です。FullAWSAccess を外して許可するサービスだけ列挙する許可リスト戦略は厳格ですが管理が重くなります。「最小の運用負荷で特定操作だけ禁止」なら拒否リストです。
  • 効かない相手がいる。管理アカウント内のプリンシパルとサービスリンクロールは対象外です。「全アカウントで強制したのに管理アカウントだけ通る」は仕様どおりで、対策は管理アカウントで本番を動かさないことです。
RCP ―― リソース側のガードレール

SCPが「自組織のプリンシパルが何をできるか」の上限であるのに対し、RCP（リソースコントロールポリシー）は「自組織のリソースに誰が触れるか」の上限です。全アカウントのS3に対し aws:PrincipalOrgID が自組織でないアクセスを一律 Deny する使い方が代表例。SCPと同じく権限は与えず、管理アカウントとサービスリンクロールは対象外です。「組織外への意図しない共有を、バケットポリシーを1つずつ直さずに止めたい」ならRCPです。

設問での見分け方

「開発者に権限委譲したい / 権限昇格を防ぎたい」→ 権限境界。「組織全体で禁止したい」→ SCP。「組織外からのアクセスを止めたい」→ RCP。主語が個人かアカウントか外部かで切り分けられます。

アクセスの可視化と点検

権限は設計した瞬間から劣化します。人が辞め、プロジェクトが終わり、使われない権限だけが残る。「棚卸しして最小権限に近づけたい」という要件は繰り返し出ます。道具は何を見たいのかで選びます。

道具答える問いデータの出どころ設問の手がかり
Access Analyzer
（外部アクセス）		組織やアカウントの外に公開されていないかポリシーの静的解析「外部に共有されているリソースを検出したい」
Access Analyzer
（未使用アクセス）		使われていないロール・キー・権限はどれかアクセス履歴の分析「未使用のロールや権限を継続的に見つけたい」
Access Analyzer
（検証・生成）		このポリシーは妥当か／実績から最小権限を作れないかポリシー文書と CloudTrail「使った操作からポリシーを作りたい」
Access AdvisorこのIDは、どのサービスに最後にいつアクセスしたか管理イベントの記録「使っていないサービスの許可を外したい」
認証情報レポート全ユーザーの認証情報の状態IAMが生成するCSV「MFA未設定のユーザーを一覧」「古いアクセスキーの洗い出し」
CloudTrailいつ誰が何のAPIを呼んだかAPIイベントのログ「証跡として残したい」「インシデント調査」

3つの違いを一言で

  • Access Analyzer は「境界の外」を見る。アカウントまたは組織を信頼ゾーンとして指定し、その外からアクセスできるリソース（S3、IAMロール、KMSキー、Lambda、SQS、Secrets Manager、SNSなど）を検出します。ログではなくポリシーを解析して到達可能性を示すので、まだ誰も触っていない穴も見つかります。ここがCloudTrailとの決定的な差です。
  • Access Advisor は「最後にいつ使ったか」を見る。ユーザー・ロール・グループ・ポリシーごとに、サービス単位の最終アクセス日時が出ます。「1年使われていない権限」を根拠つきで削れます。管理アカウントからはOUやアカウント単位でも見られ、SCPを絞る材料になります。
  • 認証情報レポートは「アカウント全体の健康診断」。全IAMユーザーのパスワード有無と最終使用日、MFAの有効化、アクセスキー2本ぶんの状態・最終ローテーション日・最終使用日がCSVで出ます。生成は4時間に1回まで。監査や報告の設問で出ます。
「検出」と「予防」を混同しない

この節の道具はすべて発見的統制で、それ自体は何も止めません。「防ぎたい」「させないようにしたい」とあれば、答えはSCP・RCP・権限境界・条件付きDenyという予防的統制の側。「検出したい」「可視化したい」ならこの節の道具です。動詞を見て側を選ぶのが確実です。

試験での判断軸

SAAは知識ではなく選択を問う試験です。設問文にこの手がかりが出たら、この答えに寄せる――という対応表を頭に入れてください。

アクセスキーをコードや設定ファイルに保存→常に不正解。ロールを使う
EC2上のアプリから他のAWSサービスへ→インスタンスプロファイル（ロール）
Lambdaから他のAWSサービスへ→実行ロール
オンプレミスのサーバーからAWS API→IAM Roles Anywhere（X.509証明書）
社内のIDで複数アカウントにログインさせたい→IAM Identity Center（許可セット）
既存のSAML IdPを単一アカウントでそのまま使う→SAMLプロバイダ + AssumeRoleWithSAML
モバイル／Webアプリの一般利用者を認証→Cognito ユーザープール
その利用者にAWSリソースを直接触らせる→Cognito IDプール
別アカウントのリソースにアクセス→クロスアカウントロール（両側に設定）
外部ベンダー・SaaSにアクセスを許す→ロール + ExternalId
プロジェクトが増えてもポリシーを増やしたくない→ABAC（タグ + aws:PrincipalTag）
開発者の権限昇格を防ぎたい→権限境界 + iam:PassRole の限定
組織のすべてのアカウントで操作を禁止→SCP（拒否リスト戦略）
組織外のプリンシパルからのアクセスを一括遮断→RCP + aws:PrincipalOrgID
HTTPS以外／特定エンドポイント以外を拒否→Deny + aws:SecureTransport / aws:SourceVpce
外部に公開されているリソースを洗い出す→IAM Access Analyzer（外部アクセス）
使われていない権限・古いキーを棚卸しする→Access Advisor / 認証情報レポート
誰が何をしたか追跡したい→CloudTrail
Cognito の2つを混同しない

ユーザープールはサインアップ・サインインを提供する認証基盤（誰であるかを確かめる）。IDプール（フェデレーテッドアイデンティティ）は、認証済みの利用者にAWSの一時認証情報を配る仕組み（何ができるかを与える）。設問で「アプリの利用者が直接S3にアップロードする」と来たらIDプールです。

迷ったときの3原則

2つに絞れて決めきれないときは、この順で見ます。①長期の認証情報を作らない方。②権限の範囲が狭い方。③手作業が少ない方。逆に、要件に書かれていない機能を足している選択肢は、技術的に正しくてもオーバーエンジニアリングとして外れます。

確認問題

先に自分で答えを決めてから開いてください。当てずっぽうで開くと、この5分が無駄になります。

Q1EC2インスタンス上で動くアプリケーションが、S3バケットにログをアップロードする必要がある。最も安全な実装はどれか。
  • A. IAMユーザーを作成し、アクセスキーをアプリの設定ファイルに保存する
  • B. IAMロールを作成し、インスタンスプロファイルとしてEC2にアタッチする
  • C. ルートユーザーのアクセスキーを環境変数に設定する
  • D. S3バケットをパブリック書き込み可能にする

正解: B

ロールをアタッチすると、EC2はインスタンスメタデータ経由で一時認証情報を自動取得し、自動で更新します。キーの保存もローテーションの運用も不要になります。

判断軸: 「アクセスキーを保存する」選択肢は、どれだけもっともらしく書かれていても選ばない。これはSAA全体を通じて有効な原則です。なおECSならタスクロール、Lambdaなら実行ロール、オンプレなら IAM Roles Anywhere に置き換わるだけで、構造は同じです。この4つを一つの型として扱えれば、この系統は読む前に答えが決まります。

Q2アカウントAのユーザーが、アカウントBのS3バケットを読む必要がある。クロスアカウントロールを使う場合、必要な設定はどれか。
  • A. アカウントB側でロールを作り、信頼ポリシーにアカウントAを記載するだけでよい
  • B. アカウントA側のユーザーに sts:AssumeRole を許可するだけでよい
  • C. 両方が必要
  • D. アカウントBのバケットをパブリックにする

正解: C

引き受けられる側（B）の信頼ポリシーに「Aを信頼する」と書き、かつ引き受ける側（A）のユーザーに sts:AssumeRole を許可する。権限の受け渡しは常に双方向の合意です。境界をまたぐリクエストは両側で評価され、どちらも Allow のときだけ通ります。

判断軸: クロスアカウントの設問で「片側だけ」の選択肢は不正解。図で言えば①と②の両方です。ロールを引き受けたあとはアカウントBの中の話になる点も押さえてください。ロールの許可ポリシーでバケットを読めるなら、バケットポリシーに改めてアカウントAを書く必要はありません。

Q3組織のSCPでS3への全アクションがDenyされている。あるメンバーアカウントのユーザーには AdministratorAccess がアタッチされている。このユーザーはS3バケットを作成できるか。
  • A. できる。AdministratorAccess が優先される
  • B. できない
  • C. バケットの所有者であればできる
  • D. MFAを使えばできる

正解: B

明示的なDenyはすべてのAllowに優先します。加えてSCPは「権限の上限」であり、アイデンティティベースポリシーとの積集合が実効権限になります。上限の外には出られません。ポリシーに優先度という概念はないので、Aの理屈は成立しません。

判断軸: 「管理者権限があるのにできない」型の設問は、SCPか権限境界を疑う。切り分けの言葉は「Allow を足して解決するか」です。解決しないなら明示的なDenyか上限の問題で、対処はポリシー追加ではなくSCPや境界の見直しになります。なお管理アカウントならSCPが適用されないため答えが変わります。そこまで読めれば上出来です。

Q4開発チームに自分たちでIAMロールを作らせたいが、作ったロールに管理者権限を持たせることは防ぎたい。適切な仕組みはどれか。
  • A. SCPで開発者アカウントのIAM操作をすべて禁止する
  • B. 開発者のIAMユーザーに権限境界を設定し、作成するロールにも同じ境界の付与を必須にする
  • C. 開発者にはロールを作らせず、すべて管理者が代行する
  • D. CloudTrailで監視し、違反があれば事後に削除する

正解: B

権限境界はこの「権限委譲したいが上限は守らせたい」ために存在します。条件キー iam:PermissionsBoundary で、境界を付けたロールしか作れないよう強制するのが定石です。

判断軸: A と C は要件（自分たちで作らせたい）を満たしていません。D は事後対応で、予防になっていません。「予防的統制か、発見的統制か」はセキュリティ設問の頻出の切り口です。あわせて権限昇格を塞ぐにはもう一枚要ると覚えてください。境界付きのロールしか作れなくしても、iam:PassRole が Resource: "*" なら既存の強いロールをEC2に付けて迂回できます。答えは権限境界 + 渡せるロールのARN限定のセットです。

Q5外部の監視SaaSベンダーに、自社AWSアカウントの読み取り権限を与えることになった。信頼ポリシーに加えるべき条件はどれか。
  • A. aws:SourceIp でベンダーのIPを限定する
  • B. sts:ExternalId に自社固有の値を設定する
  • C. aws:MultiFactorAuthPresent を true にする
  • D. 条件は不要。信頼ポリシーにベンダーのアカウントIDを書けば十分

正解: B

ExternalIdは「混乱した代理人問題」への対策です。ベンダーは多数の顧客のロールを引き受けられる立場にあるため、顧客ごとの固有値を要求して他社のIDを使ったアクセスを防ぎます。Dが不十分なのは、アカウントIDだけではそのベンダーの他の顧客担当者でも引き受けられるためです。

判断軸: Cが不正解なのは、ベンダーは自動化されたサービスでありMFAを提示できないため。設問の主体が人か機械かで、使える対策が変わります。Aは送信元IPが変動しうるうえ、根本（誰の依頼で呼んでいるか）を解決しません。相手がAWSサービスなら aws:SourceArn、という対になる型も一緒に覚えてください。
