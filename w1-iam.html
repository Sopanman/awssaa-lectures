01

舞台設定

測定データが quality-raw という S3 バケットに毎日溜まっています。あなたはこの基盤の権限設計を担当しています。これから6つの依頼が来ます。

各場面はこの順で進みます。

  1. 依頼 ―― 現場の言葉で1行
  2. 素朴な案 ―― たいてい最初に思いつくもの。動きはする
  3. 壊れ方 ―― それが実際に何を引き起こすか
  4. 正解の設計 と、その実物
  5. 試験ではこう出る
この講義の狙い

IAM の全機能は扱いません。「この依頼が来たらこう設計する」という判断を6つ作ることが目的です。細かい仕様は、模試で間違えたときに drills/mistakes.md 経由で拾ってください。

02

場面1 ―― 「解析バッチを EC2 で回したい。S3 を読ませて」

素朴な案

IAM ユーザーを1つ作り、アクセスキーを発行して、EC2 の中の設定ファイルに書く。動きます。5分で終わります。

その鍵がどこへ行くか

設定ファイルは構成管理のために社内 Git に入ります。AMI を取れば鍵ごと複製されます。検証用にと誰かがノートPCにコピーします。半年後、その鍵が何箇所にあるか言える人はいません。

外に出たときに起きること

Palo Alto Networks の Unit 42 が追跡した EleKtra-Leak というキャンペーンの実測値があります。公開 GitHub に出たアクセスキーに対し、攻撃者の偵察開始までが数分。そこから約7分で400回以上の API 呼び出しが走り、使える全リージョンに c5a.24xlarge（96 vCPU）級のインスタンスが立ってマイニングが始まりました。5週間で474台が確認されています。

96 vCPU のインスタンスは1台1日でも数十ドル規模。それが複数リージョンに何十台です。気づくのは請求書であって、監視ではありません。

しかも AWS が自動で隔離ポリシーを当てたのは検知直後でしたが、上の調査では隔離適用の4分後に攻撃者が動き出しています。自動防御は間に合わないことがある。

「S3 読み取りだけの鍵では?」 長期の IAM ユーザーは権限が溜まります。「一時的に」足した権限は消えません。3年前に作ったユーザーが今何を持っているか、作った本人も覚えていない。それに読み取りだけでも、測定データそのものは持ち出せます。

「社内 Git なら安全では?」 AWS が監視して自動隔離しているのは公開リポジトリだけです。社内に置いた鍵には自動の安全網がありません。

正解 ―― 鍵を置かない

EC2 に IAM ロールをアタッチします（この付け方をインスタンスプロファイルと呼びます）。すると、インスタンスの中からこのアドレスが読めるようになります。

EC2 の中から
$ TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" \
    -H "X-aws-ec2-metadata-token-ttl-seconds: 60")
$ curl -H "X-aws-ec2-metadata-token: $TOKEN" \
    http://169.254.169.254/latest/meta-data/iam/security-credentials/analysis-role

{
  "AccessKeyId": "ASIA...",
  "SecretAccessKey": "...",
  "Token": "IQoJb3JpZ2lu...",          // これがある = 一時認証情報
  "Expiration": "2026-09-26T18:22:11Z"  // 数時間で失効する
}

SDK も CLI も、この場所を自動で見に行きます。アプリのコードには何も書きません。期限前に自動更新されます。運ばれる鍵が存在しないので、さっきの事故は起こりようがない。

戻り値に Token（セッショントークン）が入っているのが一時認証情報の目印です。アクセスキーID が ASIA で始まるのも同じ印。長期のキーは AKIA です。

「ロールを被る」とは何をすることか ―― AssumeRole

ここで出てきた「ロール」の仕組みを、言葉から押さえます。assume は「仮定する」ではなく「（役割を）身にまとう」のほうの意味です。帽子＝ロール、被ること＝AssumeRole。

被ると、AWS の STS というサービスが別人格の、期限付きの認証情報を発行します。手で呼ぶとこうなります。

人が手で AssumeRole する場合
$ aws sts assume-role \
    --role-arn arn:aws:iam::222222222222:role/quality-report-reader \
    --role-session-name ohata-20261102

{
  "Credentials": { "AccessKeyId": "ASIA...", "SessionToken": "IQoJ...", "Expiration": "..." },
  "AssumedRoleUser": {
    "Arn": "arn:aws:sts::222222222222:assumed-role/quality-report-reader/ohata-20261102"
  }                                    // ← もう「自分」ではなく、このロールとして扱われる
}
一番の勘違いポイント

ロールを被ると、元の自分の権限は使えません。足し算ではなく置き換えです。返ってきた認証情報を使っている間、あなたはそのロールそのものになります。

たとえるなら、守衛所で「試験ライン作業者」の入館証を借りるようなものです。借りている間は試験ライン作業者として扱われ、事務棟のIDカードはその間使いません。2時間で失効し、台帳には誰がいつ借りたかが残ります。最後の点が --role-session-name で、ここに入れた名前が CloudTrail に残るので、同じロールを10人が使っていても誰の操作か追跡できます。

そして大事なのは、この講義の場面1・2・3は、すべて同じ1つの仕組みだということです。違うのは「誰が被るか」だけです。

場面誰が AssumeRole するか信頼ポリシーに書く相手
場面1 EC2 → S3EC2 サービスが自動で（インスタンスプロファイル）ec2.amazonaws.com
Lambda → S3Lambda サービスが自動で（実行ロール）lambda.amazonaws.com
場面2 別アカウントから相手のユーザーが明示的に相手のアカウント
場面3 外部ベンダーベンダーのシステムが（+ ExternalId）ベンダーのアカウント

ただしロールも万能ではない

2019年の Capital One の事件がこれです。EC2 上の WAF アプリに SSRF の脆弱性があり、外部から 169.254.169.254 を叩かせて、そのインスタンスのロールの一時認証情報を抜かれました。攻撃者はその権限で S3 のバケットを列挙してコピー。約1億人分の申込情報が流出し、OCC から8,000万ドルの制裁金が科されています。

この教訓から既定になったのが IMDSv2 です。上のコマンドで最初に PUT でトークンを取っているのがそれ。SSRF は多くの場合 GET しか送れないので、トークン取得の PUT ができず、認証情報まで到達できません。

試験ではこう出る

「EC2 上のアプリが S3 にアクセスする。最も安全な方法は?」→ アクセスキーを保存する選択肢は、どれだけもっともらしく書かれていても選ばない。これは SAA 全体を通じて有効な原則です。

「EC2 のインスタンスメタデータを保護したい」→ IMDSv2 を必須にする。

03

場面2 ―― 「解析結果を、別部署のアカウントから直接見たい」

解析結果は quality-report バケットに置いています。別部署は別の AWS アカウントを持っていて、そこから読みたいと言ってきました。

素朴な案

バケットを公開設定にする。あるいは、こちらで IAM ユーザーを作って相手に渡す。

壊れ方

公開設定は論外です。S3 の公開バケットからの情報漏洩は、クラウドのインシデントで最も件数の多い型のひとつで、いまは Block Public Access が既定で有効になっているほどです。

IAM ユーザーを渡す案は、場面1と同じ問題に戻ります。長期の鍵を組織の外に出すことになる。さらに悪いことに、その人が異動しても退職しても、鍵は生き続けます。相手部署の誰が今その鍵を持っているか、こちらからは見えません。

正解 ―― 相手に「一時的に被る帽子」を貸す

こちらのアカウントにロールを作り、相手のアカウントがそれを引き受けられるようにします。ロールには2つのポリシーがあり、役割が完全に違います。

ポリシー答える問い書く場所
信頼ポリシー誰がこの帽子を被れるかロールの「信頼関係」。Principal を書く
許可ポリシー被ると何ができるかロールにアタッチするポリシー。Action と Resource を書く
こちら側のロールの信頼ポリシー ―― 「アカウント 2222… を信頼する」
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::222222222222:root" },
    "Action": "sts:AssumeRole"
  }]
}

そして相手側でも、そのユーザーに sts:AssumeRole の許可が要ります。権限の受け渡しは常に双方向の合意です。片側だけでは成立しません。

どちら側設定するもの意味
こちら（貸す側）ロールを作り、信頼ポリシーに相手のアカウントを書く。許可ポリシーで読めるバケットを決める「この帽子は、あの部署なら被ってよい」
相手（被る側）被る人に sts:AssumeRole の許可を与える「この人は、あの帽子を被りに行ってよい」

「AssumeRole を設定する」とは言いません。設定するのはロールと2種類のポリシーで、AssumeRole はそれを使って帽子を被る行為です。

この形なら、相手部署の担当者が替わってもこちらは何もしません。相手のアカウント側で人を入れ替えるだけです。渡した鍵を回収する作業も発生しません。

試験ではこう出る

「別アカウントからアクセスさせたい」→ クロスアカウントロール。「アクセスできない。原因は?」→ 信頼ポリシーか、呼び出し側の sts:AssumeRole 許可のどちらかが欠けている。

04

場面3 ―― 「外部ベンダーの分析SaaSに、読み取りだけ許したい」

ベンダーから「このロールを作って、信頼ポリシーに弊社のアカウントIDを書いてください」と手順書が届きました。場面2と同じやり方に見えます。

場面2との決定的な違い

そのベンダーは、あなたの会社以外にも何百社の顧客を持っています。そして各社が同じように「ベンダーのアカウントを信頼する」ロールを作っています。

ベンダーの管理画面には、たいていこういう入力欄があります。

監視したい AWS アカウントのロール ARN を入力してください
[ arn:aws:iam::________:role/________ ]

ここに、まったく無関係な第三者があなたの会社のロール ARNを入れて登録したら、次のことが起きます。

  1. 第三者がベンダーに登録する（入力したのはあなたの ARN）
  2. ベンダーのシステムが、その ARN に AssumeRole する
  3. あなたの信頼ポリシーは「ベンダーのアカウントなら OK」なので通る
  4. ベンダーは取得したデータを、第三者の画面に表示する

第三者は一度もあなたのアカウントを攻撃していません。ベンダーから見れば、いつもどおりの正常な処理です。そして ARN は秘密ではありません。アカウントIDもロール名も、推測できたりどこかから漏れたりします。「ARN を知っている＝権利がある」という前提が、そもそもの誤りです。

これを混乱した代理人問題と呼びます。悪いのはベンダーでも第三者でもなく、「ベンダーのアカウントなら誰の依頼でも信じる」と書いたあなたの信頼ポリシーです。

正解 ―― 合言葉を1つ足す

信頼ポリシーに sts:ExternalId の条件を付けます。ベンダーが発行する、あなた専用の値です。

信頼ポリシーに条件を追加
{
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::<ベンダーのアカウント>:root" },
  "Action": "sts:AssumeRole",
  "Condition": {
    "StringEquals": { "sts:ExternalId": "honda-dq-7f3a91" }
  }
}

第三者はこの値を知らないので、ARN だけ入れても引き受けに失敗します。

ExternalId は鍵（認証情報）ではない

「秘密鍵のようなもの」と考えたくなりますが、違います。ベンダーが AWS に入るときの認証は、あくまでベンダー自身の AWS 認証情報と、あなたの信頼ポリシーで行われます。ExternalId はその上で、「この依頼はどの顧客のためのものか」を取り違えないための、顧客ごとの識別子です。

マンションの管理会社が何百戸ぶんの合鍵を持っているとします。部屋番号を言うだけで開けてもらえるなら、誰でも他人の部屋に入れる。ExternalId は合鍵そのものではなく、部屋ごとの合言葉のほうです。パスワードほど厳重に隠すものではありませんが、顧客ごとに一意で、他人が推測できない値である必要があります。だから発行はベンダー側が行うのが原則です。

誰が何をする
ベンダー顧客ごとに一意な ExternalId を発行する（管理画面に表示される）
あなた信頼ポリシーの Condition にその値を書く
ベンダーAssumeRole するとき、その値を添える

まともなベンダーの手順書には、最初からこの値が書かれています。書かれていなければ、そのベンダーの設計を疑ってよい。これは実務でもそのまま使える判断です。

試験ではこう出る

設問に「サードパーティ」「外部ベンダー」「SaaS」が出たら ExternalId。なお MFA を条件にする選択肢は不正解です。相手は自動化されたシステムなので、MFA を提示できません。設問の主体が人か機械かで、使える対策が変わります。

05

場面4 ―― 「開発メンバーにも、自分でロールを作らせたい」

解析基盤の開発が増えてきました。ロール作成をいちいちあなたに依頼するのは、双方にとって無駄です。開発メンバーに IAM の操作権限を渡したい。

素朴な案

IAMFullAccess を付ける。これで自分でロールを作れます。

壊れ方 ―― 実際の手順

IAM を自由に触れるということは、自分より強い権限を作れるということです。具体的にはこうなります。

  1. AdministratorAccess を付けた新しいロールを作る
  2. そのロールを自分が引き受けられるよう、信頼ポリシーに自分を書く
  3. 引き受ける

3手で管理者です。悪意がなくても起きます。「検証用にとりあえず強い権限で」が定着し、誰も消さない。IAM 操作を渡すことは、実質的に管理者権限を渡すことと同じだと理解してください。

正解 ―― 上限を先に決めておく

権限境界（Permissions boundary）は、その主体が持てる権限の天井です。境界は権限を与えません。アタッチされたポリシーとの積集合が実効権限になります。

01開発メンバーに権限境界を設定するS3 と Lambda の操作まで、と天井を決める天井が決まる
02「境界を付けたロールしか作れない」条件を課す条件キー iam:PermissionsBoundary を使う抜け道を塞ぐ
03AdministratorAccess を付けたロールを作ろうとする境界の外 → 拒否

02 が抜けていると、開発メンバーは「境界のないロール」を作ってそれを引き受けられてしまいます。自分に境界を付けるだけでは足りません。

よく混同される: 権限境界 と SCP

どちらも「上限を決める」仕組みですが、適用先が違います。権限境界は個々のユーザー/ロールに、SCP はアカウントに。設問の主語が「開発者」なら境界、「組織」「すべてのアカウント」なら SCP です。

06

場面5 ―― 「使っていないリージョンを全社で禁止したい」

場面1のマイニング事故を受けて、セキュリティ部門から依頼が来ました。東京とバージニア以外のリージョンは、どのアカウントでも使えないようにしたい。

素朴な案

各アカウントのユーザーに、リージョン制限の Deny ポリシーを付けて回る。

壊れ方

アカウントが増えるたびに付け忘れます。各アカウントの管理者は、自分でそのポリシーを外せます。そして新しく作られたユーザーには最初から付いていません。「全社で禁止」が成立していない。

正解 ―― アカウントの外側から天井を被せる

SCP（Service Control Policy）は AWS Organizations で設定し、アカウント単位で効きます。アカウントの中の管理者にも外せません。

許可リージョン以外を禁止する SCP
{
  "Effect": "Deny",
  "NotAction": ["iam:*", "organizations:*", "cloudfront:*"],
  "Resource": "*",
  "Condition": {
    "StringNotEquals": {
      "aws:RequestedRegion": ["ap-northeast-1", "us-east-1"]
    }
  }
}

NotAction でグローバルサービスを除外しているのがポイントです。IAM や CloudFront はリージョンを持たないため、除外しないと自分の首を絞めます。

SCP も権限を与えません。天井を下げるだけです。だから次の状況が起きます。

最頻出の引っかけ

「ユーザーに AdministratorAccess が付いているのに操作できない。原因は?」
→ SCP か権限境界。権限を与えるポリシーをいくら足しても、上限は越えられません。

ただし SCP は管理アカウントには適用されません。設問が管理アカウントの話なら答えが変わります。

07

場面6 ―― 「監査に『誰が何を触れるか』を説明して」

ここまでで、アイデンティティ側のポリシー、リソース側のポリシー、権限境界、SCP が同時に存在する状態になりました。「結局このユーザーは何ができるのか」を、順序立てて答える必要があります。

AWS が判定する順序

01どこかに明示的な Deny があるかどのポリシーでも、1つでもあれば即終了あり → 拒否
02SCP が許可しているか組織のメンバーアカウントのみ。管理アカウントは対象外いいえ → 拒否
03リソースベースポリシーが許可しているか同一アカウント内なら、これだけで成立するはい → 許可
04権限境界の中か設定されている場合のみいいえ → 拒否
05アイデンティティベースポリシーが許可しているかいいえ → 拒否（暗黙の拒否）
すべて通過 → 許可

3行に圧縮できます。

  1. 明示的な Deny は絶対。他に何個 Allow があっても覆らない
  2. 何も書かれていなければ拒否。暗黙の拒否が既定
  3. Allow は足し算、制約は掛け算。同一アカウント内のアイデンティティとリソースは和集合。権限境界・SCP・セッションポリシーは積集合

手で追わずに済ませる道具

道具答えてくれること
IAM Access Analyzer外部（別アカウント・インターネット）からアクセスできるリソースはどれか。使われていない権限はどれか
Access Advisorこのユーザー/ロールが、各サービスに最後にアクセスしたのはいつか（権限の棚卸しに使う）
CloudTrail誰が、いつ、何の API を呼んだか（過去の実績）
試験ではこう出る

「意図せず外部公開されているリソースを見つけたい」→ Access Analyzer。「使われていない過剰な権限を削りたい」→ Access Advisor。「誰がその操作をしたか調べたい」→ CloudTrail。

08

場面 → 答えの早見表

設問文にこの手がかりが出たら、この答えに寄せる。6つの場面で扱ったものに、周辺を足してあります。

アクセスキーをコードや設定ファイルに保存→常に不正解。ロールを使う
EC2 上のアプリから他のAWSサービスへ→インスタンスプロファイル
Lambda から他のAWSサービスへ→実行ロール
EC2 のメタデータを保護したい→IMDSv2 を必須にする
別アカウントからアクセスさせたい→クロスアカウントロール（両側の設定）
外部ベンダー・SaaS にアクセスを許す→ロール + ExternalId
開発者の権限昇格を防ぎたい→権限境界
組織のすべてのアカウントで禁止→SCP
管理者権限があるのに操作できない→SCP か権限境界を疑う

確認問題

先に自分の答えを決めてから開いてください。当てずっぽうで開くと、この時間が無駄になります。

Q1EC2 上のアプリが S3 にログをアップロードする。開発チームは「アクセスキーを環境変数に入れれば設定ファイルに残らないので安全だ」と主張している。最も適切な対応はどれか。
  • A. 環境変数なら問題ないので、その方針で進める
  • B. IAM ロールをインスタンスプロファイルとしてアタッチし、キーを廃止する
  • C. アクセスキーを90日ごとにローテーションする運用を追加する
  • D. キーを KMS で暗号化して設定ファイルに保存する

正解: B

環境変数も AMI に焼かれ、プロセス一覧から見え、クラッシュダンプに残ります。「置き場所を変える」案はすべて、鍵が存在するという根本を解決していません。

判断軸: C と D は「鍵を管理する」案です。もっともらしく見えますが、SAA では鍵をなくす案が常に上位に来ます。D は特に巧妙で、復号するための権限がまた必要になるという循環に陥ります。

Q2別アカウントのユーザーに、こちらのバケットを読ませたい。こちら側でロールを作り、信頼ポリシーに相手のアカウントIDを書いた。しかし相手は AccessDenied になる。最も可能性が高い原因はどれか。
  • A. 信頼ポリシーの書き方が間違っている
  • B. 相手側のユーザーに sts:AssumeRole の許可がない
  • C. バケットが暗号化されている
  • D. リージョンが異なる

正解: B

権限の受け渡しは双方向の合意です。引き受けられる側（こちら）の信頼ポリシーだけでは成立せず、引き受ける側（相手）にも sts:AssumeRole の許可が必要です。

判断軸: クロスアカウントの設問で「片側だけ設定した」という記述を見たら、欠けているもう片側が答えです。場面2の図の、左右どちらが欠けているかを思い出してください。

Q3外部の監視ベンダーに読み取り権限を与える。信頼ポリシーに加えるべき条件はどれか。
  • A. aws:SourceIp でベンダーのIPレンジを限定する
  • B. sts:ExternalId に自社固有の値を設定する
  • C. aws:MultiFactorAuthPresent を true にする
  • D. 条件は不要。ベンダーのアカウントIDを書けば十分

正解: B

ベンダーは多数の顧客のロールを引き受けられる立場にあります。ExternalId がないと、第三者があなたのロール ARN を登録するだけで、ベンダー経由でデータを引き出せてしまいます（混乱した代理人問題）。

判断軸: C が不正解なのは、ベンダーが自動化されたシステムで MFA を提示できないため。A は一見よさそうですが、SaaS の送信元IPは変動するうえ、IPを知っている第三者には防御になりません。

Q4開発者に IAM ロールの作成を許可しつつ、管理者権限を持つロールを作らせないようにしたい。最も適切な構成はどれか。
  • A. 開発者に権限境界を設定する
  • B. 開発者に権限境界を設定し、さらに「境界付きのロールしか作れない」条件を課す
  • C. CloudTrail で監視し、違反を見つけたら削除する
  • D. IAMFullAccess を付けたうえで、社内規定で禁止する

正解: B

A だけでは、開発者は「境界のない新しいロール」を作って引き受けることで天井を回避できます。条件キー iam:PermissionsBoundary で、作成するロールにも同じ境界を強制して初めて塞がります。

判断軸: C は事後対応で予防になっていません。「予防的統制か、発見的統制か」はセキュリティ設問の頻出の切り口です。要件が「作らせない」なら予防を選びます。

Q5組織のSCPで S3 への全アクションが Deny されている。あるメンバーアカウントのユーザーには AdministratorAccess がアタッチされ、バケットポリシーでもそのユーザーが許可されている。このユーザーはオブジェクトを取得できるか。
  • A. できる。バケットポリシーとアイデンティティポリシーの両方が許可しているため
  • B. できる。AdministratorAccess が SCP に優先するため
  • C. できない
  • D. バケットの所有者であればできる

正解: C

明示的な Deny はすべての Allow に優先します。判定の1段目で終わるので、その先のリソースポリシーもアイデンティティポリシーも評価されません。

判断軸: Allow を何個積んでも天井は越えられません。なお設問が管理アカウントだった場合は SCP が適用されず、答えが変わります。そこまで読めれば上出来です。
